## Roadmap

M1.12 (the installer), M1.13, M1.14 and M1.15 (its refinement), M2.1 (canonical execution) and M2.1b (results communication) are merged and released as alphas. What each phase holds is the orchestrator's proposal, which the owner approved (on 2026-11-03, approved or did not object to). ## Verification targets

Every phase that changes what runs (S1, M1.2, M1.4–M1.8, including M1.7b and M1.7c) is verified on both targets before its PR, and the MVP is accepted on both:

| Target | ADR 0027 tier | Shape |
| --- | --- | --- |
| Local container | co-located | The same OCI image under Podman on the developer machine, next to the agent; reduced assurance is reported. |
| Remote host | isolated | The same image on a remote Linux host as a systemd service (Podman quadlet). Outbound-only: no inbound ports; status and MCP reached through Session Manager port forwarding (the Cloudflare tunnel was removed on 2026-10-19); owner setup and TOTP enrollment run as a local command in the owner's own Session Manager session (D-IDENTITY). The App key and database never leave the host. |

From M2.1b on (D-ROADMAP), these live tests replace the remote host in each phase; the full verification of the remote host waits for the verification phase after M3, with macOS and a real PowerShell Constrained Language Mode refusal. A phase that changes what runs is tested live:
- on the co-located tier on Windows, with Docker, and with Podman on a Podman machine of its own for tests (never `podman-machine-default`, where A3 runs), before its pull request (two Podman machines do not run rootless together, so the default one is stopped meanwhile);
- on the co-located tier on Linux, on a WSL Ubuntu distro, before its pull request (a distro whose user is not UID 1000 runs beside `podman-machine-default`);
- with a Windows test runner started by a real logon (the orchestrator's placement);
- on the isolated tier, on a throwaway AlmaLinux 9 WSL distro: the sandbox tests and the host step before the pull request with a development build, and the full isolated flow after the merge on the published alpha, because the isolated install accepts only a release image (decision 15 of M2.1).

There is no deployment workflow: the Deploy workflow, the `:deploy` tag and the `remote-poc` environment were retired on 2026-10-21 (D-DEPLOY), and CI builds the image without pushing it. Releases are the only published images. A host pins a release's signed index digest by hand in the unit files, with no automatic update (no deploy key or registry credential leaves GitHub or reaches the host), and the owner places the App key on the host once. The agent never holds host credentials, so the remote target stays a genuine isolated installation. Host choice and access are decided in D-DEPLOY.
