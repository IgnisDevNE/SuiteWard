# M1.6b: Assessment and check

**Goal:** assess the exact head of each open PR against the canonical contract and publish `SuiteWard / Contract` (D-CHECKS, ADR 0015) through the outbox. That closes the exit of [M1.6](M1.6.md):
- a protected change stays blocked until the owner approves the exact revision;
- an implementation-only push keeps consent;
- a protected push needs fresh approval;
- a revoke blocks again.

**Depends on:** M1.6a. Planned 2026-10-14 with the advisor.

**Decisions:**
- D-CHECKS amendment of 2026-10-14: states, `failure`, generation, single writer, no change proposal before a canonical exists.
- The first-test-PR bootstrap moves to [M1.7b](M1.7b.md) (ADR 0010 amendment of 2026-10-14).

**Contracts:**
- [persistence](../../contracts/persistence.md#pr-checks-m16b-normative): head assessment and the check ledger;
- [runtime](../../contracts/runtime.md#check-job-and-publisher-m16b): the `github_checks` job and the `github_check` publisher;
- [github](../../contracts/github.md#m16b-check-runs-normative): check-run writes and readback.

Measured by `TestLiveChecks` on `IgnisDevNE/SuiteWardQ` PR #17 (head `859ec53`) with the test App (id 5257122). Every step passed.
- **POST.** `POST /check-runs` with `{metadata: read, checks: write}` answers 201.
- **Readback.** `GET /commits/{sha}/check-runs?check_name=…&app_id=5257122` answers 200 with **the same checks-write token**: no separate read map is needed.
  - `external_id` round-trips exactly.
  - Without `filter`, the listing still returns only the latest run per name, because the API's default filter is `latest`.
- **`in_progress` after `success` on the same head.** The latest run becomes the `in_progress` one, and the App's check suite goes back to `in_progress`. So a revoke blocks again.
- **Unknown head SHA.** A POST for a SHA that does not exist answers 422.
- **Left on PR #17.** Three runs named `SuiteWard / P0 checks`, the last one `success`.

## Verification

On `IgnisDevNE/SuiteWardQ`, per target, one at a time, as in M1.6a; the runbook is [HOST.md, section 6c](../../../deploy/HOST.md#6c-the-suiteward--contract-check-m16b). The ruleset requires `SuiteWard / Contract` from the App and `CI / test`. A check appears or updates within about 1 to 2 minutes of a push or a command (synchronization up to 60 s, `github_checks` every 30 s).
1. A PR that changes only files outside `tests/`: the check is `success`, "No protected change". SuiteWardQ has no workflow, so `CI / test` never reports and M1.6b merges nothing: the merge box shows `SuiteWard / Contract` passed and `CI / test` expected.
2. A PR that changes `tests/*.txt`: `in_progress`, with the revision `P<n>-R1` and the copyable approve command in the summary.
3. Approve R1 with a current code: the acknowledgment arrives, then `success`, "Ready for integration".
4. Push a change outside `tests/`: still `success` on the new head; consent is kept.
5. Push a change in `tests/`: a new revision `P<n>-R2`, `in_progress`.
6. Approve R2 with a new code: `success`.
7. Revoke R2 with a new code: `in_progress`. This is the revoke that blocks a head that was `success`.
8. An invalid code (`/suiteward approve P<n>-R2 123456`): `failure`, "Owner command rejected", cleared by the next valid command or push.
9. At each step the merge box lists `SuiteWard / Contract` with that state, next to `CI / test` expected and not reported. **Do not merge**: without merge detection (M1.7) a merged protected change would leave the canonical behind for good. Close the PRs unmerged.
10. `/status`: `schemaVersion` 14, no `checks` or `bootstrap` error, `outbox.failed` 0, protection `enforced`.

Each code is used once and posted within about 30 s of changing.

## Backlog from M1.6a verification (folded into B)
- The approval text "P<n>-R<m> is now eligible for promotion" overstates the outcome when the bootstrap is blocked for another reason.
- A failing `github_bootstrap` run is visible only in the service journal.
- A repository removed from `GITHUB_REPOSITORIES` without re-running setup stalls the commands watermark without a warning.
- Owner codes were rejected as stale several times with the ±1 tolerance: log the offsets to measure the window before M1.8.

## Limitations planned for this phase
- A new proposal revision is announced only in the check summary, not in a PR comment.
- Fork PRs are not measured unless P0 covers them.
- A rejected owner command posted between a push and the job first recording that head does not set `failure`; the window is about the synchronization interval plus the job interval. It is a known limitation, to be fixed with a per-head observation time.

## Carried to M1.7
- The `not-current` and `integrity-failed` branches are unreachable after `AssessHead`; decide at M1.7 whether to keep them.
- Republishing a failed message is unbounded under a permanent GitHub refusal: add a backoff or a cap.
- A 422 on POST is always treated as a vanished head.
- The unchanged-head memory is in-process: persist it with the canonical.
- The bytes of the protected files are re-read on each re-assessment.
