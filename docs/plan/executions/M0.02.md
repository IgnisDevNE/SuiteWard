## Behavior and boundaries

Proposal histories retain exact immutable revisions, reject missing/foreign/unknown references and reused revision IDs, and reject superseded references for current eligible resolution while preserving exact historical lookup. Bindings cover project, Suite, proposal/revision, explicit canonical baseline, manifest, scope, governing policy and caller-selected context. Proposal origin and approval carrier remain distinct.

Consent consumes already-authenticated, ordered commands. Retained receipts preserve original outcomes across retries and edits, including rejected outcomes; source and operation identities cannot be rebound. An identity collision returns a deterministic conflict without replacing its original receipt or inventing a second attempt ledger. New operation aliases for a repeated source are retained without another approval effect. No-op revocation preserves ordering so a delayed older approval cannot restore consent. Current eligibility rechecks the actual proposal and governing policy.

Integrity assessments compare the exact expected source and complete binding before interpreting passed, failed or unavailable evidence. Missing and mismatched evidence remain distinct. Emitter attribution does not authenticate the emitter, and a passed integrity assessment does not create consent or establish independent execution.

These are deterministic domain decisions over caller-supplied trusted snapshots. There is no GitHub authentication/parser, durable receipt storage, acknowledgment publication, transaction atomicity, canonical promotion, source-discovery implementation or execution backend in this phase. M0.03 and M0.04 add guarded transitions and application coordination. D-APPROVAL-CONTEXT remains open: this phase does not decide whether implementation-only source pushes invalidate approval.
