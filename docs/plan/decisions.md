### D-SYNC: Polling, budget and MCP boundary

Accepted 2026-10-05 as initial defaults; it no longer gates the runtime phase.

- Poll every 60 s (initial default; see the amendments) with conditional (ETag) requests.
- Use at most 50% of the installation's API rate budget.
- Supported limit: at most 20 repositories.
- MCP is limited to sync and status, authenticated with a local token.

Final numbers come from the S1 walking skeleton.

**Amendment (2026-10-15, after M1.7; owner).** *Latency.*
- **Measured.** The M1.7 verification measured 20 s to 2 min from an event to its check. The M1.7b live run measured about 2 to 3 minutes from a command to its answer. After M1.7c (2026-10-17), on both targets, a command took 16–35 s to its answer, an approval 17–36 s to its check, and a push 12–31 s to its check. Before M1.7c the floor for a command was the D-COMMANDS watermark: the earliest synchronization success minus `JOB_TIMEOUT` minus 30 s, about 90 s. Since M1.7c it is the earliest cycle start in GitHub's clock minus 10 s (D-COMMANDS amendment of 2026-10-16).
- **Approved for phase M1.7c (before M1.8):**
  - chain the jobs, so an approve or revoke, a promotion, or a sync that sees new comments enqueues the next job in the same transaction (as decided then; M1.10 amended [ADR 0005](../decisions/0005-river-background-jobs.md): the outbox carries the transactional guarantee);
  - shorten the synchronization poll to about 20–30 s.
- **Needed first.** A D-COMMANDS decision on the watermark, for example a horizon measured from the cycle's start, because chaining alone cannot beat the watermark.
- **Webhooks** come after the MVP, because they need an inbound route and changes to ADR 0001 and D-SYNC.

**Amendment (2026-10-16, phase M1.7c; owner).** *Latency.*
- **Poll.** Synchronization runs every 20 s, paced by its cost.
  - A tick starts no sooner than 18 s after the previous one. The 2 s tolerance absorbs the pickup jitter on the 20 s periodic grid.
  - It also starts no sooner than the previous tick's request count allows at 450 requests a minute. That is half of GitHub's secondary limit of 900 points a minute; a REST GET costs one point (GitHub's REST rate-limit documentation, read 2026-10-16). For example, a tick of 150 requests waits 20 s and one of 420 requests waits 56 s.
  - A cycle costs one request per repository plus one per open PR.
  - The primary budget stays at 50%. A 304 is not counted against it, and the ETag cache of each read client resets only when its token rotates, about once an hour.
  - The limit stays at 20 repositories. At that limit with 20 open PRs each, a tick costs 420 requests, so pacing spaces ticks about 56 s apart. The secondary limit is never crossed.
- **Wake-ups.** A job that may unblock another inserts a one-off run of it **after its own commit**, and the periodic runs stay as the fallback. A wake-up lost to a crash only delays the work to the next periodic run. This revises "in the same transaction" in the amendment of 2026-10-15 (owner, 2026-10-16).
  - **Sync to commands, checks and merges.**
    - A sync tick that observed a change (any response that was not a 304) wakes `github_checks` and `github_merges`.
    - Any tick that recorded a cycle wakes `github_commands`, because a cycle that changed nothing can still move the horizon past a comment observed earlier (whole-phase review, 2026-10-16).
    - A `Date` more than 5 minutes ahead of the local clock fails the cycle. This is only a sanity bound, and the local clock never enters the horizon.
  - **Commands to checks and bootstrap.** A commands run that decided at least one candidate wakes `github_checks` and `github_bootstrap`.
  - **Promotion to checks.** A promotion, by the merges job or by the bootstrap job, wakes `github_checks`.
  - **Queues.** Each of these job kinds runs on its own queue with one worker, so runs never overlap. River requires `running` in every unique state set, so a wake-up cannot coalesce with a run in progress. It is therefore inserted without uniqueness, and one that arrives during a run queues exactly one follow-up.
- **Targets.** Measured from GitHub's own timestamps in the live run:
  - a command answered in under 45 s;
  - an approval reflected in the check in under 60 s;
  - a push reflected in the check in under 45 s.

### D-SCOPE: Declaration and source-inventory semantics

Accepted 2026-10-05.

- The declaration uses gitignore-style include and exclude rules, case-sensitive.
  - **Amended 2026-10-20 (owner, security review, case-fold collisions).** Matching stays case-sensitive, and a pattern is never folded. A file of a tree is protected too when its path case-folds equal (Unicode simple folding) to a file the scope covers in the same tree, or when rewriting a directory prefix of it onto a real directory of the same tree that differs from it only in case gives a path the scope covers (so `Tests/b_test.go` is protected when `tests/b_test.go` would be, and `.GitHub/README.md` is not when `.github/README.md` is not). If several real directories fold together, any covered rewrite protects. It enters the manifest, so the approval binds its bytes, and a new one is listed as added. A symlink at such a path, or standing for such a directory, is as unsafe as one at the covered path. A look-alike (Cyrillic, fullwidth or combining characters) is another character and stays unprotected. A tree with no such collision is classified as before. A canonical built before this change that already holds a case twin gets the twin into its manifest: the next head against it shows the twin as added and needs one approval. A tree that holds more than 8 distinct spellings of one case-folded directory or file path is an invalid tree (the source is refused and the governing scope stays in force), because every spelling is a path to rewrite onto.
  - **Extended 2026-10-20 (owner, invisible characters, phase SH).** Characters that cannot be seen are never shown raw to the owner. A path or a pattern with an invisible rune (zero-width, bidirectional control, joiner, filler, variation selector) is shown escaped, and a suggestion never offers one. A notice that quotes a whole declaration refuses one it cannot show verbatim, so the owner never copies text that looks different from its bytes. Raw bytes must be valid UTF-8 before layout is removed.
  - **Declaration size (owner, 2026-10-20).** A `.suiteward.yml` read from a pull request's tree, which anyone with write access controls, is read up to 64 KiB. A larger one is an invalid source, and the governing scope stays in force. The declaration stored with the canonical is not subject to this read cap, and only to it: the pattern caps below apply to it.
  - **Pattern caps (owner, 2026-10-21, phase SH review).** A pattern has at most 64 segments, and a declaration at most 1000 patterns across `include`, `exclude` and `runner`. Beyond either cap the pattern or declaration is invalid (a head becomes an invalid source and the governing scope stays in force). The caps bound the work an untrusted declaration can cost, since matching is linear in segments times path components. Adjacent `**` segments are one. `AddPatterns` and `AddExcludes` refuse an addition that would pass them.
    - **The caps apply to the stored canonical too.** A canonical declaration over a cap is an explicit invalid state: every assessment against it fails closed with an invalid state until the repository is bootstrapped again. No known canonical is near the caps.
  - **Path length (owner, 2026-10-21, phase SH review).** A path of a tree entry longer than 4096 bytes makes the tree invalid (the source is refused as `invalid-source` and the governing scope stays in force), because the work to fold and resolve a path grows with its length for each of its directories. No real repository comes near it.
  - **Known limit (2026-10-21).** Only case is folded. Two paths that differ by Unicode normalization (NFC and NFD forms of one name) or by Windows aliasing (8.3 short names, trailing dots or spaces) are two paths here, so a checkout that treats them as one is not covered.
- A symlink or submodule inside the scope makes the declaration invalid; the governing scope stays in force.
  - **Amended 2026-10-17 (owner, M1.9 phase review).** Suggested patterns match at any depth, so this rule made every repository with a link or a submodule unprotectable. A typical case is `AGENTS.md -> CLAUDE.md`. The rule now depends on what the entry is:
    - **A symlink whose target resolves, within the same tree, to a regular file** behaves as a file. It is unsafe only when the scope covers the link's own path. The target is the link's blob, resolved relative to the link's directory, following at most 8 links.
    - **A symlink to a directory, to a path outside the repository, or to nothing** is unchanged: it is unsafe when the scope covers it or may cover a path below it.
    - **A submodule** is outside the scope. Its content is not protected and is never read. The declaration stays valid, and the replies that suggest a declaration warn about every submodule that a pattern would have reached.
    - The target is read only for a link that would otherwise be unsafe. It is resolved on the same tree that is being assessed, so it decides only whether that tree is safe and grants nothing.
  - **Amended 2026-10-19 (owner, M1.9 live run): an accepted link.** An `exclude` pattern naming exactly the link's own path, anchored (`/spec_link`) or with an interior slash, accepts that link. The link no longer makes the declaration invalid, and nothing reached through it is protected.
    - Because it is an exclude, it is a scope reduction and needs the owner's approval like any other.
    - Other excludes, such as a broader pattern or one that only matches below the link, still do not make a link safe.
    - The `invalid-source` comment for a link offers this choice with a warning, after removing the link or pointing it to a file. It does not suggest narrowing the include patterns, because that is a wider reduction the owner decides alone.
- Approval binds the raw declaration bytes plus the normalized rules.
- A candidate omission cannot remove existing protection; reducing the scope requires approval like any other change (ADR 0013).

### D-SCOPE-DEFAULTS: Which files the protected defaults cover

Accepted 2026-10-11 (owner, phase M1.3). The ADR 0013 amendment protects the workflows, the test runner configuration and the scripts that run tests; which runner files exist depends on the project's ecosystem, so SuiteWard does not guess them.

- `.suiteward.yml` is always in scope: no exclude removes it, and changing or deleting it never disables protection (ADR 0013).
- `.github/workflows/**` is a fixed default.
- The declaration has a `runner` list of patterns that the owner fills with the runner configuration and test scripts.
- Once canonical, removing `.github/workflows/**` or a `runner` entry from the scope, by exclusion or by deleting the entry, is a scope reduction and needs approval like any other change.
- The declaration is YAML, parsed with `go.yaml.in/yaml/v3`; its schema is fixed by the M1.3-A2 brief.
- An `exclude` pattern that matches `.suiteward.yml` has no effect on coverage but is still classified as a scope reduction (decided by the integrator at the owner's request, 2026-10-11): the rule-level check is syntactic, and such an edit changes a covered file, so it needs approval either way; an exact rule would need a special case that buys no safety.

### D-SCOPE-DISCOVERY: Suggesting and widening the scope

Accepted 2026-10-17 (owner, M1.9 planning, after the C2 finding in [M1.8](phases/M1.8.md#c2-outcome-dogfooding-2026-10-17)). Discovery stays a suggestion (ADR 0013): only the owner's approval changes the contract.

- **Every suggested change links to GitHub's editor** (owner, 2026-10-19). A comment that asks for a change to `.suiteward.yml` links to the editor for that file on the pull request's branch, or to GitHub's new-file page when the file does not exist yet. This holds even when the comment also carries a review suggestion or a copyable block. A change the web editor cannot make, such as removing a symbolic link, gets no link.

- **Detection is path-only.** The suggestion is built from the file paths of a tree, with no file contents.
  - **Test files.** Patterns follow the frameworks' own conventions and match at any depth (`*_test.go`, `test_*.py`, `*.spec.*`…). There is no longer one pattern per directory.
  - **Test directories.** `testdata/`, `__tests__/`, `__snapshots__/`, `__mocks__/`, `__fixtures__/` and `src/test/` count at any depth. `tests/`, `test/` and `spec/` count at the top level, or when they hold a test-named file.
  - **Runner files.** The runner list holds the files found by name, plus the higher-priority files that a runner reads first, even when they do not exist yet: pytest reads `pytest.toml` before `pytest.ini`. A suggested pattern may therefore match no file.
  - **Test directories, in full:** besides those above, `cypress/` and `src/it/` also count at any depth.
  - **Runner families.** The runner list holds whole families: a file of a family brings in every member. For example, `pytest.ini` brings `conftest.py`, `.coveragerc` brings `.nycrc*` and `.c8rc*`, and `.rspec` brings `spec_helper.rb`.
  - **Vendored directories** never count: `node_modules`, `vendor`, `.venv`, `venv`, `.tox`, `__pycache__`, `bower_components`, `jspm_packages`, `.git`.
  - **The limit** covers include and runner patterns together. When the limit cuts the list, the reply says so.
- **Mixed files.** `package.json`, `pyproject.toml`, `setup.cfg`, `tox.ini`, `Cargo.toml`, `*.csproj` and `CMakeLists.txt` can hold test settings among other content. The reply warns about the ones it finds and never suggests them, because protecting them would put every dependency update behind an approval.
- **The scope notice.** After V1, a PR revision that adds test-like files outside the governing scope gets one comment.
  - The comment lists those files and gives the full declaration to commit, with the edit link to `.suiteward.yml` on the PR branch.
  - When the PR's diff already touches `.suiteward.yml`, it also gets a review comment with a suggestion block, so the owner can use GitHub's "Commit suggestion".
  - The notice is evidence, not authority. It never changes the check, never protects a file and grants nothing.
- **`/suiteward suggest`** (owner only, no code) asks for the same reply on any open PR.
  - Before V1, the reply is the bootstrap reply of a `propose` that finds no declaration.
  - After V1, the reply is the scope notice for the PR head.
  - It is not a command for the check: it never clears `owner-command-rejected`, and a malformed or edited `suggest` never sets it (D-COMMANDS, "A wrong command has no effect").
- **Where a suggested declaration starts from.** The notice and `suggest` start from the **canonical** declaration bytes, never from the PR head's file, and only add patterns. A PR that narrowed the scope therefore never comes back as a suggestion.
  - **The one exception is the review suggestion.** It inserts the new lines into the PR head's own `.suiteward.yml`, on a list line inside a diff hunk, because GitHub accepts review comments only on such lines. This grants nothing either: a narrowing in the head is still listed as a reduction and still needs approval. When no list line falls inside a hunk, there is no review suggestion.
  - **The head's own scope only silences.** A test path that the PR's valid `.suiteward.yml` already covers is not reported. That only suppresses an advisory; the widening still needs approval.
- **Exclusions are respected.** A test-like path that matches an `exclude` of the governing scope is never reported, because adding patterns cannot undo an exclusion.
- **One notice per set.** The notice is keyed by the set of added uncovered paths, so later pushes that add nothing new do not repeat it.
- **Uncovered runner files block** (owner, 2026-10-18, M1.9 live run).
  - **The risk.** A runner file can change how the protected tests run without touching any of them. A root `conftest.py` can skip them, and a `jest.config.js` can narrow `testMatch`. So, unlike an uncovered test file, an uncovered runner file is a bypass, and a notice alone is not enough.
  - **The rule.** After V1, a PR that adds or modifies a file matching a runner family name, outside the governing scope and not excluded, gets the check `in_progress` with reason `runner-uncovered`. It is never `success` until the owner decides.
  - **Protecting the file.** The owner commits the suggested declaration, which adds the pattern, and approves it.
  - **Ignoring the file.** The owner adds the path to `exclude` and approves it. That is a scope reduction, which needs approval anyway, so the decision is recorded in the contract.
  - **What stays non-blocking.** Uncovered test files stay a notice only: they add no bypass of the existing protection, and their detection is heuristic. The runner family names are a short, exact list.
  - Rewriting the YAML can drop the owner's comments. Comments are part of the approved bytes, so the owner sees that change and approves it.
- **Widening is a protected change.** Any edit to `.suiteward.yml` creates a revision that needs approval, comments included. An agent widens the scope with such a PR; it never posts `suggest`.
- **A reduction is detailed.** The revision comment lists the rules and paths a reduction removes.
- **After the MVP:** reading the content of config files (pytest `testpaths`, Jest `testMatch`, Vitest `include`, `phpunit.xml`, `Cargo.toml` `[[test]]`); protecting a single section of a mixed file; listing complete trees for monorepos. *M1.15 studied reading config files and did not take it ([D-M1.15](#d-m115-scope-discovery-answers-and-the-merge-version-in-one-read)); it stays here.*

### D-GITHUB-ACCESS: GitHub App permissions and token lifecycle

Accepted 2026-10-11 (owner, from the S1 findings in [s1-github](../spikes/s1-github.md)).

- The App holds Metadata read, Pull requests read and write (write measured 2026-10-13, M1.6a-P0), Contents read, Administration read (since 2026-10-13, for protection verification, D-PROTECTION) and Checks write; no Administration write, no Issues, no webhooks. Reading PR comments needs Pull requests read (Issues read alone is refused).
- Installation tokens are requested with the installed repositories and an explicit, non-empty permission map (an empty map grants everything the App has), the narrowest one per use: synchronization is read-only and requests neither Checks write nor Administration; protection verification requests only Metadata and Administration read.
- A token lives one hour and is reused until five minutes before it expires.
- Acknowledgement comments use Pull requests write, requested only by the comment publisher with `{metadata: read, pull_requests: write}`. M1.6a-P0 measured on 2026-10-13 that a token requesting `pull_requests: read` from the App that holds write is granted exactly read, so synchronization stays read-only, and that the same comment POST with the read map answers 403.
- The GitHub adapter contract is [github](../contracts/github.md).
- **No Contents write, reaffirmed 2026-10-19 (owner, M1.9).** A one-click choice that commits for the owner was declined, because security and isolation are the product's core and Contents write would add a way to fail:
  - it would let the key inject commits into PR branches, run existing workflows on new branches, and create tags;
  - in the managed service, one key would write to every customer;
  - in co-located, the agent reaches the key, so it would gain a second write identity.

  The owner's choices stay copyable blocks, review suggestions (committed with the owner's own credentials), or a change the owner asks the agent to make. Checks write remains only because it is required.

### D-IDENTITY: Owner setup and identity

Accepted 2026-10-13 (owner). The owner is bound by a local setup command run on the instance itself (`suiteward setup`, through `podman exec` on the co-located target or the owner's own Session Manager session on the isolated one); no HTTP or MCP surface can set up or change the owner. Setup takes the owner's GitHub login, resolves its numeric account id through the App's installation token, and records the owner as the principal `github:<numeric id>` of kind `Human` in a new policy revision; the login is display only. Proof of identity is access to the instance, which on the isolated tier only the owner has; on the co-located tier the agent can run setup too, which is part of the reduced assurance SuiteWard reports. The trusted installation is the operator-configured `GITHUB_INSTALLATION_ID`; setup confirms it covers every configured repository. Setup also enrolls the TOTP secret (ADR 0027), records the name of the project's required test check, and records the tier the instance had at enrollment: a secret enrolled on a `co-located` instance stays within the agent's reach even if the instance is later declared `isolated`, so the effective tier is `co-located` when either the setting or the enrollment says so, and `/status` says to re-run setup when they differ. Re-running setup replaces the TOTP secret and creates a new policy revision. One owner governs the whole instance (owner answer 2026-10-13): each configured repository is one SuiteWard project, identified by the repository's numeric GitHub id (`github-repo:<id>`, stable across renames), with its own policy owned by that owner and its own required test check (`--test-check owner/name=<check>`). An approval binding includes the policy revision (`contract.NewApprovalBinding`). In M1.5 no Suite exists yet, and setup refuses to change the owner of a project that already has a Suite; Changing the owner of a project that already has a Suite stays refused in the MVP (D-COMMANDS, 2026-10-13), so a changed owner never inherits earlier authority or approvals; re-enrolling the same owner is allowed.

### D-PROTECTION: Protection verification

Accepted 2026-10-13 (owner), from the M1.5-P0 measurement on the S1 test repositories (recorded in the [M1.5 page](phases/M1.5.md)). SuiteWard verifies and reports; it never changes protection (ADR 0016 amendment). It reads the effective rules of the default branch (`GET /repos/{r}/rules/branches/{branch}`, Metadata read; GitHub returns only the rules of active rulesets, at repository and organization level, so `evaluate` and `disabled` rulesets never count) and the classic branch protection (`GET /repos/{r}/branches/{branch}/protection`, Administration read: 200 configured, 404 none, 403 unreadable), with a token that requests only Metadata and Administration read. The result is a set of findings evaluated over both sources together (a requirement met by either counts):

- `missing-contract-check`: no required check `SuiteWard / Contract` pinned to the App (ruleset `integration_id` or classic `app_id` equal to the App id; absent or `-1` is not pinned);
- `missing-test-check`: the repository's configured test check is not required (before setup there is no configured test check, so this finding also says to run setup);
- `not-up-to-date`: no source that requires the `SuiteWard / Contract` check also requires branches to be up to date (D-CHECKS: the required-check rule must be strict); when no source requires the contract check, `missing-contract-check` covers it and this finding is not raised;
- `admin-bypass`: classic protection does not enforce for administrators (`enforce_admins` false).

`enforced` means no finding. Two results are exclusive instead: `enforcement-unavailable` (a private repository whose effective rules answer 403: GitHub Free does not enforce there, or the read permission is missing; the instruction names both and SuiteWard never claims protection) and `unknown` (any other read failure, including a token whose granted permissions differ, with the instruction to grant Administration read). A ruleset's bypass list is not visible to the App, with or without Administration read (measured: an existing "Repository admin" bypass answered 0 bypass actors; GitHub returns `bypass_actors` only to a caller with write access to the ruleset, which the App does not request), so every result that relies on a ruleset carries the caveat `ruleset-bypass-unverified` with the manual check that the bypass list is empty. Verification runs at setup and every 15 minutes inside the D-SYNC budget, and `/status` shows the latest result per repository.

### D-COMMANDS: PR commands, identifiers and bootstrap

Accepted 2026-10-13 (owner answers, M1.6a planning), within ADRs 0002, 0010, 0011, 0015 and 0027.

**Who is heard**
- Only the enrolled owner's comments are commands.
- A `/suiteward` comment from any other account is recorded in the command ledger and otherwise ignored: no acknowledgment, no state change, no check effect. This is the ADR 0011 amendment of 2026-10-13.
- SuiteWard's own comments are recognized by the App bot's numeric account id and never parsed.

**A wrong command has no effect** (owner, 2026-10-19, after the M1.9 review). The model is the usual one: a typo or an accidental Enter changes nothing.
- A command that is not recognized, is malformed, or is rejected for any reason gets its acknowledgment, which says it was not accepted, and changes nothing else. The check of the pull request does not change, whatever the verb (`approve`, `revoke`, `propose`, `skip`, `suggest`).
- **The one exception is a wrong confirmation code**: `invalid-code` or `replayed-code`, on any command that carries a code. Only that sets the check `failure` / `owner-command-rejected`, because a failed code is a security signal. A replay means someone reused a code from a public comment.
- This supersedes the earlier rule, where every rejected disposition, or a processed command with a rejected consent result, set `owner-command-rejected`, and the carrier limit for shared rejections.

**Command syntax**
- `/suiteward approve <ref> <code>` and `/suiteward revoke <ref> <code>` (ADR 0027).
- The first line of the comment body that starts with `/suiteward`, outside fenced code blocks, is the command; the rest of the body is ignored.
  - **Amended 2026-10-18 (owner, M1.9 live run).** The prefix and the verb are matched without regard to case, so `/SuiteWard suggest` or `/Suiteward Approve P1-R1 123456` from a phone's auto-capitalization is a command. A missing argument, an extra token or a malformed reference or code is still refused as malformed. The reference stays `P<n>-R<m>` as written.
  - **Amended 2026-10-20 (owner, security review).** A command is read only where GitHub shows it as text. A line inside an HTML comment (from a line that contains `<!--` through the next line that contains `-->`) and a line indented four or more columns (a tab counts as four, measured before trimming) are not commands, as a fenced line is not. It fails closed: an unclosed `<!--` hides the rest of the body, and a `<!-- -->` on a command line hides that line, so such a command is silently `not-command`. A fence closes only at a fence indented 0 to 3 columns; a fence opened after a list or quote marker, or indented 1 to 3 columns, is never closed and hides the rest of the body; a backtick run whose info string holds a backtick is not a fence; a fence line wins over a `<!--` in its info string; a lone carriage return ends a line. Known limit: raw HTML blocks (`<details>` up to a blank line, `<pre>`, `<code>`) and multi-line inline code spans are not modelled, so a command there is read although GitHub shows it as code; it still needs a current, unused code (owner, 2026-10-21, phase SH review).
- `<ref>` is `P<n>-R<m>` (ADR 0002 and ADR 0010 examples), resolved inside the PR's project and its single Suite. `<code>` is the 6-digit TOTP code.
- `/suiteward suggest` takes no argument and no code. It asks for a suggested declaration ([D-SCOPE-DISCOVERY](#d-scope-discovery-suggesting-and-widening-the-scope)), grants nothing, and is not counted as the owner's latest command.

**TOTP**
- The code is verified against the comment's `created_at` with a tolerance of one 30-second step either side (owner answer 2026-10-13).
  - **Data for the decision before M1.8.** In the M1.7b live run (2026-10-16), one approval code was refused because of timing, per the owner. The offset was not captured.
  - The commands job logged, for every rejected code, whether a window of 2 steps would have matched and at which offset (`github command code rejected`, `would_match`). The decision read those lines from the host journal. The measurement is over and the fields were removed in SH-H5.
  - **Decided 2026-10-17 (owner, M1.8 planning): keep ±1.** The M1.8 acceptance reads the host's `would_match` lines. Only near misses there widen the window to ±2, as a new owner decision.
  - **Confirmed by the M1.8 acceptance (2026-10-17): the window stays ±1.**
    - The host's journal held 20 rejected codes from 2026-10-15 to 2026-10-17, and every one had `would_match` false. These were wrong codes, not late ones: dead authenticator entries and one mistyped code.
    - No near miss was seen.
- A step is consumed once per owner across all commands (ADR 0027). The consumed step records the command that used it, so a retry of the same command after a crash is not a replay.

**Order and binding of a code to its command (ADR 0027)**
- Commands are processed one at a time across all repositories, ordered by the comment's `created_at` and then its comment id.
- The command order given to the domain is the GitHub comment id.
- **Sync watermark.** A comment is processed only once every enrolled repository has completed a successful synchronization cycle that began after the comment was created. "Began after" was approximated as finished at least `JOB_TIMEOUT` plus 30 s of clock skew after `created_at`. Since M1.7c it is measured in GitHub's clock (amendment of 2026-10-16 below), and `JOB_TIMEOUT` no longer delays commands.
  - Without the watermark, an agent using the owner's GitHub identity could copy the owner's code into a command on another repository, sync that repository first, and use the code before the owner's own command.
  - Cost: a repository that cannot synchronize delays every command. `/status` shows the reason.
- **Edited before observed.** A comment whose first observed version was already edited (`updated_at` differs from `created_at`) is not a command. It uses up no step and is acknowledged with the reason.
  - Without this rule, an innocuous comment edited after the owner's code appeared would carry an earlier `created_at` than the owner's command.
- **Result.** With these two rules, the first command that can use a code is the one the owner wrote. That is what ADR 0027 means by a code "bound to the command it authorizes".
- **Closed pull requests (owner, 2026-10-20, security review).** An approve, revoke or skip that the sync first observed after its pull request stopped being open is ignored: it uses no step, records no consent and gets no acknowledgment. One the sync observed while the pull request was listed open is decided after the pull request closes. Both times are the sync's own clock, so a comment's `created_at` never decides. Equal times count as closed.
- **A command applies to its own pull request (owner, 2026-10-20, security review).** An approve or a revoke that names a proposal carried by another pull request is refused before its code is checked, with the new disposition `other-pull`. It uses no step and records no consent. The acknowledgment names the reference and says where to comment, and, like any wrong command, it does not change the check. A reference to a proposal that does not exist keeps its earlier answer.
- **An unconfigured repository holds nothing back (owner, 2026-10-20).** A repository that is enrolled but no longer named in `GITHUB_REPOSITORIES` is skipped by the sync watermark, so it cannot delay the commands of the others. `/status` and the MCP `status` list it as `unconfiguredRepositories`.

**One comment is one action**
- D-COMMENT-EDIT applies: only the first observed version of a comment id is processed, once.

**Bootstrap of an existing repository (ADR 0010)**
1. When a configured repository has an enrolled owner and no Suite, SuiteWard creates its Suite with no canonical, governed by the owner's current policy revision.
2. When that repository has an open PR, SuiteWard:
   - pins the default branch head as the origin;
   - proposes its protected inventory as `P1-R1`, carried by the lowest-numbered open PR;
   - proposes nothing while that inventory is empty: the project keeps awaiting its initial contract and never gets an empty baseline (ADR 0010). ADR 0010's other path, bootstrapping from the first PR that carries tests with a readiness check, is not in M1.6a; the owner moved it into the MVP as phase M1.7b, after M1.7 and before M1.8 (2026-10-14);
   - posts the bootstrap summary in that PR, with the copyable `/suiteward approve P1-R1 <code>`.
3. After the owner's valid approval, SuiteWard re-reads the origin tree, records the integrity assessment for the origin, and bootstraps the first canonical `V1` without waiting for the PR to merge.
4. If the default branch has moved meanwhile, the origin stays pinned. It is not silently moved (ADR 0010).

**One instance per repository**
- Two SuiteWard instances must never watch the same repository.
- Both post as the same App, and each has its own TOTP secret. So one would reject the owner's codes and, from M1.6b, publish `failure`.
- HOST.md says so. A target that is not under verification runs without GitHub settings, or with other repositories.
- The remote host (isolated) watches the test repositories by default (owner answer, 2026-10-13). The co-located stack runs with GitHub only during its own verification.

**Owner change**
- Changing the owner of a project that already has a Suite stays refused in the MVP, as `setup` does since M1.5.
- Re-enrolling the same owner (TOTP rotation) is allowed.
- This amends D-IDENTITY's M1.6 note.

**Amendment (2026-10-16, phase M1.7b rework; owner).** Two commands are added. Both are owner-only, and any other account is ignored as before.
- **`/suiteward propose`.** No reference and no code: it only creates a proposal, which grants nothing.
- **`/suiteward skip <code>`.** No reference, and it carries a TOTP code verified and consumed like `approve`. It lets a PR pass the check before the first contract.

Their dispositions are `proposed`, `propose-refused`, `skipped` and `skip-refused`. They follow the existing serialized order and retry rules. A propose whose GitHub read fails is retried, and recorded `failed` after 5 attempts, like any other candidate. A source that cannot be read as a contract (an invalid declaration, a link, a truncated tree) is deterministic: it is refused at once with reason `invalid-source`, so it never stalls the queue (clarified 2026-10-16). The rules are in D-CHECKS (amendment of 2026-10-16).

**Amendment (2026-10-16, phase M1.7c; owner).** *The sync watermark in GitHub's clock.*
- **The rule is unchanged.** A comment is processed only once every enrolled repository has completed a successful synchronization cycle that began after the comment was created.
- **What changes is how "began after" is measured.**
  - A cycle's start is the HTTP `Date` of that repository's first response in the cycle, the first page of its open pull requests. This is GitHub's own clock, the same one as the comment's `created_at`, so no local clock skew enters.
  - The horizon is the earliest such start among the enrolled repositories, minus a margin of **10 s**. The margin covers GitHub's listing lag and the one-second resolution of `Date`.
  - `JOB_TIMEOUT` and the 30 s skew no longer enter the horizon.
- **The margin is a named constant and has not been measured.** The sync logs the listing lag it can see: a cycle that started after a comment was created but did not list it (`missed_by_ms`, runtime contract "Latency (M1.7c)").
  - This is a detector, not a proof. It sees lag only when a cycle happens to start inside the lag window. The bot's acknowledgments give many samples.
  - The margin is raised if any value comes near 10 s.
- **Fail closed.** A repository that has no recorded start holds the horizon back, as a repository with no successful cycle does today. This is the case before its first cycle under M1.7c. A `Date` that is missing or cannot be parsed fails that cycle; it never falls back to the local clock.

### D-CHECKS: The `SuiteWard / Contract` check

Accepted 2026-10-13 (owner), from the S1 proposals ([s1-github](../spikes/s1-github.md)): one check run named `SuiteWard / Contract` per PR head SHA, published by the App and required with the App's `integration_id` as its source; never `neutral` (it passes a required check); `in_progress` while a contract change awaits approval; one publication per (head SHA, state); only an invalid command authored by the owner sets `failure`; a command from any other account is ignored (D-COMMANDS); the required-check rule must require branches to be up to date. M1.5 verifies the protection side; M1.6 publishes.

**Amendment (2026-10-14, phase M1.6b; owner answers).**

*States.* For each open PR head of a repository with an enrolled owner:

| State | When |
| --- | --- |
| `success` | the head's protected inventory under the canonical scope equals the canonical (an implementation-only change), or the PR's current proposal revision is ready for integration (`CheckPromotionReadiness` answers ready: exact revision approved under the governing policy, against the current canonical, with a passed integrity assessment of this head) |
| `in_progress` | approval missing (including a revision rebound after the canonical or the policy changed); the head cannot be read yet (a transient GitHub or tree failure); the repository has no canonical yet (bootstrap pending, including a default branch without protected files) |
| `failure` | an invalid command authored by the owner on this PR (superseded 2026-10-19 by D-COMMANDS, "A wrong command has no effect": only a wrong or reused code); an invalid declaration or source (an invalid `.suiteward.yml`, a symlink or submodule in scope); a confirmed integrity failure |

`neutral` and `skipped` are never published. Comments by other accounts never affect the check.

*Owner-command failure.* It applies to the PR's current head when the owner's latest command on that PR was rejected (malformed, invalid code, replayed code, unknown proposal, edited before read, or a rejected consent result). It lasts until the next state change for that PR: a later processed command or a new head. (Superseded 2026-10-19 by D-COMMANDS, "A wrong command has no effect": only a wrong or reused code sets it.)

*No enrolled owner.* Nothing is published; the missing required check already blocks merges, and `/status` says why.

*Publication.*
- One check run per (PR, generation). The generation is a per-PR counter that advances when the head or the computed state changes. This replaces "one publication per (head SHA, state)".
- POST only: the latest run with the name wins on GitHub. PATCH is not used.
- A single writer, the `github_checks` job, decides states and enqueues publications. Approve, revoke and promotion are picked up on its next run (every 30 s).
- The publisher posts a message only while its generation is the PR's current one, so a delayed message never overrides a newer state.
- The summary names the state, the proposal revision when there is one, the installation tier and the next action (the copyable approval command when approval is missing); it never claims that tests ran, and it stays below GitHub's output limit. *Amended 2026-10-26 ([D-M2.1](#d-m21-canonical-execution-the-receipt-and-the-go-profile)): under `canonical: required` the summary may say that SuiteWard ran the approved tests, with counts. Amended 2026-10-27 (owner): no summary says that SuiteWard does not run tests.*

*No change proposal before a canonical exists.* A PR proposal is created only for a repository that has a canonical, so a PR head can never become canonical through the existing-baseline bootstrap.

**Amendment (2026-10-15, phase M1.7b; owner answers).**

*The bootstrap proposal from a PR.* While the Suite has no canonical and the default branch has no protected files, one PR carries a bootstrap proposal from its exact head: the lowest-numbered open non-fork PR whose head has protected files (ADR 0010, amendment of 2026-10-15).
- It is the only proposal allowed before a canonical. It is a baseline proposal, not a change proposal: its revisions expect no canonical and carry the origin kind `pull`.
- A PR head can become V1 only through a merge. The domain refuses an existing-baseline promotion of a `pull` revision.

*`bootstrap-ready`.* That PR's head gets `success`, titled "Bootstrap ready for integration", when the owner approved its exact current revision and the integrity assessment of that head passed. It says no canonical exists yet. Until then it is `in_progress`, `approval-missing`, with the reference. Every other PR stays `bootstrap-pending`.

*Precedence* (superseded by the amendment of 2026-10-16: the newest proposal wins, and nothing is proposed automatically). Once the default branch has protected files, the existing-baseline path wins: a pending PR-head proposal is superseded, and V1 comes from the pinned default-branch commit. This avoids drift between the canonical and what the branch holds (owner: "the option that avoids conflicts or drift that could be irrecoverable").

**Amendment (2026-10-15, after M1.7; owner).** *One comment per new revision.*
- **When.** When a PR gets a new revision that needs approval, SuiteWard posts one comment with:
  - the protected files added, changed and removed against the canonical, bounded;
  - the base version;
  - the copyable `/suiteward approve P<n>-R<m> <code>`;
  - a line saying the previous revision is superseded.
- **Only then.** PRs with no protected change, and implementation-only pushes, get no comment.
- **Never edited.** Each revision gets a new comment. The comment is evidence, not authority: approving still needs a TOTP code for the exact revision.
- **Schedule.** Phase M1.7b.

**Amendment (2026-10-16, phase M1.7b rework; owner answers).** The first live run showed the automatic bootstrap was unsafe. A first PR without `.suiteward.yml` was proposed with only `.github/workflows/**` protected, so a V1 would have silently left the PR's tests out. The bootstrap is now explicit.

*Before V1.*
- **Default state.** Every open non-fork PR gets `in_progress` with reason `bootstrap-awaiting`, and one comment saying how to start.
- **No automatic proposal.** The automatic carrier choice and the automatic baseline proposal are removed.
- **The owner's two commands decide.**
  - **`/suiteward propose`** (owner only, no code). It creates the bootstrap proposal carried by this PR. The source depends on where `.suiteward.yml` is:
    - on the default branch: a baseline pinned to its head;
    - otherwise in the PR head: a baseline from that head, which becomes V1 only from its exact merge commit;
    - otherwise: no proposal. The reply gives a suggested `.suiteward.yml` built from the source's test-like paths, and a one-click link that opens GitHub's editor on the PR branch with the file filled in.

    The newest proposal of the Suite supersedes earlier unpromoted ones. A protected push after the proposal cancels it: there is no automatic new revision, and the owner proposes again.
  - **`/suiteward skip <code>`** (owner only, with a TOTP code like approve). The PR's check becomes `success` with reason `bootstrap-skipped`, so an infrastructure PR can merge before the first contract.
    - This is not a contract assessment. The summary says so.
    - It applies to the whole PR until V1 exists, and is refused once V1 exists.
- **Order of states for a PR before V1:**
  1. fork: `fork-unsupported`;
  2. the carrier of the Suite's latest bootstrap proposal: approval missing, `bootstrap-ready`, or `bootstrap-awaiting` after a cancel;
  3. skipped: `bootstrap-skipped`;
  4. otherwise: `bootstrap-awaiting`.

  Skip and propose on a fork are refused. Skip on the carrier is refused. Propose on a skipped PR makes it the carrier.
- **Guidance is not a failure.** A refused propose or skip is guidance and never sets the owner-command `failure`.

*SuiteWard stays read-only on code* (D-GITHUB-ACCESS). It never commits the declaration. The link only pre-fills GitHub's editor, and the commit is the owner's.

### D-INTEGRATION: Merge methods and the integrated source

Accepted 2026-10-15 (owner, phase M1.7), from the S1 proposals ([s1-github](../spikes/s1-github.md#merge-methods-and-integrated-source)):

- **Supported methods.** Merge, squash and rebase are supported. They are not told apart.
- **The integrated source.** For each method it is the merged PR's `merge_commit_sha`. The protected inventory is recomputed from that commit's tree and compared with the approved revision, never with the PR head or a moving branch tip.
  - A mismatch keeps the canonical and is reported in the PR.
  - A rebase onto a moved base that brings in another change is such a mismatch.
- **Same SHA.** A merged PR whose `merge_commit_sha` equals that of another merged PR of the repository is not promoted, and the PR says so. An outcome already recorded for the other PR stands.
- **Unsupported or unreadable integration.** A merged PR whose merge commit is still absent or unreadable after a bound gets an explicit state in the PR and no promotion.
- **Forks.** Fork PRs are not supported in the MVP, which fails closed on them. A PR whose head repository differs from the base repository, or has been deleted:
  - gets no proposal;
  - keeps its check `in_progress` with an explanation;
  - is never promoted, and its merge is reported.
- **Missed merges.** Besides the open listing, each repository's recently closed PRs are listed, so a PR opened and merged between two polls is still seen. A merge of the target branch is reported even when SuiteWard never saw the PR open.
- **No merge without an outcome.** Every merge into the configured target of a repository with a canonical ends in one recorded outcome:
  - promoted;
  - corrected;
  - no protected change;
  - blocked, with its reason.

  A blocked merge leaves the canonical unchanged. Recovery is a later PR, which either restores the canonical content or carries the integrated content for a new exact approval (ADR 0018). There is no reset command.

### D-RELEASE: Platforms, versions, license and notices

  - The bot pushes a tag only with the owner's authorization quoting the commit.
  - **Amended 2026-10-17 (owner): only the owner creates release tags.**

    - `v0.1.0-rc.1` was the last tag pushed by the bot, before the ruleset existed.

      - Package write access is held by this repository's workflows (the package's Actions access gives the repository the Admin role, checked 2026-10-17). A workflow on any branch the bot pushes can therefore push a tag (`:vX.Y.Z`, `:latest-stable`, `:deploy`) with `GITHUB_TOKEN`, so consumers must verify the signature and pin the digest.
      - **Decided 2026-10-17 (the owner asked for the market standard).** For the MVP, keep publishing with `GITHUB_TOKEN` inside the protected environments, and pin by digest wherever it matters.
        - The install guide offers `Image=…@sha256:<digest>`.
        - The governing host (the dogfooding setup of M1.8) runs `v0.1.0` pinned by its digest.
      - **The real closure is signing, in place from the first release built after the 2026-10-20 amendment of [ADR 0008](../decisions/0008-progressive-integrity-and-execution.md) (the `v0.2.0` release candidate; `v0.1.x` images are not signed).**

        - Signing does not stop another workflow from pushing a tag. A consumer who pins and verifies the digest is protected; one who follows a tag is not.
        - **Release notes name the index digest (2026-10-21).** The release run writes `Index digest:` to its summary, and the owner copies that line into the notes, so every host can pin the signed index without inspecting the image.
- **License.**
  - `AGPL-3.0-only`.
  - The repository carries the official text in `LICENSE`, and the README carries the notice.
  - No per-file headers.
- **Third-party notices.** The image build gathers the license file of every module linked into the binary into `/licenses/THIRD_PARTY_NOTICES`. A module without a license file fails the build.
- **Corresponding source (AGPL section 13).** `/status` reports `source`: the URL of the exact revision the image was built from. The install guide says where the source is. A user who modifies SuiteWard must point `source` at their own modified source.

### D-INSTALL: End-user install, update, backup and dogfooding

Accepted 2026-10-17 (owner answers, M1.8 planning).

- **The end user never needs our dev loop.** They install from the guide, create the GitHub App, run `setup` and create the ruleset once. After that they only approve, with `/suiteward approve`, the PRs that touch protected files. Phase branches, the `remote-poc` promotion and smoke tests are ours alone.
- **The MVP is self-hosted; the managed service comes after it** (owner, 2026-10-17).
  - The owner's target for the end user is the managed service. There the user installs our App, enrolls TOTP and points it at a repository, and all host wiring stays ours.
  - It needs what the self-hosted design does not have: a public App, several owners per instance (D-IDENTITY is one owner), enrollment through a web page with a GitHub login instead of `setup`, and a trust model in which we are the host administrator (ADR 0027). It is recorded as D-MANAGED-SERVICE in Post-MVP.
  - For the MVP, the install guide leads with the co-located path, one command on the user's machine. The isolated host is the operator path: ours, and for whoever self-hosts on a separate machine.
- **Ruleset.** The user creates it, guided by a direct link to the repository's rulesets page and the exact boxes to tick. The App keeps no Administration write, so it can never change its own protection.
- **GitHub App.** The user creates it by hand, from a checklist in the install guide that lists the exact permissions of [D-GITHUB-ACCESS](#d-github-access-github-app-permissions-and-token-lifecycle). The manifest flow is backlog. *Amended 2026-10-21: [D-INSTALLER](#d-installer-the-installer-and-the-first-distributable-version) creates the App through the manifest flow.*
- **Updates.** The user pins the image by digest and updates when they choose: pull the new `vX.Y.Z`, verify its signature, change both `Image=` lines to its digest, then `restart suiteward-migrate.service`, which migrates and restarts the service (install guide, section 11). *Amended 2026-10-21 by [D-INSTALLER](#d-installer-the-installer-and-the-first-distributable-version): the install guide is rewritten around the installer, which leads with one command and updates through `suiteward install --upgrade`.* Automatic updates are not supported (amended 2026-10-20, below): the migration unit cannot be updated by Podman, so an automatic update would start the service alone on an old schema.

- **Dogfooding.**
  - SuiteWard governs its own tests on the isolated host, with `CI / Gate` as the test check (the name of the required check of `ci.yml`), after the acceptance run on a test repository.
  - The agent's bot (`ignisdevne`) is then the governed party. Its installation must have neither Checks write nor Administration write.
  - The ruleset requires `SuiteWard / Contract` from the host's runtime App only.
  - A PR that touches protected files then also needs the owner's approval of its current revision.
  - **The governing host follows release tags** (2026-10-17; the owner asked for the best practice).
    - It runs a pinned `vX.Y.Z` and is updated by hand, exactly as the install guide says, never by auto-update.
    - The reason: an instance that auto-deploys what is merged into the repository it governs would let a merged change replace its own governor.
    - The Deploy workflow and its `:deploy` tag were retired on 2026-10-21 (D-DEPLOY), so there is nothing else for the governing host to follow.
  - **What C2 set up** (owner, 2026-10-17):
    - **The host** runs `v0.1.0` pinned by digest, with `SUITEWARD_JOB_TIMEOUT=3m`.
    - **The scope** covers tests and runner. It protects the Go tests and testdata, the script tests, the CI scripts (`scripts/ci.ps1`, `scripts/check-*.ps1`, `scripts/dev-env.ps1`, and since H6 `scripts/dev.ps1`), the tool pins (`dev/tools.json`), `.golangci.yml` and `codecov.yml`, so that a PR cannot weaken `CI / Gate` or `codecov/patch` without an approval.
    - **The protection.** `main` keeps its classic protection (`CI / Gate`, `codecov/patch`, up to date, administrators included) and gains the ruleset `suiteward-contract`: `SuiteWard / Contract` pinned to the host's App, `CI / Gate`, up to date, and an empty bypass list. Classic protection only offers checks that ran in the last week, so a check that has never run can only be required through a ruleset.
  - **The isolation gap** (owner, 2026-10-17). This session could reach the host App's private key, which was stored on the owner's PC, and the host itself, through the owner's AWS terminal. Until the owner closes both, SuiteWard's `isolated` tier is not assured for this repository. To close them, without an agent session running, the owner:
    1. rotates the App key and installs the new one on the host;
    2. deletes the PC copy and revokes the old key;
    3. stops leaving an AWS session open where an agent can reach it.
  - **Closed** (owner, 2026-10-17). The owner rotated the App key from terminals outside any agent session, revoked the old key and deleted the PC copies, then logged out of AWS. The `isolated` tier holds again for this repository, as long as the host, its App key and AWS access stay out of agent sessions (orchestration.md).

### D-SECURITY-REVIEW: Decisions of the security review (phase SH)

Accepted 2026-10-20 (owner), from the [threat model](../security/threat-model.md) and the hardening phase ([SH](phases/SH.md)). The rules themselves sit with the decision they amend; this entry lists them and records the ones that have no other home.

- **Closed pull requests:** a command first observed after its pull request stopped being open is ignored (D-COMMANDS, [ADR 0027](../decisions/0027-agent-human-trust-separation.md)).
- **A command applies to its own pull request:** a reference to a proposal carried by another pull request is refused before its code is checked, as `other-pull` (D-COMMANDS, ADR 0027).
- **Case-fold collisions and invisible characters:** D-SCOPE amendments of 2026-10-20.
- **Declaration size and unconfigured repositories (bounded input and reported state):**
  - a declaration read from a pull request is capped at 64 KiB (D-SCOPE);
  - an enrolled repository that is not configured no longer holds back commands, and `/status` lists it (D-COMMANDS);
  - a new canonical is verified right after its promotion: the promotion wakes the integrity job, which runs on its own queue, so a mismatch is reported when it happens and not at the next periodic run.
- **The service's database role:** the service connects as a least-privilege role and only `suiteward migrate` holds the owner credential ([ADR 0007](../decisions/0007-canonical-contract-authority.md) amendment).
- **The isolated host is AlmaLinux 9 (EL9) only, with Podman 5.5 or later.** The host also needs the fix for CVE-2026-57231, which AlmaLinux backports without changing the version, so the install guide checks the package changelog. Other distributions are not covered, and the earlier Ubuntu host is replaced by a new AlmaLinux 9 host, not converted.
- **Automatic image updates are not supported.** A host follows a release only by the owner changing the digest in both unit files (D-INSTALL, "Updates"). There is no `AutoUpdate=`, no `latest-stable` following and no timer: the migration unit cannot be updated by Podman, and an instance that updates itself from a tag lets whoever moves the tag replace its governor.
- **Static analysis and supply chain.**
  - `gosec` runs through `golangci-lint`. Its only exceptions are two linter settings, G505 and G401 (SHA-1), because RFC 6238 TOTP and git object IDs require SHA-1. There are no `//nolint` comments and no path exclusions; an integer conversion that can overflow goes through a checked helper.
  - `zizmor` audits the workflows, `gitleaks` scans the whole git history and `trivy` scans the release image for fixable HIGH and CRITICAL vulnerabilities before it is pushed (linux/amd64 only). The tools and the base images are pinned by digest, and a check confirms every copy of a pin agrees.
  - The parsers of untrusted input are fuzzed every week.
- **Review pass (owner, 2026-10-21):**
  - the pattern and path caps (D-SCOPE) and the fence rules of command reading (D-COMMANDS);
  - `serve`, `setup` and `probe` refuse to start when the migration credential is in their environment, so only `suiteward migrate` can hold it;
  - the comment payload shims for v0.1.1 and older are removed: such an instance upgrades to v0.1.3 first and lets its queued comments go out;
  - the authenticator entry names the tier and the first 8 characters of the instance id, and `/status` shows those characters as `instance` (the full id is already public in the pull request comments).
- **Backlog (owner, 2026-10-20):** a maintainer command to authorize or refuse the merge of a fork pull request, after a deeper analysis. Until then a fork pull request fails closed (D-INTEGRATION).

### D-INSTALLER: The installer and the first distributable version

Accepted 2026-10-21 (owner, M1.12 planning). It amends D-INSTALL: the App is created through the manifest flow, and the install guide is rewritten around the installer. The phase is [M1.12](phases/M1.12.md); it ships as `v0.3.0-alpha.1`.

- **Why.** Installing takes about 11 commands co-located and about 62 isolated, with nine pastes, the image digest typed three times and a hand-made App, and several mistakes stay silent. Most of that can be automated.
- **Order of work:** `doctor`, then the isolated installer with the ruleset and setup assistance, then the App manifest flow, then the release-pinned binary.
- **One App per instance, created through the manifest flow.** One owner per instance, up to 20 repositories. The App keeps exactly the five permissions of D-GITHUB-ACCESS: no Contents write, no Administration write, webhook off and `public: false`. So the ruleset stays a human Import click per repository, from a JSON the installer writes. The manifest code is converted on the machine that keeps the key (for isolated, the host), with a random `state` and a listener on 127.0.0.1 only. The code passes through the user's browser, as the PEM download does today; the threat model says so.
- **GitHub Free and private repositories (owner, 2026-10-22).** GitHub does not enforce rulesets on a private repository of an account or organization on the Free plan (spike S2). The installer warns plainly before the ruleset Import that the repository will not be protected there, suggests a public repository or a paid plan, and continues. `doctor` and `/status` report `enforcement-unavailable`.
- **Starting the Podman machine after a reboot (owner, 2026-10-22).** The co-located installer makes the stack come back whenever the machine starts. Starting the machine at Windows logon stays out of the alpha: `doctor` reports a stopped machine and the docs say to run `podman machine start`. Auto-start is post-MVP.
- **Runtimes.**
  - **Isolated:** Podman only.
  - **Co-located:** Podman is strongly recommended. Docker is allowed co-located only, as an explicitly discouraged option, and the installer and the docs say so plainly. The reasons:
    - the Docker daemon is rootful by default;
    - Docker has no secrets outside Swarm. Amended by spike S2 (2026-10-22): a file bind-mounted from Windows shows up as mode `777` inside Docker's VM, so the installer keeps Docker's secrets in named volumes instead, **one volume per consumer**, each mounted read-only into its own container only:
      - the database password, for the database;
      - the owner URL and the app URL, for migrate;
      - the app URL, the App key and the MCP token, for serve.

      `serve` therefore never sees the owner URL, as on Podman. Each secret is written through stdin, owned by the uid that reads it, mode `0400`, so it never touches the Windows disk. Whoever controls the rootful daemon can still read that volume, where Podman keeps them in its rootless secret store ([S2](../spikes/s2-installer.md)).
  - A rootful Podman connection is refused. The installer never runs as root: isolated splits the administrator steps (`sudo suiteward install host`) from the service-account steps (`suiteward install`).
- **The GitHub env file moves to the service account.** `/etc/suiteward/github.env` (written by an administrator, install guide 10.6) becomes `~/.config/suiteward/github.env`, owned by `suiteward` and loaded with `EnvironmentFile=%h/.config/suiteward/github.env`. Its values (App ID, installation ID, repositories) only exist after the manifest flow, which runs as `suiteward`. Administrator ownership was never a control: the install guide records no reason for it, and the file holds no secret. What the instance can reach is bounded by the installation's repository selection on GitHub, not by this file. Adoption copies an existing `/etc` file to the account and keeps the source; the installer prints the `sudo rm` line once the service reads the new file, and never deletes anything under `/etc` itself.
- **Plain prompts, not `huh`.** The prompts are plain line prompts (standard library plus `golang.org/x/term` for no-echo input), which work in every terminal and are accessible, and each has a flag and an answers-file key. The TUI library `huh` is rejected for its dependency weight; polish is post-MVP. *Amended 2026-10-23 ([D-M1.13](#d-m113-macos-the-one-line-install-installer-screens-the-change-report-and-encrypted-backups)): the polish is delivered as full-screen steps, with no TUI library, and the plain line mode stays.* *Amended 2026-10-23 ([D-M1.14](#d-m114-installer-ux-refinement-after-a-fresh-install)): the choices are made with the arrow keys on a full screen, still with no TUI library; typed and numbered answers stay as the fallback and in plain mode.*
- **The binary is a release asset.**
  - `suiteward` is built for linux/amd64, linux/arm64, windows/amd64 and darwin/arm64 and uploaded to the Release the owner created, with `SHA256SUMS` and a keyless `cosign sign-blob` bundle per file, under the same workflow identity as the image. macOS is covered by build and tests only. *Amended 2026-10-23 (D-M1.13): a fifth binary, darwin/amd64, and `install.sh` join the signed files, and the macOS tests run in CI on a macOS runner; live validation on a Mac is still pending.* *Amended 2026-10-28 (M2.1b): the installer then ran live on a real Mac, without GitHub, in M1.15 ([outcome](phases/M1.15.md#outcome)); the test runner, the GitHub flow with its setup window and later releases have not been seen on macOS ([D-ROADMAP](#d-roadmap-the-order-after-m21)).*
  - Each binary embeds the signed index digest of its own release, so an install never takes an image from a tag. A development build without that digest requires `--image`.
  - On the isolated host, which has no cosign or PowerShell, the binary is verified once on the PC and the host checks the same files against `SHA256SUMS`.
- **`deploy/local.ps1` is removed in the alpha.** The installer adopts a stack it made, and `suiteward install --upgrade` converts one. `suiteward uninstall [--purge]` replaces `local.ps1 -Down`; `--purge` also removes the secrets, volumes and settings and keeps the backups.
- **Before the alpha (owner, 2026-10-22, from the M1.12 reviews):**
  - **Setup guard, and `suiteward enroll`.** `install` runs setup only when `/status` shows no owner. When an owner is enrolled, or `/status` cannot be read, setup is skipped, so a re-run or a restore never replaces the TOTP secret. Re-enrolling is the deliberate verb `suiteward enroll`, and the installer's messages name it.
  - **Upgrade with the service down.** `install --upgrade` refuses, because the backup includes `/status`. On a terminal it first asks whether to start the installed service, then continues once `/status` answers.
  - **Pasting the manifest code.** The fallback paste prompt may echo. The code is never a flag, so it never reaches argv. *Amended 2026-10-23 (D-M1.14): the paste is offered after 2 minutes, hidden, and never echoed.*
  - **An App named in the settings without its key secret.** The installer stops and offers two routes: give the App's key file, or create a new App (the old one is named for deletion). A terminal asks; otherwise the error names both.
  - **`v0.1.x` isolated hosts** are not converted by `--upgrade`. No installation of v0.1.x exists outside our own hosts, which already run v0.2.0.
- **Hand-over.** `v0.3.0-alpha.1`, a pre-release, goes to individual testers. Everything after the alpha is post-MVP.

### D-M1.13: macOS, the one-line install, installer screens, the change report and encrypted backups

Accepted 2026-10-22 and 2026-10-23 (owner, M1.13 planning, after the alpha). It amends D-INSTALLER. The phase is [M1.13](phases/M1.13.md).

- **macOS (owner, M1.13 planning).**
  - The installer ships as `darwin/arm64` and `darwin/amd64` binaries. CI builds and tests the Go code on a `macos-15` runner (Apple silicon); lint and the sqlc check stay on Windows and Linux, whose pinned tools exist for those platforms only.
  - The binary is **not notarized.** A browser download may meet Gatekeeper's quarantine, and when it does the user removes the flag with `xattr -d com.apple.quarantine <file>` after verifying the file. A `curl` download carries no flag. *Amended 2026-10-26 (D-M1.15, MAC-5): an outside tester's browser download was not blocked. A terminal that holds the Developer Tools permission starts programs without the check, and a file without the flag is not checked.*
  - The co-located tier uses a Podman machine, or Docker Desktop (discouraged). The isolated tier stays Linux only.
  - The owner validates on their own Mac. Until then the docs say: validated live on Windows; on macOS by CI tests, live validation pending. *Amended 2026-10-28 (M2.1b): an outside tester ran the installer live on a real Mac with Podman, without GitHub, in M1.15 (2026-10-25, `v0.4.0-alpha.2`: the one-line install, an install, `doctor`, backup and restore, and a purge). The docs now say that, and that the test runner, the GitHub flow with its setup window and later releases have not been seen on macOS yet; the verification phase after M3 covers macOS ([D-ROADMAP](#d-roadmap-the-order-after-m21)).*
- **The one-line install.**
  - `scripts/install.sh` is a release asset, `install.sh`, listed in `SHA256SUMS` with its own `install.sh.sigstore.json`. It downloads the binary of the platform, checks it against `SHA256SUMS` and, when cosign is installed, verifies the signature of `SHA256SUMS` with the identity that `scripts/verify-release.ps1` pins. Without cosign it says that the signature was not verified, prints the hash of `SHA256SUMS` and the commands to check it elsewhere. It never uses `sudo` and runs nothing it installs. The manual path of the install guide stays the stronger one.
  - **The one-liner needs `SUITEWARD_VERSION=<tag>` until a final release carries `install.sh`.** GitHub never makes a pre-release the latest release, today's latest release is `v0.2.0`, and neither it nor the alpha pre-releases carry `install.sh`. The script is the same file in every release, so it learns nothing from the address it came from. Once a final release ships `install.sh`, the default of the latest release works. `SUITEWARD_RELEASE_BASE`, which points the script at another origin, exists for the script's own test and takes only an `https://` or a `file://` base (`https://` only with wget).
  - There is no Windows one-line install in this phase.
- **Installer screens (owner, 2026-10-22).** The mockup shown in chat is the template: a frame with a title bar, the step list, numbered choices, progress bars and a summary screen, in the SuiteWard colors. It lives in `internal/installer/ui` with the standard library, `golang.org/x/term` and `golang.org/x/sys/windows`: no TUI library and no new dependency. A plain mode keeps the line output, and is the mode with no terminal, with `NO_COLOR`, with `TERM=dumb` and with `--plain`. On a full screen, the installer leaves the screen while setup runs, because setup prints the TOTP secret: its output is on the normal terminal and the installer's screen keeps none of it. The installer then waits for Enter, so that the secret can be copied before the screen comes back. *Amended 2026-10-23 ([D-M1.14](#d-m114-installer-ux-refinement-after-a-fresh-install)): on Windows and macOS setup opens in a window of its own, and the installer waits on its own screen; Linux, SSH, the isolated tier and plain mode keep this hand-over.*
  - **After the live checks (owner, 2026-10-23).** Every full-screen command ends on a page that waits for Enter: a summary, or its last page, which `doctor` ends with its counts. Closing the screen keeps every check and warning of the run, with its mark, on the normal terminal. Ctrl-C exits 130 "interrupted" on every installer command, `doctor` included; `doctor --json` keeps the code of its checks. *Amended 2026-10-23 (D-M1.14): the install and the upgrade end by running `doctor` in their summary, and a Ctrl-C during those checks is an interrupt (130), while one before them only skips them.*
  - **A failed command (owner, 2026-10-23).** A command that fails on the full screen shows its error on the screen, under the page it stopped on and with the title bar saying `failed`, and waits for Enter before it closes the screen (`Screen.Fail`, called by `endConsole`, which every command defers). Stderr and the exit code are what they were, and Ctrl-C or the end of the input at that wait keeps them. Plain output, an interrupt (130) and a usage error (2) do not wait, and `doctor`'s failed checks keep their one page of counts.
- **The change report (owner, 2026-10-22).** The revision comment becomes a numeric summary and links to the full HTML report, which the instance serves on its loopback address. The installer gives the service `SUITEWARD_REPORT_BASE_URL=http://127.0.0.1:<HTTP port>` on both tiers for the link. The link opens only where the instance is reachable: the same PC, or the isolated host through a port forward. Nothing new goes to GitHub, because the App keeps no Contents write ([D-GITHUB-ACCESS](#d-github-access-github-app-permissions-and-token-lifecycle)).
  - **Delivered.**
    - The comment states the numbers: the files added, modified and removed, the lines `+N/−M` (counted in some of the files), the files not shown line by line, and the marker lines seen. It names the 20 changed files with the most lines and the 10 that have no line-by-line diff, and links the report.
    - The markers are deterministic and never a verdict: removed assertion lines, added skip and focus lines, removed test declarations and removed test files. No agent analyzes anything.
    - The page is rebuilt on every request from the revision's manifest, which the checks job keeps in the artifact store under its digest, and from the manifest of the base canonical. It is static and escapes everything that comes from the repository. It answers only a loopback `Host`, and has no authentication beyond that: anyone who can reach the HTTP port reads it ([threat model](../security/threat-model.md)).
    - The numbers are counted when the comment is delivered. A comment whose numbers cannot be counted is posted with the lists of paths and says that the numbers are unknown, and a revision recorded before M1.13 has no numbers and no page. The check summary states the numbers, with no link and no path.
    - The runtime contract has the details ([Change report (M1.13)](../contracts/runtime.md#change-report-m113-normative)), and the install guide has the user's view ([section 9](../install.md#9-day-to-day)).
  - **Stays post-MVP:** the diff on the check's Details page, a link to the diff of each file, a marker for changed runner files, and a report served by the managed service behind its sign-in.
- **Backups (owner, M1.13 planning; the key kind, 2026-10-23).** The backup is an encrypted archive with an age key pair of the **hybrid post-quantum kind, ML-KEM-768 with X25519**: a backup lives for years and holds the TOTP secret. The instance keeps only the public key. The private key goes into a recovery kit that the owner keeps off the machine. Remote backup storage ([ADR 0021](../decisions/0021-release-backups-and-health-reconciliation.md)) stays deferred, because it needs Contents write.
  - **Delivered** ([backup runbook](../backup.md)).
    - `suiteward backup init` makes the key pair, writes the kit (a file only the user can read, never overwritten, confirmed by a typed `stored`) and stores only the public key in the settings. `suiteward backup` writes one encrypted file, `suiteward-backup-<date>-<time>.tar.age`, while the service runs, with the dump never in plaintext on disk. `install --upgrade` takes the same backup before it changes anything and refuses, before any change, when no key is set and nothing can ask for one (`--backup-recipient` gives the public key). On the isolated tier the replaced units are also kept as plain files beside the archive.
    - `suiteward restore` verifies the whole backup, previews it, asks the operator to type the instance id, backs up the state it replaces, stops the service, loads the dump in one transaction that the server rolls back when it is cut short, replaces the artifact volume, migrates, starts and compares `/status`. It restores a backup of the same release only, and it does not restore credentials. `--plaintext-dir` restores the directories that the alpha releases made.
    - Task B3 makes the restore refuse a backup whose manifest has a release or tier that is not a plain name, an image digest or instance id that is not well formed, or a member hash that is not hexadecimal, and a plaintext directory whose status says `unavailable`, and clean control and format characters from what it prints from `status.json`. Encryption still does not say who wrote a backup: what the fields claim stays a claim.
  - **Delivered differently from the ADRs.** The archive is a whole-instance backup, with the TOTP secret in it, and not a project archive. The restore replaces data in place and has no recovery mode. [ADR 0019](../decisions/0019-encrypted-backups-and-instance-recovery-key.md) and [ADR 0020](../decisions/0020-guided-local-cli-recovery.md) list the differences, and the in-place restore is accepted for the alpha ([D-RESTORE-INPLACE](#d-restore-inplace-the-in-place-restore)).
  - **Stays post-MVP:** scheduled backups, the separate backup container, backup receipts and health reporting, remote storage (D-BACKUP-REMOTE), the recovery mode of the restore, and an exclusion mechanism for an old and a replacement instance.
- **CI (owner, 2026-10-23).** A job, "Quadlet units on AlmaLinux 9", renders the units of both installer shapes (with and without GitHub) and dry-runs AlmaLinux 9's Podman quadlet generator over them, because the isolated host runs that OS. `CI / Gate` requires it. The AlmaLinux image is pinned by digest and the Podman package is not: it is the current el9 build, as on the host, and the job prints its version ([CI and coverage](../ci-and-coverage.md)).
- **The settings file and the purge (owner, 2026-10-23, after an incident).** `suiteward uninstall --settings <a file that did not exist> --purge --yes` fell back to the defaults and purged the owner's real co-located instance, with no backup. Decided: a settings file that is named must exist for every command that reads one (exit 1, naming the path, before any runtime call; only `install` without `--upgrade`, which writes it, is exempt); no destructive action runs on defaults that no settings file named (`uninstall` and `restore` with no settings file need `--runtime` and `--connection` on the co-located tier, or `--tier isolated`; `enroll` on the co-located tier refuses and points to `suiteward install --upgrade`, which saves the settings); `uninstall --purge` needs the instance id, typed or `--instance` with `--yes`, as `restore` does (read from `/status`, else the database, else `unknown`, which `--yes` refuses while there is no settings file and the database volume is there: it is typed on a terminal, or the settings file is passed); and `uninstall` says the instance id, the runtime and the settings file before it asks.

### D-ARCHIVE: The encrypted backup archive

Decided 2026-10-23 within [D-M1.13](#d-m113-macos-the-one-line-install-installer-screens-the-change-report-and-encrypted-backups) ([ADR 0019](../decisions/0019-encrypted-backups-and-instance-recovery-key.md)); it moved here from Post-MVP. The format is one age file encrypted to the instance's post-quantum recovery recipient, whose plaintext is a tar of `status.json`, `suiteward.sql`, `suiteward-artifacts.tar`, `settings.yaml`, the unit files of the isolated tier and a `manifest.json` that records the size and SHA-256 of every member. There is one recovery kit per instance, and the instance keeps only the public key. The first part is in `suiteward backup init`, `suiteward backup` and the backup of `install --upgrade` ([backup runbook](../backup.md)); the amendment of the ADR lists what differs and what stays deferred: the separate backup container, periodic and promotion-triggered backups, receipts and health reporting, size budgets, and a coordinated recovery point.

### D-RESTORE: The guided restore

Decided 2026-10-23 within [D-M1.13](#d-m113-macos-the-one-line-install-installer-screens-the-change-report-and-encrypted-backups) ([ADR 0020](../decisions/0020-guided-local-cli-recovery.md)); it moved here from Post-MVP. `suiteward restore <backup.tar.age>` restores the instance it runs on: it verifies, previews, asks for the instance id, backs up the state it replaces, loads in one transaction, replaces the artifacts and compares `/status`. It differs from the ADR in three ways that the amendment lists: it replaces data in place, it has no recovery mode with reconciliation before resumption, and the operator names the file. The first is accepted for the alpha ([D-RESTORE-INPLACE](#d-restore-inplace-the-in-place-restore)); the others are deferred.

### D-M1.14: Installer UX refinement after a fresh install

Accepted 2026-10-23 (owner, after a fresh install of `v0.4.0-alpha.1` on Windows with a Podman machine, run as a new user would, to find what such a user meets: findings UX-1 to UX-25). ### D-M1.15: Scope discovery answers and the merge version in one read

Accepted 2026-10-25 (owner, M1.15 planning, and after the test-discovery study and its review). It records the answers to the owner's questions Q2 to Q4 on scope discovery (raised 2026-10-17, after the C2 finding in [M1.8](phases/M1.8.md#c2-outcome-dogfooding-2026-10-17)) and takes the one-read merge version that was left after the MVP. It amends [D-SCOPE-DISCOVERY](#d-scope-discovery-suggesting-and-widening-the-scope) and changes no invariant. The phase is [M1.15](phases/M1.15.md); its installer work and its live findings are on the phase page. *Extended 2026-10-26 with what the live checks of `v0.4.0-alpha.2` decided: the bullets from "The live results" on.*

- **Q2: `suiteward scope add [--runner] PATTERN...`.** A local command that a user or an agent runs in a checkout to add the patterns that the suggestion missed to `.suiteward.yml`: to `include`, or with `--runner` to `runner`.
  - **It edits text and grants nothing.** It reads no setting and no environment. It inserts one line for each new pattern after the last item of the block list, with the indentation and line break of that item and the quoting that every item of the list shares (plain when they differ, and quoted where YAML needs it), and every other byte stays, comments included, because the owner approves the bytes ([D-SCOPE](#d-scope-declaration-and-source-inventory-semantics)). The patterns protect more files only once the owner approves the revision on a pull request ([D-SCOPE-DISCOVERY](#d-scope-discovery-suggesting-and-widening-the-scope), "Widening is a protected change"), and the command says so when it writes.
  - **It refuses and skips rather than guesses.** A pattern that the domain refuses, or that holds a tab, a backslash or a character that cannot be seen, is refused before the file is read. A pattern that the list holds already is skipped and reported. The result must read back, with the domain parser, as the old declaration plus the new patterns, and within the cap of a declaration. The file is replaced through a temporary file in its directory and keeps its mode. The command never creates a declaration and never replaces a symbolic link.
  - **What it leaves to the user.** Where it cannot insert safely (for example, the declaration is invalid, the key is not a list or the list is absent, the list is a flow list such as `[a, b]`, the list has an anchor or a tag, its last item is not a line of the form `- value`, or the result would not read back as the old declaration plus the new patterns), it changes nothing, prints on stderr the lines to add by hand, and exits 1. The key goes with those lines only when the list is absent.
  - **Exit codes.** 0 when it added the patterns or found nothing to add; 1 when it did not change the file (a pattern refused, no regular `.suiteward.yml` in the current directory, a declaration left to the user, a failed write); 2 for a usage error (no pattern, an unknown flag, or a pattern that starts with `-` after another pattern).
- **Q3: the existing answer stands.** [D-SCOPE-DISCOVERY](#d-scope-discovery-suggesting-and-widening-the-scope) decided it, and M1.15 adds nothing to it. A test folder added between versions is marked as protected by a pull request that changes `.suiteward.yml`, approved with the TOTP code; `scope add` is how a user or an agent writes that change. SuiteWard reports new test-like paths outside the scope (the scope notice and `/suiteward suggest`) and, for a runner file, holds the check at `runner-uncovered` until the owner decides. It never protects them itself, because only the owner's approval changes the contract.
- **Q4: the study.** [`docs/spikes/s3-test-discovery.md`](../spikes/s3-test-discovery.md) read how Codecov and similar tools, the test runners and seven CI workflows find tests. No tool finds tests in a source tree without being told where, or without running code: the reporting tools ingest what a CI run produced, the runners enumerate by executing, and the rest ask the user to declare. SuiteWard's model, path conventions and then a declared scope that the owner approves, is the same one. What does not transfer: test and coverage reports, runner enumeration, executable config, shell strings and CI test commands (the workflow is already protected by a fixed default).
- **Config reading is not done (owner, 2026-10-25, after the study; this replaces the first decision of M1.15 to read config files).** Detection stays path-only ([D-SCOPE-DISCOVERY](#d-scope-discovery-suggesting-and-widening-the-scope)).
  - The configs that the study read name the top-level `tests` directory (Flask, requests, Laravel's `phpunit.xml.dist`) or do not exist (Express), and the path rules already suggest `/tests/` and `/test/` for all four.
  - A configured directory is not a safe suggestion. It says where the runner looks, not which files are tests, and an in-package layout names production packages: pandas has `testpaths = "pandas"` and astropy `["astropy", "docs"]`.
  - A reading gated to directories that look like test directories would have suggested nothing that the path rules miss on the sample.
  - The layouts that the path rules miss are served by `scope add`. Inline Rust unit tests and Python doctests are visible to neither paths nor configs, and the owner declares them. Section 5 of the study stays as the design to start from if reading is reconsidered, and the item stays under "After the MVP" of D-SCOPE-DISCOVERY.
- **`nextMergeVersion` reads the earlier versions in one read.** The merge promotion allocates `V<n+1>` and decides a correction when an earlier version holds the integrated manifest. It used to read each earlier version with `Tx.Version`; it now reads them all with one `Tx.VersionsHolding(digest)`, a query of the stored digests of the locked Suite that decodes no manifest ([persistence contract](../contracts/persistence.md#merge-outcome-internalapplicationgovernance), step 8).
  - **Checked:** every version `V1` to `V<n-1>` is there (a gap is `ErrInvalidState`, naming it), and the promotion of each binds the manifest digest that the version stores (another digest is `ErrInvalidState`, naming it). These are the checks of `Tx.Version`, and a version without a promotion is missing, as for it.
  - **Not checked:** the earlier manifests are not decoded or hashed again. The digest is compared as stored: it is written with its manifest, `suite_versions` is immutable by trigger, and the earlier versions only choose between a promotion and a correction, because the version being corrected is the current one, which is read in full.
- **The live results of `v0.4.0-alpha.2` (2026-10-25 and 2026-10-26).** What was seen, what is still to be seen, the limits and the reasoning behind WIN-7 are on the [phase page](phases/M1.15.md#outcome).

### D-M2.1: Canonical execution, the receipt and the Go profile

Accepted 2026-10-26 (the owner's decisions of M2.1 planning, on the [phase page](phases/M2.1.md#owner-decisions-2026-10-26), the owner's answers after the first review of the design, and the design that task A0 wrote into [ADR 0028](../decisions/0028-canonical-execution-and-the-receipt.md) and the contracts). It amends the M2 of [ADR 0008](../decisions/0008-progressive-integrity-and-execution.md) and changes no invariant: canonical immutability, candidate non-authority, exact-revision approval, atomic promotion and the distinction between evidence and authority all hold. An execution result never enters the consent binding ([D-APPROVAL-CONTEXT](#d-approval-context-approval-binding-for-implementation-only-changes)).

- **Opt-in (owner).** Nothing runs until the canonical declaration names a profile: `execution: {profile: go}` in `.suiteward.yml`. Turning execution on is a governed change approved with a TOTP code. With a profile, `canonical` defaults to `advisory` (`off | advisory | required`) and `receipt` to `advisory` (`off | advisory | before-approval | required`). Unknown keys under `execution` are refused. **A level named without a `profile` is an invalid declaration** (owner), so nobody believes a policy is on while nothing runs; `execution: {}` stays valid and means no policy. Weakening a level, or removing the block, is reported as a reduction. **The canonical declaration governs every pull request, the one that changes it included.**
- **One engine, two plans (owner).** The **canonical plan** runs the governing tests on the head of every open pull request: those of the canonical version, or, once a consent covers the head, those of the consented revision. The whole governing manifest is laid over the head's tree (tests, `testdata`, runner files, the declaration, workflows), and a head file that the governing scope covers but the manifest lacks is removed. The **receipt** runs the tests that a revision adds or changes, on the head and on a base side: the base commit plus the head's version of every file that the canonical `include` matches and the head adds or changes. Only the approved `include` decides what crosses, so no head-added pattern can move code into the base run, and a fix that is a dependency bump is still detected. A test that needs a symbol of the head's non-test source reads NEW API, and in Go that holds for its whole package.
- **A receipt can be `not-applicable` or empty.** When no file that the canonical `include` matches is added or changed in the revision (only runner files or the declaration changed, or tests were only deleted), no job runs, the receipt gate does not apply (the approve needs no mode) and no Receipt check is published. When such files changed but hold no test function that was added or changed (only `testdata` or helpers, say), the receipt is complete and empty: the gate treats it like a not-applicable one, the Receipt check is `success` with the counts of the seven states at zero (corrected 2026-10-27 from "six"), and the page lists the changed files.
- **The mode comes from the owner (owner).** `/suiteward approve P<n>-R<m> [fix|feature|refactor] <code>` carries the gating mode, with the TOTP code. `/suiteward mode <fix|feature|refactor>` has no code and only sets the preview that the receipt page shows. No gate reads it.
- **Gates (owner).** The receipt gates the approval: `before-approval` refuses only while the receipt is pending, whatever the result, and `required` also needs a mode and a summary that is met. The code is verified and consumed first, so a refused comment cannot be reused with another mode, and the check does not change. Canonical execution gates the `SuiteWard / Contract` check under `required`: a pending or unavailable run keeps it `in_progress`, a failing, missing or flaky test fails it, and it never becomes `success` from integrity alone. After an approval, a push that breaks the approved tests keeps the approval, and only the canonical gate reacts.
- **The escape, `/suiteward unblock <code>` (owner).** Only the owner, with a TOTP code consumed like an approve's. It applies to the pull request's current head and lifts only the runs that are `unavailable` there (the executor is down, say), in both gates. It never lifts a failing test or a pending run. It binds to the jobs that were unavailable when it was processed (a job created later for the same head needs its own unblock). It is recorded (`unblocked`, or `unblock-refused` with a reason such as `not-unavailable`), and the Contract and Receipt checks of that head say that the head was unblocked by the owner. A new push needs a new unblock if its run is unavailable too. *Amended 2026-10-28 (owner, M2.1b; [ADR 0029](../decisions/0029-results-communication.md), which amends [ADR 0028](../decisions/0028-canonical-execution-and-the-receipt.md)): "It never lifts a pending run" no longer holds. When the head reads not responding (no lease request or heartbeat of the executor for about 30 seconds), an unblock also lifts the head's jobs that wait for the test runner: it ends each as `unavailable` with the reason `no-executor` and lifts it. A job that a test runner that is responding holds is refused (`runner-responding`). Every unblock holds, early or after the wait: the unblocked job is not replaced when the runner returns, and the next push runs as usual. It still lifts only gates and never a failing test or an approval, and the TOTP code is consumed as before.*
- **Retries.** An attempt that an executor leased and then lost or failed (a lease that expired, a run past its time, a runtime error, a failed fetch of a dependency) is retried automatically, up to 3 failed attempts with a backoff, and then it is final for that job and the owner can unblock it. A run that the repository caused (a failed source check, a toolchain mismatch, a size cap, no merge base) is final for its head and binding. When no executor was seen (no lease request or heartbeat) for `EXECUTOR_LEASE_WAIT` (2 minutes by default since owner decision 22 of 2026-10-28; 5 minutes before), the pending jobs are `unavailable` with the reason `no-executor` at once and are not retried; job age alone never causes it, so a healthy executor working through a queue keeps its jobs pending, and a dead one reads `unavailable` within minutes. A failed GitHub read never consumes an attempt and never reads `no-executor`: the job stays pending as `github-unavailable` and becomes unavailable after `EXECUTOR_GITHUB_WAIT` (30 minutes by default). With no executor configured the jobs are created already `unavailable`. Neither that nor `no-executor` is final for good: once an executor is configured, or a real request from one arrives after a `no-executor` outcome, a fresh job replaces the old one, and an unblock of the old job does not carry over. *Amended 2026-10-28 (owner, M2.1b; ADR 0029): a job that the owner unblocked is not replaced, so the old job and its unblock hold until the next push; the sentence above describes a job that nobody unblocked. A job that ended for `executor-not-configured` is still replaced once a token is configured, whatever the owner did. A head with waiting jobs also reads "not responding" after about 30 seconds without the executor, before `EXECUTOR_LEASE_WAIT` ends them as `no-executor`.*
- **The `SuiteWard / Receipt` check (owner).** Not required. `failure` only on FAILS or MISSING, `neutral` when the receipt could not be produced, `success` otherwise, and `in_progress` while pending. Counts only, no link. The full receipt is an HTML page served on loopback. The revision comment, still posted once and never edited, gains one fixed line with its link.
- **A separate executor (owner).** `suiteward execute` holds only an executor token: no database role, no GitHub credential, no access to the service's store. The service never gets a container-runtime socket. It leases jobs over `/executor/v1`, streams the commit archives itself and validates the result. The source of a run is checked against the tree entries of the commit, and the archive is not trusted. Sandboxes have no network at all. The reads that execution makes of GitHub count in the D-SYNC budget and pacing.
- **No network in the sandbox (owner).** The executor prefetches the modules that the `go.sum` of each side names from `proxy.golang.org`, and follows its redirects only to `storage.googleapis.com` over HTTPS (an egress allow-list for those two names is recommended; corrected 2026-10-27 from "`proxy.golang.org` only", which would stop the zips the proxy redirects), after it validates every module path and version and bounds their count and bytes. A `replace` outside the tree fails. The files enter the sandbox in the same stdin tar as the source, never on a host filesystem, and the sandbox runs `go` with `GOPROXY=file:///...`. The integrity of the bytes is TLS to the proxy plus the candidate's `go.sum`, as in a networked install and not stronger. A validation failure, an outside `replace` or a bound is `install-failed`, deterministic. A fetch error is a counted failure, `fetch-failed`, final after 3. The tar is built from the verified tree in the stream. The limits are `--memory 3g --memory-swap 3g --cpus 4 --pids-limit 512`, a 1 GiB tmpfs, user 65534, `--log-driver=none` (the runtime keeps no copy of the output on the host; added 2026-10-27) and one pinned image per profile, and the evidence records the runtime. `go test -timeout` equals the lease's `testTimeoutSeconds`, and `go test` kills a binary a minute past it (the test reads `fail`); `EXECUTOR_JOB_TIMEOUT` ends a whole attempt as a counted `timeout`, the executor's only time kill is at that deadline (less 30 s), and the setting must be at least 12m30s: the test bound, `go test`'s own kill, the executor's 30 s margin and 60 s for everything around the test binary (corrected 2026-10-27 from "at least one binary's bound", which let the executor's drop come before `go test`'s own kill). The floor covers the first run of a hung test, not its reruns: a test that hangs on every run still ends the attempt as a counted `timeout`, and `unavailable` after the third, which fails closed. Before a run the executor refuses with `too-large` when the unpacked tree and modules pass half the tmpfs. Only out-of-band signals make a `resource-limit` (final; a candidate can cause it, so the owner should read it before unblocking it). The executor is a native process on both tiers, under its own account `suiteward-exec` on the isolated one (a systemd user unit with linger, a `Delegate` drop-in, nft rules rejecting the two instance-metadata addresses by destination). A Podman machine's loopback port can fail from Windows, which `doctor` detects.
- **Sealing and honesty (owner).** On the isolated tier the executor runs on the host under its own account, pinned to the signed release and checked by `doctor`, with images pinned by digest. On the co-located tier the pins catch drift, not a determined agent, and that is stated. Code that behaves differently under test cannot be ruled out. When the exit status of a `go test` invocation contradicts its report, every expected test of that invocation reads `fail`. Remote attestation is an M3 or managed-service candidate.
- **What this changes in earlier decisions.**
  - **D-CHECKS** says that the check "never claims that tests ran", and [ADR 0015](../decisions/0015-required-contract-check.md) says "Success never means that SuiteWard executed the tests". Under `canonical: required` the Contract check may say that SuiteWard ran the approved tests, and give the counts. Under `advisory` and `off` both statements still hold. ADR 0015 carries a note for this. D-CHECKS also lists the states of the check: `canonical-pending` and `canonical-unavailable` are new `in_progress` reasons, `canonical-failing` a new `failure` reason (the names of the domain), and the check can say that the owner unblocked the head.
  - **D-COMMANDS.** `approve` gains the optional mode, and `mode` and `unblock` are new owner-only verbs. The new dispositions are `receipt-refused`, `mode-set`, `mode-refused`, `unblocked` and `unblock-refused`. None of them sets `owner-command-rejected`, so "A wrong command has no effect" holds (a wrong code on an `unblock` sets it, as on any command that carries a code), and `receipt-refused`, `unblocked` and `unblock-refused` have consumed their step. The malformed reasons gain `missing-mode` and `bad-mode`. The closed-pull-request guard covers `unblock`.
  - **D-GITHUB-ACCESS.** The archive download uses a token with `{metadata: read, contents: read}`, requested only for it. The merge-base read uses the synchronization token. The App's permissions do not change, and there is still no Contents write.
  - **D-SCOPE.** The declaration gains the `execution` block, and its strict-key rule applies to it.
  - **D-SYNC.** The reads of execution count in the budget and in the pacing of the synchronization tick.
  - **D-RUNTIME.** The one binary gains `suiteward execute`. The "no endpoint changes state" of the HTTP surface is amended for the executor API.
- **The executor's pin on the isolated tier (owner, 2026-10-27).** `suiteward install host` refuses to set up the executor without `--sha256sums`, the release's `SHA256SUMS`: the binary must be listed there, so the pin is the signed release's and not only the hash of the program that happened to be copied. `doctor` never reads the sums: it compares the binary with its pin, and fails an isolated executor whose binary differs from its pin or whose pin does not name a release asset (`suiteward_<tag>_linux_<arch>`), as a pin made by hand does not. On the co-located tier, where the agent can reach the binary anyway, a pin without the sums stays a `doctor` warning. *As implemented (2026-10-27), with this entry's main sentence corrected on 2026-10-28 (M2.1b): the decision first said that `doctor` fails a binary that the release's sums do not list. The host step reads the sums, and `doctor` checks the pin that the step wrote.*
- **What a text says about running tests (owner, 2026-10-27).** M1 ran no tests; from M2.1 SuiteWard does. One rule holds for every text and every current document, with no variant by profile, level or tier: none says that SuiteWard does not run tests, and only a text computed from a run says what ran or did not run. The texts that change and the test that guards the rule are in the [runtime contract](../contracts/runtime.md#what-a-text-says-about-running-tests). ADRs and the pages of past phases are records and keep their words; an ADR that states the M1 claim as a rule gains a note ([ADR 0014](../decisions/0014-merge-triggered-canonical-promotion.md#note-2026-10-27-suiteward-runs-tests-since-m21), and ADR 0015's amendment).
- **A nested module cannot silence an approved test (owner, 2026-10-27, from the whole-phase review).** In the canonical plan only a `go.mod` that the governing manifest lists makes a nested module, whose tests are `EXCLUDED`. Under any other, one that the head adds for example, the tests run and a setup failure counts as `FAIL`. A repository with a real nested module protects that `go.mod`. *As implemented (2026-10-27): the tree is the manifest laid over the head, and a head file that the manifest lacks is removed when the governing scope covers its path, so a head `go.mod` at a covered path is gone and the tests run as usual; one at a path that the scope does not cover stays, `go` cannot resolve the package of the tests under it, and they read `build-error`, which is `FAIL`.* The first design let any `go.mod` of the composed tree exclude tests, so a pull request could silence the approved tests of a protected directory (decision 16 of the [phase page](phases/M2.1.md)).
- **The same rule in the receipt (owner, 2026-10-27).** In the receipt only a nested `go.mod` present in the merge base or listed in the revision's manifest excludes tests; any other one runs the test, and a setup failure counts as `FAILS` (decision 17). *As implemented (2026-10-27): "listed in the revision's manifest" is read as a head `go.mod` that the canonical version the revision expects lists, or whose path that canonical's approved patterns cover (a pattern that only the head adds counts for nothing). A nested module of the base that the head removed is no module of the head, so its tests run and the base side reads `build-error`: a head pass is `NEW API`.* Both rules are in [ADR 0028](../decisions/0028-canonical-execution-and-the-receipt.md#4-which-tests-a-profile-can-run) and the [runtime contract](../contracts/runtime.md#execution-m21-normative).
- **The executor is never a window, and the installer speaks plainly (owner, 2026-10-27, from the co-located live run).** On Windows the co-located executor runs with no console window, stops with its whole process tree and starts again after it exits; every installer text says what happened, whether it is a problem and what to do; the ruleset file the install writes is deleted once protection is read (decisions 18-20 of the [phase page](phases/M2.1.md)).
- **A suggested command names the same instance (owner, 2026-10-28).** Every command that the installer and `doctor` suggest repeats the `--settings`, `--token-file` and given `--tier` of the run; the removal of another instance says to pass that instance's flags (decision 21).
- **What changes before the release, and what waits (owner, 2026-10-28).** In M2.1: the Contract check's approve names the mode as the revision comment does, the check states the counts of a complete canonical run while it awaits approval (the ledger compares the counted job, migration `00022`), the receipt link is a hyperlink, and `EXECUTOR_LEASE_WAIT` defaults to 2 minutes. A results-communication phase before M2.2 takes the rest: a results comment on every pull request, one page per pull request with tables, the meaning of each state and the reason for each mode's summary, a signal for an approved test that a change edits and that fails in its approved version, an early "test runner not responding" state with the unblock offered, an installer that asks on screen what it can instead of taking flags, and the remaining wording (decision 22).
- **Choices of task A0.** The names, sizes and durations that the contracts mark with † were chosen inside this decision: the reason codes, the lease, attempt and backoff numbers, the size caps, migration `00021`, and the settings `EXECUTOR_TOKEN`, `EXECUTOR_JOB_TIMEOUT`, `EXECUTOR_LEASE_WAIT`, `EXECUTOR_GITHUB_WAIT`, `EXECUTOR_URL` and `EXECUTOR_RUNTIME`. The integrator may change them.
- **Open.** Nothing of M2.1 is open. What is deferred is listed in [Open](#open) (`D-EXECUTION-LATER`) and in the ADR.
- **Not in this phase.** Python and TypeScript, integration tests that need a service such as PostgreSQL, sealed tests kept outside the repository, mutation testing, remote attestation, execution by a managed service, and the pruning of stored results.

### D-M2.1B: Results communication

Accepted 2026-10-28 (the owner's decisions 1 to 14 on the [phase page](phases/M2.1b.md#owner-decisions-2026-10-28), and the design that task A0 wrote into [ADR 0029](../decisions/0029-results-communication.md) and the [runtime contract](../contracts/runtime.md#results-communication-m21b-normative)). It takes the rest of decision 22 of M2.1, amends [D-M2.1](#d-m21-canonical-execution-the-receipt-and-the-go-profile) and [ADR 0028](../decisions/0028-canonical-execution-and-the-receipt.md) where it says so, and changes no invariant: canonical immutability, candidate non-authority, exact-revision approval, atomic promotion and the distinction between evidence and authority all hold. A comment, a page and a result are evidence and never authority.

- **The comments of a head (owner 1, 2, 3, 9, 12, 13).** The checks job writes three comments, each once for its key and never edited, because the App has `pull_requests: write` and no `issues` permission. The results comment says what the head's runs found, when every run that the head wants is final. The not-responding comment says that the test runner has not answered, when the head first reads not responding. The runner-back comment warns, when a test runner returns after the owner's early unblock, that the head was unblocked and its tests did not run. They are written only where the canonical declaration names a profile and some run is wanted, a pull request with no protected change included: with nothing wanted there is no comment. A comment holds counts and the general situation, never a test name or a path. The set that follows an approval is written unless both it and the earlier set have nothing to say, and the burst after an upgrade or a long outage (a comment on every open pull request whose runs are final) is accepted.
- **One page for each pull request (owner 14).** `GET /pulls/{owner}/{repo}/{pull}` replaces the receipt page: the tests by state and by run in tables, the three kinds of change and why each is met or not, the situation, the evidence binding, the preview mode, and the change report of the revision without its hunks, with links to the report of the revision, which keeps them. `/receipts/...`, which the older revision comments link, answers 308 to it. Each part has a budget, and the cap is 12 MiB and answers 503, so a page never answers 413.
- **The weakened-test signal.** An approved test that the change edits, and that fails, is missing or is flaky in its approved version, is pointed out: the page names it, the results comment counts it and says to read the edit before approving, and the Contract check of a head that awaits approval states the count under `canonical: required`. For that, the counts of an awaiting-approval check wait for every run that the head wants (owner 11), so the check and the comment agree. It needs both runs complete and is otherwise unknown, never an absence. No migration.
- **The reason in words (owner 7).** One fixed sentence for each flagged test, from the stored outcome of its runs (`pass`, `fail`, `build-error`, `skip`, `absent`) and its state, and what each state means. No test output is stored or shown.
- **Not responding, the early unblock and its hold (owner 4, 5, 6, 10); amends D-M2.1 and ADR 0028.** A head reads not responding when no test runner has checked in for about 30 seconds (a constant, read at the first pass after it: 30 to 60 seconds) and one of its wanted jobs waits for the runner. The Contract check says `canonical-not-responding` under `required`, and the Receipt check says `receipt-not-responding`. `/suiteward unblock` works as soon as the head reads not responding: it ends the head's waiting jobs as `unavailable` for `no-executor`, which exists, and lifts them in one transaction that compares each job's state and lease id. A run that a responding test runner holds is refused with `runner-responding`. Every unblock holds: the job is not replaced when the test runner returns, the next push runs as usual, and the runner-back comment says so. To keep a healthy test runner out of this state, its heartbeat is every 10 seconds and its error backoff stops at 20 seconds, the service counts a lease answer and a result post as seen, and the Windows test runner restarts about 5 seconds after it exits instead of 61 (owner decision 4, task I0). No new reason, no new column.
- **The installer's list of installations and the select page (decision 22 of M2.1).** `install` and `install --upgrade` keep a list of the installations of the computer in `installations.yaml` beside the default settings file. With several installations, a terminal and no installation flag, `install --upgrade`, `uninstall`, `enroll`, `backup`, `backup init`, `restore` and `doctor` ask which installation on one page, instead of taking up to five flags. The owner decided two points: with `--yes` or `--answers` the command is treated as one with no terminal, and with several installations and no flag it refuses and names `--settings` and `--token-file` (`doctor --json` is the exception); and the page shows the full text of each installation above the choice, so a long path does not hide its description, and preselects none. The flags stay for scripts.
- **Plain wording (owner's rule of 2026-10-27; tasks W1 and W2).** Every comment, acknowledgment, check summary and page text says what happened, whether it is a problem and what to do, in short sentences. The installation type has one set of words, shared by the checks, the comments and the page (`commandtext.TierWords`: "on a separate server", "on the same computer as your coding agent"), and the notice of the co-located tier says that its protection is reduced. Commands, flags, paths, check names, reason codes and the texts that code parses did not change.
- **What changed during the phase from live findings.** H1: on a real AlmaLinux 9 host with SELinux enforcing (found on the AWS host, 2026-10-28), `systemd-run --user --machine=<user>@.host` fails when it has no terminal, so the host step runs the test runner account's commands through `runuser` and that account's own user manager, with no `--machine`, and waits up to 60 seconds for that manager; and `sudo` there does not search `/usr/local/bin`, so the hints and the guides say `sudo /usr/local/bin/suiteward install host`. F1: Podman 4.9 (the package of Ubuntu 24.04 LTS) refuses `podman secret create --replace` for a secret that does not exist, so a first co-located install failed (found on a throwaway Ubuntu distro, 2026-10-29); the installer now creates a missing secret without `--replace`. I0, the 5-second restart on Windows, was owner decision 4 and not a live finding.
- **This repository's execution (owner 8).** `.suiteward.yml` of this repository names `execution: {profile: go}` with the default levels, `canonical: advisory` and `receipt: advisory`, in this phase's own pull request. `required` waits for a later phase, after a few pull requests on the AWS host. The change is a protected one and needs the owner's approval; it was not in the file when this entry was written.
- **No migration.** The schema stays at 22 (`SupportedVersion`).
- **Choices of task A0.** The names, numbers and texts that ADR 0029 and the contract mark with † were chosen inside this decision (`notRespondingAfter`, the reason codes `canonical-not-responding`, `receipt-not-responding` and `runner-responding`, the heartbeat and backoff numbers, the page route and its budgets). The integrator may change them.
- **Open.** The two questions of the phase, a Podman floor for the co-located tier and the name of the "Security limit" row, are under [Open](#open) (`D-PODMAN-FLOOR`, `D-SECURITY-LIMIT-LABEL`).
- **Not in this phase.** Caching between containers, the pruning of results, the hung-test rerun policy and the queue limits (M2.4); test output on the page; `required` levels for this repository; and the full verification of the AWS host (the verification phase after M3).

- **D-PODMAN-FLOOR:** whether the co-located tier needs a Podman version floor, or a warning (raised by M2.1b, 2026-10-29, [D-M2.1B](#d-m21b-results-communication)). The owner decides.
