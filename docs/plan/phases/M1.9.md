# M1.9: Scope discovery

**Goal:** a new user gets a declaration that covers their tests, and SuiteWard tells the owner when a PR adds tests outside the scope.

**Decisions:** [D-SCOPE-DISCOVERY](../decisions.md#d-scope-discovery-suggesting-and-widening-the-scope) and the `suggest` verb in D-COMMANDS, accepted 2026-10-17. The research behind them is summarized below.

**Exit:**
- Over SuiteWard's own file list, the suggestion covers every `*_test.go`, all of `testdata/` and `codecov.yml`, without being cut.
- On the co-located target with a release candidate, live:
  - a `propose` without a declaration suggests include and runner patterns and warns about mixed files;
  - a PR that adds a test outside the scope gets the scope notice, and committing its declaration and approving it promotes the next version;
  - a PR that edits `.suiteward.yml` and misses a test gets a review suggestion whose "Commit suggestion" works;
  - `/suiteward suggest` answers after V1;
  - a reduction lists what it removes.
- The guide covers widening the scope and rotating the App key with a fingerprint check.

## Research (2026-10-17)

- **Codecov** does not detect test files. It finds report files, skips a list of vendored directories, and asks the runner which tests exist. Only the ignore list carries over, because SuiteWard does not run code.
- **Path-only prior art** (Linguist and go-enry, Semgrep, CodeQL) uses curated patterns that match at any depth. Tools that need exact results (Sonar on Maven, Gradle and .NET; Launchable) read the build or runner configuration. That reading is after the MVP here.
- **Runner precedence is a bypass.** pytest uses the first config file it finds, and Mocha and PHPUnit work the same way. The suggestion therefore names the higher-priority files that do not exist yet.
- **GitHub's editor** fills in content only on `/new/`, not on `/edit/` (checked 2026-10-17). An existing `.suiteward.yml` therefore gets a copyable block and the edit link, or a review suggestion when the PR's diff already touches it.

## Live verification

The governing host stays on `v0.1.0` until a release. The live run uses the co-located stack with a release candidate the owner tags on the phase head. It covers two repositories:
- **IgnisDevNE/SuiteWardA2**, which already has a canonical (V3), as an upgrade check;
- **IgnisDevNE/SuiteWardA3**, a new repository created for M1.9. It holds `AGENTS.md -> CLAUDE.md`, a submodule `libs/shared`, a `package.json`, a Python test with no pytest config and no `.suiteward.yml`.

The bot opens the scenario pull requests on A3. The owner posts every `/suiteward` command and makes every commit that SuiteWard only suggests.

**Run 1 (`v0.1.1-rc.1`, 2026-10-18).**
- A2 upgraded from schema 18 to 19 with `integrity` `passed`.
- On A3, the suggestion had `test_*.py`, the whole pytest runner family, the `package.json` warning and the submodule warning.
- The proposal accepted the `AGENTS.md` link.
- The run found three gaps, fixed on the phase branch:
  - `deploy/local.ps1` needs the repository list quoted in PowerShell;
  - the bootstrap notice did not name `/suiteward suggest`;
  - the bootstrap summary did not list the runner rules.
- The owner closed the pull request unmerged, to rerun it with the next candidate.

**Run 2 checklist (next candidate).** All of these are on A3 unless marked.

*Before V1:*
1. The bootstrap notice on a new pull request names `/suiteward suggest`.
2. `/suiteward suggest` with no `.suiteward.yml` gives a suggestion with its own wording. It shows include and runner patterns, the `package.json` warning and the `libs/shared` warning, and the editor link opens with the file filled in.
3. `/suiteward propose` with no declaration gives the same suggestion under the `propose` wording.
4. `/suiteward suggest foo` gets the malformed (extra text) acknowledgement.
5. The owner commits the suggested file through the editor link.
6. `/suiteward suggest` with the declaration present says a `.suiteward.yml` already exists and that nothing changes until it is committed and approved.
7. `/suiteward propose` gives a bootstrap summary that lists the include and runner rules. `AGENTS.md` (a link to a file) does not make the source invalid, and the submodule is outside the inventory.
8. Approve, merge, and V1 is promoted from the merge commit.

*After V1:*

9. A pull request that adds `spec/calc_spec.rb` (not covered) gets one scope notice. The notice lists the file and gives the canonical declaration plus `*_spec.rb`, with the edit link and the mixed-file and submodule warnings. The check is unchanged.
10. A second push to that pull request that adds no new uncovered file posts no second notice.
11. The owner commits the declaration from the notice, approves the revision, merges, and V2 is promoted.
12. A pull request that adds a runner file outside the scope (for example `jest.config.js`) gets a notice for it.
13. A pull request that edits `.suiteward.yml` (block style) and still misses a new test file gets a review comment with a suggestion. "Commit suggestion" yields a valid declaration, and the revision then needs approval.
14. `/suiteward suggest` after V1 on a pull request with an uncovered file gives the scope-notice reply. On one with nothing uncovered, it says every test-like path is in the scope.
15. A pull request that only changes a comment in `.suiteward.yml` is a protected change and needs approval.
16. A pull request that removes a pattern or adds an `exclude` gets a revision comment listing the removed rules and paths. Once that exclusion is canonical, a test file under the excluded path gets no notice.
17. A pull request that adds a link to a directory where a pattern can reach (for example `spec_link -> app`) gets the check `failure`, `invalid-source`.

*Upgrade (A2):*

18. `/status` keeps `integrity` `passed` after the upgrade. A pull request touching a protected file still needs approval on the new candidate.

**Not covered live:** `not-open` on a closed pull request. Comments are listed only for open pull requests, so a command posted after the close is never seen. Unit tests cover the processing path.
