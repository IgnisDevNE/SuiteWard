# Installing SuiteWard with a coding agent

This page is for a coding agent that a user asked to install or configure SuiteWard, and for the user who supervises it. It is meant to be read by both: nothing here is hidden from the user.

SuiteWard protects a repository's tests from the coding agent that works on it. **The agent is the party SuiteWard governs**, so an agent can help with the installation but must never hold what makes the owner's approval trustworthy: the GitHub App's private key, the TOTP secret, the owner's codes, and the repository's protection. An installation where the agent did those steps protects nothing.

The installer (`suiteward install`) does most of the work in one command, and it does the sensitive steps itself: it creates the App through the owner's browser, writes the App's key straight into the secret store, and runs setup on a real terminal. That is why the agent does not run it with GitHub: whoever runs the installer's GitHub flow holds the App key in that process for a moment, and the setup step prints the TOTP secret on that terminal. The installer refuses to run setup without a real terminal (it prints the command instead), and it never takes a secret as a flag. Those are guards, not a license: the user runs the installer.

## Rules for the agent

**Stop and hand the step to the user** when it involves any of these. Do not work around a refusal, and never ask the user to paste a secret into the chat.

A command that the installer prints, in a hint or a fix, names the program as that run reached it: `suiteward` where the shell finds this binary by that name, else the path of the binary, quoted when it needs it (with `&` in front on Windows). It is the same command, and every rule on this page applies to it.

| Never | Why |
| --- | --- |
| Run `suiteward install` with GitHub (the manifest flow, or an App's ID and key), or create the GitHub App, or see, copy, move or store its private key (`.pem`), or the manifest code | Whoever holds the key can publish SuiteWard's check and comments. The code is a credential until the installer converts it. If the browser cannot reach the installer, it asks the user to paste the address of the error page, or its `code=` value, at a hidden prompt: only the user pastes it, there and nowhere else. |
| Run `suiteward enroll` or `suiteward setup`, or the installer's setup step, or see its output, the `otpauth://` URI, the base32 secret or a 6-digit code | They are the owner's second factor; with them, the agent could approve its own changes. |
| Import, create, change or bypass the ruleset or branch protection | The ruleset is what makes the check binding. The installer writes a file, and only the owner imports it. |
| Post any `/suiteward` command, `mode` and `unblock` included | Commands are the owner's. A command from any other account is ignored anyway. `unblock` lifts a gate that withholds a check or refuses an approval, and it needs the owner's code, so an agent that has the owner's GitHub identity still cannot post it; `mode` needs no code, and that is why no gate reads it. |
| Install on, log in to, or run commands on an isolated host (`sudo suiteward install host --sha256sums <the release's SHA256SUMS file>`, the service-account install) | Isolation means the agent cannot reach it. |
| Read or copy the SuiteWard database, its volumes, its secrets (Podman secrets or Docker secret volumes), the MCP token copy, the executor's token copy (`executor-token`, beside it), an answers file that holds anything private, or a backup | They hold the TOTP secret and the enrollment. The executor's token lets a process speak to the service as the executor: lease the jobs, download the source of every enrolled repository's commits and post results, which can lift a `required` gate or make an approval refuse. |
| Run `suiteward execute`, stop, replace, restart or reconfigure the executor (its scheduled task, launch agent or unit, its program, its pin, its files), or put the executor's token anywhere | The executor runs what a pull request brings, and what it reports is evidence that a gate can read. A second executor on the same container engine removes the sandboxes of the first when it starts. A copy of the program that the agent replaced is a different program that reports what the agent likes. |
| Run `suiteward backup init` or `suiteward restore`, read or copy a recovery kit (the file `suiteward-recovery-kit-*.txt`, or its `AGE-SECRET-KEY-PQ-1...` line), or name, change or supply the backup key (`--backup-recipient`, `backup_recipient` in an answers file, `suiteward backup init --replace`) | The kit holds the private key that opens every backup, and a backup holds the TOTP secret. `backup init` writes the kit, and `restore` takes it and replaces the instance's data with a backup. The public key decides who can read every later backup: an agent that names its own key can read them all. |
| Run `suiteward uninstall --purge`, or supply or guess its `--instance` id, or run `suiteward uninstall` with a `--settings` path it has not checked | A purge deletes the database, the owner's TOTP enrollment, the secrets and the App key, and nothing brings them back without a backup. The command asks the user to type the instance id for that reason: the user runs it, in their own terminal. |
| Approve, merge, or give the user a code to type | Only the owner decides. |

## What the agent may do

| Step | The agent can |
| --- | --- |
| Prerequisites ([section 3](install.md#3-before-you-start)) | Check that Podman and the Podman machine run, that the machine has a rootless connection (`podman system connection list`: the stack must run rootless), that the repositories are public or on a plan that enforces rulesets, and read the release to use. |
| Get and verify the installer ([section 4](install.md#4-get-and-verify-the-installer)) | Download the release files and, when the user wants the check (it is optional, but the binary is the trust root of the install), run `verify-release.ps1` on them (it holds no secret), and report the result. On the user's own Linux or macOS PC, and only when the user asks for it, it may run the one-line install with the tag the user chose: `curl -fsSL <release>/install.sh \| SUITEWARD_REQUIRE_COSIGN=1 SUITEWARD_VERSION=<tag> sh`. The script installs the binary, runs nothing, and uses no secret and no `sudo`, and `SUITEWARD_REQUIRE_COSIGN=1` makes it stop unless cosign verified the signature. The agent leaves that variable out only when the user explicitly accepted the hash-only path (no signature check, [section 4.1](install.md#4-get-and-verify-the-installer)). It sets no other `SUITEWARD_*` variable, `SUITEWARD_INSTALL_DIR` and `SUITEWARD_RELEASE_BASE` included, and it runs no `suiteward` command until the user has accepted the binary it installed. It reports what the script printed, above all a warning that the signature was not verified: only the user accepts that, by installing cosign or by checking the `SHA256SUMS` hash elsewhere. A binary for an isolated host is verified by the user as section 4.2 says, never taken from an agent's install, and the agent never runs the script on an isolated host. The user decides which release. |
| Install ([section 5](install.md#5-install-co-located)) | Prepare the exact `suiteward install` command line with placeholders, and explain each prompt. The agent never runs the GitHub flow. When the user explicitly asks for a stack without GitHub, it may run `suiteward install --github no`, which creates no App and enrolls no owner; the user runs the install again for GitHub. The installer never changes the Podman default connection, and the agent never does either. Two parts of the installer exist only on a full screen, which an agent's session never gets (a pipe or a script is not a terminal): the window that setup opens on Windows and macOS, and, on Windows, the offer to copy `suiteward.exe` to the user's PATH. The user answers both. A pseudo-terminal (`ssh -t`, `expect`) would give the full screen, and an agent never uses one to answer them. On the co-located tier the install also makes the executor, which runs the tests in sandboxes, as a process of the user ([section 5.4](install.md#5-install-co-located)): the agent explains it and reads its `doctor` results, and never starts, stops, replaces or reconfigures it. On the isolated host the executor belongs to the administrator's step, which the agent never runs. |
| Update ([section 11](install.md#11-updating)) | Prepare the `suiteward install --upgrade` command and remind the user that it backs up first, into an encrypted file that holds the TOTP secret, and that it needs a recovery key: the user makes it with `suiteward backup init` before the upgrade, in a terminal the agent cannot read, and keeps the kit off the machine. The agent never runs `backup init`, never reads the kit or the backup, and never gives `--backup-recipient`. |
| Uninstall ([install guide, "Uninstalling"](install.md#uninstalling)) | Prepare the `suiteward uninstall` command line for the user and explain what it removes: a plain `suiteward uninstall` keeps the data (and, on the co-located tier, stops the executor and removes its program and its definition), and the command says which instance it is about to remove before it asks. The agent runs a plain uninstall only when the user asks for it, with the `--settings` file of that instance, and never `--purge`. |
| Back up and restore ([the backup runbook](backup.md)) | Run `suiteward backup` on the co-located tier, only when the user asks for it and only when the settings already hold the user's key (`backup_recipient`, made by the user with `backup init`). It prints no secret: the dump stays in the process's memory and reaches the disk only inside one encrypted file that only the kit opens. If the command offers to make a key, the agent answers no and stops: a key it made would be the key that every later backup, the TOTP secret included, is encrypted to. The agent never reads the file it wrote, and never runs `backup init` or `restore`, reads a kit, or supplies a key. For a restore it explains the command and prepares the command line with placeholders for the user: a restore replaces the instance's data, so the user runs it and confirms it by typing the instance id. On an isolated host it runs nothing. |
| Check ([section 12](install.md#12-the-installer-flags-answers-file-and-what-it-does)) | Run `suiteward doctor` or `suiteward doctor --json`, read the result and explain each `WARN` and `FAIL` and its fix (a `WARN` is a pass that needs a look: it leaves the exit code at 0). It only reads, and its results carry identifiers, logins and repository names, never a key, a token or a connection string. Without a real terminal, as in an agent's session, it prints plain lines, with no counts and no wait, and never draws the full screen; `--plain` forces that, and `--json` is always plain. On a real terminal it draws the results with their counts and holds the page until Enter. `suiteward version` prints the version of the binary and the digest of the release image it installs: it reads no setting and no secret, so the agent may run it to report which binary the user has. |
| Setup ([section 6](install.md#6-run-setup)) | Prepare the `suiteward enroll` command line (with `--tier isolated` on the isolated tier) for the user, not `setup`: the agent never runs either. The user runs it in their own terminal, with recording off. |
| Ruleset ([section 7](install.md#7-create-the-ruleset)) | Explain what the ruleset must contain, and read `/status` afterwards to confirm `enforced`. |
| Declaration ([section 8](install.md#8-first-use-bootstrap)) | Draft or improve `.suiteward.yml` and open a pull request with it. To widen the scope, `suiteward scope add [--runner] PATTERN...` adds patterns to the file in the current directory and changes only the lines it adds. It reads no setting and no secret, and it protects nothing by itself. The owner reviews the pull request and posts `/suiteward propose`, or approves the new revision. |
| Execution ([section 9](install.md#running-the-tests-canonical-execution-and-the-receipt)) | Draft the `execution` block of `.suiteward.yml` in a pull request, for example `execution: {profile: go}`, and explain the levels (`canonical` off, advisory or required; `receipt` off, advisory, before-approval or required) and what each does. The block turns on the running of tests and is a protected change: the owner approves its revision with a code, and a pull request that lowers a level is approved the same way, with the lowering listed in its comment as a reduction. The agent never decides a level for the owner. |
| Day to day | Read SuiteWard's comments, the Receipt check, the receipt page and `/status`, explain them, and explain why the agent's own changes touched protected files, or why a test reads `INERT`, `NEW API` or `MISSING`, when the owner asks. A result is evidence about one head, never an approval: the agent never posts `approve`, `mode` or `unblock`, and never gives the owner a code to type. |

## Tier

- **Isolated** (full assurance): the agent's role ends at preparing commands and explaining steps. Everything on the host is done by the user or an operator.
- **Co-located** (reduced assurance): SuiteWard runs on the agent's machine, so the agent could reach its key, database and secret if it tried. The executor runs as the same user as the agent, so the agent could also read the executor's token and files, speak to the service as the executor and report what it likes: what the executor reports on this tier catches drift and accident, not a determined agent. SuiteWard says so in the check summary, the receipt page and its proposal, revision and merge comments, and the installer says it once, on the page that introduces the tier, in its summary and at the end of a plain install or upgrade (the rows of `doctor` do not repeat it). The rules above still apply: on this tier the user relies on the agent following them, and SuiteWard's TOTP and the GitHub account's own protection are the remaining safeguards.

## For the user

- Run the steps marked "never" yourself, in a terminal or browser the agent does not control, with terminal recording off.
- Run the installer yourself from a terminal the agent cannot read. If an agent ran it through a pipe, setup would refuse, but the GitHub flow would already have handled the key.
- Answer the installer's own offers yourself: the setup window (Windows and macOS) and, on Windows, the copy of `suiteward.exe` to your PATH. The agent runs neither.
- Make the recovery key yourself (`suiteward backup init`), in a terminal the agent cannot read. Copy the kit off the machine and delete the copy: on the co-located tier the agent runs as you, so a kit that stays on the machine is a kit it can read, and with it and a backup it can approve as the owner.
- After the installation, check that the agent's GitHub identity is not yours and does not have Administration or Checks write on the repositories.
- Post `/suiteward unblock` yourself, and only after you have read why the run is unavailable (the receipt page names the reason): it lifts the gate for that head, and the checks then say that you unblocked it and that the tests did not run.
- On the co-located tier, choose the execution levels knowing that the executor runs next to the agent: its results are evidence, not proof against an agent that wants to fool it ([limits](install.md#limits-of-canonical-execution)).
- If an agent asks for a code, the key, or to change the ruleset, refuse. That request is the threat SuiteWard exists for.
