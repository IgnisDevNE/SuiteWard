# M1.7: Promotion on merge

**Goal:** after a confirmed merge into the integration target, promote exactly the approved, integrated contract, and say clearly in the PR when promotion is impossible ([ADR 0014](../../decisions/0014-merge-triggered-canonical-promotion.md)). Also verify the stored canonical bytes on a schedule.

**Depends on:** M1.6b. Planned 2026-10-15 with the advisor.

**Decisions:** D-INTEGRATION (accepted 2026-10-15; owner answers):
- merge, squash and rebase are resolved through the tree of `merge_commit_sha`;
- a merge commit shared with another merged PR blocks the PR (an outcome already recorded stands);
- an unreadable integration after a bound is an explicit state;
- forks are unsupported and fail closed;
- recently closed PRs are also listed.

**Contracts:**
- [persistence](../../contracts/persistence.md#merges-m17-normative): merge facts, `PromoteMerge`, canonical integrity, the check-republish cooldown, and the relay rule for a kind without a publisher;
- [runtime](../../contracts/runtime.md#merges-and-integrity-jobs-m17): the `github_merges` and `canonical_integrity` jobs, the `merge:` comment, the check-job changes and `/status`;
- [github](../../contracts/github.md#m17-merge-reads-normative): `Pull`, `ClosedPulls` and `HeadRepo`.

**Exit:**
- For each supported merge method, the integrated source is resolved exactly, and the canonical advances atomically with its artifacts.
- These end in an explicit, reported state that keeps the canonical:
  - a merge without approval;
  - an integrated contract that differs from the approved revision;
  - a fork;
  - a shared merge commit;
  - an unreadable integration.
- A correction is a corrective PR, recorded as such.
- A confirmed integrity failure turns every check of the repository into `failure`.

## Verification plan

- **Per task:** `check`, `persistence` on a freshly reset database for A1, A3, C and B2, RED observed, then `sw-reviewer`.
- **Phase:** `check` and `persistence` on the final head, the race integration run, a whole-phase review and the advisor.
- **Live, host first.** Before deploying, the owner adds `phase/M1.7` to the `remote-poc` deployment branches, removes `CI / test` from ruleset 24829664 and confirms that merge, squash and rebase are enabled. On SuiteWardQ:
  1. an implementation-only merge: no version;
  2. a protected PR approved and merged with a merge commit: the next version and a comment;
  3. the same with squash, then with rebase;
  4. two protected PRs approved, then one merged: the other goes back to `in_progress` with a new revision; re-approve it and merge it;
  5. a protected PR closed without merging: nothing;
  6. a corrective PR reverting the most recent protected merge, so the protected files equal an earlier version exactly: a correction of the current version;
  7. `/status`: `merges` and `integrity` clean, `outbox.failed` 0.
- **Co-located stack, after the host.** `-Down -Purge` and a new `setup`, so its V1 is the `main` the host left. Then steps 2 and 5, and an integrity tamper on a local artifact, confirmed by the owner at the time.
- **The two targets keep separate canonicals:** every merge approved through one target makes `main` diverge from the other's canonical. That is why the co-located stack is reset after the host.
- **Covered only by tests:** a merge without approval (the ruleset has no bypass), a PR merged within one poll, a shared merge commit, and forks.

## Known limitations planned

- **Merges between the bootstrap pin and V1.** A merge after the bootstrap pinned the default branch but before V1 was promoted is `before-canonical`. If it changed protected files, later PRs show that change for approval.
- **Closed listing size.** The closed listing reads 30 PRs per run.
- **Merges into other branches are read.** A merge into a branch other than the target, or before V1, still has its tree read before `PromoteMerge` records `not-target` or `before-canonical`, so a slow or unreadable tree there can delay that repository's later merges by up to the 30-minute bound.
- **One target per repository.** Each target keeps its own canonical; merges approved through one make `main` diverge from the other, which then reports them as `unapproved-change` and catches up through a new approved PR (HOST.md 6d.4).
- **Commands after a merge.** A command posted after the merge is never observed.
- **Carried from M1.6b, not in this phase:**
  - the persisted unchanged-head memory;
  - protected bytes re-read on each re-assessment;
  - every 422 on a check POST treated as a vanished head;
  - the HeadSince window.
- **`integrity` after a promotion.** `/status` shows no `integrity` for a new canonical version until the hourly `canonical_integrity` run (or a restart) verifies it. Running the verification after each promotion would close the gap.
- **The `not-current` branch is kept.** It is re-evaluated once merges promote; nothing reaches it yet.

## Outcome

- **On the host:**
  - a merge commit, squash and rebase each promoted the next version from the integrated commit's tree (V2 to V5);
  - after another promotion, an approved PR needed a fresh approval of its exact revision (V6, V7);
  - a corrective PR was recorded as a correction (V8);
  - an implementation-only merge and a PR closed without merging produced nothing.
- **On the co-located stack:**
  - a fresh bootstrap produced V1;
  - a merge commit promoted V2;
  - a PR closed without merging produced nothing;
  - a confirmed integrity failure of the stored canonical blocked every PR, and restoring the bytes cleared it.
- **Divergent targets.** The host reported the stack's unapproved merge, and caught up through one approved PR (V9).
- **Covered only by tests:**
  - a merge without approval;
  - a PR merged within one poll;
  - a shared merge commit;
  - forks;
  - squash, rebase and a correction on the co-located stack.
- **Next.** M1.7b, the bootstrap from the first PR that carries tests, builds on this merge detection. Its page is refined when M1.7 is merged.
