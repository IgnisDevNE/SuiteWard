# M1.8: MVP acceptance

**Goal:** an installable MVP that the owner uses on SuiteWard itself.

**Decisions:** D-RELEASE (supported platforms and license notices) was decided on 2026-10-17.

**Exit:** on both [verification targets](../README.md#verification-targets) (local container, co-located; remote host, isolated), a fresh install following the guide protects a real repository end to end (bootstrap, protected PR blocked, TOTP approval, merge, promotion, correction); backup and re-bootstrap are rehearsed; SuiteWard's own tests are governed by SuiteWard; assurance wording matches ADR 0014 and ADR 0027.

## Decisions (owner, 2026-10-17)

The planning answers are recorded in [open decisions](../decisions.md):
- [D-RELEASE](../decisions.md#d-release-platforms-versions-license-and-notices): the image only (`linux/amd64`, `linux/arm64`), `vX.Y.Z` plus `latest-stable`, `AGPL-3.0-only`, notices in the image, and `/status` `source`.
- [D-INSTALL](../decisions.md#d-install-end-user-install-update-backup-and-dogfooding): a manual GitHub App checklist, a pinned version updated by hand, a plain backup, and dogfooding on the isolated host with `CI / Gate`.
- D-COMMANDS: the TOTP window stays ±1, pending the acceptance's `would_match` lines.
- D-DEPLOY: `main` triggers the deployment, and the promotion approval stays.

**Risks pinned at planning:**
- **Propose size.** SuiteWard has about 195 protected files, over the ~150 a `propose` reads in one `JOB_TIMEOUT` of 1 minute. Raise `JOB_TIMEOUT` on the host. Since M1.7c it no longer delays commands, so the guide documents it as the knob for large repositories.
- **The bot is the governed party.** Before dogfooding, verify that the bot's installation lacks Checks write and Administration write, and that the required check is pinned to the runtime App.
- **The fresh install purges** the host's SuiteWardQ (V12) and SuiteWardQ2 state. The backup rehearsal comes first.
- **The phase PR merges ungoverned.** It changes `.github/workflows/**`, which dogfooding protects, so dogfooding starts after it.

## Backlog carried into M1.8 (known limits and loose ends)

- **Not exercised live:** the default-branch bootstrap path (V1 at approval from a branch proposal) and the one-click editor link for a branch name containing `/`. The acceptance run should cover both.
- **Command limits:**
  - About 150 protected files per `JOB_TIMEOUT` for a `propose`.
  - Moving the reads out of the commands queue, or raising `JOB_TIMEOUT`, is open.
- **Carrier rejections:** a mistyped `skip` or `propose` on the carrier turns it `failure`, because the ledger does not record the verb. The carrier gets one cancelled comment per revision.
- **Merges before V1:** they read trees for every merge. A tree unreadable for 30 minutes stalls that repository's merge queue.
- **Sync and wake-ups:**
  - `sync_repo` (MCP) requests are not counted in the pacing.
  - A wake-up check and insert are not atomic, so there is one extra job per concurrent waker.
  - The wake-up Warn line drops the error, by the contract's rule.
- **Orbit:**
  - The Node preload fix is merged upstream (PR #69) but is in no released build: 2.163.65 predates it.
  - After every Orbit reinstall, repeat the extraction in [orbit.md](../orbit.md), known issue 5.
- **Memtrace:** the MCP server of the orchestrator session was disconnected through M1.7b and M1.7c. Reconnect it, or keep the documented fallback.

## C2 outcome: dogfooding (2026-10-17)

The host now governs IgnisDevNE/SuiteWard. The intervals come from GitHub's own timestamps.

- **The release.** The owner created `v0.1.0` on `20d6af3`. Its image index is `sha256:debd19f0…feec` (amd64 and arm64), and `latest-stable` points at the same digest. The host runs that digest, with `SUITEWARD_JOB_TIMEOUT=3m`.
- **Enrollment.**
  - The host's App was also installed on SuiteWard.
  - The `suiteward-contract` ruleset was added next to the classic protection ([D-INSTALL](../decisions.md#d-install-end-user-install-update-backup-and-dogfooding)).
  - Setup ran again with both repositories, and `/status` showed `enforced` for both.
  - The bot's installation has Checks read and no Administration, checked in the organization's settings.
- **Bootstrap.** The carrier was PR #32, with a `pull` baseline whose `.suiteward.yml` covers 209 files.
  - propose → proposal P1-R1: 65 s;
  - approval → recorded: 27 s;
  - merge (`e2b3a38`) → V1 promoted: 58 s, with tier `isolated`.

  The propose read 209 files well within the 3-minute job timeout.

**Found in C2:**
- **The test check is `CI / Gate`, not `CI / test`.** Fixed in #32.
- **The scope suggestion misses tests in a large repository.**
  - `inventory.SuggestScope` emits one `<dir>/<glob>` per directory and keeps the first 20 in alphabetical order. The comment does not say when the list was cut.
  - It recognizes test directories only at the top level, and never suggests `testdata/`, script tests or runner files.
  - Run over SuiteWard's own files, it would have covered 137 of 209 files. It would have left out 33 `_test.go`, most of them in `internal/domain/*`, plus all 21 `testdata` files.
  - #32 used a hand-written declaration instead.
- **The isolation gap.** The owner closed it the same day, by rotating the App key from outside any agent session (D-INSTALL).
- **A failed outbox message is never sent again.** During the key rotation, the publication of the check for #33's head `1b562d6` failed every attempt. `/status` showed `outbox.failed: 1`, and the required check stayed missing, so the merge was blocked. Only a new head revision publishes a new check. Backlog: re-deliver failed messages, or recompute the check of an open head, once GitHub answers again; and document the recovery in the guide.

**Open questions on test discovery,** to answer after M1.8:
1. Detect more tests:
   - collapse a glob repeated across directories into `**/<glob>`;
   - find `testdata/` at any depth;
   - say when the list was cut.
2. A command for the owner, or an agent, to add a path the detection missed.
3. A test directory added after V1. Today the owner widens the scope with a PR that changes `.suiteward.yml`, approved like any protected change. Could SuiteWard report test-like paths outside the scope? It may report them, never protect them: only the owner's approval changes the contract.
4. How tools such as Codecov discover their inputs, and whether any of that carries over. Codecov looks for coverage reports, not test files, so the question is which heuristics transfer.
