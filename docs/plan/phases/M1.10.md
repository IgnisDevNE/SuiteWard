# M1.10: Code review and maintenance

**Goal:** the codebase is reviewed end to end and left organized before the security gate. That means no dead code, no hidden impossible states, and no dangerous complexity left unaddressed, with the same product behavior.

**Decision:** owner request, 2026-10-19. The security gate comes after this phase, on clean code.

**Rules:**
- **No behavior change.** Every refactor keeps the existing tests green. A change that would alter behavior is a finding for the owner, not a refactor.
- **Defects found during the review follow the [TDD rule](../../tdd.md).** The failing test is committed first.
- **This repository is governed by SuiteWard.** Refactors that touch protected tests need the owner's approval of the final revision, so fixes are batched to keep the approval rounds few.
- **Least code:** a refactor deletes or merges code more often than it adds abstractions. The [nil-check rule](../../development-guide.md#nil-checks) applies.

**Exit:**
- **Dead code:** no unreachable or unused functions, types or payload fields, outside documented compatibility shims, each of which carries its removal condition.
- **Nil handling:** no `return nil, nil`, no swallowed error and no empty `default` that hides an impossible state. Nil checks exist only at trust boundaries, and each returns an explicit error.
- **Complexity:** every function above the agreed cyclomatic or cognitive threshold (set during planning, from the measured baseline) is refactored or recorded with the reason it stays. The hotspots (complexity × recent churn) are reviewed first.
- **Duplication:** duplicated helpers are merged.
- **Carried findings:** the M1.9 low findings ([backlog](M1.9.md#backlog-carried)) are fixed or explicitly kept with a reason.
- **Checks:** `check`, `persistence` and `-race` pass. Coverage does not drop below the current level.

## Method (planned at phase start)

1. **Baseline.** These tools only measure, and none of their output counts as verification evidence:
   - Memtrace: `find_dead_code`, `find_hotspots`, `find_most_complex_functions`, `find_duplicate_code`;
   - the linters already in `golangci-lint`;
   - a nil and error scan.

   The baseline becomes the phase's task list.
2. **Review by area.** Independent `sw-reviewer` passes cover these areas:
   - `domain`;
   - `application`;
   - `adapters` (postgres, github, river, mcp);
   - `app` and `config`;
   - scripts and deploy.

   Each pass reports ranked findings.
3. **Tasks.** One worktree and one task per area or finding cluster, implemented by `sw-implementer` and reviewed by `sw-reviewer`.
4. **Close.** A whole-phase review and the advisor. Then one integration PR and a patch release (`v0.1.2`), if anything shipped changes.
