# Installing SuiteWard

This guide installs SuiteWard with its installer, the `suiteward` binary: one guided command on your own machine (co-located) or two on a separate host (isolated). The installer creates the stack, creates the GitHub App, writes the ruleset for you to import, and runs the owner setup. After that you only approve the pull requests that change protected test files. For the short path, see the [quickstart](quickstart.md). If a coding agent helps you install, give it [agent-install.md](agent-install.md) first.

You do not need this guide open to run the installer. On a full screen, every question has a page that says what it asks, the choices, which one is recommended and the default. This guide is the reference: the details behind those pages, and what the plain mode (a script, an agent, `--plain`) needs, because the explanations are for the full screen only.

Two rules apply to every command:

- Pin one release. Replace `<tag>` with the release you install, everywhere it appears (the first release that has the installer is `v0.3.0-alpha.1`). Do not use a moving tag. Where a command names the image index digest of the release, replace `<index>` with it. The release notes name it, on the line `Index digest:`.
- Replace each value in angle brackets, such as `<owner/name>`, with your own value. Never put a token or a TOTP secret or code into a file, a log, a pull request or a chat. The only secrets a file may hold are the App's private key (`--github-app-key-file`, or `github-app-key` in the answers file) and a manifest code (`manifest-code` in the answers file), in a file at mode 600 that you delete afterwards.

## 1. What SuiteWard does and does not do

SuiteWard keeps the `SuiteWard / Contract` check of a pull request that changes the protected test files pending until the owner approves that exact revision, and your ruleset (section 7) blocks the merge: SuiteWard does not block it by itself. When the pull request merges, SuiteWard checks the approval and the integrity of the protected files at the merge commit, and promotes the approved contract as the new canonical version.

SuiteWard does not replace your CI's tests, and it does not claim that your CI ran them. A merge is not proof that the tests ran, passed or are correct. Your review and your own test check decide that.

SuiteWard can also run tests itself, but only where the approved `.suiteward.yml` asks for it: with `execution: {profile: go}`, a separate executor, installed with SuiteWard (sections 5 and 10), runs the approved tests on each head and the tests that a pull request adds or changes, in disposable sandboxes. Nothing runs before the owner approves that block. The result is evidence about one head, reported by this instance's executor. It is never an approval, never enters the approval's binding, and cannot rule out code that behaves differently under test. SuiteWard says what the runs found in a comment on the pull request and on one page for each pull request. Section 9 ("Running the tests: canonical execution and the receipt") says how to turn it on and what each level does, and "Limits of canonical execution" lists what it cannot do. The statement for M1, which a note in the record updates, is in [ADR 0014](decisions/0014-merge-triggered-canonical-promotion.md), and [ADR 0028](decisions/0028-canonical-execution-and-the-receipt.md) records execution.

## 2. Choose a tier

The tier says where SuiteWard runs compared with your coding agent. The way you install SuiteWard declares the tier. SuiteWard never detects it, and it reports the tier in `/status` and in the check summary.

- **Co-located:** SuiteWard runs on the same machine as the coding agent. The App key, the database, the TOTP secret and the executor's token are then reachable by the agent, and the executor, which runs the tests, is a process of the same user as the agent. SuiteWard states this reduced assurance and does not claim protection it cannot provide: what the executor reports on this tier catches drift and accident, not a determined agent. The installer says it once, in these words: "On this computer the test runner (the executor) and SuiteWard run as your user, next to your coding agent, so SuiteWard's checks catch mistakes, not a determined agent." It is on the page that introduces the tier on a full screen (shown only when the question about the installation type is asked), in the summary of a co-located install and of a co-located upgrade on a full screen (as its row `Security limit`), and at the end of a plain co-located install and of a plain co-located upgrade that upgrades, which have no summary (an upgrade that says `Nothing to upgrade` does not print it). The rows of `suiteward doctor` do not repeat it, and the isolated install does not say it. Section 5 installs it with one command, the path most users follow.
- **Isolated:** SuiteWard runs on a separate host that the coding agent cannot reach, or in a VM or under another OS user when the agent has no access to the container runtime and the keyring. The executor runs there too, under an account of its own. This tier gives the full assurance. Section 10 installs it, for whoever self-hosts on a machine the agent cannot reach.

Neither tier protects against a compromised host administrator. The coding agent must use its own GitHub identity, never your credentials. [ADR 0027](decisions/0027-agent-human-trust-separation.md) gives the reasoning.

Never let two SuiteWard instances watch the same repository; one instance serves up to 20. Two instances post as the same App, and each has its own TOTP secret. One of them then rejects the owner's codes and publishes a failing check.

## 3. Before you start

- **A GitHub account** that owns or administers the repositories, and up to 20 repositories to protect. The account that owns the instance must be a user account, not an organization or a bot. The App can belong to your personal account or to an organization you administer.
- **GitHub Free and private repositories.** GitHub does not enforce rulesets on a private repository of an account or organization on the Free plan. SuiteWard cannot protect such a repository: `/status` and `suiteward doctor` report `enforcement-unavailable`. Use a public repository, or a paid plan (GitHub Team). The installer warns before the ruleset step and continues.
- **An authenticator app** that scans an `otpauth://` URI or accepts a base32 secret.
- **A container runtime.**
  - **Podman, rootless, is strongly recommended**, and is the only runtime of the isolated tier. A rootful Podman connection is refused.
  - **Podman 4.9, on the co-located tier,** works: the co-located install ran on Ubuntu 24.04 LTS, which ships Podman 4.9.3 ("Validation", section 9). This guide does not set a version floor for that tier. Podman 4.9 rootless does not report a sandbox that was killed for memory as such. SuiteWard still reads its exit status 137 as `resource-limit`, so a run that ran out of memory reads the same there. The isolated tier needs Podman 5.5 or later (section 10).
  - **Docker is allowed on the co-located tier only, and discouraged.** Its daemon is rootful by default, and Docker has no secret store outside Swarm, so the installer keeps the secrets in named volumes that anyone who controls the Docker daemon can read. Podman keeps them in its own rootless secret store. Section 5 says how to choose Docker anyway.
  - **The executor uses the same runtime,** through its command line, to run the tests in sandboxes. A sandbox may use 3 GiB of memory (with its swap) and 4 CPUs, and the runtime must be able to honor every limit, or the run is `unavailable`. The sandbox spike measured 1.5 to 2 GiB as the floor for this repository's own tests on Docker Desktop and measured nothing on a Podman machine, so give a Podman machine or Docker Desktop's VM the memory your tests need (`podman machine set --memory`, or Docker Desktop's settings): a sandbox that runs out of memory is killed and reads `resource-limit`.
  - **The executor needs a network for the dependencies,** not the sandbox: it reaches the service on the loopback address and `proxy.golang.org` over HTTPS, directly (it never honors proxy environment variables). The proxy sends the module zips that it does not serve itself to `storage.googleapis.com`, and the executor follows a redirect to that host only, over HTTPS: an egress allow-list for this tier needs both names, because `proxy.golang.org` alone would stop the zips that the proxy redirects there. Execution is off until the owner approves it, so a stack that never names a profile makes no such request.
- **A real terminal.** The installer prompts, and setup prints your TOTP secret. A pipe, a script or a coding agent cannot run setup. On Windows and macOS, setup opens in a window of its own (section 6).
- **Co-located PC:** Windows or macOS with a Podman machine that has a rootless connection (`podman machine init`, then `podman machine start`), or Docker Desktop; or Linux with rootless Podman. Co-located on Windows is the path validated live. macOS is covered by the unit tests, which CI runs on a macOS machine against a fake runtime, and the installer ran on a real Mac with Podman, without GitHub, in phase M1.15 (the test runner, the GitHub flow with its setup window and later releases have not been seen on macOS; no Docker Desktop on a Mac has been tried). Linux is covered by the same unit tests only. Expect rough edges on both. The executor of this tier (section 5.4) is a scheduled task, a launch agent or a user unit of your user. On Windows, the task that this release installs ran on a real machine with Docker. No co-located executor has run on a real macOS or Linux machine, or with Podman ("Validation", under "Limits of canonical execution" in section 9). The macOS binaries are not notarized (section 4). Verifying the download is optional (section 4); to do it by hand you need cosign 3.x, PowerShell 7.2 or later and the release source. The one-line install needs `sh`, `curl` or `wget`, and `sha256sum` or `shasum`; with cosign 3.x it also checks the signature.
- **Isolated host:** AlmaLinux 9 (EL9) with systemd user services, cgroup v2 and 4 vCPUs and 8 GiB of memory at least: one sandbox at a time takes 3 GiB, the executor up to 3 GiB (its unit limits it to that), and the database and the service need the rest. Other distributions are not covered, and the isolated commands refuse any system that is not Linux, macOS included. `sudo /usr/local/bin/suiteward install host --sha256sums <the verified SHA256SUMS>` checks Podman 5.5 or later with the fix for CVE-2026-57231 and offers to install it (section 10; 10.2 says why the command names the full path). To create the GitHub App from the host, your PC needs a port forward to the host: the AWS CLI and the Session Manager plugin on AWS, or your own, such as `ssh -L <port>:127.0.0.1:<port> <host>`. Or give an App you made by hand. The host step that makes the executor needs the verified `SHA256SUMS` of the release on the host (section 10.1 and 10.2).

## 4. Get and verify the installer

The installer is a release asset. Each binary embeds the signed image index digest of its own release, so the co-located install never takes an image from a tag.

**Verifying the download is optional.** The installer runs without it, and nothing later asks whether you did it. It is worth doing because the binary is the trust root of the install: it creates the secrets, the App's key store and the stack, and a signature proves that the file came from the release workflow of this repository (you still choose the tag). Verifying by hand needs `scripts/verify-release.ps1`, which is in the release source and not among the release files, so it means cloning the repository or downloading its source at the tag. The one-line install (4.1, Linux and macOS) needs no source: it checks the hash itself, and the signature when cosign 3.x is installed. The lightest check, on any system, is to compare the SHA-256 of the file with its line in the release's `SHA256SUMS`: that catches a damaged download, not a file replaced at its source. If you skip every check, you run a binary that nothing proved to be the release's.

There are two ways to get it and check it: the one-line install on Linux and macOS (4.1), and the download by hand with a signature check (4.2), which works on every platform and is the stronger path.

**4.1 The one-line install (Linux and macOS).** `install.sh`, a file of the release, downloads the binary of your platform, checks it and puts it in `~/.local/bin`:

```
curl -fsSL https://github.com/IgnisDevNE/SuiteWard/releases/download/<tag>/install.sh | SUITEWARD_VERSION=<tag> sh
```

Use the same `<tag>` twice, and always set `SUITEWARD_VERSION`. The script is the same file in every release and learns nothing from the address it came from. Without the variable it installs GitHub's latest release, which is never a pre-release. At the time of writing that is `v0.2.0`, which has no installer binaries, so the script stops and says to set `SUITEWARD_VERSION`. Use `v0.4.0-alpha.2`, the first release with the installer this guide describes. `v0.4.0-alpha.1` is the first release whose page lists `install.sh`, and no release built before phase M1.13 has one, `v0.2.0` and the alpha pre-releases `v0.3.0-alpha.1` and `v0.3.0-alpha.2` included (those have four binaries). There is no one-line install on Windows: use 4.2.

The script does this, and nothing else:

- It reads your system and refuses anything but Linux or macOS on amd64 or arm64.
- It downloads `SHA256SUMS` and the binary, and compares the binary's SHA-256 with the line of `SHA256SUMS`, which must list the file exactly once. Over curl, every request is HTTPS only, redirects included. (`SUITEWARD_RELEASE_BASE`, below, can add a `file://` base for the script's tests, and redirects stay HTTPS only.) wget has no such flag, so its redirects are not restricted: prefer curl.
- With cosign 3.x installed, it first verifies the signature of `SHA256SUMS` against the identity that `scripts/verify-release.ps1` fixes: the release workflow of this repository, at a release tag. Without cosign, it says that the signature was **not** verified, prints `SHA256SUMS sha256: <hex>` and the commands that verify the signature on another machine. When the downloader is BusyBox wget (Alpine, some routers), which can skip the check of TLS certificates, it says that too. `SUITEWARD_REQUIRE_COSIGN=1` turns a missing cosign into an error.
- It puts the file in place in one step (mode 755), says where, and tells you when the directory is not on your PATH. It never uses `sudo`, and it never runs the binary or anything else it downloaded: the next command is yours.

| Variable | Meaning | Default |
| --- | --- | --- |
| `SUITEWARD_VERSION` | The release tag, `<tag>` above. | The latest release, never a pre-release. |
| `SUITEWARD_INSTALL_DIR` | The directory that gets `suiteward`. It must be one you can write: the script never asks for more rights. | `$HOME/.local/bin` |
| `SUITEWARD_REQUIRE_COSIGN` | `1` stops when cosign is not installed. `0` or unset goes on without it. Any other value is an error. | unset |
| `SUITEWARD_RELEASE_BASE` | For the script's own tests only: it replaces GitHub as the origin of `SHA256SUMS` and the binary, so never set it for a real install, and never run an install that someone else set it for. The script takes only a base that starts with `https://` or `file://` (with wget, only `https://`) and refuses anything else, `http://` included, before it downloads. With a base, curl takes only https and file, and follows a redirect to https only. | unset |

Know what this proves. Piping a script into a shell runs it before you read it, so it is as trustworthy as GitHub's HTTPS and the tag you named. Without cosign, the binary is checked against a `SHA256SUMS` that came from the same place: that catches a damaged or cut download, not a release file replaced at its source. If BusyBox wget skipped the certificate check, a network attacker could replace both files. With cosign, the binary is checked against the signature of the release workflow, as in 4.2. The script itself is not verified before it runs. To read or verify it first, download it, verify it as 4.2 says (it is listed in `SHA256SUMS` and has its own signature), read it, and run `SUITEWARD_VERSION=<tag> sh install.sh`. The script is one function that its last line calls, so a download that stops half way runs nothing.

On the isolated host, run the script as the administrator's own user, and then copy the binary where the service account can run it: a path inside a home directory is not readable by it, so `sudo install -m 755 ~/.local/bin/suiteward /usr/local/bin/suiteward`. The isolated host needs no cosign, and without it the script prints the `SHA256SUMS sha256: <hex>` line: compare it with the hash that `verify-release.ps1` printed on your PC (4.2) before you run the binary.

**4.2 Download and verify by hand.** The release page `https://github.com/IgnisDevNE/SuiteWard/releases/tag/<tag>` lists these files:

| File | What it is |
| --- | --- |
| `suiteward_<tag>_linux_amd64`, `suiteward_<tag>_linux_arm64`, `suiteward_<tag>_windows_amd64.exe`, `suiteward_<tag>_darwin_amd64`, `suiteward_<tag>_darwin_arm64` | The installer for each platform. A release built before phase M1.13 has no `darwin_amd64`. |
| `install.sh` | The one-line install script (4.1). A release built before phase M1.13 has none. |
| `SHA256SUMS` | The SHA-256 of the five binaries and of `install.sh`. |
| `SHA256SUMS.sigstore.json` and `<file>.sigstore.json` | The keyless cosign signatures of `SHA256SUMS` and of each binary and `install.sh`, made by the release workflow. |

Download `SHA256SUMS`, `SHA256SUMS.sigstore.json` and the binary of your platform into one folder. Get the release source of `<tag>` as well (clone the repository and check out the tag, or download its source): it holds `scripts/verify-release.ps1`. On a machine with PowerShell 7.2 or later (it also runs on Linux and macOS) and cosign 3.x, run from the release source:

```
pwsh ./scripts/verify-release.ps1 -Blob <folder>/SHA256SUMS -Bundle <folder>/SHA256SUMS.sigstore.json
```

Expect `Verified: … was signed by the SuiteWard release workflow.`, and a line `SHA256SUMS sha256: <hex>`: the SHA-256 of the file you verified. Then check that the binary is the one `SHA256SUMS` lists:

```
pwsh ./scripts/verify-release.ps1 -Sums <folder>/SHA256SUMS -File <folder>/suiteward_<tag>_<os>_<arch>
```

Expect `Matched: … is listed in … with its SHA-256.`, and the same `SHA256SUMS sha256: <hex>` line. If either command fails, do not run the binary. The script fixes the signing identity (`release.yml` of this repository at a release tag, through GitHub's OIDC issuer) and refuses any other. A signature proves that the file came from the release workflow, not that it is the version you meant: you chose the tag.

To check `install.sh` itself before you run it, download it and `install.sh.sigstore.json` as well, and run `pwsh ./scripts/verify-release.ps1 -Blob <folder>/install.sh -Bundle <folder>/install.sh.sigstore.json`.

To run it by name, rename the binary to `suiteward` (`suiteward.exe` on Windows), keep it somewhere only you can change, and put it on your PATH. On Linux and macOS, make it executable first: `chmod +x suiteward`. You can also run it where it is, by its path: on Windows the installer offers to copy itself to a folder on your PATH when it ends (section 5.7), and every command it prints names the program as this run reached it. This guide writes `suiteward` for it. `suiteward version` (also `--version`) prints the version of the binary and the digest of the release image it installs. The binary is the trust root of the install: it creates the secrets and the App, so verify it once and run no other copy. A development build has no embedded digest and needs `--image`.

**macOS and the quarantine flag.** The macOS binaries are not notarized. A file that you download with a browser usually gets Apple's quarantine flag, and Gatekeeper may then refuse to open it. It may also let it run: a terminal that holds the Developer Tools permission (System Settings, Privacy & Security, Developer Tools), as iTerm2 often does, starts programs without that check, and a file without the quarantine flag is not checked at all. When macOS does refuse, verify the file and then remove the flag: `xattr -d com.apple.quarantine <file>`. A file that `curl` downloads, as the one-line install does, has no such flag.

For the isolated host, verify on your PC as above, then copy the binary and the verified `SHA256SUMS` to the host and compare them there. The host needs neither cosign nor PowerShell:

```
sha256sum --check --ignore-missing SHA256SUMS
```

Expect `suiteward_<tag>_linux_<arch>: OK`. `--ignore-missing` is needed because `SHA256SUMS` also lists the binaries of the other platforms, and the file keeps the name it had on the release page. Then copy the binary to a shared place such as `/usr/local/bin/suiteward`: the service account must be able to run it, and a path inside a home directory is not readable by it.

If your remote shell cannot copy files, download the binary and `SHA256SUMS` on the host with `curl` from the release page. Then compare the `SHA256SUMS sha256: <hex>` line that `verify-release.ps1` printed on your PC with the output of `sha256sum SHA256SUMS` on the host before you run the check above: the two hashes must be the same. [The host runbook](../deploy/HOST.md) shows the commands.

## 5. Install co-located

Run this on the PC that also runs your coding agent. Read section 2 first: on this tier the agent can reach the App key, the database and the TOTP secret. If a coding agent helps you, read [agent-install.md](agent-install.md) first: the agent never runs the install with GitHub, and never runs setup.

**5.1 Start the runtime.** On Windows and macOS, the Podman machine must exist and run (`podman machine init` once, then `podman machine start`). The installer picks the machine's only rootless connection, refuses a rootful one, and never changes your Podman default connection. With several machines, choose one with `--connection <name>`. To see the connections, run `podman system connection list`: the rootless one has `/run/user/<number>/podman/podman.sock` in its URI. The installer records its choice in its settings file, so `suiteward doctor` and a re-run use the same one. Any `podman` command you run by hand against this stack must reach the same store, so run `$env:CONTAINER_CONNECTION = '<name>'` first in that PowerShell session, or `export CONTAINER_CONNECTION=<name>` in a POSIX shell on macOS.

The commands of this guide that run inside the machine write its user as `user`, the user of a Windows machine. On macOS the rootless user of a machine can have another name: the installer and `suiteward doctor` look it up themselves, and the installer prints its commands with it. It is also in the connection's address in `podman system connection list` (`ssh://<user>@…`).

**5.2 Run the installer.**

```
suiteward install
```

It asks only what it cannot decide, and each question also has a flag and an answers-file key (section 12): a question that a flag or the answers file answers is not asked, and has no page. On a real terminal it runs full screen, in the SuiteWard colors, with the steps listed beside the page, from its first question. Each question has a page of its own that explains it (what it is, the choices, the recommended one, the default) and clears what came before; the checks, warnings and kept lines of earlier pages stay. A choice between a few answers is a list: Up and Down move, Enter picks, and the highlighted row is the default. A multiple choice, such as the repositories, has a box per row: Space picks or drops the row under the cursor, and Enter confirms. The hint line at the foot says which keys apply. Ctrl-C at a list or at any other question ends the command with exit code 130, as everywhere else, except at the two offers that come after the work, which count it as No (section 12). Where the terminal cannot read single keys (a system other than Windows, Linux and macOS, or a terminal that refuses the mode), the list is numbered and you type the number, and a multiple choice takes numbers or names, comma-separated. With no terminal, or with `--plain`, it prints plain lines and typed questions instead, with no explanation pages ("The installer's screens", section 12): a question there shows its default in brackets, and Enter takes it. The installer works in this order and changes nothing until the checks pass:

1. **Choices.** On a terminal, it asks for the installation type (`co-located`, with a page titled `Where SuiteWard runs` before the question on a full screen; the flag is `--tier`) and the container program (`podman`; the flag is `--runtime`; choosing Docker asks you to type `yes` after a page that names its two risks). It then prints `Using <engine> <version> (runs without administrator rights).`, or `(runs as root)` for Docker: it names the engine it is about to use. Then it asks for the HTTP port (default 27081) and the MCP port (default 27091), both on 127.0.0.1, and the release image. A stack that exists keeps the ports it has: only a new install takes the defaults. The image defaults to the one already installed, else to the release the binary carries. On a full screen the page shows that default as a row of its own, because the reference is long, and the question is just `Release image`: Enter takes the default, as the hint line says. In plain mode the question is `Release image (with its digest) [<default>]:`.
2. **Checks.** Both ports are free (inside the Podman machine on Windows and macOS), no stranger's container uses the stack's names, and the database secrets are consistent. It pulls the images that the engine lacks, by digest, before it removes anything: the release image, PostgreSQL, and the Go image that the executor's sandboxes run from.
3. **GitHub** (section 5.3), if you say yes.
4. **The stack** (section 5.4), and then the executor (section 5.4, "The executor").
5. **Setup** (section 6), then, on a full screen, a summary that holds the result of `suiteward doctor` (section 5.7).

A stack that the PowerShell start script of v0.2.0 and earlier made is adopted under the same names. Any difference the installer cannot carry over stops the install and prints the diff, so nothing is overwritten silently. A second run keeps the data and the secrets. On Docker it leaves a running, healthy stack with the same settings alone and replaces only what changed or is stopped; on Podman it replaces the containers, with the same settings and data.

**5.3 The GitHub App.** The installer asks `Set up GitHub now (creates a GitHub App in your browser)?` (the default is No). Say yes. Every step below runs on this machine:

1. **Create the App.** The installer first asks which account will own it: `personal` (your own account, the default) or an organization. On a full screen the question is a list of those two, and choosing the organization asks for its login; in plain mode you type `personal` or the login. `--github-account <personal|login>` answers it. For an organization, before the browser opens, the installer asks GitHub, without signing in, whether the account exists and is an organization: a name that GitHub does not know, or a personal account, is refused, and a person is asked again. When GitHub cannot answer (the unauthenticated rate limit of 60 requests an hour for each address, an error of GitHub, no network), the installer warns and goes on, and checks the owner again once the App exists. It does not check that you may create Apps in the organization: that is decided on GitHub's own page. The installer then prints an address on 127.0.0.1, `http://127.0.0.1:<port>/`. Open it in the browser of this machine. It sends the App manifest to GitHub. GitHub asks you to confirm: one click creates the App. The App gets exactly five permissions: Metadata, Contents and Administration read-only, Pull requests and Checks read and write. It has no webhook, it is private (`public: false`), and it is named `suiteward-<random>` unless you rename it. Note the name: if the install cannot finish, you delete that App by hand.
2. **The code.** GitHub redirects your browser to the listener with a one-time code and a random `state` that the installer checks. The installer continues by itself: it converts the code into the App's private key on this machine, and writes the key straight into the secret store, never to disk and never to the terminal. The code passes through your browser, as a downloaded key would: it is valid for one hour, and the installer never prints or draws it.
3. **If the browser cannot reach the listener,** the address bar of the error page still shows the full redirect address. After 2 minutes without an answer, on a terminal (a full screen or plain lines), the installer asks you to paste that address, or only its `code=` value, and press Enter. The question is hidden: nothing you paste is echoed, drawn or kept. Where the terminal can be waited on (a terminal of Windows, Linux or macOS, which is the usual case), GitHub's answer ends the question by itself and the installer goes on, as its page said it would: the question reads `If the browser shows an error, paste its address, or press Enter to keep waiting`, and an Enter with nothing pasted keeps waiting. Where it cannot be waited on, only an Enter ends the question: it reads `Paste the address, or press Enter if the browser says SuiteWard received the answer`, and an Enter with nothing pasted takes the answer if it came meanwhile. The label is chosen when the question opens: when a wait fails while the question is open, the waits are turned off for the rest of the run, that question keeps its label but only an Enter ends it (and takes the answer if it came meanwhile), and the next offer reads the other label. The question comes again after another 2 minutes. The wait ends after 15 minutes with an error: run the installer again. The code converts once. With no terminal, the installer waits for the callback only. `--manifest-port <port>` fixes the listener's port (default: any free port). `manifest-code: <code>` in the answers file hands over a code from an earlier attempt, within its hour. It is never a flag, because a flag would show in the process list: the installer refuses `--manifest-code`.
4. **Install the App.** The installer prints `https://github.com/apps/<slug>/installations/new`. Open it, choose the account and give the App access to the repositories to protect, and no others. The installer polls every 5 seconds for up to 10 minutes, and goes on by itself when it sees the installation. It then lists the repositories the App can reach and asks which to protect, at most 20, all of one owner. On a full screen that is a multiple choice with every repository picked when there are 20 or fewer (pick at least 1); in plain mode you type numbers or `owner/name`, comma-separated.
5. **The owner.** Your GitHub username, as in `github.com/<username>`: only that account's `/suiteward` commands and approvals count, and it cannot be an organization or a bot. The default is the App's account when it is a user account.
6. **The test check.** SuiteWard does not replace your CI's tests: the ruleset of each repository requires your CI's test check beside `SuiteWard / Contract`, so a pull request needs both to pass. The installer never offers the two checks that SuiteWard publishes (`SuiteWard / Contract` and `SuiteWard / Receipt`) and refuses them as a test check. For each repository, the installer offers the check runs on the head of the default branch, and you choose one or type the name your CI publishes. On a full screen that is a list of the check runs, with `another name…` as its last row, which asks you to type the name. Enter takes the run that is the only one with `test` in its name (in any case), or the only run there is. With several runs and none or more than one of those names, nothing is highlighted: an Enter is refused with a note until an arrow has picked a row (a numbered list asks again on an empty answer). In plain mode you choose by number or type the name. It never offers a check from a ruleset that does not exist yet. When the repository has no check runs yet, type the name: `suiteward doctor` and `/status` report `missing-test-check` until a check with that name exists. `--test-check 'owner/name=CI / test'` answers it, once for each repository, or give one plain name for a single repository.
7. **The ruleset.** For each repository the installer writes a JSON file, `suiteward-ruleset-<owner>-<name>.json`, into the folder of its settings file (`%APPDATA%\suiteward` on Windows, `~/Library/Application Support/suiteward` on macOS, `~/.config/suiteward` on Linux), and shows where. It requires `SuiteWard / Contract` with your App as the source, and your test check, on the default branch, with branches up to date and an empty bypass list. You import it yourself, because the App has no permission to change rules: open `https://github.com/<owner>/<repo>/settings/rules`, choose **New ruleset**, then **Import a ruleset**, select the file and create it. If an older SuiteWard ruleset (of an earlier App) is there, delete it first: both would apply. For a private repository, the installer first warns that GitHub Free does not enforce rules there (section 3); the install continues. **The file is deleted once it has done its job:** when the protection of a repository reads as `enforced` (the caveat `ruleset-bypass-unverified`, which every ruleset result carries, does not keep it), the installer deletes that repository's file and says `The ruleset file of <owner/name> was deleted: the import worked.` On a full screen, the closing checks (section 5.7) also delete the file of a repository whose protection passes with no warning. The file stays while the import is still needed: for a repository whose protection is not enforced yet or could not be read, and for one where GitHub does not enforce rules (`enforcement-unavailable`). When you skip the check, the file stays unless the closing checks then see an import that worked. The closing summary names the file of a repository whose protection lacks what the ruleset requires. If a file cannot be deleted, a warning says so, and that you do not need it any more.
   - **On a full screen** the installer pauses at a page that shows, for each repository, its name with the file of its ruleset and, on the next row, the exact link of its rules page (`https://github.com/<owner>/<repo>/settings/rules`), and asks: `I imported it, check now` or `Skip, import later`. The first reads the protection back from GitHub, and deletes the file of each repository that reads as enforced. A repository that is not protected yet (or whose protection cannot be read) stays on the page with what is missing, said with each code and its words (for example `missing-test-check (the test check is not required)`), and the two choices come again; a repository where GitHub does not enforce rules (`enforcement-unavailable`) is not waited for, because no import can help. The second goes on with a warning that says the repositories are not protected. The file and the exact rules link of each repository that is not protected stay in your terminal's scrollback after the screen closes (on a window of 80 by 24 the page shows three repositories that each miss one thing, but only two that each miss two; the rest is cut behind a line that says to enlarge the window, and the scrollback keeps every file), and the closing checks (section 5.7) report it.
   - **In plain mode and without a terminal** there is no pause page. The installer asks `Press Enter when the rulesets are imported` (the default is yes, and `--ruleset-imported yes` answers it: with no terminal it defaults to yes), then reads the protection back, prints the result of each repository (section 7) and deletes the file of each repository that reads as enforced. A repository that is not protected is reported, and the install goes on: read that result.

In PowerShell, quote a comma-separated list, as in `--github-repositories 'owner/a,owner/b'`: unquoted, PowerShell passes two arguments and the installer stops with a usage error. To use an App you already have, give `--github-app-id`, `--github-installation-id`, `--github-owner` and `--github-repositories`, and the key as `--github-app-key-file <path>` (or `-` for standard input). Create such an App by the checklist in section 10, step 10.4. `--github no` (or `--github-app-id none`) skips GitHub: the stack then runs without it, on both tiers, and a later run with `--github yes` sets it up. Any GitHub value given without an App is refused. On the isolated tier, a run without GitHub is also refused while `~/.config/suiteward/github.env` still names an App, because the service would read that App without its key: empty the file first.

**An App named without its key.** When the settings, the isolated env file (`~/.config/suiteward/github.env`) or the record of an unfinished install name an App whose key secret is not in the secret store (it was purged, or the host was rebuilt), the installer never creates a new App behind your back, and the old one would stay on GitHub. It stops, before any change, and offers two routes:

1. **The App's private key file.** Give `--github-app-key-file <file>`. The installer checks the key with `GET /app` (it must be that App's key; the key of another App is refused), stores it, and goes on. Create a key on the App's settings page if you have none.
2. **A new App.** Give `--github new-app`. The installer names the old App (or Apps) first, with the page that deletes each (the settings only hold the App's id, so it names the lists of Apps of your account and of the organization, and the ID to look for), runs the manifest flow, and prints the same note at the end.

On a terminal, it asks instead, and only the person at the terminal answers (no flag or answers-file key does). A full screen shows a page and a choice between `key file` and `new App`; in plain mode it prints:

```
The App 4242 of the settings has no key in the secret store (suiteward-github-app-key).
  1) give the App's private key file
  2) create a new App (the old one stays on GitHub: delete it at https://github.com/settings/apps (or, if an organization owns it, https://github.com/organizations/<owner>/settings/apps), the App with the ID 4242)
Choose 1 or 2:
```

Without a terminal, the error names both flags. `--github new-app` stops, before it creates anything, while a key secret exists, because the key of the new App cannot be stored over it. The error says whose key the secret holds. If it is the key of the App of the settings, remove the secret (the error gives the command), then run again: that App stops working on this instance, and you delete it on GitHub. If it is the key of an App an earlier run created and recorded, run again without `--github new-app` to take that App up.

**A new App that stops partway.** From the moment a new App exists, its key is the secret and the App is recorded (`settings.yaml.pending-app`). If the run stops after that (the installation does not arrive, Ctrl-C, a prompt), run the installer again with the same answers and without `--github new-app`: the recorded App wins over the App of the settings, so the run takes it up, waits for its installation, and replaces the App in the settings when it succeeds. Nothing creates a third App, and the old App never runs with the new key. While such a record exists, `--github no` and `install --upgrade` refuse (the stack would start with the App of the settings and the key of the recorded one): finish the install first with a plain `suiteward install`, or follow the way out the error names.

**5.4 The stack.** The installer creates the network and the volumes, generates the database owner password, the application role's password and the MCP token, and starts the stack in this order: the database (it waits up to 90 seconds for it to be healthy), the application role `suiteward_app`, the one-shot `suiteward migrate`, then the service, only when migrate succeeded. The service connects as `suiteward_app`, which cannot change the schema; only the migrate container holds the owner's URL. Secrets are written through standard input and never printed. Expect `The database update (migration) finished: the database is at the version this release needs.`, then `Started suiteward-db and suiteward (<image>). GitHub is set up.` (`GitHub is not set up.` when GitHub was skipped).

The installer also writes a copy of the MCP token for a local agent's client (its screens call it the access token file, and its summary row is `Access token file`), readable by your user only: `%LOCALAPPDATA%\SuiteWard\mcp-token` on Windows, `suiteward/mcp-token` in your configuration directory elsewhere (`~/Library/Application Support` on macOS, `~/.config` on Linux; `--token-file` changes it). It prints the path (`The access token for your coding agent's client is in <path>. It is not shown here.`), never the token. The MCP listener serves a local agent's `sync` and `status` tools, nothing else.

**The executor.** After the stack is up, the installer makes the executor, the process that runs the tests ([ADR 0028](decisions/0028-canonical-execution-and-the-receipt.md), section 10). The installer's screens call it "the test runner (the executor)", and the summary row is `Test runner`; this guide keeps the name that the contract uses. The stack does not depend on it. When its setup fails, the install says so in a warning (`Note: the test runner (the executor) could not be set up: <why>. SuiteWard itself runs, but it cannot run tests until the test runner works.`, then ``Fix the cause, then run `suiteward install` again.`` and that `suiteward doctor` lists what is missing) and goes on: the stack runs, and canonical execution has nothing to run on until you fix the cause. The one failure that running the install again cannot fix, a restricted PowerShell on Windows, leaves that advice out (see "Seven things to know"). On a full screen the summary has a row `Test runner`: how the executor is kept running and the path of its program, or `not set up: <why>`. The install creates:

- **A token for the executor API:** 32 random bytes, as hex. It is the only secret the executor holds. The installer keeps a copy as `executor-token`, readable by your user only, in the directory of the MCP token copy, and stores the secret `suiteward-executor-token` (a Podman secret, or a file in a named volume on Docker), which the service container reads through `SUITEWARD_EXECUTOR_TOKEN_FILE`. A copy that exists while this instance has no such secret is refused, because it may belong to another instance, as the MCP token's copy is. A re-run keeps the token.
- **The executor's directory,** `executor`, beside the token copies (`%LOCALAPPDATA%\SuiteWard\executor` on Windows, `~/Library/Application Support/suiteward/executor` on macOS, `~/.config/suiteward/executor` on Linux), readable by your user only. It holds a copy of the installer's program that the executor runs (`suiteward-executor`, with `.exe` on Windows), its pin `executor.pin` (see "The pin" below), the log `executor.log` (Windows and macOS), and, on Windows only, the two files of the scheduled task: `run.cmd`, the script that it runs, and `task.xml`, the definition that the install registered, which `doctor` compares with the one this program makes. The launch agent's file is in `~/Library/LaunchAgents` on macOS, and the user unit is in `~/.config/systemd/user` on Linux. It is a copy so that moving or deleting the program you ran does not take the executor along, and its own name tells its process from the runs of the installer.
- **Its definition,** which is the mechanism each operating system has for a program that starts when you log on and is kept running, with no administrator rights and no stored password. The executor must run as your user, because the container runtime that it drives (a Podman machine, rootless Podman, Docker Desktop) is yours, so a system service would need a password or a rootful runtime.
  - **Windows:** a scheduled task, `SuiteWard Executor`, that starts at your logon with the rights of your user (no password, no elevation) and has no time limit; a start while it runs is ignored. It has no window: the task runs `conhost.exe --headless` with `cmd.exe`, which runs the script `run.cmd` in the executor's directory (the system programs by their full path under `System32`). The script switches the console to UTF-8 (`chcp 65001`, so that a folder name with a letter outside ASCII works), sets the environment, and runs the executor with its output appended to `executor.log`. Whenever the executor ends, whatever the reason, the script writes `The test runner stopped. It starts again in 5 seconds.` to the log, with the date and time, waits about 5 seconds (`ping -n 6`: `timeout` reads the console, which the task does not have) and runs it again. The wait is short on purpose: SuiteWard says that the test runner is not responding after about 30 seconds without it (section 9), and a routine restart must stay well below that. The Linux user unit restarts after 5 seconds too (`RestartSec=5`). Task Scheduler does not start an action again once it has exited (its `RestartOnFailure` setting covers only a start that failed), so the script does it and the definition sets no restart of its own.
  - **macOS:** a launch agent, `io.suiteward.executor` (`~/Library/LaunchAgents/io.suiteward.executor.plist`), loaded at login and kept alive, with an exit timeout of 45 seconds. Its output goes to `executor.log`.
  - **Linux:** a systemd user unit, `suiteward-executor.service` (`~/.config/systemd/user/`), enabled and started now, restarted after a failure (`Restart=always`), with a stop timeout of 45 seconds and `KillMode=mixed`. A user unit runs while your user manager does: without linger it starts at your login, not at boot. Its output is in the user journal (`journalctl --user -u suiteward-executor.service`).
- **Its environment:** the address of the service (`http://127.0.0.1:<HTTP port>`), its token file, the runtime (`podman` or `docker`), the Podman connection or Docker context that the installer chose, and the PATH of the runtime's command (a launch agent and a user manager start with a short one of their own). The executor reads only the first three, and it refuses to start when its environment holds a credential of the service.
- **The Go image** of the sandboxes, pinned by digest, which the install pulls with the two others (step 2 above). Every sandbox starts with `--pull=never`, so an engine without that image makes every run `unavailable`; `doctor` checks that the image is there.

**The pin.** `executor.pin` holds one line, which `doctor` compares with the copy of the program. By default it is the SHA-256 of the copy, so it catches drift and accident, and nothing checked it against a release. `suiteward install` and `suiteward install --upgrade` take an optional `--sha256sums <the verified SHA256SUMS of the release>`: this program must then be listed in that file exactly once as a binary of this system, and the release's line is the pin. A program that the file does not list exactly once is refused before anything changes, and an empty value is a usage error. Without the flag, the install says once: ``The test runner has not been checked against an official release. This is normal for a development build. To check it, run `suiteward install --upgrade --sha256sums <the release's SHA256SUMS file>` with the program from that release.`` Verify the download as section 4 says first; the command also pins an executor that already runs, with nothing to upgrade. `doctor` warns while the pin is only the hash of the copy. The isolated tier takes the file at the host step instead, and requires it (10.2).

A re-run (and `install --upgrade`, section 11) makes the executor what the settings and the program say, and leaves what is right alone: an executor that runs with the same program and the same definition is not stopped, because it may be in the middle of a job. A new program or a changed definition stops it first (Windows cannot replace a program that runs) and starts it again. On Windows a registered task whose program is not running is stopped first too, because its script may be waiting out its minute and would start the old program next to the new one.

The sandboxes have no network at all. The executor, which has one, fetches the modules that each side's `go.sum` names from `proxy.golang.org` and gives them to the sandbox with the source, so it needs outbound HTTPS to `proxy.golang.org` and to the `storage.googleapis.com` that the proxy redirects zips to (section 3). On this tier the executor has no memory limit and no `GOMEMLIMIT`: the isolated unit sets both (section 10.2), and a scheduled task, a launch agent and a user unit as written here do not. At its peak it holds about 1.5 GiB of live data, as the isolated unit's comment counts it: a module body that comes with no length (up to what is left of the 512 MiB prefetch budget, and for a moment twice that), up to 64 MiB of output from one test invocation, and the analysis files of both sides.

Seven things to know about this tier:

- **Reduced assurance.** The executor is a process of your user, next to your coding agent. The agent can read the executor's token copy and the executor's files, and speak as the executor to the service, and what the executor reports is only as good as the executor. The pins that `doctor` checks (the copy of the program and its hash) catch drift and accident, not a determined agent. The Receipt check, the comments of a head and the pull request page say so, and the installer states it once (section 2); the rows of `doctor` do not repeat it. Section 9 ("Limits of canonical execution") says what a forged result can and cannot do.
- **Stopping.** On SIGTERM or SIGINT the executor stops asking for jobs at once, gives the job in flight 30 seconds to finish and post its result, then kills its sandbox, posts nothing and exits: the lease expires, and the job is leased again (the attempt counts as `lease-expired`). A supervisor must wait longer than that, which is why systemd and launchd are set to 45 seconds. **Windows has no such grace.** A stop (the install that replaces the executor, `install --upgrade`, `uninstall`) ends the whole tree at once, with no signal that the executor could catch. The installer ends the task (`schtasks /End`, which ends only the task's console host), lists the programs that run, and ends this instance's console host, script and executor with their children (`taskkill /T /F`, by process id, for the programs whose command line names this instance's script or whose path is this instance's program, never by name, so that another instance's executor survives). It lists them again, and a process that is left stops the install, the upgrade or the removal before anything is replaced or deleted. A job in flight ends as `lease-expired`, counts as a failed attempt and is retried, up to 3 failed attempts. Logging off ends the executor with the session.
- **No window on Windows, and a restart after about 5 seconds.** A console program that a task of the logged-on user starts gets a window, which in Windows Terminal is the first thing you see, so the task runs the script through `conhost.exe --headless` and nothing is drawn: there is no window to close by accident. The install says so: `The test runner has no window. It runs in the background, and if it stops it starts again after about 5 seconds.` If the executor ends for any reason, the script starts it again after about 5 seconds (an earlier release waited a minute). An executor that an earlier build registered, a task that runs `run.cmd` itself and so has a window, is replaced by `suiteward install` or `install --upgrade`, which end its tree first, and `doctor` fails `executor.lifecycle` for it until then: its `task.xml` is not the definition this program makes (`The scheduled task of the test runner is not the one this version of SuiteWard makes (it may come from an older version, or it was changed). This needs your action.`).
- **The log is not rotated** on Windows and macOS: `executor.log` grows until you remove it (on Windows it also gets a line each time the script starts the executor again). Linux uses the journal.
- **One executor for each container engine, and one for each computer.** When it starts, the executor removes every container whose name starts with `suiteward-sandbox-` on its engine, to clean up what a crash left. A second executor on the same engine, started by hand or by another instance, would remove the sandboxes of the first. The task, the launch agent and the unit also have one name for each user, so a computer has one co-located executor. A second instance never touches the first one's: its install and its upgrade refuse a settings file of its own without a `--token-file` of its own before they change anything ("One more instance on the same PC", below section 5.7), and with one they leave the registered executor as it is, warn that this instance has none (the row `Test runner` of the summary reads `not set up: …`: ``a computer has one test runner, and yours belongs to another instance. This instance left it as it is. To use this instance's own, remove the other instance with `suiteward uninstall` (pass that instance's `--settings` and `--token-file`; the default instance needs neither), then run `suiteward install` again`` (that command repeats this instance's own flags, as "One more instance on the same PC" says)). Its `doctor` says the same: `executor.lifecycle` fails with "The test runner on this computer belongs to another instance, not to the one that uses the token file …", `executor.running` fails with "the test runner on this computer belongs to another instance, so none runs for this one", and the fix of both says that the test runner belongs to another instance: it is that instance's removal, not an install, which would skip it. Without `--token-file`, the `doctor` of a settings file of its own fails `executor.token` and checks no other executor row. Never start `suiteward execute` by hand on a computer that has one.
- **Two engine limits.** On Windows and macOS with a Podman machine, the executor is a program of your PC and reaches the service through the machine's published loopback port, which does not always answer from the PC (section 15 mentions it for `/status`). `doctor` detects it (`executor.loopback`); the service then never sees the executor, the heads read not responding after about 30 seconds, the runs read `no-executor` after 2 minutes, and the owner can unblock each head. With `--runtime docker`, the executor needs Docker's own CLI and engine: a real Docker CLI that talks to Podman's socket fails closed, because the sandbox passes a flag that only Podman knows, so every run reads `sandbox-unavailable`. Only Podman's own `docker` shim (the `podman-docker` package) works against Podman, and for Podman `--runtime podman` is the choice.
- **Windows needs PowerShell, and a folder without a percent sign.** The installer lists the programs that run with Windows PowerShell (`Get-CimInstance Win32_Process`, from `System32`), to tell this instance's executor from another instance's and to end its whole tree, so an install, an upgrade, an uninstall and `doctor` need a PowerShell that can run that command. Where PowerShell is restricted (constrained language mode, as AppLocker or WDAC set it), a **first** install sets up no executor: it writes none of its files, installs the stack all the same, says in its note why: `could not list the programs that run on this computer: <why>`, then that SuiteWard could never stop or update the test runner without that list, so it did not install it, and that an administrator, or a separate server, is the way out (for restricted PowerShell, `<why>` ends `(a policy may have stopped PowerShell)`). It leaves out the advice to run the install again because that cannot help, and shows `not set up: …` in the row `Test runner`. An executor that was installed before PowerShell was restricted can no longer be stopped, updated or removed by the installer: the step fails, and `uninstall` goes on and ends with the by-hand steps ("Uninstalling"). A folder for the executor whose path has a percent sign (`%`) is refused when the install or the upgrade would set up the test runner there: Windows reads `%name%` in the arguments of a scheduled task and `cmd` reads it in a script, so a path with one would not reach the script as written. Give `--token-file` a path without one. The refusal is for setting up, not for what already exists. An older install in such a folder is still checked by `doctor` and removed by `uninstall`. If no test runner of this instance is registered there, `doctor` fails `executor.lifecycle` with the same message and checks no other executor row. If one is registered, `doctor` checks it as usual, and the fix of each result about it says how to move this instance: `suiteward uninstall` (your data stays), then `suiteward install --token-file <a file in a folder without a percent sign>`, which makes a new access token file, so point your coding agent's client at it. A folder name with a letter outside ASCII works, because the script switches the console to UTF-8 (`chcp 65001`) before it reads any path.

**5.5 After a restart.** On Podman, the installer enables `podman-restart.service` for the machine's rootless user, so the containers start whenever the machine starts. On a Windows (WSL) machine, Podman creates that user's `~/.config/systemd/user` owned by root, so `systemctl --user enable` is denied; the installer then links the unit as root, which is what `podman machine ssh <machine> 'mkdir -p /home/<user>/.config/systemd/user/default.target.wants && ln -sf /usr/lib/systemd/user/podman-restart.service /home/<user>/.config/systemd/user/default.target.wants/'` does, and checks that `systemctl --user is-enabled podman-restart.service` says `enabled`. It does not start the machine itself: after Windows or macOS restarts, run `podman machine start`. Starting the machine at logon is not part of this release. `suiteward doctor` reports a stopped machine. On Docker, the containers restart when Docker Desktop starts. The executor does not wait for any of this: it starts by its own mechanism (section 5.4), at your logon on Windows and macOS and with your user manager on Linux. Its sandboxes need the machine, so a restart of Windows or macOS needs `podman machine start` for them too, and `suiteward doctor` reports an executor that is not running.

**5.6 Setup.** On a real terminal, the installer runs setup for you, as section 6 describes, after it told you to turn off session recording. On a full screen it first shows a page that says what setup does and that the installer never sees the secret, and waits for Enter. On Windows and macOS, setup then opens in a window of its own while the installer waits on its screen; on Linux, over SSH and in plain mode it takes your terminal. It runs setup only when `/status` shows no owner: an owner that is enrolled is never replaced. Without a real terminal, it prints `suiteward enroll` for you to run on one, and stops.

**5.7 Check the instance.** On a full screen the install runs the checks of `suiteward doctor` itself, as its last step, and its summary shows what they found: the counts (`N ok, N warnings, N failures`), and one line with the fix for every result that needs a look (a `WARN`, such as GitHub not configured, or a `FAIL`, such as a ruleset that is not imported yet). A failed check does not fail the install: its exit code stays 0, so read the summary. Ctrl-C while the checks run ends the command with exit code 130; one that came before they started only skips them. In plain mode, and with no terminal, the install does not run them: it prints ``Then check that everything works with `suiteward doctor`.`` (an install without GitHub says instead that GitHub is not set up yet, so nothing is protected, and how to set it up), then the reduced-assurance sentence of section 2, which a full screen shows in its summary as the row `Security limit`, and you run it:

```
suiteward doctor
```

Expect no `FAIL` and exit code 0. Every line is `ok`, except the warnings of an instance installed without GitHub, and one `WARN executor.binary` after an install that was not given `--sha256sums`: `The test runner has not been checked against an official release.` Its pin is then only the hash of its own copy, so nothing checked it against a release. That is normal for a development build, and it does not change the exit code; `suiteward install --upgrade --sha256sums <the verified SHA256SUMS of the release>`, run with the program of that release, clears it (section 5.4). On a real terminal the screen draws a `✓` for each `ok`, and the page ends with the counts (`N ok, N warnings, N failures`) and stays until you press Enter. A line that starts with `FAIL` names the problem and its fix (section 12 lists them). A `WARN` line is a pass that needs a look, such as GitHub not being configured: it does not change the exit code. The one other way to exit with 1 when every result passed is a terminal that fails while doctor runs, and the command says why on stderr and never turns its code into 1 without a word: `suiteward: the terminal failed while doctor ran: <error>` when the screen cannot be written to or put back, and `suiteward: wait for Enter: <error>` when the final Enter cannot be read. `suiteward doctor --json` prints the same as JSON. It reads the settings file the installer wrote, so with a second instance, or any instance that has a settings file of its own, pass `--settings <path>` and `--token-file <path>` (the token file that instance's install was given), or choose the installation when `doctor` asks ("Which installation a command works on", section 5): the executor's files are beside the token file, and without it doctor does not know where they are. For a settings file that is not the default one it then fails `executor.token` and checks no other executor row, so that it never reports the main instance's executor as this one's. The doctor command that an install or an upgrade prints names `--token-file` in that case.

**The `suiteward` command on Windows.** A downloaded file is not on your PATH, so a command that the installer prints, such as `suiteward doctor`, would not work in a terminal. Every command it prints therefore names the program as this run reached it: `suiteward` where the shell finds this program by that name, else the path of this program, quoted when it needs it (with `&` in front on Windows, which PowerShell needs to run a quoted path). On a full screen, the end of an install or an upgrade also offers to copy the program to `%LOCALAPPDATA%\SuiteWard\bin\suiteward.exe` and to add that folder to the PATH of your user, so that a new terminal finds `suiteward`. The default is Yes; Ctrl-C or the end of the input is a No. The offer is made only when all of these hold: the screen is full, nobody answered for you (`--yes` or `--answers` is not given), the program is a release (a development build is never offered), no copy exists, and the shell does not already find this program by its name. When another `suiteward` is on your PATH, the page names it, the folder goes at the end of the PATH so that program keeps the name, the hints keep naming the path, and the default is No. This terminal keeps the PATH it started with: the summary shows the PowerShell line that adds the folder here, `$env:Path += ';<folder>'`, and new terminals find the command by name. The copy sits in your own profile, so a program that runs as you can replace it (on the co-located tier, that includes the coding agent); it is no safer than the file you ran. Only `suiteward install --upgrade` refreshes the copy, on every screen and also when there is nothing to upgrade, without asking; once it has, the hints of that run name the program as `suiteward` (when your user PATH holds its folder and no other `suiteward` is found first), and not the path of the build that ran the upgrade; a copy that a running program holds is renamed to `suiteward.exe.old`, which a later run removes, and a development build leaves it alone and says so. `suiteward uninstall --purge` offers to remove the copy and its PATH entry (the default is No; the offer is not made with `--yes`). Linux and macOS have no such offer: `install.sh` puts the binary in `~/.local/bin` (section 4.1).

**Docker, discouraged.** Install with `--runtime docker`, and confirm with `--accept-docker` (or type `yes` at the prompt that prints the warning). On a PC that also runs Podman, the name `docker` can be Podman's shim, and the default Docker endpoint (the `docker_engine` pipe) belongs to whichever engine started first. So the installer never trusts the name: on Windows it runs Docker Desktop's own CLI by its full path (`C:\Program Files\Docker\Docker\resources\bin\docker.exe`) against the `desktop-linux` context, identifies the engine behind it, refuses Podman's, and says which engine it uses. On macOS it runs the `docker` on your PATH against the same `desktop-linux` context, and refuses Podman's shim the same way. `--connection <context>` selects another Docker context. Docker has no `--replace` and no secret store, so the installer removes a container before it runs it again, and keeps the secrets in one named volume for each container that reads them, mounted read-only, one file for each secret (mode 0400, owned by the uid that reads it), written through standard input. `serve` therefore never sees the owner's URL, and no secret touches the host's disk. Whoever controls the Docker daemon can still read the volumes. Use a port pair of your own (`--http-port`, `--mcp-port`) when a Podman stack runs on the same PC.

**One more instance on the same PC.** The default settings file and token file belong to the first instance. The installer refuses to take them over; give the second one its own `--settings` and `--token-file`, and its own ports. `install` and `install --upgrade` also refuse a settings file that is not the default one when `--token-file` is left out, before they change anything and after the container runtime is opened (on Docker, after you typed `yes`), because the default token file, and the executor that is beside it, are the main instance's. The refusal names the way out for the only instance on this computer that has a settings file of its own: `--token-file` with the default token file. Give the same two to `suiteward uninstall --purge` of the second instance: the settings do not record where its token file is, and a purge with another settings file never removes the default token file unless `--token-file` names it, so without `--token-file` the second instance's own token file stays (see "Uninstalling"). `suiteward doctor` needs both too (section 5.7), or it asks which installation, as the next paragraphs say. `backup` and `restore` take the default backups folder beside the token file and use the default token file when `--token-file` is left out, so the backup of a second instance without it lands in the main instance's `backups` folder (the file has its own date and time, and nothing is overwritten): give them `--token-file`, or the folder itself with `--to` (`backup`) or `--backup-dir` (`restore`). `suiteward uninstall` that names the default settings file with `--settings` is guarded like one that leaves `--settings` out: it refuses, before it removes anything, when that file records another runtime or another connection than the one the command uses.

**Which installation a command works on.** The installer keeps a list of the installations that it made on this computer: `installations.yaml`, next to the default settings file (in your per-user configuration folder, readable by your user only). `suiteward install` and `suiteward install --upgrade` add their installation to it, or refresh its entry, when they save its settings, and an upgrade does the same when it says `Nothing to upgrade`. An installation made before the list existed joins it at its next `install --upgrade`. `suiteward uninstall --purge` takes the entry out with the settings file, and a plain `uninstall` keeps it, as it keeps the settings. An entry holds paths, the installation type, the container program, the connection, the instance ID and the two ports, and never a secret.

A command that works on an installation that exists (`install --upgrade`, `uninstall`, `enroll`, `backup`, `backup init`, `restore` and `doctor` without `--json`) reads the list when you name no installation. You name one with `--settings`, or with a token file (`--token-file`, or `token-file` in the answers file). `--tier`, `--runtime` or `--connection` alone do not name an installation. The candidates are the listed installations whose settings file still exists, and the default settings file when it exists, listed or not. A listed installation whose settings file is gone is skipped, and the page says how many.

- **One candidate:** the command uses it and says which: `This computer has one SuiteWard installation, so the command uses it. Its settings file is <file>.`
- **Several candidates and a terminal:** on a full screen, the page `Which installation?` gives the full text of each installation (its settings file, and its details: the instance, `on this computer` or `on a separate server`, the container program with its connection, and the two ports; the default one says so), then the choice. No row is picked beforehand, so Enter alone never picks the default installation. In plain mode (`--plain`), the command lists them and asks you to type the settings file of one. A name that is none of them stops the command, and nothing is changed.
- **Several candidates, and no terminal, or `--yes`, or `--answers`:** nothing can be asked, so the command stops before it changes anything: `This computer has several SuiteWard installations (<settings files>). Say which one with `--settings <file>` and `--token-file <file>`. A stack that has no settings file is named with `--token-file <file>` plus `--runtime` and `--connection`.` A script that relied on the default installation while a second one is listed must now pass the flags. `suiteward doctor --json` never asks and never stops for this: it checks the default installation.
- **A list that cannot be read** (damaged, written by a release that this program does not know, or an entry whose path is not absolute or holds a control character) stops the command with the reason, and says to name the installation with `--settings <file>` and `--token-file <file>`, or to fix or delete the list. Each installation adds its own entry again at its next install or upgrade.

`suiteward install` without `--upgrade` never asks: it makes a new installation, with its own `--settings` and `--token-file` or the defaults.

**The commands that the installer suggests name the same instance.** A command that the installer or `doctor` suggests repeats the `--settings`, the `--token-file` and, when you gave it, the `--tier` of the command you ran, so a command that you copy acts on the same instance and never on the default one. `enroll` leaves out `--token-file` and `doctor` leaves out `--tier`, because they have no such flag. The host step (`install host`) names no instance, and neither does the removal of another instance: this run does not know that instance's flags, so the text says to pass that instance's `--settings` and `--token-file` (the default instance needs neither). The ports, `--runtime` and `--connection` are not repeated, because the settings file holds them. This guide writes every command for the default instance, and so do the installer's texts that it quotes: for an instance of its own, add its `--settings` and `--token-file` (and `--tier`) to each command. The rows that the service adds to `doctor` and to the summary (the warnings of `github.app`, `github.installation`, `github.permissions`, `github.repositories` and `owner.enrolled` for an instance with no GitHub, the fix of `owner.enrolled`, and the fix of `protection.<owner/name>` when no test check is configured) carry the same flags, because the installer writes them in ("What `suiteward doctor` checks"). Two limits remain. The protection lines that `install` and setup print, and the rows of a service of an earlier release, still say a bare `suiteward install` or `suiteward enroll`. Add the flags yourself there.

## 6. Run setup

Setup binds you as the owner and enrolls your TOTP secret. On the co-located tier, the installer runs it for you at the end of the install, on a real terminal: it runs setup in the service container with a terminal, never captures or logs setup's output, and refuses to run it without a real terminal (it prints `suiteward enroll` instead). The isolated install does the same, as `suiteward` in the shell of step 10.3. It never runs unless `/status` shows no owner. Where setup runs depends on the screen:

- **A full screen on Windows or macOS, not over SSH: a window of its own.** A page says what will happen (setup shows the secret once, as text, and the installer never sees it) and waits for Enter. Setup then opens in a new window: a console window of PowerShell on Windows, Terminal on macOS (through a script that deletes itself). The installer waits on its own screen ("waiting for the owner enrollment in the other window"), so it does not look as though it had failed. In the window, add the secret to your authenticator, type the code, then press Enter at `Press Enter to close this window`. The window then clears its screen and its scrollback, so the secret does not stay in it: on Windows the window closes, on macOS the Terminal window stays open and empty, and you close it. The installer learns how setup ended from the exit code that the window leaves, never from what setup printed, and the page it comes back to says that setup finished without repeating anything of it. Ctrl-C at the installer stops the wait, and the command ends as interrupted (exit code 130): on Windows it also closes the window, on macOS you close it yourself. A setup that had already ended well stays a success. The limits: a window that is killed by force clears nothing, so the secret stays on its screen until you close it; and on macOS the installer waits up to 15 minutes for the window, and then says to finish in it or to run `suiteward enroll` again. If no window can be opened, setup runs in the terminal of the installer, as below, and says so.
- **Everywhere else** (a full screen on Linux, an SSH session, the isolated tier, plain mode): setup runs on your own terminal. On a full screen the installer leaves the screen for it, so setup's output is on your normal terminal and the installer's screen keeps none of it; it then waits for you to press Enter, so that you can copy the secret before the screen comes back ("The installer's screens", section 12).

**When the installer runs setup.** After it starts the stack, it reads `/status` (it waits up to about 30 seconds for the service) and acts on what it finds:

- **No owner is enrolled,** and this run knows the owner login and the test checks: on a real terminal it runs setup; without one it prints `suiteward enroll` (section 6, "Enroll again").
- **No owner is enrolled,** and this run does not know them (a re-run that took the App from the settings or the env file): it prints `suiteward enroll`, which asks for the login and takes the test checks from the settings.
- **An owner is enrolled:** it skips setup and the TOTP secret stays as it was, so a re-run, an upgrade, or a restore onto a new machine is safe. It prints `suiteward enroll` for the case where you want to enroll again, for example after losing the authenticator: that is a deliberate command, and it replaces the secret.
- **`/status` cannot be read in time:** it does not run setup, and prints the reason and `suiteward enroll`.

Run setup on the machine that runs the instance you are enrolling: the PC for co-located, the host for isolated. Its `--test-check` options name only the repositories of that instance, and each instance keeps its own owner and secret.

Until setup succeeds, SuiteWard comments nothing and publishes no `SuiteWard / Contract` check, so a pull request shows that required check as waiting. This is expected.

Before you start:

- Have your authenticator app ready.
- Turn off recording of the terminal session. Setup prints the `otpauth://` URI and the base32 secret to its terminal (the window of its own, or yours), and a recorded session keeps them. Make sure that no coding agent can read that terminal. If recording was on, turn it off and run setup again. That replaces the secret, so the old one stops working.

Setup takes your login and one `--test-check` for each configured repository (`suiteward enroll` fills them in, see "Enroll again" below). The check name is the exact name of the required status check that runs your tests, as it appears in that repository's ruleset. Do not use `SuiteWard / Contract` or `SuiteWard / Receipt`: SuiteWard publishes both itself, and neither is your tests' check. Quote each `--test-check` value, for example `--test-check 'owner/name=CI / test'`: check names often contain spaces and slashes, and an unquoted value would be split by the shell.

```
podman exec -it suiteward /suiteward setup --owner <login> --test-check '<owner/name>=<check name>' --test-check '<owner/name>=<check name>'
```

`suiteward enroll` runs this command for you, on the right engine and connection, so you do not type it. Run it by hand only when `suiteward` is not on the machine: on the co-located PC, in the shell session where you selected the rootless connection (step 5.1), so that `podman exec` finds the stack (on Windows or macOS with Podman, add `--connection <name>`).

Setup then works through these steps:

1. It looks up your login, which must be a user account, and every configured repository. If one lookup fails, it exits with code 1 before it writes anything.
2. It prints a warning and waits. Press Enter to continue. End of input or Ctrl-C exits with code 1, before any secret is created.
3. It prints the `otpauth://` URI and the base32 secret, once. Scan the URI with your authenticator, or type the secret in. The entry is named `SuiteWard:<login> (<tier> <instance>)`, for example `SuiteWard:octo (isolated 1a2b3c4d)`: `<instance>` is the first 8 characters of this instance's id, which `/status` shows as `instance`, so each instance has its own entry. Setup says the same on stderr. If you type the secret in, give the entry that name yourself.
4. It asks for the current 6-digit code. You get three attempts. Three wrong codes exit with code 1 and write nothing.
5. It stores the owner and the secret, records each repository's test check, and checks protection for each repository (section 7).

A missing, extra or duplicate `--test-check` is a usage error: exit code 2, and nothing is written. Setup exits with code 0 once enrollment succeeded, whatever the protection results.

Afterwards, check the result with `suiteward doctor`, or read `/status` at `http://127.0.0.1:<HTTP port>/status` (the HTTP port is 27081 unless you chose another). On the co-located PC the installer prints that address when `/status` answers from this PC, which it did on Windows with a Podman machine when this was checked; when it does not, it prints the command that reads it inside the machine instead (on Windows, `podman machine ssh --username user <machine> "curl -s http://127.0.0.1:<HTTP port>/status"`). On the isolated host, as `suiteward`, run `curl -s http://127.0.0.1:<HTTP port>/status`. The output shows `owner` with your login and the `protection` result of each repository.

Only a setup that prints the protection result of each repository and exits with code 0 counts. Confirm it with `/status`: `owner.enrolledAt` changes on every successful run, so a value that did not change means that setup did not complete. An interrupted setup can leave an authenticator entry that matches nothing: delete it.

Running setup again replaces the TOTP secret, and the new entry has the same name as the old one of this instance. Before you add it, delete any existing entry with this exact name. Entries of other instances (another id in the name) stay. An older entry named `SuiteWard:<login>`, with no instance in its name, predates this release: delete it once the new entry's code is accepted. Never paste the setup output, the URI, the secret or a code into a chat, an issue or a pull request.

### Enroll again

Enroll again when you lost the authenticator, or when setup ran with session recording on. Run it on a real terminal with session recording off, on the machine that runs the instance:

```
suiteward enroll [--owner <login>] [--test-check '<owner/name>=<check name>' ...] [--settings <path>] [--tier isolated]
```

On the isolated host, run it as `suiteward` in the shell of step 10.3, with `--tier isolated`. Give `--settings` when the install used a settings file of its own. On the co-located tier it needs the settings file, because it replaces the owner's TOTP secret and must not do that to an instance that defaults picked: with none (a stack that the PowerShell start script of `v0.2.0` and earlier made, `deploy/local.ps1`, which is no longer in the repository), run `suiteward install --upgrade` first, which converts the stack and saves the file. On Linux with no settings file (a host installed by hand), it needs `--tier isolated` (as the service account), as `install --upgrade` does; for a co-located stack, its error says to run `install --upgrade --tier co-located` first, which saves the settings file. The command finds the instance as `install` and `uninstall` do (a stack that this installer did not make, or that was edited, is left alone), reads `/status`, and then runs setup exactly as above, in the window or the terminal of section 6, with its output never captured or logged:

- **It needs a real terminal** on standard input and standard output, because setup prints the TOTP secret. Without one it stops, and changes nothing: `enroll needs a real terminal, because it shows the authenticator secret (the TOTP secret) there, and nothing was changed: run it from your own terminal, not through a pipe or a script`.
- **The service must be running.** When `/status` cannot be read it stops and tells you to start the service: it cannot tell whether an owner is enrolled.
- **The owner login** is `--owner`, else asked, with the enrolled login as the default. It is resolved first, so that the warning below can name it.
- **An owner is enrolled:** it warns that enrolling again replaces the TOTP secret (and the owner `<old>` with `<new>`, when `--owner` is another login), so that the old entry in your authenticator app stops working, and asks you to type `enroll` (on a full screen a page first says that nothing changes until you type it). Anything else, or the end of the input, stops it with nothing changed. There is no flag that answers this question.
- **The test checks** are the `--test-check` values, else the ones of the settings; it asks for a repository that has none. It refuses a check for a repository that the instance does not serve, and `SuiteWard / Contract` and `SuiteWard / Receipt`, which SuiteWard publishes itself and are never the test check (the install refuses them too).

Then delete the old entry of this instance in your authenticator before you scan the new one, as described above.

## 7. Create the ruleset

SuiteWard reports protection and never changes it, so you set the protection of each repository once, on its default branch. On both tiers, the installer wrote a ruleset file for each repository (`suiteward-ruleset-<owner>-<name>.json`, in the folder of its settings file: `~/.config/suiteward` on the isolated host; section 5.3, step 7, and step 10.4): open `https://github.com/<owner>/<repo>/settings/rules`, choose **New ruleset**, then **Import a ruleset**, and select it. The install waits for the import and reads the protection back (section 5.3, step 7), and the closing checks of a full screen name the file to import for every repository whose protection lacks what the ruleset requires (`suiteward doctor` reports the protection of each repository at any time). The installer deletes the file of a repository once its protection reads as enforced, because the import worked and nothing needs the file any more: a file that is still there belongs to a repository that was not read as enforced (section 5.3, step 7). The App must be installed on the repository first, or GitHub refuses the import with `Invalid parameter required_status_checks: Invalid integration ids`. On a private repository on GitHub Free, GitHub imports the ruleset but does not enforce it (section 3). Create the rules by hand only when GitHub was skipped, or you did not use the file: open the same address and create a ruleset (or classic branch protection, at `https://github.com/<owner>/<repo>/settings/branches`). Either way, it must do the following:

- [ ] Targets the default branch. SuiteWard reads the rules of that branch.
- [ ] Requires the status check `SuiteWard / Contract`, with your SuiteWard App as its source. A check from any other source does not count.
- [ ] Requires your test check, the name you gave to setup.
- [ ] Requires branches to be up to date before merging.
- [ ] Has an empty bypass list. SuiteWard cannot read a ruleset's bypass list, so check it yourself.
- [ ] Does not require `SuiteWard / Receipt`. That check is never required: a pull request whose receipt does not apply publishes none, so a rule that requires it would wait for ever.
- [ ] Enforces the rules for administrators, if the repository uses classic branch protection (`enforce_admins`).

SuiteWard checks protection when you run setup, and then every 15 minutes. `/status` reports each repository's overall result as `enforced`, `findings`, `enforcement-unavailable` or `unknown`; when it is `findings`, the `findings` list names one or more of the codes below. The results mean the following:

| Result or finding | Meaning | What to do |
| --- | --- | --- |
| `enforced` | Nothing is missing. | Nothing. |
| finding `missing-contract-check` | `SuiteWard / Contract` is not required from your App. | Require it, with your App as the source. |
| finding `missing-test-check` | The test check you gave to setup is not required. Before setup, this result appears too. | Require the check, or enroll again with `suiteward enroll` (with `--tier isolated` on the isolated tier). |
| finding `not-up-to-date` | The required checks do not require branches to be up to date. | Turn on the up-to-date requirement. |
| finding `admin-bypass` | Classic protection does not apply to administrators. | Enforce it for administrators. |
| `enforcement-unavailable` | GitHub does not enforce rules on this private repository, or the App cannot read the rules. SuiteWard does not claim protection here. | Either use a GitHub plan that enforces rules on private repositories (GitHub Free does not), or give the App the read permission (the checklist of step 10.4). |
| `unknown` | The protection could not be read, for example because the App's token lacks Administration read. | Check the App's permissions against step 10.4. |
| caveat `ruleset-bypass-unverified` | Shown with a ruleset result. SuiteWard cannot see the bypass list. | Check by hand that the bypass list is empty. |

## 8. First use: bootstrap

A repository has no contract until its first one is approved. Until then, each open pull request shows the `SuiteWard / Contract` check as `in_progress` (GitHub shows "In progress"), reason `bootstrap-awaiting`, with three exceptions: a pull request from a fork shows `fork-unsupported` instead; the pull request carrying the current proposal shows its own state (`in_progress`, `approval-missing` while it waits for your approval, or `success`, `bootstrap-ready` once approved); and a pull request you skipped shows `success`, `bootstrap-skipped`. SuiteWard comments with how to start. It proposes nothing by itself.

On the pull request that should carry the first contract, post one of these commands as the first line of a comment. Only the owner's comments count:

- `/suiteward propose` creates the first proposal from that pull request. It needs no code, and it grants nothing by itself.
- `/suiteward skip <6-digit code>` lets the pull request pass the check before any contract exists. The check then reads "Skipped by the owner before the first contract", and nothing was assessed. SuiteWard refuses this once a contract exists.

Where `.suiteward.yml` is decides the source of the proposal:

1. **On the default branch.** The proposal is pinned to the default branch's head. After you approve it, SuiteWard promotes the first version (V1) by itself, within about a minute, without waiting for a merge.
2. **Only in the pull request's head.** The proposal is that head. Its V1 comes only from this pull request's exact merge commit, after the pull request merges.
3. **Nowhere.** Nothing is proposed. SuiteWard replies with a suggested `.suiteward.yml` and a link. The link opens GitHub's editor on the pull request branch with that file filled in. You review the file and commit it yourself. SuiteWard never commits it. After you commit it, wait about a minute — until the check shows the new head — then comment `/suiteward propose` again.

   The suggestion is built from the file paths of the pull request's tree, never from file contents, and it has two lists:
   - `include:` holds patterns for test files and test directories. They match at any depth, so one pattern such as `*_test.go` covers every directory, and `testdata/` counts wherever it is. Files under vendored directories (`node_modules`, `vendor`, `.venv` and similar) never count.
   - `runner:` holds the test runner files it found, plus the files that the same runner reads before them. Those may not exist yet. For example, when it finds `pytest.ini`, it also lists `pytest.toml`, which pytest reads first. Protecting a file that does not exist yet means that a pull request that adds it needs your approval, so nobody can override your runner settings by creating it.

   The list is limited to 20 patterns, `include` and `runner` together. The runner names it found keep their room, and the `include` patterns give way, so a runner name is never dropped because of a long `include` list. When SuiteWard cut the list, the reply says so. Read the suggestion as a start, and add what is missing before you commit it.

   The reply also warns about mixed files: `package.json`, `pyproject.toml`, `setup.cfg`, `tox.ini`, `Cargo.toml`, `*.csproj` and `CMakeLists.txt`. They can hold test settings among other content. SuiteWard names the ones it found and never suggests them, because protecting them would put every dependency update behind an approval. You decide whether to add one.

   The reply also warns about submodules. A submodule is outside the scope: SuiteWard never reads one, so its contents are not protected, whatever you write in `.suiteward.yml`. When a suggested pattern would reach a submodule (a pattern such as `*_test.go` can reach one that is not vendored), the reply lists it, at most 20, and says that its contents are not protected.

The declaration has `version: 1`, optional `include`, `exclude` and `runner` lists of path patterns, in gitignore style and case-sensitive, and an optional `execution` block that turns on the running of tests (section 9, "Running the tests: canonical execution and the receipt"). A pattern is never folded, but a file whose path differs only in case from a protected file, or that lies in a directory that differs only in case from one where the protected path would be covered, is protected too, because a case-insensitive checkout would put it on the protected file. A tree that spells one name in more than 8 case variants is refused as an invalid source. Any other key makes it invalid, and so does an unknown key inside `execution`:

```yaml
version: 1
include:
  - <test path pattern>
  - "*.spec.ts"
runner:
  - <test runner configuration or script pattern>
```

Quote a pattern that starts with `*` or `!`, such as `"*.spec.ts"` or `"!fixtures/**"`. YAML reads an unquoted leading `*` as an alias and a leading `!` as a tag, not as a literal character, so the pattern would otherwise be invalid YAML.

`.suiteward.yml` itself and `.github/workflows/**` are always protected. Put your test files in `include`, and your test runner configuration and test scripts in `runner`.

**Symbolic links and submodules.** SuiteWard reads the tree of a commit without checking it out, and it treats the two kinds of entry that are not plain files in this way:

- A symbolic link matters only when a pattern of the scope matches the link's own path or could match a path below it. SuiteWard then resolves the link's target inside the same tree, one path component at a time, and follows at most 8 links.
  - A link to a file of the repository is accepted, unless the scope covers the link's own path. If it does, the declaration is invalid (`invalid-source`): protect the file itself.
  - A link to a directory, to a path outside the repository, to nothing (dangling), or a loop of links makes the declaration invalid whenever a pattern can reach it. Replace the link with the files, or, if its content does not need protection, accept the link by adding its exact anchored path to `exclude` (for example `/spec_link`). The `invalid-source` comment shows that declaration. It is a scope reduction, so it needs your approval, and nothing reached through the link is protected.
- A submodule is outside the scope and never makes a declaration invalid. SuiteWard never reads it, so its contents are not protected, and every reply that suggests a declaration warns about the submodules that its patterns would reach.

SuiteWard's proposal comment shows the copyable command. Approve the exact revision it names, for example `/suiteward approve P<n>-R1 <6-digit code>`.

Keep these points in mind:

- A `.suiteward.yml` larger than 64 KiB in a pull request or on the default branch is invalid (`invalid-source`). A real declaration is a few lines.
- A declaration with a pattern of more than 64 segments, or more than 1000 patterns in all, is invalid (`invalid-source`). This also holds for the declaration stored with the canonical: one over a cap fails every assessment until the repository is bootstrapped again.
- A tree that holds a path longer than 4096 bytes, or more than 8 spellings of one name that differ only in case, is invalid (`invalid-source`).
- If a protected file changes after the proposal, SuiteWard cancels the proposal and comments. Post `/suiteward propose` again.
- Pull requests from forks get no proposal. Their check shows `fork-unsupported`, because forks are not supported in this release.
- SuiteWard cannot read a repository whose tree GitHub truncates, which happens with very large monorepos. `propose` refuses it as `invalid-source`, the bootstrap job stops at `origin-not-passed`, and the check of a pull request shows `source-unavailable` (section 9). Such a repository cannot be protected in this release.
- Reading a very large test suite can take longer than the job timeout. SuiteWard reads the protected files eight at a time and keeps what it read, so the default of one minute covers about a thousand files, and a pass that is cut off resumes where it stopped. For a suite far beyond that, raise `SUITEWARD_JOB_TIMEOUT` (section 13): on the co-located PC with `--job-timeout` of `suiteward install`, on the isolated host with an `Environment=SUITEWARD_JOB_TIMEOUT=<value>` line in `suiteward.container`, which the installer carries over.

## 9. Day to day

After the first contract, you only handle pull requests that change protected files.

**Revision comments.** When a pull request gets a new protected revision that needs approval, SuiteWard posts one comment that states:

- the approved version that the revision is compared with (`V<n>`), and the installation type (`on a separate server` or `on the same computer as your coding agent`);
- what changed in the protected files, as numbers: `Files: N added, N modified, N removed`; `Lines: N added, N removed (counted in N of N files)`, because a binary file, or one that is too large or too different to compare, has no line count; `Not shown line by line: N files`, when there are some; and `Marker lines seen:` with their kinds, or `none`;
- the changed files with their lines, `+N/−M`, the most changed lines first, at most 20 (the heading says `(20 of N)` when there are more);
- the files without a line-by-line diff, at most 10, each with its reason: a binary file, too large to compare, too different to compare, not compared because the work budget of the report ran out, or a diff left out to keep the report within its size budget;
- a link, `Full change report` (below), with a note that the link opens on the computer that runs SuiteWard (for a separate server, forward its HTTP port to your computer first) and that Ctrl+click (Cmd+click on a Mac, or middle-click) opens it in a new tab: GitHub removes `target="_blank"` from the links of a comment, so no link can force a new tab;
- the copyable `/suiteward approve P<n>-R<m> <6-digit code>`, after the sentence `This comment is a record, not an approval. To approve this exact revision, comment:`;
- a line saying which earlier revision this supersedes (`This supersedes `P<n>-R<m>`.`), if there is one.

The comment counts and points out. It never says that the change is right or wrong. When the revision's receipt applies, it carries one fixed line, before the approve command, that says what the receipt is (evidence, not a verdict), where its results are (a link named `Pull request page`, below; an instance with no `SUITEWARD_REPORT_BASE_URL` has no link, and the line points to the `SuiteWard / Receipt` check instead), that this check carries the counts and, under `before-approval` and `required`, what approving needs (`Approving waits until the receipt is complete.`, or that the approve names a mode, the kind of change that the receipt meets). Beyond that line, the comment says nothing about tests. A **marker line** is a line to look at, never a verdict. SuiteWard finds them with simple rules on the lines that changed, by file extension: an assertion line removed (`assert`, `expect(`, `t.Fatal` and the like), a skip line added (`t.Skip`, `it.skip`, `@pytest.mark.skip`), a focus line added (`.only(`), a test declaration removed, and a test file removed. A line that only moved or was reindented gets no marker. Files with other extensions only get the assertion rule. When the revision reduces the scope, a removed file left the protected files and may still exist, so the comment says `removed from the protected files`.

The numbers are counted when the comment is posted, from the revision's stored manifest and the files of both versions that SuiteWard already holds. When they cannot be counted, the comment lists the protected files added, modified and removed, up to a bound, and says: `SuiteWard could not read the files of this revision to count the changed lines, so it has no counts. The lists above still show the protected files that changed.` It has no link then. SuiteWard never edits a comment, so it stays so. A revision that was recorded before M1.13 has no stored manifest: it gets that list, and no report page.

Each new revision gets a new comment, and SuiteWard never edits one. A pull request with no protected change, and a push that changes only the implementation, gets no revision comment. (Where a profile is named, the results of its test run are another comment: "The comments of a head", below.) An implementation-only push keeps your approval. A push that changes a protected file creates a new revision that needs its own approval.

**The change report.** The link in the comment opens the full report of that revision, one page that your own instance serves at `http://127.0.0.1:<HTTP port>/reports/<owner>/<repo>/P<n>-R<m>`. It shows the revision, the approved version that it is compared with and the numbers of the comment, and for every changed protected file its status, its `+N/−M` (or why it has none), its marker lines and its unified diff, with the deleted and added lines. It is one static page in the SuiteWard colors, light and dark, with no script and nothing to load, and it is not an approval. The page stays on your instance: the App never writes contents, so nothing of it goes to GitHub.

- **Where it opens.** The link names the loopback address and the HTTP port of the instance (`SUITEWARD_REPORT_BASE_URL`, which the installer sets from `--http-port`; section 13), so it opens in a browser on the machine that runs the instance. On the co-located PC that is the same PC: on Windows with a Podman machine, the published loopback port answered from Windows when it was checked, so the link opens there. If the port does not answer from your Windows (the installer then prints the command that reads `/status` through the machine, instead of its address), the link does not open, and the numbers in the comment are still there. On the isolated host, forward the host's HTTP port to your PC as for `/status` (step 10.4) and open the link on the forwarded port: the link names the host's port, so forward to the same local port number, or change the port in the address (the page answers on any port).
- **Who can read it.** The page answers only a request whose `Host` is `127.0.0.1`, `localhost` or `[::1]`, so a web page in your browser cannot read it through a name that it made point at 127.0.0.1 (DNS rebinding). That is not a login. Anyone who can reach the HTTP port of the instance can read the reports of the enrolled repositories, which show the protected files of a proposal, as they can read `/status`: on the co-located PC every program that you run, on the isolated host every user of the host.
- **What it reads.** Each request rebuilds the report from the revision's stored manifest, the manifest of its base version, and the bytes of the files that differ, so a revision that a later push superseded still has its page. A file with a side over 1 MiB is not read: the page lists it as too large to compare, with its sizes. A revision whose other files would take more than 32 MiB to read, and a page over 8 MiB, answer `413`. One report is built at a time, and a request waits for its turn up to 20 seconds.
- **When it answers no.** `404`: the repository is not enrolled, the revision is unknown, the revision is the baseline of the first contract (there is nothing to compare it with), or it was recorded before this release. `403`: another `Host`. `503`: the report cannot be built now, with a fixed text; the log of the service has the cause.

The summary of the `SuiteWard / Contract` check states the same numbers (the files, the lines, the files not shown line by line and the marker lines seen) for a revision that has an approved version, and says that marker lines are lines to look at, not a verdict. The numbers carry no link and no file name, because a check summary is public. Under `canonical: required`, the summary of a head whose canonical run is complete also states the counts of that run in plain words (`Approved tests: N tests ran. N passed. …`), and again no path and no test name (below, "Running the tests: canonical execution and the receipt"). For a head that awaits your approval, it states them once every run that the head wants has ended (the canonical run, and the receipt where one applies), as the results comment does. If an approved test fails, is missing or is flaky, it says so and adds that a test that is edited can pass by checking less. When the change itself edits an approved test that fails in its approved version, the summary says how many such tests there are, in place of that sentence ("A test that a change edits to accept a regression", below).

**Approve and revoke.** Only the owner's comments are commands. Another account's `/suiteward` comment is ignored without a reply.

- `/suiteward approve P<n>-R<m> <6-digit code>` approves that exact revision. With execution on, the owner can name a mode between the reference and the code, `/suiteward approve P<n>-R<m> fix <6-digit code>` (`fix`, `feature` or `refactor`), which judges the receipt; a `required` receipt that is complete and not empty needs one (below).
- `/suiteward revoke P<n>-R<m> <6-digit code>` withdraws that approval. It takes no mode.
- `/suiteward mode <fix|feature|refactor>` and `/suiteward unblock <6-digit code>` belong to execution (below).

The command is the first line of the comment that starts with `/suiteward` outside a code block. Nothing else may follow the code on that line. Other lines in the comment are ignored. SuiteWard replies on the pull request with the outcome: approved, revoked, no active approval, refused by the receipt gate (below), or rejected with the reason.

**Codes.**

- A code works once. A step is used up by the first command that uses it, across all commands. A second command needs the next code that your authenticator shows. A replayed code is refused.
- A code is accepted within one 30-second step before or after the comment's creation time. Post the command with a fresh code.
- Post each command once, and do not edit it. SuiteWard processes only the first version of a comment. Editing or deleting it afterwards changes nothing. A command edited before SuiteWard read it is refused. For another action, post a new comment.
- SuiteWard lists comments only on open pull requests, so a command posted after the pull request closed or merged is never seen, and a promotion uses only the consent given before the merge. A command that SuiteWard saw while the pull request was open and had not processed when it closed is processed as usual, except `propose` and `suggest`, which answer `not-open` and do nothing.
- SuiteWard reads new comments about every 20 seconds, so an answer usually comes within a minute.

**What the check states mean.** The check is `SuiteWard / Contract`. Its summary names the state and the next action. GitHub's UI shows `in_progress` as "In progress".

| State and reason | Meaning |
| --- | --- |
| success, `unchanged` | There is no protected change, so there is nothing to approve. |
| success, `ready` | The exact revision is approved and assessed, and it is ready for integration. |
| success, `bootstrap-ready` | The first contract is approved. V1 follows (section 8). |
| success, `bootstrap-skipped` | Skipped by the owner before the first contract. Nothing was assessed. |
| in_progress, `approval-missing` | Approve the current revision with the command in the check or in the comment. Under `receipt: required` the command names a mode (`fix`, `feature` or `refactor`). Under `canonical: required` the check is written again once every run that the head wants has ended (the canonical run, and the receipt where one applies), and then states how the approved tests ran on this head. If one failed, is missing or is flaky, read the change before you approve: an edited test can pass by checking less. If the change edits an approved test that fails in its approved version, the check says how many. |
| in_progress, `bootstrap-awaiting` | There is no contract yet. Post `propose` or `skip` (section 8). |
| in_progress, `runner-uncovered` | The pull request adds or changes a test runner file (for example `conftest.py` or `jest.config.js`) that the contract does not cover. Such a file can change how the protected tests run, so the check waits for your decision. SuiteWard's comment offers two ways out, each one click when the pull request's diff shows `.suiteward.yml`: protect the file (add its pattern) or ignore it (add the path to `exclude`). Then approve the new revision. |
| in_progress, `not-current` | This pull request's revision is no longer the current one. Use the newest revision comment. |
| in_progress, `source-unavailable` | GitHub cannot list the whole tree of this revision, so SuiteWard cannot read it. This happens with very large monorepos, which cannot be protected in this release. |
| in_progress, `fork-unsupported` | Pull requests from forks are not supported. They get no execution job either. |
| in_progress, `canonical-pending` | Only under `canonical: required`: the canonical run of this head has not finished. Wait; the check never turns `success` from the approval and the integrity alone. |
| in_progress, `canonical-not-responding` | Only under `canonical: required`: the test runner has not answered for about 30 seconds, and the canonical run of this head waits for it. This is a problem only if it lasts. SuiteWard keeps trying. Check that the test runner is running, or the owner lifts it for this head at once with `/suiteward unblock` (below, "When the test runner does not respond"). |
| in_progress, `canonical-unavailable` | Only under `canonical: required`: the canonical run of this head could not be completed (no executor, a failed source check, a timeout, and so on). The reason is on the pull request page. Fix the executor or the cause, or the owner lifts it for this head with `/suiteward unblock` (below). |
| in_progress, `assessment-pending` | SuiteWard is still reading the pull request. Wait a few minutes. |
| failure, `invalid-source` | `.suiteward.yml` is invalid, or a symbolic link that the scope reaches points at a directory, outside the repository or nowhere, or the scope covers the link itself (section 8), or it is larger than 64 KiB, or a pattern has more than 64 segments, or it holds more than 1000 patterns; or the tree holds a path longer than 4096 bytes or more than 8 case spellings of one name; or the `execution` block has an unknown key, a profile other than `go`, or a level without a profile. Fix it. A submodule never causes this: its contents are not protected. |
| failure, `integrity-failed` | A canonical artifact no longer matches its integrity record. SuiteWard fails the check on every pull request of that repository and does not promote; it does not block merges by itself — your branch protection does that, if you require the check. Restore the artifact from a trusted copy or a backup, never edit the database, and restart the service: it re-verifies at once. On the isolated host, as `suiteward`, run `systemctl --user restart suiteward.service`: the image did not change, so migrate does not run again. On the co-located PC, restart the service container: `podman restart suiteward` on Podman (with `--connection <name>` if the install used one), `docker restart suiteward` on Docker. (A Docker re-run of `suiteward install` leaves a running, unchanged service alone, so it does not re-verify.) |
| failure, `canonical-failing` | Only under `canonical: required`: the canonical run is complete, and an approved test failed, is missing or is flaky. A push that fixes the head clears it. An approval stays through such a push. |
| failure, `owner-command-rejected` | A confirmation code on your latest command was wrong or reused. Post a valid `approve` or `revoke` with a current code, or push a new head. A later `skip`, `propose` or `suggest` does not clear it. Any other wrong command only gets a reply and changes nothing. |

A success means that the protected files match what the owner approved, except `bootstrap-skipped`, where nothing was assessed. Under `canonical: required` it also means that the executor ran the approved tests on this head and none failed, was missing or was flaky (skipped tests are counted and allowed). In every other case the state of the check does not depend on any test result: the results of an `advisory` run are on the pull request page, and your own test check decides whether your tests pass.

**Links and submodules.** Section 8 explains the rules, which hold for every pull request. A link to a file of the repository is accepted unless the scope covers the link's own path. A link to a directory, to a path outside the repository or to nothing makes the check fail with `invalid-source` when a pattern can reach it. Submodules are outside the scope: their contents are not protected, and a reply that suggests a declaration warns about the submodules its patterns would reach.

**At merge.** When a pull request with an approved revision merges, SuiteWard comments naming the new canonical version — or, if it could not promote, a comment saying it did not promote, with the reason (the merged files do not match the approved revision, for example a rebase that brought in another change). Recover with a new pull request: one that restores the protected files of the last canonical version, or one that carries the merged content for a new exact approval ([D-INTEGRATION](plan/decisions.md)). There is no reset command.

### Widening the scope

The scope is the list of paths that `.suiteward.yml` protects. A test directory or a runner file that a pull request adds later is outside it, so nothing protects it. SuiteWard reports such files and never protects them: only your approval changes the contract.

**The scope notice.** When a pull request adds test-like or runner files that the current scope does not cover, SuiteWard posts one comment that:

- lists those files, at most 20 with the total, the mixed files it found and the submodules that a suggested pattern would reach (section 8), and says that the current contract does not protect the files. Submodule contents are never protected;
- gives the full new `.suiteward.yml` in a code block that you can copy, and a link that opens GitHub's editor on the pull request branch;
- says that nothing is protected until you commit the file and approve the revision it creates.

Keep these points in mind:

- The check does not change, and the comment never says that tests ran.
- The comment appears once for each set of new files, not for each push. A later push that adds no new uncovered file posts nothing. A new approved contract that changes the suggested file posts the notice again, once; one that leaves the suggested text as it is posts nothing.
- A path that matches an `exclude` of your scope is never reported: the exclusion is your choice.
- The suggested file starts from the approved `.suiteward.yml` and only adds patterns. It may be re-indented and lose blank lines.
- Comments in `.suiteward.yml` are part of the approved bytes. A pull request that edits only a comment is a protected change and needs your approval. Compare the suggested file with your own before you commit it, because it may have lost a comment.
- A pull request whose own `.suiteward.yml` is valid and already covers the files gets no notice. That widening still needs your approval.
- A declaration that cannot be shown, because it is larger than 8192 bytes (a declaration over 64 KiB is invalid, not just hidden) or holds a character you cannot see (a zero-width or bidirectional control character, for example), is never put in a comment. The comment then lists the new patterns alone, as lines to copy under the `include` and `runner` lists, with the same link to the editor. This holds for the notice, for the reply of `/suiteward suggest` and for the runner comment.

**A suggestion on the diff.** SuiteWard also posts a review comment, together with the notice, when all of these hold: the pull request changes `.suiteward.yml`, the file in its head is a valid declaration in block style, and the diff shows an item line of the `include:` list or the `runner:` list. The comment sits on that line, with the line and the new patterns as a suggestion. Use GitHub's "Commit suggestion" button to accept it. It leaves out the patterns that the file already lists. A list written as `include: [a, b]`, or a list with no item line in the diff, gets no suggestion: copy the block from the notice instead.

**Ask for it: `/suiteward suggest`.** Post it as the first line of a comment on any open pull request. Only the owner's comments count, and it takes no code.

- After the first contract, SuiteWard replies with the scope notice for that pull request's head. If every test-like file is already in the scope, it says so.
- Before the first contract, it replies with the suggestion of section 8, as `propose` does when it finds no declaration.
- It grants nothing and changes no check.
- SuiteWard can refuse it, and the reply names the reason:
  - `fork`: the pull request comes from a fork, and forks are not supported in this release.
  - `not-open`: the pull request is no longer open.
  - `invalid-source`: SuiteWard cannot read the head well enough. Its tree is invalid or truncated, the approved contract has no declaration, or the reply cannot be written (an unusable branch name, for example).

  If the approved contract fails its integrity check, the command gets no reply: SuiteWard retries it and then records it as failed.

**Add what the suggestion missed.** `suiteward scope add [--runner] PATTERN...`, run in the root of a checkout, adds the patterns to the `include` list of its `.suiteward.yml` (to `runner` with `--runner`). It changes only the lines it adds and prints them, and where it cannot insert safely (a list written as `[a, b]`, for one) it changes nothing and prints the lines to add by hand. Nothing is protected until you approve the revision that the changed file creates on a pull request.

**An agent widens the scope** with a pull request that edits `.suiteward.yml`, for example with `suiteward scope add`. The edit creates a protected revision, and you approve it like any other. An agent cannot use `/suiteward suggest`: only the owner's comments are commands.

**A reduction.** When a revision removes rules or paths from the scope, its revision comment says `This revision reduces the protected scope.` and lists the rules and the paths that the reduction removes, so you see what would stop being protected before you approve. A revision that lowers an execution level, or removes the `execution` block, says `This revision lowers the test requirements.` and lists each level that gets weaker under `Test requirements lowered` (for example `approved tests: required -> advisory`, or `receipt: required -> advisory`); when that is all it reduces, the comment lists no path. When a reduction has more detail than fits, the comment says so and tells you to compare `.suiteward.yml` with the one in the approved version.

### Running the tests: canonical execution and the receipt

SuiteWard can run tests in disposable sandboxes, through the executor that the install made (sections 5 and 10). It is off until the owner approves it, it covers Go only in this release, and what it reports is evidence about one head, never an approval ([ADR 0028](decisions/0028-canonical-execution-and-the-receipt.md) records the design, and the [runtime contract](contracts/runtime.md#execution-m21-normative) the behavior). There are two kinds of run:

- **Canonical execution** runs the approved tests on the head of every open pull request.
- **The receipt** runs the tests that a protected revision adds or changes, on the head and on the code before the change, so that you see whether they detect anything before you approve them.

**Turn it on.** Add an `execution` block to `.suiteward.yml`, in a pull request, and approve its revision like any other protected change:

```yaml
execution:
  profile: go            # the only value in this release
  canonical: advisory    # off | advisory | required
  receipt: advisory      # off | advisory | before-approval | required
```

- **Nothing runs without a `profile`.** With one, `canonical` and `receipt` default to `advisory`, so `execution: {profile: go}` is enough. No `execution` block, or `execution: {}`, means that both levels are `off`. A block that names a level without a `profile` is an invalid declaration (`invalid-source`), so that nobody believes a policy is on while nothing runs. An unknown key under `execution`, or a profile other than `go`, is invalid too, and so is a key with no value (`execution:` alone, or `execution: ~`): write `execution: {}` for an empty block. To turn execution off, remove the block, or keep the profile and set both levels to `off`.
- **It is a protected change.** The pull request that adds or changes the block is a revision that you approve with a code. Before the first contract (V1) nothing runs.
- **The canonical declaration governs every pull request, the one that changes the block included.** A pull request that lowers the levels still meets the old levels until its approved version is promoted. Lowering is, from the strongest: `canonical` `required`, `advisory`, `off`, and `receipt` `required`, `before-approval`, `advisory`, `off`; removing the block lowers both to `off`. A revision that lowers a level lists it in its comment as a reduction (`approved tests: required -> advisory`), so you see it before you approve it. Raising a level lists nothing.
- **Pull requests from forks get no run.** Their check stays `fork-unsupported`.
- **The toolchain is not a setting.** Go is the Go of the release's pinned sandbox image (1.27.3 in this release). A `go` or `toolchain` line of a side's `go.mod` that asks for a newer one makes the run `unavailable` (`toolchain-mismatch`).

**What each level does.**

| Level | What it does |
| --- | --- |
| `canonical: off` | Nothing runs. |
| `canonical: advisory` | The approved tests run on each head. The results are in the comment of the head and on the pull request page. The Contract check does not change. |
| `canonical: required` | The same, and the run gates `SuiteWard / Contract` where it would otherwise be `success`. A run that is pending keeps it `in_progress` (`canonical-pending`; `canonical-not-responding` when the test runner has been silent for about 30 seconds), and so does one that cannot be completed (`canonical-unavailable`). An approved test that failed, is missing or is flaky makes it `failure` (`canonical-failing`). A run with no declared test is complete, and the check says that 0 tests ran. A head that awaits your approval stays `approval-missing` whatever the run says, and its check is written again with the counts once the runs of the head have ended. |
| `receipt: off` | No receipt. |
| `receipt: advisory` | The receipt of each revision that has one runs, and its results are on the Receipt check, in the comment of the head and on the pull request page. It never refuses an approval. |
| `receipt: before-approval` | An approve is refused only while the receipt is pending, whatever it says. A receipt that is unavailable does not refuse: you chose to look at the receipt, and you approve with its answer in front of you. |
| `receipt: required` | An approve is refused unless the receipt is complete, the approve names a mode, and the summary for that mode is met. A receipt that is unavailable refuses, unless you unblocked that job for the head (`/suiteward unblock`, below): the approve then passes and needs no mode. A receipt that is complete and empty passes, and needs no mode. |

**The canonical run.** It runs the head's tree with the governing manifest laid over it. The governing manifest is that of the current canonical version, and, once a consent covers the head, that of the consented revision. Every file of the manifest is written at its path (the tests, `testdata`, runner files such as `conftest.py`, `.suiteward.yml`, workflows), and every head file that the governing scope covers but the manifest lacks is removed. Other head files stay. So a head can add a test, but it cannot silence one or change how the approved tests run. The expected tests are the top-level test functions that the manifest's Go test files declare. After an approval, a push that breaks the approved tests keeps the approval: only the canonical gate reacts, by failing the check until a push fixes the head.

Each declared test ends in one state: `PASS`, `FAIL` (it failed, panicked, timed out or did not build), `SKIPPED`, `MISSING` (expected, and no result), `FLAKY` (its runs differed: a failure or a missing result is run again, twice, on the same side) or `EXCLUDED` (below).

**The receipt.** It exists for a head that has a protected revision when `receipt` is not `off`, and when it **applies**: at least one file that the canonical `include` matches (and its `exclude` does not) is added or changed in the revision, against the canonical version the revision expects. A revision that changes no such file, because only runner files or the declaration changed, or tests were only deleted, has a receipt that is not applicable: no job runs, the receipt gate does not apply (the approve needs no mode) and no Receipt check is published. A receipt that applies but holds no test function that was added or changed (only `testdata` or helpers, say), or whose tests are all excluded, is complete and empty: the gate passes it as it passes a not applicable one, the Receipt check is `success` with every count at zero, and the page lists the changed files.

- **Head side:** the head's tree. **Base side:** the base commit's tree (the merge base of the head and the pull request's base branch) plus the head's version of every file that the canonical `include` matches and the head adds or changes (test files, `testdata`, helpers). Nothing else of the head crosses: source, `go.mod`, `go.sum`, `vendor/`, runner files and `.suiteward.yml` come from the base commit. Only the approved `include` decides what crosses, so a pattern that the head adds to its own declaration moves nothing.
- **Evaluated tests** are the top-level test functions added or changed, by declaration text, against the canonical version the revision expects (not against the merge base, and not against the consented manifest, so the receipt does not turn empty after an approval).
- **Not evaluated.** Files that the pull request adds or changes and that the head's own `include` matches but the canonical `include` does not are listed as "not evaluated: pattern not approved yet". The list is for display.
- **Each evaluated test ends in one state,** the first that applies:

| State | Meaning |
| --- | --- |
| `EXCLUDED` | Declared, and not runnable in this profile (below). It counts nowhere. |
| `MISSING` | No result on the head, or none on the base although the base's package built. |
| `FLAKY` | Its runs differed on a side. |
| `SKIPPED` | It was skipped on the head. |
| `FAILS` | It failed on the head, or did not build there. |
| `NEW API` | It passes on the head and does not build on the base: it needs something that exists only in the head's source. |
| `DETECTS` | It passes on the head and fails on the base. |
| `INERT` | It passes on the head, and passes (or skips) on the base: it protects nothing against this change. |

- **The mode** is a lens that the owner names when approving. It judges the receipt and never changes it:
  - `fix` is met when at least one test is `DETECTS` and none is `FAILS`, `MISSING` or `FLAKY`;
  - `feature` is met when none is `FAILS`, `MISSING` or `FLAKY` and at least one is `DETECTS` or `NEW API` (all `INERT` is not met: no test detects anything);
  - `refactor` is met when every evaluated test is `INERT`;
  - without a mode there are counts only, and no judgment. For an empty receipt `fix` and `feature` are not met and `refactor` is, and the gate does not judge an empty receipt.

**The owner's commands.** Only the owner's comments count, and the commands that carry a code use one, as for `approve` (section 9, "Codes").

- **`/suiteward approve P<n>-R<m> [fix|feature|refactor] <code>`.** The mode travels with the code, so it comes from you and never from the pull request's text. The receipt gate reads the head that is current when the command is processed, and only for an approve that names the proposal's current revision. **The code is verified and consumed before a refusal,** or anyone could take it from a refused comment, which is public, and post it again with another mode. A refusal records no consent, the Contract check does not change, and the reply says why: `receipt-pending`, `receipt-unavailable`, `mode-required` or `mode-not-met` (with the counts). The next attempt needs the next code. The ledger keeps the receipt's state at the approval whether it was refused or not.
- **`/suiteward mode <fix|feature|refactor>`.** No code. It sets the **preview** that the pull request page shows for the pull request, and no gate reads it, because whoever holds your GitHub identity can post it. A bare `mode`, or another word, gets a reply.
- **`/suiteward unblock <code>`.** The escape. When the test runner is down, the Contract check of a `canonical: required` repository stays `in_progress` and a `required` receipt refuses every approve, the approve of the pull request that lowers the levels included, and the ruleset has an empty bypass list. The unblock applies to the pull request's current head. It lifts the **jobs** of that head that are `unavailable` at that moment: the canonical job and the receipt job when it applies (a job that exists because no executor is configured is one of them). It also works before that, as soon as the head reads not responding (below, "When the test runner does not respond"): it then ends each run of the head that waits for the silent test runner as `unavailable` (`no-executor`, with no result and no failed attempt) and lifts it, so you do not have to wait for the 2 minutes of the lease wait. A run that a test runner that responds is working on, or is about to take, cannot be unblocked: the command is refused as `runner-responding`, and its code is used. In the gates only: the Contract check stops being withheld and the receipt stops refusing, and the approve then needs no mode. It never lifts a failing, missing or flaky test, a run that waits for GitHub, a run that a responding test runner holds, or another head. The unblock changes no result: the jobs stay `unavailable`, and both checks of the head say that you unblocked it and that the tests did not run.
  - **Every unblock holds.** When the test runner comes back, SuiteWard does not replace the job that you unblocked, so nothing runs the tests of that head, and the next push runs as usual. This changes what an earlier release did, where a fresh job replaced a `no-executor` job once an executor was seen again. A job that ended for `executor-not-configured` is still replaced once a token is configured: fixing the configuration is what you wanted. If the pull request is still open when the test runner is seen again, SuiteWard posts one comment, **The test runner is back.**, that says that you unblocked this commit while the test runner was not responding, that its tests did not run, and that a new push runs them.
  - **Later jobs.** A job that appears later for the same head (a new governing manifest after an approval, a changed policy) is another job that needs its own unblock, and so does a new push.
  - **Refusals.** It is refused as `unblock-refused` when the pull request is a fork (`fork`) or not open (`not-open`), when a run waits for a test runner that responds (`runner-responding`), or when nothing of the head can be lifted (`not-unavailable`); the code stays consumed. If the test runner comes back between SuiteWard's reading of the head and the command's effect, the command is tried again and reads `runner-responding`.
  - **Who can post it.** An agent cannot post it, because it needs the code. An adversary that makes runs unavailable gains nothing from it, which only you can post.

**The Receipt check.** For a receipt that applies, SuiteWard publishes a second check, `SuiteWard / Receipt`, once for each head. It is **never required**: the ruleset that the installer writes asks for `SuiteWard / Contract` and your test check, and nothing else. It is `in_progress` while the receipt is pending (`receipt-running`, or `receipt-not-responding` when the test runner has been silent for about 30 seconds), `failure` when an evaluated test `FAILS` or is `MISSING` or a changed test file does not parse, `neutral` when the receipt could not be produced, and `success` otherwise, an empty receipt included. It never depends on a mode. When a head that had a Receipt check stops having a receipt (the approved version moved, or the level went to `off`), one last `neutral` run says so. Its summary is public text: a title (`Receipt pending`, `Receipt waiting: test runner not responding`, `Receipt: failing or missing tests`, `Receipt ready`, `Receipt unavailable` or `No receipt for this revision`), what the state means, the installation type, and, for a receipt that finished, the counts in the words of the results comment (`Tests this change adds or edits: N.`, then a line for each of the states that says what it shows), the tests that SuiteWard cannot run, the changed test files that cannot be read, the lines to look at, and the sentence `What the test runner saw is evidence, not a verdict.` (every run but the last one of a head that no longer has a receipt, where nothing was observed). A receipt that could not be produced adds why, in words, and a sentence that you unblocked the head when you did. On the co-located tier it ends with the sentence that the protection is reduced. It has no repository text, no path, no test name and no link.

**The comments of a head.** SuiteWard posts up to three kinds of comment about the runs of a head. A comment is a new comment, never an edited one (the App has no permission to edit), it is written once for its head and its runs, and it holds counts and the general situation only: never a test name, a path, a package or any text of the repository or of the test runner. Each ends with the link `Details: pull request page` (below), with the note that it opens on the computer that runs SuiteWard; an instance with no `SUITEWARD_REPORT_BASE_URL` says instead that it has no web address, so the comment has no link, and that the checks of the commit carry the counts. They are written only where the approved `.suiteward.yml` names a profile and the levels are not both `off`, for an open pull request that is not from a fork, once the first contract exists. A repository with no profile gets none, since nothing runs there.

- **The results comment** is posted once every run that the head wants has ended: the canonical run, when `canonical` is not `off`, and the receipt, when `receipt` is not `off` and it applies. A run that is `unavailable`, or that you unblocked, has ended. A pull request with no protected change gets its comment from its canonical run. A pull request where no run is wanted (`canonical: off`, and no receipt that applies) gets none. A head that moves before its runs end gets none: its runs are cancelled, and the new head has its own. The comment says, in short sentences: whether the tests ran and whether something needs your attention; the approved tests (how many ran, passed, failed, gave no result, gave different results when they ran again and were skipped, and how many cannot be run and are not covered), or why they did not run; the tests that this change adds or edits, by what each shows (they fail before the change and pass now; they pass before and after, so they show nothing; they use code that the old code lacks; they fail with the change; they give no result; they give different results when run again; they are skipped) and the lines to look at; whether the receipt meets each kind of change, `fix`, `feature` and `refactor`, and for one that it does not meet, why; how many approved tests that this change edits now fail (the weakened tests, "A test that a change edits to accept a regression", below); that you unblocked the head, when you did; and the next step, which is the approve command, or to change the code or the tests and push, or the unblock command, or nothing. Where neither level is `required`, it adds that the results are for information and do not hold the pull request. It ends with the sentence that the results are what the test runner saw, evidence and not a verdict, and, on the co-located tier, the reduced-protection notice.
- **A second results comment after an approval.** When you approve, the head gets a new canonical run of the approved version of the tests, which is another set of runs. SuiteWard posts its comment unless both that set and the earlier one have nothing to say (no failing test, and no tests that did not run). A head that is clean before and after keeps one comment, and a later comment can correct an earlier one. A head whose first canonical run was cancelled because you approved first has only the later set, and that comment is always written.
- **After an upgrade or a long outage,** SuiteWard posts a results comment for every open pull request whose runs have ended, however long ago. Expect one burst of comments.
- **The not-responding comment** and **the runner-back comment** are described above, with the unblock ("When the test runner does not respond").

**The pull request page.** `http://127.0.0.1:<HTTP port>/pulls/<owner>/<repo>/<pull>` shows the situation of a pull request and the results of its current head (the last head recorded, for a pull request that is not open), rebuilt on every request from stored rows. The comments of a head link it, and so does the revision comment when the receipt applies. The old address `/receipts/<owner>/<repo>/<pull>`, which comments posted before this release link, answers `308` and sends the browser to the new one. In this order, the page shows:

- **The top:** the pull request, the repository, the commit (its short SHA and its full SHA), the commit of the base branch, the installation type, one sentence for the situation of the head (waiting for the test runner, not responding, not run, unblocked, or done), and, when there are some, how many weakened tests there are.
- **Situation:** one sentence for each wanted run that has something to say: the test runner is not responding (and how long ago SuiteWard last heard from it); the tests did not run, and why in words; the owner unblocked the commit (and that SuiteWard had stopped waiting for the test runner, when the unblock ended the wait); or the test runner is responding again after an unblock.
- **Tests by state:** a table with a row for each state (`PASS`, `FAIL`, `SKIPPED`, `MISSING`, `FLAKY`, `EXCLUDED`, `DETECTS`, `INERT`, `NEW API`, `FAILS`), a sentence that says what the state means, and how many tests are in it in the approved tests and in the tests of this change. Below it: the tests that SuiteWard cannot run, the lines to look at and the changed test files that cannot be read.
- **Approved tests** (the canonical run) and **Tests this change adds or edits** (the receipt): a table for each, with the columns State, Test, Package, File, Reason and Note. The Reason is a fixed sentence for each flagged test, one in the state `FAIL`, `FAILS`, `MISSING`, `FLAKY`, `NEW API` or `INERT` (an excluded test shows the reason that is stored for it). It is made from the state and the stored result of each run (passed, failed, did not build, skipped, gave no result), for example `The test failed or did not finish.` or `The code did not build, so the test could not run.` No output of a test is stored or shown, so a timeout and a result that contradicts the exit status both read as `failed or did not finish`. The Note marks a weakened test (`Weakened: this change edits this test.` in the approved tests, `Weakened: the approved version of this test fails on this commit.` in the tests of this change). The receipt part also lists the changed files, the files that are not evaluated because their pattern is not approved yet, the skipped submodules and the lines to look at. A test name is shown escaped.
- **The kinds of change:** a table with `fix`, `feature` and `refactor`, each `Met` or `Not met`, and for a kind that is not met the reason in words (for example `No test fails without the change, so none shows that it fixes something.`). Under it, the preview mode: it is only a preview, and no check and no approval reads it.
- **How these results were made:** the evidence of each run: the approved version of the tests that governed it (the governing manifest and its source), the levels, the profile, the version of the test runner and the fingerprint of its program, the name and version of the container program, the fingerprint of the image, the times, and the attempts of a run that was tried again. A run that was created already final, or ended at the GitHub bound, has no such evidence: the page shows it as `not run` with its reason.
- **Change report:** the summary lines of the current revision's report, a table of its changed files (status, file, lines) without the changed lines, a link to the full report of the revision (`/reports/<owner>/<repo>/P<n>-R<m>`, which keeps the changed lines), and links to the reports of the earlier revisions of the proposal. When the report cannot be built (no stored files of the revision, a file missing from the store, or a revision too large), one sentence says so, and the rest of the page is built.
- **The closing sentences:** that the results are evidence reported by a test runner and not a verdict, and, on the co-located tier, the reduced-protection notice.

The page has the rules of the change report page: it opens on the machine that runs the instance, only a loopback `Host` is answered, and anyone who can reach the HTTP port can read it. A pull request with no run yet shows `No execution results for this pull request yet.`, and one whose revision changes no file that the approved patterns match says that it has no receipt. A pull request that SuiteWard has not seen, or a repository that is not enrolled, answers `404`. A page that cannot be built answers `503`.

**The size of the page.** Every part of the page has a budget, counted in the bytes that are written, so that a pull request with two runs of 10,000 tests never makes the page too large: 3 MiB for each table of tests, 1 MiB for the table of changed files and 2 MiB for the rest. A table writes its rows in order of importance, the weakened tests first, then the flagged ones, then the rest. The rows that do not fit are counted in one sentence (`N more tests are not shown here. The counts above include them.`) and are not named. The counts and the sentences are always complete. The page has a cap of 12 MiB, which the budgets keep out of reach, and it answers `503` and not `413` if it were ever passed. The page has no changed lines for that reason too: they stay on the report page of the revision, which keeps its own `413` for a revision whose files would take more than 32 MiB to read.

**Evidence, not a verdict.** A result says what one executor observed when it ran the tests on one head. SuiteWard says so in the checks, in the comments and on the page. It never approves anything, never enters the approval's binding and never replaces your review. A forged or flawed result can lift a `required` gate, flatter an advisory result, hold a check that should pass (a failing result for a head that passes) or make a `required` receipt refuse an approve. It cannot approve or consent for you, because the code and the exact-revision approval do not change. On the co-located tier the executor is next to the agent, so this is the stated reduced assurance ("Limits of canonical execution", below).

**When a run is unavailable.** A run that cannot be completed is `unavailable` with one reason, never a pass: the canonical gate and a `required` receipt read it as "not complete" unless you unblock it. The pull request page, the results comment and the Receipt check's summary name the reason, in words. What to do:

| Reason | What happened | What to do |
| --- | --- | --- |
| `no-executor` | No executor asked the service for a job for 2 minutes (`SUITEWARD_EXECUTOR_LEASE_WAIT`), or the owner unblocked a run that waited for a test runner that did not respond (the unblock ends it with this reason). It is final for that job. A fresh job replaces it once an executor is seen again, unless the owner unblocked it: an unblocked job stays, and the next push runs the tests. | Start the executor; `suiteward doctor` says why it is not running (sections 5.4 and 10). |
| `executor-not-configured` | The service has no executor token. A fresh job replaces it once one is configured. | Install or upgrade so that the service has the token (sections 5.4 and 10). |
| `executor-error`, `sandbox-unavailable`, `archive-unavailable`, `lease-expired`, `timeout`, `fetch-failed` | The attempt failed on the executor's side, or a module could not be fetched from `proxy.golang.org`. The job is queued again, up to 3 failed attempts (a pause of 30 seconds, then 2 minutes), and then it is final for that job. | Read the executor's log. `timeout` is an attempt that passed `SUITEWARD_EXECUTOR_JOB_TIMEOUT`. A private module that is not vendored can only read `fetch-failed`. |
| `github-unavailable` | GitHub could not be read for the job (its tree, the merge base, an archive, the request budget). It consumes no attempt, and the read is tried again each minute for up to 30 minutes (`SUITEWARD_EXECUTOR_GITHUB_WAIT`), and then it is final for that job. | Wait; see the budget in `/status` (section 15). |
| `install-failed` | The dependencies were refused before any fetch: a `go.mod` or `go.sum` that does not parse, a module path or version that fails validation, a `replace` to a directory outside the tree, or too many modules or bytes. Final for the head. | Fix the module files. |
| `toolchain-mismatch` | A side's `go.mod` needs a newer Go than the pinned image. Final for the head. | Lower the `go` or `toolchain` line, or wait for a release with a newer image. |
| `source-mismatch` | The source check failed: a file is missing, extra or different from the commit's tree, a symbolic link is unsafe, a name aliases another (below), or a path holds a control or invisible character. Final for the head. | Fix the tree; see "Limits of canonical execution" for the names that are refused. |
| `too-large` | An archive, a tree, a declaration, a result, or the tree and modules together passed a limit. Final for the head. | Reduce the repository; the limits are below. |
| `resource-limit` | The sandbox was killed by its memory limit, or exited with status 137 that the executor did not cause, or one invocation's output passed 64 MiB. Final for the head. | Read the cause before you unblock it: a candidate can cause it, for example with a test that hogs memory. |
| `profile-unsupported` | The job names a profile or an image that this executor does not have: the service and the executor are of different releases. Final for the head. | Upgrade both (section 11). |
| `no-merge-base` | GitHub has no merge base for the head and the base branch. Final for that head. | Push again, or rebase onto the base branch. |

After a final outcome, a new head makes a new job, and you can lift the head with `/suiteward unblock`.

**When the test runner does not respond.** SuiteWard sees the test runner when it asks for a job, sends a heartbeat (about every 10 seconds while it runs a job) or posts a result. A head *reads not responding* when no test runner has been seen for about 30 seconds and a run that the head wants waits for one: a run that is leased, or pending for a reason other than a failing GitHub read. The 30 seconds are fixed and are not a setting. The checks job reads them every 30 seconds, so a head reads not responding 30 to 60 seconds after the last sign of the test runner. A routine restart of the test runner stays well below that: it takes about 5 seconds on Linux and, in this release, on Windows, and at most about 10 on macOS. This is a problem only if it lasts. SuiteWard keeps trying, and the runs start when the test runner answers.

- **The Contract check,** under `canonical: required` and only where it would otherwise pass, says `canonical-not-responding` ("Test runner not responding") in place of `canonical-pending`, and offers the unblock. Under `advisory` it does not change.
- **The Receipt check** says `receipt-not-responding` ("Receipt waiting: test runner not responding") in place of `receipt-running`. It is never required, so it offers the unblock only where the receipt gate would refuse an approve (`required`, or `before-approval` while the receipt is not complete).
- **A comment.** SuiteWard posts one comment, **The test runner is not responding.**, once for each set of waiting runs: it says that the tests of the commit are waiting and that SuiteWard has not heard from the test runner for about half a minute, that this is a problem only if it lasts, to check that the test runner runs on the machine that runs SuiteWard, and that SuiteWard stops waiting after a while. It offers the unblock where a gate holds. A test runner that goes quiet twice during one set of runs gets one comment, so that a runner that flaps cannot fill the pull request. Like every comment of a head, it has a link to the pull request page (below).
- **The pull request page** says the same, with how long ago SuiteWard last heard from the test runner.
- **At the lease wait** (2 minutes without a test runner, `SUITEWARD_EXECUTOR_LEASE_WAIT`), the waiting runs that are pending end as `unavailable` (`no-executor`), as before. No second not-responding comment is posted for them: the results comment says that the tests did not run and why.
- **The service and the test runner must be of one release.** A test runner of an earlier release backs off for up to 60 seconds after an error, so next to this release's service a head can read not responding after such an error.

**What runs: the Go profile.**

- **Which tests.** The top-level functions `func TestXxx(t *testing.T)`, of the files that match the sandbox's build context (linux, the sandbox's architecture, cgo off, no extra tags, and the release tags of the executor's Go). `TestMain`, benchmarks, fuzz targets and examples are not tests here. A declared test that the profile cannot run is `EXCLUDED`, decided before any run, listed with its reason and never counted as a pass: a file that a build constraint leaves out (`//go:build integration`, a name such as `_windows_test.go`), or a file in a directory under a nested `go.mod` that the repository protects, which the root invocation cannot run (the rule is under "What the source check refuses", below). **Canonical assurance does not cover excluded tests,** and the page says how many there are. Integration tests that need a service such as PostgreSQL are outside this release.
- **How.** The sandbox runs `go test -json -count=1 -shuffle=on -run '^(Name1|Name2)$' <package>` (chunked when the list is long) with `-timeout` of 600 seconds, a fresh `HOME`, no CI variables, `GOTOOLCHAIN=local`, `GOWORK=off`, `GOFLAGS` empty, `GOSUMDB=off` and `GOPROXY` pointing at the prefetched files. The report is cross-checked with the exit status of the process: when they contradict each other (a non-zero exit with no failing test in the report, or a zero exit with one), every expected test of that invocation reads `fail`.
- **Dependencies.** A side that has `go 1.14` or later in its `go.mod` and a `vendor/modules.txt` uses `vendor/`, and nothing is fetched. Otherwise the executor fetches the modules that the side's `go.sum` names from `proxy.golang.org` (at most 2000 modules and 512 MiB), after it validates every module path and version, and gives them to the sandbox with the source. A `replace` to a directory inside the tree needs no fetch, and one outside the tree fails. The bytes are as safe as TLS to the proxy and the candidate's `go.sum`, which is what a networked install would give, and not more. **Private modules work only when vendored.**
- **The sandbox.** Every run gets disposable containers from one image pinned by digest, with **no network at all**, a read-only root, a work directory in memory of 1 GiB, all capabilities dropped, `no-new-privileges`, user 65534, the limits `--memory 3g --memory-swap 3g --cpus 4 --pids-limit 512`, and `--log-driver=none` (on both engines, so that the runtime keeps no copy of the container's output on the host: Docker on Linux would keep an unbounded one; the executor still reads the output through the attached command). The sandbox holds no secret. A runtime that cannot honor one of the properties makes the run `unavailable`; a weaker sandbox is never used.
- **Markers.** For a receipt, SuiteWard flags test-aware code in the non-test files that differ between the base and the head, as lines to look at and never a verdict: `testing` imported outside a test file, `testing.Testing()`, `flag.Lookup("test.`, an exit inside `init` (also `syscall.Exit` and an exit in a package-level initializer), reads of `_test.go` paths, reads of the `TESTING` or `CI` variables, and a `\x16` byte in a string literal (the framing that `go test` uses for its events).

### Limits of canonical execution

Read these before you rely on a result, and before you choose `required`.

**What the evidence is worth.**

- **Code that behaves differently under test cannot be ruled out.** A test run in a sandbox says nothing about what the same code does elsewhere. Two layers help and prove nothing: the report is cross-checked with the exit status, and the markers above flag test-aware code. A marker is a signal, never a verdict.
- **Test events can be forged, and only the markers say so.** A non-test file's `init` (or a package-level initializer, or `syscall.Exit`) can print `go test`'s event frames and exit with status 0, which forges a pass with no contradiction between the report and the exit status. The markers `exit-in-init` and `forged-event` are the only signal, they belong to the receipt (the canonical plan has no base commit), and they miss code that the scanner cannot see: dot-importing `os`, `flag` or `testing` (`import . "os"`) hides the calls from them.
- **The co-located tier has reduced assurance.** The executor is a process of the agent's own user, so the agent can read its token and its files, report what it likes and run as the user that owns the sandbox. What `doctor` pins (the copy of the program and its pin, the image's digest) catches drift and accident, not a determined agent. The isolated tier runs the executor under its own account, which the agent never reaches, with a binary whose pin is the release's line of `SHA256SUMS`, which the host step requires and checks (`doctor` compares the binary with the pin and checks that the pin names a release asset; it never reads the file).
- **A result is evidence, not authority.** A forged result can lift a `required` gate, flatter advisory evidence, hold a check or make a `required` receipt refuse an approve. It cannot approve or consent. The executor's version, binary hash and image digest are what the executor reports, as trustworthy as the executor.
- **The sandbox's limits depend on the host.** A runtime that cannot honor a limit makes the run `unavailable`, but rootless Podman on a host with cgroup v1 can ignore the limits with only a warning. AlmaLinux 9, the isolated tier's host, uses cgroup v2, so the risk is residual there.
- **`DETECTS` does not prove the reason.** It means that the test failed on the base side, not that it fails for the reason that this change fixes.
- **A test that a change edits to accept a regression.** Say a change breaks the code and edits an approved test to accept the wrong result. The edited test passes on the head and fails on the base side, so the receipt reads it `DETECTS` and can meet `fix` and `feature`: it does tell the head from the base, and that is all `DETECTS` says. SuiteWard points this out. An approved test that the change edits, and that fails in its approved version, is a **weakened** test (it fails, is missing or is flaky, on the same head and under the same approved version of the tests). What shows it to you:
  - the pull request page marks each weakened test in both tables (`Weakened: this change edits this test.`) and says how many there are at its top, under every level;
  - the results comment states how many there are, under every level (`1 approved test that this change edits fails, is missing or is flaky on this commit, in the version that was approved. A test that is edited can pass by checking less. Read the edit before you approve.`, and the same for N tests), and says that the page names them;
  - under `canonical: required`, the Contract check of the head that awaits your approval states the same count in place of its general sentence (`At least one approved test fails, is missing or is flaky on this commit. If this change edits that test, read the edit before you approve. …`), which stays when the count is 0 or unknown, because it is still true;
  - the marker line of the change, such as `removed assertion line` (a line to look at, never a verdict), and the change report that the revision comment links.

  The count needs both runs, the canonical run and the receipt, to be complete, and it does not change when you approve, because it is read from the run of the version that was approved, not from the run that follows your approval. When either run is off, missing or not complete, the count is unknown, and the signal is not stated: it is never stated as an absence of weakened tests. The Receipt check never states it, and the Contract check under `canonical: advisory` does not change. A comment and a check name no test; the page does. A fresh receipt job that replaces an unavailable one later does not rewrite the check: the comment of the new jobs and the page carry the new count.

  With `canonical: off` nothing runs the approved version, so only the marker line and the change report are left. At no level does the failing run hold the head back: before you approve, the head waits for your approval anyway, and once you approve, the approved version is the edited one and the canonical run passes. Read the change of every edited test before you approve.
- **`NEW API` covers a whole package.** A test that needs a new dependency, or a symbol that only the head's non-test source has, does not build on the base. In Go a build failure belongs to a package, so every evaluated test of that package reads `NEW API`.
- **Two tests of one name read as one.** An internal and an external test package of one directory that both declare a test of one name are reported once, with the worst observation of the two, because `go test -run` selects by name alone.
- **Excluded tests are not covered,** and the tests of a nested module that the repository protects are among them (a nested module that it does not protect excludes nothing; see "What the source check refuses").
- **Not stronger than a networked install.** The dependencies are as safe as TLS and the candidate's `go.sum`. A module that the proxy cannot give, a private one included, cannot be tested unless it is vendored.

**What the source check refuses, and when it is wrong.**

- **Names that alias another are refused, also when no alias exists.** Any name that holds `~` followed by a digit (`file.go.~1~`, `report~2024.txt`: the shape of a Windows short name), two names that are equal but for case (`Docs/` and `docs/`, `README` and `readme`, a file and a directory of one such name; the comparison upper-cases first, so a dotless `ı` and `i` collide too) and a name with a trailing dot or space make the run `unavailable` with `source-mismatch`, final for that head. The sandbox is Linux and could hold them apart, but the refusal is deliberate defence in depth. **When such a name is in the governing manifest, every canonical run reads unavailable** until a governed change renames it.
- **A directory name with `...`** acts as a package wildcard when `go` reads it.
- **A directory with its own `go.mod`** (a nested module) is not run when the repository protects that `go.mod`: the root invocation cannot name its packages, so its tests are `EXCLUDED`. The root `go.mod` is never a nested module. A pull request must not silence an approved test by adding a `go.mod` over its directory, so a `go.mod` that the head adds excludes nothing:
  - **In the canonical run,** only a `go.mod` that the governing manifest lists makes a nested module. A `go.mod` that the head adds excludes nothing, in one of two ways. The canonical run lays the manifest over the head and removes the head files that the manifest lacks and that the governing scope covers, so a head `go.mod` at a covered path is gone and the approved tests run as usual. One at a path that the scope does not cover stays: `go` cannot resolve the package of the manifest's tests under it, and they read `FAIL` (an approved test that cannot build blocks `canonical: required`). A repository with a real nested module protects its `go.mod`: cover it with an `include` or a `runner` pattern.
  - **In the receipt,** only a `go.mod` of the head that is protected makes one: the merge base has a `go.mod` at that path, or the canonical version that the revision expects lists it, or the approved patterns of that canonical cover its path (a pattern that only the head adds to its own declaration counts for nothing). Under any other `go.mod` of the head, a test of the pull request runs, `go` cannot resolve its package, and it reads `FAILS`. A nested module that the base has and the head removed is no module of the head: its tests run on the head, and on the base side, where it still is a module, `go` cannot resolve the package, so a test that passes on the head reads `NEW API` (and not `MISSING`).
  - **A package that `go` cannot resolve** (a directory under another module, which `go` names by its `./dir` pattern and not by an import path) reads `build-error`, as a package that does not build does (the test then reads `FAIL`, and the page shows the state of a test and not the reason), and `go` runs the other packages of the invocation.
- **A module whose zip directory is over 4 MiB** (tens of thousands of files) reads `too-large`.
- **Release tags come from the executor's Go.** A file with `//go:build go1.99` is in or out by the Go that the executor was built with, which is the pinned image's.
- **The other limits** are fixed in the contract: a commit with more than 50,000 tree entries, a declaration over 1 MiB, a lease answer over 16 MiB, an archive over 256 MiB, a listed file over 8 MiB, a result over 4 MiB, and an unpacked tree and modules over half of the 1 GiB work directory (512 MiB) are each `too-large`, final for the head. The other half is left to the build cache: a build cache that fills it still reads as a build error.

**Cost and time.**

- **The same archive is downloaded many times.** Each container recomposes its tar, so a receipt downloads about 7 archives through the service, up to about 13 with reruns, and a canonical job reads each manifest file again for each container. Each container also fetches its modules from `proxy.golang.org` again. All this counts in the GitHub request budget and in the pacing of the synchronization. A cache is later work (D-EXECUTION-LATER in the [decision register](plan/decisions.md#open)).
- **A candidate can burn three times the job timeout.** A test binary that outlasts `go test`'s own kill (a minute past `-timeout`) keeps the attempt running until `SUITEWARD_EXECUTOR_JOB_TIMEOUT` ends it as `timeout`, which is counted and retried, up to 3 failed attempts: up to 3 times the job timeout of executor time before the job is final.
- **A test that hangs on every run ends the attempt as `timeout`, not as `fail`.** A failing test is run again on its side, twice (section 9), and each run of a hung test lasts up to its `-timeout` of 10 minutes (a minute more when `go test` has to kill the binary) after a cold build. At the default job timeout of 30 minutes the three runs pass the executor's drop, 30 seconds before the deadline, so the attempt ends as `timeout`: counted and retried, up to 3 failed attempts, and then the job is `unavailable` (`timeout`). That fails closed: a `required` gate waits, and the owner can unblock the head, so read why the job is unavailable before you do, because a candidate's hung test is the usual cause. The floor of the setting (12m30s) makes the first run of a hung test end as `go test`'s own kill; it does not cover the reruns.
- **The pull request page is built on every request.** It reads the stored result and the test rows of each run, and, for a head that the owner approved, the canonical run of the approved version again, to find the weakened tests, so a page of two runs of thousands of tests costs those reads. A page has size budgets (below, "The pull request page"), and one that a correct build cannot reach is never refused for its size.
- **A pull request that is retargeted keeps its receipt.** The merge base is read when the receipt job is created, so a pull request moved to another base branch keeps its head's receipt until a new push.
- **Every open pull request costs a read.** Even with both levels `off`, the checks job reads the Receipt check record of each open pull request of the repository on every run, to find a published check to withdraw.
- **A ready head reads its revision's manifest on every run.** Before it creates the canonical job that the revision governs, the checks job reads that revision's manifest from the content store: one read for each ready head in each pass, whether or not a job exists.
- **Results are not pruned.** No stored result or test row is deleted in this release.

**What waits, and what looks stuck.**

- **A lost executor blocks `required`.** With `canonical: required` or `receipt: required`, no executor makes every head read not responding after about 30 seconds and then `unavailable` after the lease wait (2 minutes), and each head needs its own `/suiteward unblock` until the executor is back. The owner can give it from the moment a head reads not responding. A head that was unblocked does not run when the executor comes back: its next push does.
- **A job that cannot be leased jams the queue.** The service leases the oldest job first, and a job whose governing manifest is missing from the content store, or whose repository is unknown, makes every lease answer 500 until it is fixed: no job of the instance runs meanwhile. The checks job keeps the manifest of the current canonical in the content store on every run of a project whose policy is not `(off, off)`, and writes a revision's manifest when it records the revision, so a missing object of a canonical is put back by the next run (a canonical that a bootstrap or an upgrade promoted has no revision of its own, and this is how its manifest gets into the store). It plans no canonical job for a revision whose manifest the store lacks (a revision recorded before M1.13, or an object that was lost): the step of that pull request fails (`/status` problem `failed`) and its check is held. What can still jam the queue is a job that already exists, governed by a revision, whose manifest object was lost afterwards. The service logs the failed lease at Error level and names the job (`read the manifest <digest> of job <id>`): put the object back (a backup holds the artifact volume), or push a new head, or close the pull request: either cancels that job (`head-moved`, `closed`) on the next run of the checks job. A repository that is unknown to the service cannot happen in a healthy instance, because it is never deleted.
- **A manifest that cannot be stored holds every head of the project.** When the checks job cannot put the canonical's manifest in the content store, its run fails (`prepare the execution of the project: …` in the log), plans no job and cancels none as unwanted for an open head (the jobs of closed pull requests and of heads that moved are still cancelled), and decides no new success: every open pull request of that project keeps its stored check, or reads `assessment-pending`, until a run can store it.
- **A slow first job can fail the next one falsely.** The 15-second deadline for the tree reads is shared by every job that one lease prepares, so a slow or too-large first job can leave the next a second and record a false GitHub failure on it. The lease then answers 502, no attempt is counted, and the job is tried again within a minute.
- **A token but no GitHub settings.** The service serves the executor API and its leases answer 502, so the jobs end `github-unavailable` once the GitHub wait has passed.
- **A wrong executor token** makes every lease request answer 401. The executor backs off to 20 seconds, for ever, and logs it; the service sees no executor, so the heads read not responding after about 30 seconds, and the runs read `no-executor` after the lease wait.
- **A download that fails with 401, 503 (the service is stopping) or a network error** reads `archive-unavailable` and counts an attempt. A container that cannot be removed after a run reads `sandbox-unavailable`, and is retried.
- **A clock skew moves the executor's deadline.** The executor drops a job 30 seconds before the deadline the service gave it, by its own clock. A skew of 30 seconds or more between the two moves that drop. Both run on one machine on both tiers.
- **A result that the service does not take is sent again only until its lease ends.** While the service answers 503 or does not answer, the executor sends the same result again, after a pause of 5 seconds that doubles up to 10, until the attempt is dropped (30 seconds before its deadline) or the 30 seconds after a stop signal are over. Its heartbeats stop before the first post, and a lease lasts 60 seconds from the last one, so a service that comes back after about a minute answers the resend with `lease-lost`: the result is discarded and the attempt is lost, as if the executor had died. Failures of the connection other than a certificate that cannot be verified, a failed TLS handshake included, are sent again too, until that same limit; it does no harm, because the service knows the same body by its digest. A certificate failure is not sent again.
- **A failing check can flip while the executions store cannot be read.** When the checks job cannot decide a head (GitHub could not be read, say), it keeps the head's stored check, and reads the counts of a stored `canonical-failing` check, or of a `success` under `canonical: required`, from the store again. A `canonical-failing` check whose counts cannot be read says `in_progress` (`assessment-pending`) instead, and goes back to failing on the next run that decides the head: two more check runs on GitHub, and it fails closed. A kept `success` whose counts cannot be read, or no longer fit a success (a failing, missing or flaky test), goes out without them.
- **An approval that is missing can be written without its counts or its mode.** Under `canonical: required`, the check of a head that awaits approval is written again with the counts once every run that the head wants has ended. A message that SuiteWard writes while it cannot read the counts or the policy (a lost message sent again, or, more rarely, a change of reference on the same head) goes out without the counts, and they come back with the next job of that head. The pull request page has them at any time. A message written while the policy cannot be read also shows the approve with no mode. Under `receipt: required`, use the command of the revision comment, which names the mode: an approve with no mode is refused (`mode-required`) when the receipt is complete and not empty, and its code is used up.
- **Windows has no stop grace, and a stop ends the whole tree:** a job in flight ends as `lease-expired`. The executor's log is not rotated on Windows and macOS (section 5.4).

**Two instances on one computer.**

- **The backup of a second instance without `--token-file` lands in the main instance's `backups` folder.** `backup` does not refuse: the default folder is beside the default token file. The file has its own date and time and nothing is overwritten, but the main instance's folder then holds a backup of another instance. Give `--token-file`, or `--to` (section 5, "One more instance on the same PC").
- **On Docker, the install asks you to type `yes` before it refuses.** `--runtime docker` is confirmed in the first step, and the refusal of a settings file of its own without `--token-file` comes after it (pass `--accept-docker` to answer it). Nothing is changed by either.
- **On Windows, a main instance whose `run.cmd` or `task.xml` you deleted by hand reads as belonging to another instance.** The task of this user is known as this instance's only through those two files, so `install` and `doctor` treat it as another instance's test runner (`doctor` says `The test runner on this computer belongs to another instance`). Remove the task first, and end what still runs, because a program that runs cannot be replaced on Windows and an install that finds no task of its own does not stop one: `schtasks /End /TN "SuiteWard Executor"`, then `schtasks /Delete /TN "SuiteWard Executor" /F`, then sign out of Windows and sign in again, which ends the script and the program that the task started (the installer never ends a program by its name, because the script would start it again after its pause and a name would also end another instance's executor). Then run `suiteward install` again.

**The proxy variables.** The executor's own HTTP clients never honor `HTTP_PROXY` and its relatives: its egress is direct, and an allow-list (`proxy.golang.org` and the `storage.googleapis.com` that it redirects zips to) is the control. The container runtime's command keeps them, for the pull of an image.

**Validation.** What has run on a real machine, and what has not. Expect rough edges where it has not.

- **Seen, co-located on Windows** (Docker Desktop, a development build, a real GitHub App and a throwaway repository), through seven pull requests:
  - a fix whose new test the receipt reads `DETECTS`, with the mode `fix` met, the Receipt check, the line of the revision comment and the page;
  - a test that protects nothing, read `INERT`, with the preview `mode` and an approve that the receipt gate refused;
  - a change that breaks an approved test, which the Contract check reports as `canonical-failing`;
  - a test that a change edits to accept the wrong result (the limit "A test that a change edits to accept a regression", above);
  - an exit inside `init`: the approved tests read `MISSING` and the check failed. No marker was shown, because a pull request that changes no test has no receipt, and the markers belong to the receipt;
  - a `go.mod` that the head adds in a folder of its own: the tests read `FAIL` and not `EXCLUDED`, as owner decision 16 says (the page shows the state of a test and not the reason);
  - a stopped executor: the Contract check read `canonical-unavailable`, and `/suiteward unblock` let that head pass.
- **Also seen there:** the executor with no window; its restart about a minute after its process was killed (the script waited a minute then; it waits about 5 seconds now, which has not been seen on a real machine yet); an upgrade that stopped the running executor's whole tree by itself, started the new one and moved the database to version 22 with its data kept; and the purge.

That sums file does not exercise the pin of a signed release.
- **Seen on the published `v0.5.0-alpha.1`, isolated, on a throwaway AlmaLinux 9.8 distro** (WSL, 2026-10-28, a throwaway repository):

### Correcting the canonical

A correction puts an earlier version's protected files back, for example the previous version's.
- **How:** open a pull request whose protected files equal that earlier version's exactly, for example a revert of the last protected merge. Approve its revision like any other, and merge it.
- **What you see:** SuiteWard promotes a new version that holds those files, and its comment says that it is a correction of the current version.
- **What is kept:** the corrected version stays. SuiteWard erases no version ([ADR 0018](decisions/0018-corrective-pr-rollback-and-audit-history.md)).
- **Anything else:** protected files that match no earlier version exactly make an ordinary promotion, not a correction.

### Stop protecting a repository

A repository stays enrolled until setup runs again without it. While it is enrolled but missing from the configuration, SuiteWard skips it: nothing is synchronized or checked there, and the commands of the other repositories keep working. A command it had already observed there can still be decided, and its reply may fail. `/status` and the MCP `status` tool name it in `unconfiguredRepositories`, and the log warns once. Deleting the repository on GitHub has the same effect.
1. Remove the repository from the list: run `suiteward install --github-repositories '<owner/name>,<owner/name>'` with the repositories you keep (on an isolated host, as `suiteward` in the shell of step 10.3, with `--tier isolated`). The installer verifies the App again, asks the test checks again and writes the rulesets. It skips setup, because an owner is enrolled. A running service keeps the settings it started with, so on an isolated host restart it afterwards with `systemctl --user restart suiteward.service`.
2. Enroll again (section 6, "Enroll again") with one `--test-check` for each repository you keep: `suiteward enroll --test-check '<owner/name>=<check name>' ...` (on an isolated host, with `--tier isolated`). Setup replaces the TOTP secret, so delete the entry of this instance from your authenticator app before you scan the new one (the entry with this exact name, `<tier> <instance>` included; entries of other instances stay), then add the new entry. An entry named only `SuiteWard:<login>` predates this release: delete it once the new entry's code is accepted.
3. Comment your command again. A command written before the new setup is ignored and gets no reply.

SuiteWard changes nothing on GitHub: remove the App from the repository, and the ruleset rule that requires `SuiteWard / Contract`, yourself.

## 10. Running on a separate host (operators)

This installs the isolated tier (section 2): SuiteWard on a separate host that your coding agent cannot reach, for whoever self-hosts on a machine the agent cannot reach. It gives the full assurance. The host runs AlmaLinux 9 and Podman 5.5 or later, rootless, for an unprivileged account that this guide calls `suiteward`. Only Podman is supported here.

The install is split by privilege, and the installer never runs as root. `sudo /usr/local/bin/suiteward install host --sha256sums <the verified SHA256SUMS>` does the administrator steps once. `suiteward install --tier isolated`, run as the account `suiteward`, does the rest, with the same GitHub flow as the co-located tier. Each step below says who runs it.

The host runs three container units: `suiteward-db` is PostgreSQL, `suiteward-migrate` is a one-shot `suiteward migrate` that runs as the database owner, and `suiteward` is the service, which requires the migration and connects as the least-privilege role `suiteward_app`. Starting the service always migrates first. The **executor**, which runs the tests, is not one of the three: it is a process of a second account, `suiteward-exec`, under its own rootless Podman, which the administrator's step makes (10.2) and the service account never reaches. The service reads its token from a Podman secret and serves it the jobs.

**10.1 Get the installer onto the host (as the administrator).** Verify the binary on your PC and copy it to the host as section 4 says: `sha256sum --check --ignore-missing SHA256SUMS`, then a copy at `/usr/local/bin/suiteward`. **Keep the verified `SHA256SUMS` on the host:** step 10.2 needs it, as `--sha256sums <path>`, to set up the executor. It is the release's own file (a release asset, next to the binaries, section 4.2), and it is trustworthy only after you verified it on your PC with `verify-release.ps1 -Blob` and its `SHA256SUMS.sigstore.json`, and compared the `SHA256SUMS sha256: <hex>` line that script printed with `sha256sum SHA256SUMS` on the host (section 4.2 and [the host runbook](../deploy/HOST.md) show the commands). A file that nobody verified would make the pin of the executor's binary no better than the binary.

**10.2 Prepare the host (as the administrator).** Run it with the verified `SHA256SUMS` of the release (10.1):

```
sudo /usr/local/bin/suiteward install host --sha256sums <path to the verified SHA256SUMS>
```

Write the full path after `sudo`. On AlmaLinux 9, `sudo` looks for a program only in its own list of folders, and that list does not include `/usr/local/bin`, so `sudo suiteward install host …` stops with `sudo: suiteward: command not found`. Use the path where you put the program in 10.1. The installer names the program by the path it runs from in every command it prints.

The step needs the file, because the executor's binary is pinned by the release's line of it (item 4): give `--sha256sums`, or, on a terminal, answer the question `Where is the release's SHA256SUMS file?`. With no terminal (a script, an agent) and no flag, or with an empty value, it refuses (a usage error, exit 2) and changes nothing; it also refuses, before any step, a program that the file does not list exactly once as a Linux binary. The step asks before it changes anything that you did not ask for, except the executor's own steps (item 4), and does these in this order:

1. **Podman.** It checks that Podman runs, is 5.5 or later, and has the fix for CVE-2026-57231. A distribution can backport that fix without changing the version, so it reads the package changelog. If something is missing, it asks before it runs `dnf install -y podman` or `dnf upgrade -y podman` (`--yes` answers yes). It refuses to go on when the fix is still missing: do not run SuiteWard on that host.
2. **The accounts.** First it writes the drop-in `/etc/systemd/system/user@.service.d/delegate.conf` (`Delegate=cpu cpuset io memory pids`), which gives the user managers the cgroup controllers that the sandboxes' limits need (EL9 gives a manager only `memory` and `pids`, and `podman run --cpus` fails without `cpu`), and has systemd read it. It does this before any account lingers, because restarting a user manager stops its containers. Then, for `suiteward` (the service) and `suiteward-exec` (the executor), it creates the account with no login shell if it does not exist, gives it subordinate user and group id ranges that no other account uses (two rootless Podmans must not share a user namespace), and enables linger, so the account's services start at boot and run without a login. It starts the executor account's user manager and checks that it has the `cpu` controller; a manager that was already up without it is restarted (it holds no container of the stack, and the service account's manager never is), and the step stops when it still lacks it after that. It then waits, up to 60 seconds, until that manager answers on its bus, because a manager that was just started or restarted does not answer at once. If it does not answer, the step stops and names the `journalctl` command that shows why; run the step again after you fix the cause.
3. **The metadata rule.** On a host where the cloud instance metadata address `169.254.169.254` answers, it asks whether to add the nftables rule that refuses that address for the `suiteward` account (`--metadata-rule yes` or `no`). The metadata service hands out the instance's credentials, and rootless containers connect as a process of the service account, so a rule for that account covers them. The rule loads at every boot, through the unit `suiteward-imds-block.service`, and covers IPv4 only. It never adds the rule without a yes. When nothing answers at that address, it says so and adds nothing. `suiteward doctor` reports an unrefused address.
4. **The executor.** The executor is a native process, `suiteward execute`, of the account `suiteward-exec`: it runs candidate code in disposable sandboxes through that account's own rootless Podman. It holds one credential, its token. This step does not ask about any of the following, because the executor runs what a pull request brings:
   - **The rule that refuses it the metadata addresses.** An nftables table `suiteward_exec` (`/etc/suiteward/exec-block.nft`, loaded at every boot by `suiteward-exec-block.service`) rejects `169.254.169.254` and `fd00:ec2::254` for the uid of `suiteward-exec`, by destination and on every port, which covers its containers too (rootless networking makes their connections from a process of that account). It is installed whether or not anything answers at those addresses, and `doctor` checks the file and its unit.
   - **The Go image.** It pulls the pinned Go image of the sandboxes into the rootless storage of `suiteward-exec`, through that account's user manager, and checks that it is there under its digest. The step reaches that account's user manager as the account itself, with `runuser`, and not through `systemd-run --machine`: without a terminal, that command fails on AlmaLinux 9 with SELinux enforcing (found on the AWS host). Every sandbox starts with `--pull=never`, so an account without the image would end every job as unavailable, and no other account can read that storage, which is why the administrator's step does it. It runs at every host step, because a release can name a new image.
   - **The token,** `/etc/suiteward/executor-token`: 32 random bytes as hex, mode 0400, owned by `suiteward-exec`, written once and never replaced by a later run. When the administrator removes it, the next run makes a new one and restarts a running executor, and `install --upgrade` at the installed release gives the service the new token (section 11).
   - **The binary.** A root-owned copy of this program at `/usr/local/libexec/suiteward/suiteward-executor`, in a directory that only root writes, so the executor cannot change it, with its pin `executor.pin` beside it. This program must be listed exactly once, as a Linux binary, in the `SHA256SUMS` you gave, and that line is the pin. The step checks this before it changes anything: a program that the file does not list is not the release's, and the step refuses to run. `suiteward doctor` never reads the `SHA256SUMS`: it compares the binary with its pin and fails an executor whose pin does not name a release asset, as a pin made by hand does not.
   - **The unit,** `/etc/systemd/user/suiteward-executor.service`, root's, which every user manager reads: `ConditionUser=suiteward-exec` keeps the manager of another account from running it, and it is enabled for `suiteward-exec` only. It points the executor at the service, `http://127.0.0.1:<HTTP port>`: the port is `--http-port`, else the one in the service account's settings, else the one its installed unit publishes, else 27081. The unit sets `MemoryMax=3G`, `MemorySwapMax=0` and `GOMEMLIMIT=2500MiB` (a variable of the Go runtime, not a setting of the executor; below the cgroup limit, it makes the runtime collect before the cgroup kills the process), `KillMode=mixed` (systemd signals the executor only, which stops its own sandbox: a signal to the `podman run` child would reach the tests and fail the job), `TimeoutStopSec=45` (a job in flight gets 30 seconds after SIGTERM) and `Restart=always`. The 3 GiB is what the executor holds at its peak, about 1.5 GiB live with the headroom of Go's collector: a module body that comes with no length, buffered up to what is left of the 512 MiB prefetch budget (for a moment twice that), up to 64 MiB of output of one `go test` invocation, held and parsed, and the analysis files of both sides. Each sandbox gets a cgroup scope of its own under `user@UID.service`, bounded by its own `--memory 3g`, so it counts outside the unit's 3 GiB: that is assumed, and a live host has not confirmed it. `NoNewPrivileges` stays off in the unit, because it would stop `newuidmap` and `newgidmap`, which rootless Podman needs. `hidepid` on `/proc`, which would hide the service account's processes from `suiteward-exec`, is deliberately not used: ADR 0028 allows it only when made persistent and tested, and neither has been done.
5. **The account's folder.** It creates `~/.config/suiteward` for `suiteward`, mode 0700, where the GitHub settings and the ruleset files go. It gives `suiteward` a copy of the executor's token there, `executor-token`, owned by that account, which the service step turns into the service's secret (a copy that is a link is refused, and one that is the same is left alone). A GitHub env file from a hand-made install (`/etc/suiteward/github.env`) is copied there, and the old file stays until the service has moved to the new one.

It ends by printing the command for the next step, with the account's user bus filled in: the path of the binary, then `install --tier isolated`. It also says that the executor already runs and waits for the service, and that the step must be run again with `--http-port <port>` when the service will publish another port. The step is safe to run again, as an upgrade needs (section 11). The command carries `--image sha256:<signed index digest>` only when the binary is a development build, because a release binary carries its own digest. `--answers <file>` gives the answers from a file (section 12).

**10.3 Open a shell as `suiteward` (as the administrator).** The account has a `nologin` shell, so `sudo -iu suiteward` fails. Open a shell with its user bus, and start every new session this way:

```
r=/run/user/$(id -u suiteward)
sudo -u suiteward -H env XDG_RUNTIME_DIR=$r DBUS_SESSION_BUS_ADDRESS=unix:path=$r/bus bash
```

Check it with `whoami`, which prints `suiteward`. The next steps run in that shell, unless they say they run on your PC. `sudo` gives the shell its own list of folders to search, which may lack `/usr/local/bin`, so type the program by its full path, `/usr/local/bin/suiteward`, as the host step prints it. Where this guide says `suiteward install` or another `suiteward` command in this shell, it means that path. Turn off session recording and Session Manager logging before the steps that print a secret: setup prints your TOTP secret, and a logged session keeps it.

**10.4 Install the stack (as `suiteward`).** Run:

```
/usr/local/bin/suiteward install --tier isolated
```

Pass `--tier isolated`: the default tier is `co-located`. The installer asks for what it needs and works in this order. A refusal in the first four steps changes nothing:

1. It refuses to run as root, or as any account but `suiteward`, and checks the account's systemd user manager and linger.
2. It takes the ports and the job timeout from `--http-port`, `--mcp-port` and `--job-timeout` (or the answers file). Given on a re-run, they change the installed stack, the run says what changes, and a running service is restarted to read them; not given, the installed values are kept. When the HTTP port changes, the executor is still pointed at the old one: run the host step again with `--http-port <port>` (and `--sha256sums`, 10.2) so that it finds the service. It refuses a port that something already listens on (`ss -ltn`), except the ports of this stack while its service runs: every WSL2 distro shares one network with the others and with a Podman machine. Without `ss` it notes that the ports were not checked; any other failure of `ss` stops the install.
3. It adopts an existing install (step 10.6), and decides the image: `--image` if you give it, else the one installed, else the release the binary carries. A development build has no release, so it needs `--image sha256:<index>`: take the index digest from the release notes and verify it first, from the release source on a machine that has cosign 3.x (`pwsh ./scripts/verify-release.ps1 -Reference ghcr.io/ignisdevne/suiteward@sha256:<index>`).
4. It pulls the PostgreSQL image and the release image by digest.
5. **GitHub**, the same flow as section 5.3, with the choice of App described below.
6. It checks that there is an App key to store, and prints its fingerprint when you give the key of an App that exists (a key that the flow created and stored itself is not printed): `SHA256:` followed by base64 text. Compare it with the fingerprint that the App's settings page shows for that key. A wrong or revoked key looks right to every other check, and GitHub calls then stop about an hour later. An install that names an App but has no key for it, given or stored, is refused here, before any change. An install without GitHub needs no key: its service unit mounts none.
7. It writes `~/.config/suiteward/github.env` (the three GitHub values; they are not secrets), then creates the Podman secrets that are missing: the database password and the owner's URL, the MCP token and the App key, and `suiteward-executor-token`, made from the copy of the executor's token that the host step left in the account's folder (10.2, item 5). A secret that holds another token than that copy is replaced, because a token that is not the executor's would lock it out; the service reads its secrets only when it starts, so a running service is restarted. It never prints them, and it never replaces a database password that exists, because the database keeps it in its volume. When the host step has not run (no copy of the token), the service's unit leaves the executor's lines out, the install says that the service runs without an executor, and canonical execution has nothing to run on until the administrator runs the host step and this install runs again.
8. It writes the six unit files into `~/.config/containers/systemd/`, runs the Podman generator's dry run to be sure Podman reads every one of them, and reloads systemd.
9. It starts the database, waits until it is healthy, creates the application role `suiteward_app` with its URL secret, starts the service (which runs the migration first) and checks that the three units are active. It then waits until `/readyz` answers four times in a row, two seconds apart, while systemd counts no restart of the service; a service that keeps restarting fails the install, and the error names `journalctl --user -u suiteward.service`. Only then does it save its settings in `~/.config/suiteward/settings.yaml`.
10. Setup (step 10.5).

*Create the App through the manifest* (`--github yes`, or yes at the prompt). The browser of your PC must reach the installer's listener on the host, which listens on 127.0.0.1 only. Pin the port with `--manifest-port <port>` (for example 8765), so you can start the forward before the installer asks. Without it, the installer picks a free port and prints the forward command with that port. From your PC, with the AWS CLI and the Session Manager plugin:

```
aws ssm start-session --region <region> --target <instance-id> --document-name AWS-StartPortForwardingSession --parameters '{"portNumber":["<port>"],"localPortNumber":["<port>"]}'
```

Leave it open and open `http://127.0.0.1:<port>/` in the browser of your PC. Use the same number for `portNumber` and `localPortNumber`, and for the browser: the listener answers 403 to any other Host, and GitHub redirects to `127.0.0.1:<port>`. On a host that is not on AWS, use your own forward, for example `ssh -L <port>:127.0.0.1:<port> <host>`. From there, the steps are those of section 5.3: confirm the App on GitHub, install it on the repositories to protect, choose the repositories, the owner and the test checks. If the forward is not up, the paste fallback of section 5.3 works in the Session Manager terminal: after 2 minutes the installer asks you to paste, hidden, the address that the browser's error page shows, or its `code=` value. The App key goes from the response of GitHub straight into the Podman secret store of the host.

*Use an App that exists* (`--github-app-id`). Create it by hand first, by the checklist below, and give `--github-app-id <app id> --github-installation-id <installation id> --github-repositories '<owner/name>,<owner/name>' --github-owner <login>`, with one `--test-check 'owner/name=<check name>'` for each repository. The key comes from `--github-app-key-file <path>`, from `-` (standard input; then every other answer must be a flag or in the answers file), or from `github-app-key` in the answers file (mode 600): never as an argument. To paste the key without echo into a file, run this in the shell of step 10.3, wait until the cursor stops, paste the whole PEM, press Enter, then press Ctrl-D. You see nothing while you paste:

```
trap 'stty echo' INT; stty -echo; (umask 077; cat > ~/app-key.pem); stty echo; trap - INT
```

Then give `--github-app-key-file ~/app-key.pem`, and delete the file afterwards in the same shell, `shred -u ~/app-key.pem`, and your own copy of the `.pem`. The App checklist:

- [ ] Create a GitHub App under your user account, or under an organization you administer.
- [ ] Set the **Homepage URL**. GitHub requires one, and any URL works, for example the repository's.
- [ ] Leave the webhook inactive: uncheck **Active**. SuiteWard polls GitHub and receives no webhooks.
- [ ] Set the repository permissions to exactly these, and nothing else:
  - Metadata: Read-only (GitHub requires it)
  - Pull requests: Read and write
  - Contents: Read-only
  - Administration: Read-only
  - Checks: Read and write
- [ ] Answer "Where can this GitHub App be installed?" with **Only on this account**.
- [ ] Generate a private key. GitHub downloads a `.pem` file. Keep it somewhere safe until the installer has stored it. Never commit it. Do this before the next item: the private key must exist before GitHub allows the installation.
- [ ] Install the App on the repositories you want to protect, and no others. The limit is 20.
- [ ] Note the **App ID** (on the App's settings page) and the **installation ID** (the number in the address of the installation's settings page).
- [ ] Optional: upload [`assets/brand/png/suiteward-github-app.png`](../assets/brand/png/suiteward-github-app.png) as the App's logo, with the badge background color `#12202F`, so its comments and checks carry the SuiteWard mark.

Keep these permissions off, for these reasons:

- **Administration: Write** stays off. SuiteWard reads protection and never changes it. You import the ruleset yourself (section 7).
- **Contents: Write** stays off. SuiteWard reads code and never commits. The `.suiteward.yml` declaration is yours to commit.
- **Issues** stays off. Pull request comments are covered by the Pull requests permission.
- **Webhooks** stay off. This release polls GitHub and accepts no inbound webhooks.
- **Any other permission** stays at No access. SuiteWard does not request it.

*The ruleset.* For each repository, the flow writes a ruleset file on the host, `~/.config/suiteward/suiteward-ruleset-<owner>-<name>.json`, and prints its path and the Import steps of section 5.3 (step 7), with the Free-plan warning for a private repository. The Import is a click in your browser, so get the file to your PC: print it in the Session Manager session with `cat ~/.config/suiteward/suiteward-ruleset-<owner>-<name>.json`, copy the text and save it as a file on your PC, or copy the file over with your own tool. Then import it. When the installer reads the protection back and finds it enforced, it deletes the file on the host. On a full screen the installer pauses at a page with the choices `I imported it, check now` and `Skip, import later`, and reads the protection back when you say so; in plain mode it waits at `Press Enter when the rulesets are imported` and then reads it back. Without a terminal it does not wait: `ruleset-imported` defaults to yes, so give `--ruleset-imported yes` knowingly, and read the protection result.

**10.5 Setup and check (as `suiteward`).** On a real terminal, the installer runs setup for you at the end, after it warns you to turn off session recording: it passes the terminal through and never captures or logs setup's output. Without a real terminal it prints `suiteward enroll --tier isolated` to run on one. Section 6 says what setup does, and when the installer skips it. On a full screen the summary has already run the checks of `suiteward doctor` (section 5.7); otherwise run `suiteward doctor` and expect `ok` on every line.

The ports are published on the host's loopback only (27081 and 27091 unless you chose others; a host installed before M1.14 keeps 8081 and 8091, because an upgrade never moves a port). To read `/status` from your PC, forward the port with your own remote-access tool (on a host that is not on AWS, for example `ssh -L 27081:127.0.0.1:27081 <host>`), or on AWS for example `aws ssm start-session --target <instance-id> --region <region> --document-name AWS-StartPortForwardingSession --parameters portNumber=27081,localPortNumber=27081`. SuiteWard provides no remote access.

**10.6 Re-runs and a host installed by hand.** A second run creates only what is missing, applies the ports and job timeout you give (step 10.4, item 2), and restarts a running service when its ports, job timeout or GitHub settings change. A host from the v0.2.0 install guide is adopted: the installer compares the installed units with the units of the release, carries over the tier, the ports and the job timeout when you give none, and moves the GitHub env file from `/etc/suiteward/github.env` to the account's folder (step 10.2 copies it, and the installer prints the `sudo rm` line for the old file once the service uses the new one). Any other difference stops the run and prints the diff: nothing is overwritten silently. When the settings file holds no GitHub values, the installer reads them from `~/.config/suiteward/github.env`. It parses that file strictly: exactly the three keys once each, a positive App id and installation id, and one to 20 `owner/name` pairs of one owner. A file that is not that stops the install before any change, and the error names the file and the line. So a host with a GitHub App already is never offered a second one. A host prepared by an earlier release has no executor account, token or unit: its service unit, which has no executor lines, is adopted as a known shape, and the host step (10.2) followed by this install adds them. For a release that differs from the installed one, use `install --upgrade` (section 11).

For the manual procedure of the v0.2.0 release, which this guide no longer repeats, see [the install guide at the tag v0.2.0](https://github.com/IgnisDevNE/SuiteWard/blob/v0.2.0/docs/install.md).

## 11. Updating

Pin one release, and update when you choose. Updates are always explicit, by digest. Automatic updates are not supported: Podman's auto-update cannot update the migration unit, so an automatic update would start the service alone on an old schema, which the service refuses, and loop. Never add `AutoUpdate=` to a unit or enable `podman-auto-update.timer`.

Get the new release's installer as section 4 says, and verify it if you choose to (on Linux and macOS, the one-line install replaces the binary in its install directory: run it with the new tag in `SUITEWARD_VERSION`; on the isolated host, copy the new binary to `/usr/local/bin/suiteward` again, as 4.1 says), then run it with `--upgrade`:

```
suiteward install --upgrade
```

On the isolated host, run it as `suiteward` in the shell of step 10.3. The release is the one the binary carries, or `--image sha256:<index>` (a development build needs it). `--yes` answers the question about the upgrade plan only (it never starts a service that is down, see step 2, and never makes a recovery key, see step 3), `--backup-dir <directory>` chooses where the backup file is made, and `--backup-recipient age1pq1...` gives the public recovery key where no terminal can be asked. An unattended `suiteward install --upgrade --yes` therefore needs a recovery key, which releases before M1.13 did not: run `suiteward backup init` once first ([the backup runbook](backup.md#the-recovery-key-once)), or pass `--backup-recipient`. Without a key and without a terminal the upgrade refuses before it changes anything, because a backup is never written in plaintext. When several installations are listed, `--yes` also needs `--settings` and `--token-file`, because nothing can be asked which installation (section 5, "Which installation a command works on"). The upgrade takes these steps, in order:

1. **It adopts what is installed.** A difference it cannot carry over stops the run, with the diff, before any change. An upgrade keeps the installed ports and job timeout: `--http-port`, `--mcp-port` or `--job-timeout` with another value stop it before any change, and the message names the re-run of `suiteward install` that changes them. The tier comes from the settings file. On Linux with no settings file (a host installed by hand), pass `--tier isolated` as the service account, or `--tier co-located`.
2. **It makes sure the service answers, shows what changes** (the release, and the PostgreSQL pin when it moves) **and asks.** When the stack already runs this release, it says `Nothing to upgrade`. When the service does not answer `/status`, which the backup records, it first asks on a terminal: `The service is not running, so the backup cannot record its status. Start the installed service now? If you answer no, the upgrade stops and nothing is changed.` (a choice between Yes and No on a full screen, with Yes highlighted; `[Y/n]` in plain mode). On a yes it starts the installed stack as it is, without changing the release (isolated: `systemctl --user start suiteward.service`; co-located: `start` on the existing containers, the database first, and nothing is created again), waits up to about 90 seconds for `/status` (at most 60 probes, one a second, within that deadline), and goes on to the plan and its question. A no to the plan after it started the service stops with the note that the service was started and nothing else was changed. On a no, at the end of the input, without a terminal, or when the start does not help, it refuses and names the command that starts the service, or the [manual backup](backup.md#isolated-host-bash-as-suiteward) (Appendix A of the backup runbook; [section 2](backup.md#2-back-up) points to it). `--yes` does not answer this question and never starts the service.
3. **An encrypted backup first,** as one new file, `suiteward-backup-<date>-<time>.tar.age`, in the backup folder, readable by your user only (mode 0600, or an owner-only ACL on Windows, granted to your user's SID). It is the backup that `suiteward backup` makes, with the same members and the same rules ([the backup runbook](backup.md#2-back-up)): `status.json` (the release the files belong to), `suiteward.sql` (a `pg_dump` of the database), `suiteward-artifacts.tar` (the artifact volume), the settings and, on the isolated tier, the unit files. It is encrypted to your recovery key, so the TOTP secret is never in plaintext, and only the kit opens it. The key is the one in the settings. With none, the upgrade settles it before it starts anything, a service that is down included: on a terminal it asks whether to make one, as `suiteward backup init` does (`--yes` does not answer that question); without a terminal it takes `--backup-recipient age1pq1...`, or `backup_recipient` in the answers file, which is stored in the settings when the upgrade is done; and otherwise it refuses. A key that differs from the one in use is refused: replacing it is `suiteward backup init --replace`. The default folder is `backups` beside the MCP token copy on the co-located tier (so `%LOCALAPPDATA%\SuiteWard\backups` on Windows, not the roaming profile, and `~/Library/Application Support/suiteward/backups` on macOS), and `~/.config/suiteward/backups` on the isolated tier. On the isolated tier the unit files that the upgrade replaces are also kept as plain files, which hold only the names of secrets, in the directory `suiteward-backup-<date>-<time>.units` beside the archive. The service must be running: the backup reads its `/status`, so a service that is down is started first (step 2) or the upgrade waits until it is up. A backup that fails leaves nothing behind and changes nothing; when the upgrade had started a service that was down, its message says that the service it started is running and that nothing else was changed. When the stack already runs this release, the upgrade says `Nothing to upgrade` and needs no key.
4. **It pulls the new images, and replaces the release.** Co-located, it recreates the containers as an install does: database, role, migrate, then the service. Isolated, it stops the service, writes the new units, checks them with the generator's dry run, reloads systemd, restarts the database when its image changed, restarts the migration unit (which migrates), starts the service and waits until it is stable, as an install does (step 10.4, item 9). An `/etc` env file of a hand-made install is moved to the account, and the installer prints the `sudo rm` line for the old one.
5. **It checks, and ends with the way back.** On a full screen the summary runs the checks of `suiteward doctor` and shows their counts, as an install does (section 5.7); in plain mode, run `suiteward doctor`. Check that `version` in `/status` is the release you meant. The upgrade also prints the way back for its tier, with your paths filled in: the commands of [the backup runbook](backup.md#going-back-after-an-upgrade). On Windows it refreshes the copy of the program on your PATH, if you made one (section 5.7).

A co-located `suiteward install --image <another release>` over a running stack refuses, and points to `--upgrade`. So does the isolated install for an installed image.

**The executor in an upgrade.** The service and the executor must be of one release. Upgrade them together. This release's executor sends a heartbeat about every 10 seconds and backs off for at most 20 seconds after an error, which keeps a healthy executor below the 30 seconds after which a head reads not responding (section 9); an executor of an earlier release does not.

- **Co-located.** `install --upgrade` does for the executor what an install does (section 5.4): it copies the new program over the executor's copy and updates its pin (the hash of the copy, or, with the optional `--sha256sums <the verified SHA256SUMS of the new release>`, the release's line of that file: a program that the file does not list is refused before anything changes, and the flag counts also when the answer is `Nothing to upgrade`), writes its definition again, pulls the Go image when the release names another, and restarts the executor when the program or the definition changed (it stops it first: Windows cannot replace a program that runs; an executor that runs with the same program and definition is left alone, because it may be in the middle of a job). On Windows that stop ends the whole tree (section 5.4), and a task that an older build registered, which has a window, is replaced by the one that has none. The upgrade does all this also when it says `Nothing to upgrade`, so that a program replaced since reaches the executor and an executor that stopped is started. The first upgrade into the release that has the executor makes its token (the service container is replaced to read it), its directory and its definition. A failure to set up the executor is a warning that says what to do, not a failed upgrade.
- **Isolated.** The executor is the administrator's, so an upgrade has two steps, in this order. First copy the new binary to `/usr/local/bin/suiteward` (section 10.1) and run `sudo /usr/local/bin/suiteward install host --sha256sums <the verified SHA256SUMS of the new release>` with it: it replaces the executor's copy and its pin, pulls the Go image again, and restarts the executor when its binary or token changed. Then run `install --upgrade` as `suiteward`. The first upgrade into the release that has the executor needs the host step first: until it has run, the service has no executor token, runs without an executor and says so, and the upgrade names the host step; run it, then `suiteward install --tier isolated` as `suiteward` to give the service the token (which restarts it): once the release is the installed one, `install --upgrade` has nothing to upgrade and, for a service that has no token yet, says so and names that command (the same command is the fix that `doctor` names for a service without the token). A new token (the administrator removed the old one) restarts a running executor, and `install --upgrade` at the installed release gives the service the new token and restarts it, instead of saying only `Nothing to upgrade`.
- **A window between the two steps.** When a release moves the Go image's pin, a service and an executor of different releases name different images, and the executor refuses a job whose image is not its own: a job leased in that window is `unavailable` with `profile-unsupported`, final for that head. The owner can unblock it, and a new head makes a new job. Run the two steps one after the other.
- **An older service refuses what a newer one approved.** A service of an earlier release reads the `execution:` block of the canonical declaration as an unknown key and refuses the declaration as invalid. Do not start an older release on a database whose canonical has the block: the way back is `suiteward restore` of a backup made before the upgrade ([the backup runbook](backup.md#going-back-after-an-upgrade)).
- **The lease wait.** `SUITEWARD_EXECUTOR_LEASE_WAIT` is 2 minutes by default, which is also its lowest value (section 13). When the service has not seen an executor for that long, the pending runs read `unavailable` (`no-executor`). A head reads not responding earlier, after about 30 seconds of the same silence (section 9, "When the test runner does not respond").
- **A backup holds neither the executor nor its token** ([the backup runbook](backup.md#1-what-a-backup-holds)).

*If a step fails.* The message says how far the upgrade got.

- **Before migrate**, the schema and the data are unchanged (after the step's own error, the message says `The database update (migration) did not run, so your data is unchanged.`), and it names the backup and the exact commands. Co-located: run `suiteward install` with the same options as this run to start the release in the settings again, or `suiteward install --upgrade` to retry. Isolated, with the service stopped: to go back, copy the unit files that the upgrade replaced, which are saved in the `.units` directory beside the backup (the message names it), to `~/.config/containers/systemd/`, run `systemctl --user daemon-reload` and `systemctl --user start suiteward.service`. To go on once the cause is fixed, run `systemctl --user daemon-reload`, then `systemctl --user restart suiteward-db.service` (only if the database image changed), then `systemctl --user restart suiteward-migrate.service` and `systemctl --user start suiteward.service`.
- **From migrate on,** migrations only go forward. An older image refuses to start on a newer schema, and nothing migrates it back. The way back is `suiteward restore` of the backup, with its kit, on the previous release, which loses everything after the backup ([the backup runbook](backup.md#going-back-after-an-upgrade); that way has not been rehearsed end to end). Do not start an older image on the upgraded database. On the isolated tier the units then name the new release while the settings still name the old one, so a second `--upgrade` says `Nothing to upgrade`: restore the backup instead of retrying.

An upgrade from a release before M1.13 changes four things you will see. The backup is encrypted and needs a recovery key (above), so an unattended `install --upgrade --yes` fails until you make one. Ctrl-C and SIGTERM end the installer commands with exit code 130 (section 12). The service gets `SUITEWARD_REPORT_BASE_URL`, so the revision comments of new revisions link their report; a Docker re-run of `suiteward install` over such a stack keeps a running service without it, and only `install --upgrade` adds it (section 12, "What the installer does"). And the revisions recorded before the upgrade have no stored manifest, so a comment of theirs that is delivered after the upgrade shows no numbers, and their report page answers 404.

An upgrade from a release before M2.1 moves the database to version 22 (the migrations `00021` and `00022`, which add the tables of execution and the counted job of a check). Migrations only go forward: an older image refuses to start on that database, and the way back is the restore of the backup that the upgrade made (above). The upgrade also gives the service the executor's token and sets up the executor (the executor in an upgrade, above; on the isolated tier the host step comes first). Nothing runs until the approved `.suiteward.yml` names `execution: {profile: go}` (section 9), and once it does, an older release cannot read that declaration.

Read the release notes first. An instance on v0.1.1 or older upgrades to v0.1.3 first, and then to v0.2.0: later releases no longer read the comment payloads that v0.1.1 or older queued. A co-located stack that the PowerShell start script of v0.2.0 and earlier made is converted by `--upgrade`, under the same names, even when it already runs this release. An isolated host from v0.1.x has no migration unit, and `--upgrade` does not convert it: follow [the v0.2.0 guide](https://github.com/IgnisDevNE/SuiteWard/blob/v0.2.0/docs/install.md) to v0.2.0 first.

### Uninstalling

```
suiteward uninstall
```

It first says which instance it is about to remove (the instance ID that `/status` shows, the container program, and the settings file), asks (`--yes` skips the question), then removes the stack and keeps the data. On a full screen a page shows the rows `Instance ID`, `Container program` and `Settings file`, and says `Nothing is removed until you confirm.` where a question is going to ask; a plain uninstall asks Yes or No (a choice with No highlighted), and a purge shows one red statement of what it deletes (`This deletes the database, the saved files (artifacts), the secrets and the settings of instance <id>.`) and asks one question, to type the instance id (below):

- **Co-located:** the executor first, because it asks the service for jobs: it is stopped (on Windows its whole tree is ended, section 5.4, and a process that is left stops the removal before anything is deleted), and its program, its pin, its log and its definition (the task, the launch agent or the user unit) are removed (`Stopped the test runner (the executor) and removed its program and its settings.`). Then the three containers (`suiteward`, `suiteward-migrate` and `suiteward-db`). The executor is this instance's only when the token file is: beside a token file that may belong to another instance it is kept (`Kept the test runner (the executor) in <folder>: it is next to a token file that may belong to another instance.`), and so is the test runner that this user has for another instance (`Kept the test runner (the executor): it belongs to another instance, and a computer has one test runner.`). When it cannot stop or remove the executor, the uninstall goes on and ends with a note, `Note: the test runner (the executor) was not removed: <why>. It is in <folder>. To remove it by hand, <steps>.`, whose steps are, on this system: on Windows, ``run `schtasks /End /TN "SuiteWard Executor"`, then `schtasks /Delete /TN "SuiteWard Executor" /F`, sign out of Windows and sign in again to end what still runs, then delete that folder`` (no `taskkill` by name: the script would start the program again after its pause, and a name would also end another instance's executor); on macOS, `` run `launchctl bootout gui/$(id -u)/io.suiteward.executor` to stop it, then delete that folder and `~/Library/LaunchAgents/io.suiteward.executor.plist` ``; on Linux, ``run `systemctl --user disable --now suiteward-executor.service` where your user session runs to stop it, then delete that folder and its unit file``. The volumes, the secrets, the settings and the executor's token copy stay: run `suiteward install` again to start the stack and the executor. `--purge` also removes the volumes (the database and the saved files, called artifacts), the secrets, the network and the settings file, and the MCP token copy (the access token file) and the executor's token copy (`executor-token`, beside it) when they are this instance's: the file that `--token-file` names, else the default token file, but only when the settings file is the default one (`--settings` left out, or naming that file by its own path, in any letter case on Windows; a relative path is resolved against the current directory first). Any other settings file is another instance's, whose default token file may be the first instance's, so the purge keeps that file and says so, if it exists; give `--token-file` to have a purge remove a token file.
- **Isolated,** run as `suiteward` in the shell of step 10.3: it stops the services and deletes the six unit files. It never touches the executor, which is the administrator's (its account, unit, binary, token and rule): the executor keeps asking for jobs of a service that is gone, and the command prints, for an administrator, how to stop it (`systemctl --user --machine=suiteward-exec@.host disable --now suiteward-executor.service`) and what to delete to remove all of it (the unit `/etc/systemd/user/suiteward-executor.service`, `/usr/local/libexec/suiteward`, `/etc/suiteward/executor-token`, `/etc/suiteward/exec-block.nft`, the unit `suiteward-exec-block.service`, and the account). `--purge` also removes the secrets (the executor's token secret included), the volumes, the network, the copy of the executor's token in the account's folder, `~/.config/suiteward/github.env` and the settings file, and stops any SuiteWard service that an earlier uninstall left running without its unit file (alpha.1 left the network service so, and the next install then failed with `network not found`). It never touches `/etc`: when the installed units read `/etc/suiteward/github.env`, it prints the `sudo rm` line for an administrator. With no settings file on Linux, a host installed by hand needs `--tier isolated`.

**A co-located purge lists what it deletes before it acts.** Under the instance, in plain mode and on the full screen alike, it says `This purge deletes:` and names `the access token file <path>` and `the test runner's token file <path>` (when they are this instance's), the volumes `suiteward-data` and `suiteward-db-data`, the secrets of the instance and the network `suiteward`, the settings file, and the record of a GitHub App that is being set up (`settings.yaml.pending-app`) only when there is one. A token file that it keeps is named first (``The access token file <path> is kept: it may belong to another instance. To delete a token file with this purge, give it as `--token-file <path>`.``). The lines stay in the scrollback after the screen closes, and `--yes` shows them before the first removal too. The isolated tier's purge has no such list. The warning line of a plain purge names the access token copy only when the purge removes it.

`--purge` deletes your TOTP enrollment and every contract version, so back up first (`suiteward backup`, [the backup runbook](backup.md)). It keeps every backup in the backup folder, those of `suiteward backup`, of `--upgrade` and of `suiteward restore` alike, but it removes the settings file, and with it the public half of the recovery key: after a reinstall, make a new key (`suiteward backup init`), and keep the old kit, which still opens the old backups. It removes the record of an unfinished GitHub App (`settings.yaml.pending-app`, see Troubleshooting). The command leaves a stack that this installer did not make, or whose units or containers were edited, alone. On Docker, it uses the runtime and connection that the install recorded. SuiteWard changes nothing on GitHub: delete the App, and the ruleset rule that requires `SuiteWard / Contract`, yourself. The account `suiteward`, the metadata rule and Podman stay on the host; remove them with the administrator's own tools if you no longer need them.

**`--purge` needs the instance id, as `suiteward restore` does.** On a terminal it asks you to type the id of the instance it names. Where nothing can ask (a script, an agent's session) or with `--yes`, pass it: `suiteward uninstall --purge --yes --instance <id>` (with several installations listed, also `--settings` and `--token-file`, because `--yes` cannot be asked which one), the 8 characters shown as `instance` in `/status` (`http://127.0.0.1:<http port>/status`, 27081 by default). A wrong id removes nothing. When the service does not answer, the id is read from the database; when neither names it (the usual state after a plain `suiteward uninstall`, which leaves no database container), the id is `unknown` (the line that names the instance adds what the database answered), which you type or pass on purpose. With no settings file and the database volume `suiteward-db-data` still there, `--yes` refuses `unknown`, because no id would be checked against the data it deletes: type the word on a terminal, or pass `--settings` with the settings file of the instance (a plain uninstall keeps it). With no database volume left, `--yes --instance unknown` works. A plain `suiteward uninstall` keeps its yes-or-no question.

On Windows, a purge on a full screen ends with an offer to remove the copy of the program and its PATH entry that an install made (section 5.7), when there is one: the default is No, `--yes` does not ask, and a copy that a running program holds is renamed to `suiteward.exe.old`, which you delete by hand.

**The settings file decides which instance this is.** A file that you name with `--settings` must exist: a mistyped path stops the command (exit 1, naming the path) before it calls the container engine, in every command that reads the file (`uninstall`, `enroll`, `backup init`, `backup`, `restore`, `install --upgrade` and `doctor`). Only a plain `install`, which writes the file, may name one that is not there yet. With no `--settings` and no file at the default path, `enroll` on the co-located tier refuses and points to `suiteward install --upgrade`, and `uninstall` and `restore` do not run on the defaults of this PC, which may be another instance: name the engine, `--runtime podman --connection <name>` (`--connection=` for the default one), as the way to remove a stack whose settings were never saved, for example after an install that failed early; or give `--tier isolated` as the service account. The file must also hold both ports (`http_port` and `mcp_port`, which the installer always writes): a file without them is refused, because a default port would move a stack that exists to another port at the next run. A stack keeps its ports across releases; only a new install takes the defaults, 27081 and 27091.

### Rotating the App key

Rotate the key when it may have been seen by something it should not, for example by a coding agent. Do it yourself, from a terminal that no agent can reach. A co-located install gives the agent access to the key anyway (section 2): there, rotation helps against a past exposure and a key that left the machine, not against an agent that still shares your PC user. The installer has no command for rotation: once the key secret is gone, a run with the key file (`--github-app-key-file`) verifies that App again, and a run without it stops and offers the key file or a new App (section 5.3). Replace the secret by hand.

**On macOS,** run the co-located commands below in your own shell instead of PowerShell. Select the connection with `export CONTAINER_CONNECTION=<name>` (step 5.1). In R.5, create the secret with `podman secret create suiteward-github-app-key - < <path of the new PEM>` and delete the file with `rm`. Run the `openssl` pipelines of R.4 and R.6 as they are, with your machine's user in place of `user` in `podman machine ssh --username` (step 5.1). The installer has run on a real Mac, without GitHub, but these rotation steps have not, so check each fingerprint as the steps say.

The order matters. After you replace the key, the service keeps working for up to an hour on installation tokens that it already holds. A wrong key therefore shows up late, when every GitHub call stops. So check the fingerprint at each step, and delete the old key last.

**R.1 Generate a new key.** On the App's settings page, under **Private keys**, generate a private key. GitHub downloads a `.pem` file and shows the key's fingerprint, `SHA256:` followed by base64 text. Note it. Leave the old key in place.

**R.2 Stop the service and remove the old secret.**

- Isolated host, as `suiteward` (a shell opened as in step 10.3):

  ```
  systemctl --user stop suiteward.service
  podman secret rm suiteward-github-app-key
  ```

- Co-located PC on Podman, in the PowerShell session where you selected the rootless connection (step 5.1). The first command removes the containers and keeps the secrets:

  ```
  suiteward uninstall --yes
  podman secret rm suiteward-github-app-key
  ```

- Co-located PC on Docker: this release has no procedure. The key is a file in a named volume that only the installer writes. Use Podman, or back up, `suiteward uninstall --purge`, install again and restore.

**R.3 Put the new key in a file.** On the isolated host, paste it without echo, as in step 10.4 (*Use an App that exists*). On the PC, use the `.pem` that GitHub downloaded.

**R.4 Check the file's fingerprint** before you use it. It must be the text you noted in R.1.

- Isolated host, as `suiteward`:

  ```
  openssl rsa -in ~/app-key.pem -pubout -outform DER 2>/dev/null | openssl dgst -sha256 -binary | openssl enc -base64
  ```

- Co-located PC: in Git Bash, run the same command with the path of your `.pem` file in place of `~/app-key.pem`, written as Git Bash accepts it, for example `/c/Users/<you>/Downloads/<file>.pem`.

If it differs, delete the file (`shred -u ~/app-key.pem` on the host, `Remove-Item <path of the new PEM>` on the PC), and repeat R.3 with the right file.

**R.5 Create the secret, and start the service.**

- Isolated host, as `suiteward`:

  ```
  podman secret create suiteward-github-app-key ~/app-key.pem
  shred -u ~/app-key.pem
  systemctl --user start suiteward.service
  ```

- Co-located PC on Podman:

  ```
  Get-Content -Raw <path of the new PEM> | podman secret create suiteward-github-app-key -
  suiteward install
  Remove-Item <path of the new PEM>
  ```

  The second command runs without GitHub flags: it finds the key secret, so it does not run the GitHub flow, and it creates the containers again.

**R.6 Check the secret's fingerprint again.** It must be the text of R.1.

- Isolated host, as `suiteward`:

  ```
  podman secret inspect --showsecret --format '{{.SecretData}}' suiteward-github-app-key | openssl rsa -pubout -outform DER 2>/dev/null | openssl dgst -sha256 -binary | openssl enc -base64
  ```

- Co-located PC, in Git Bash. The Podman machine has no OpenSSL, so the secret goes out to the PC's:

  ```
  podman machine ssh --username user "podman secret inspect --showsecret --format '{{.SecretData}}' suiteward-github-app-key" | openssl rsa -pubout -outform DER 2>/dev/null | openssl dgst -sha256 -binary | openssl enc -base64
  ```

**R.7 Confirm that GitHub accepts the key.** The service starts without a cached token, so its first reads already use the new key. Run `suiteward doctor`: `github.app` and `github.installation` must be `ok`. Then wait about a minute and read `/status` twice, a minute apart (section 15 shows how). The `lastSuccess` of each repository must advance, and no repository may show a `lastError`. That is the proof. The log line `bot account could not be resolved` appears only when SuiteWard processes an owner command, so its absence proves nothing. If you do see it, the key is wrong. This prints the lines it finds:

- Isolated host, as `suiteward`:

  ```
  podman logs --since 10m suiteward 2>&1 | grep 'bot account could not be resolved'
  ```

- Co-located PC:

  ```
  podman machine ssh --username user "podman logs --since 10m suiteward 2>&1 | grep 'bot account could not be resolved'"
  ```

**R.8 Delete the old key.** Only now, on the App's settings page, delete the old private key. Then delete every other copy of a `.pem` file, including the one GitHub downloaded in R.1.

If R.4 or R.6 shows a different fingerprint, or R.7 shows no advance or a `lastError`, do not delete the old key. Stop the service, and repeat from R.2.

## 12. The installer: flags, answers file and what it does

Every command prints its flags with `--help`. The exit code is 0 on success, 1 on a failure, and 2 on a usage error. `install`, `install host`, `uninstall`, `enroll`, `backup init`, `backup`, `restore` and `doctor` exit with 130 when you interrupt them (Ctrl-C, or SIGTERM): the message says what the step left behind and how to clean it up (`doctor --json` keeps the code of its checks). Any error that ends a command after the interrupt is reported that way, so a restore that you interrupt during the load of the dump exits 130 too, with the message of where it stopped; the database stays as it was, because the load is one transaction that is committed only at the end ([the backup runbook](backup.md#3-restore)). `suiteward version` (also `--version`) prints two lines, the version of the binary and `image: <digest>`, the release image it installs by default (`none (development build)` for a development build, and `not recorded in this binary` for the binary inside the release image, which is built before its digest exists). It reads no setting, and any argument after it is a usage error (exit code 2).

### Commands and flags

`suiteward install`:

| Flag | Meaning |
| --- | --- |
| `--answers PATH` | Read answers from a YAML file. A flag wins over the file. |
| `--settings PATH` | The installer settings file (default: `suiteward/settings.yaml` in your per-user configuration directory). A file that you name must exist, except for a plain `install`, which writes it (see "Uninstalling"). An empty value (an unset shell variable) is a usage error, never the default file. The default is the per-user directory, and it is this instance's only with the default settings file: `install` and `install --upgrade` refuse another `--settings` file without `--token-file`, before anything changes (section 5, "One more instance on the same PC"). `uninstall --purge` removes the files it names (the MCP token copy and the executor's), and otherwise only those of the default token file of the default settings file. |
| `--tier` | `co-located` (default) or `isolated`. The isolated install passes it, and `--upgrade` on Linux with no settings file needs it. |

Default on both tiers: the installed image, else the release the binary carries. A development build carries none, and needs it. With `--upgrade`: the release to move to. |
| `--sha256sums` | Co-located, optional, with or without `--upgrade`: the verified `SHA256SUMS` file of the release that this program was downloaded from. `sudo /usr/local/bin/suiteward install host`: `--answers PATH`, `--yes` (answer yes to installing Podman with `dnf`), `--metadata-rule yes|no`, `--http-port PORT` (the loopback port of the service's HTTP listener, which the executor is pointed at; default: the port of the installed stack, else 27081), `--sha256sums FILE` and `--plain`. `--sha256sums` is the verified `SHA256SUMS` of the release that this program was downloaded from (10.1). On a terminal, without the flag, the step asks where the file is. With no terminal and no flag, the step refuses to run (a usage error, exit 2) and changes nothing, and it refuses a program that the file does not list exactly once as a Linux binary (the line that lists it is the executor's pin). An empty value is a usage error too.

`suiteward uninstall`: `--purge`, `--yes`, `--instance ID` (only with `--purge`, or it is a usage error: the instance id, which `--yes` needs and a terminal asks you to type), `--settings`, `--token-file`, `--tier`, `--runtime`, `--connection` and `--plain`, as above. With `--purge`, `--token-file` names the token copy to remove: the purge of an instance that has its own settings file must be given it. Without `--purge`, the executor is stopped and removed only when the token file is this instance's (the one `--token-file` names, or the default one with the default settings file). On the isolated tier, give `--tier isolated` when there is no settings file; on the co-located tier, give `--runtime` and `--connection` then.

`suiteward enroll`: `--owner LOGIN`, `--test-check OWNER/NAME=CHECK` (repeat it), `--settings PATH`, `--tier` (give `--tier isolated` as the service account) and `--plain`. It needs a real terminal and a running service, and asks you to type `enroll` before it replaces the TOTP secret of an enrolled owner (section 6, "Enroll again").

`suiteward backup init`: `--kit PATH`, `--yes`, `--replace`, `--settings PATH`, `--token-file`, `--tier`, `--runtime`, `--connection` and `--plain`. It writes the recovery kit and stores the public key in the settings. `--kit` names the kit file (default: `suiteward-recovery-kit-<instance>.txt` in the current directory), and a file is never overwritten. `--yes` says, where no terminal can ask you to type `stored`, that the kit is copied off this machine. `--replace` replaces a key that is set. It needs the settings file and a service that answers `/status`.

`suiteward backup`: `--to DIR` (default: the backup folder of section 11, beside the token file: with `--token-file` left out it is beside the default token file, so a second instance gives `--token-file` or `--to`), `--settings PATH`, `--token-file`, `--tier`, `--runtime`, `--connection` and `--plain`. It takes the encrypted backup of the running instance, with the key of the settings.

`suiteward restore <backup.tar.age>`: `--kit PATH`, `--yes` with `--instance ID`, `--backup-dir DIR`, `--plaintext-dir DIR` (instead of the file, for the directory of an earlier release), `--settings PATH`, `--token-file`, `--tier`, `--runtime`, `--connection` and `--plain`. The key of the kit is never an argument: without `--kit` it is pasted hidden, or piped in. On the isolated tier, give `--tier isolated` when there is no settings file; on the co-located tier, give `--runtime` and `--connection` then. [The backup runbook](backup.md) says what each one does.

`suiteward doctor` (with several installations listed and neither `--settings` nor `--token-file`, it asks which one, and `--json` never asks): `--json`, `--settings PATH`, `--token-file PATH` (where the instance keeps its MCP token copy, which the executor's files are beside; give it for an instance that has a settings file of its own, as for `install` and `uninstall --purge`: without it, a settings file that is not the default one fails `executor.token` and no other executor row is checked) and `--plain`.

`suiteward execute` is the executor itself, not an installer command: it reads only `SUITEWARD_EXECUTOR_URL`, `SUITEWARD_EXECUTOR_TOKEN` (or `SUITEWARD_EXECUTOR_TOKEN_FILE`) and `SUITEWARD_EXECUTOR_RUNTIME`, and the unit, task or launch agent that the installer writes runs it. Do not run it by hand on a computer that has an executor (section 5.4).

### The installer's screens

Every installer command (`install`, `install --upgrade`, `install host`, `uninstall`, `enroll`, `backup init`, `backup`, `restore` and `doctor`) draws its output on one console, in one of two modes. Both run the same steps in the same order, with the same flags, answers-file keys and exit codes. What differs is what a person sees: the explanations of the questions are for the full screen only.

- **Full screen.** On a real terminal, the command takes over the window, as an editor does: a title bar, the list of its steps with the current one marked (from the first question), the page of the step, progress bars for the waits, a spinner for work of unknown length, and a last page that waits for Enter, so that you can read it before the window closes. For an install, an upgrade, `backup init`, `backup` and `restore` that last page is a summary; for `uninstall`, `install host`, `enroll`, `doctor` and an upgrade with nothing to do it is the page the command ended on, with `Enter to finish` at the foot. It uses the SuiteWard colors, and the nearest of the 256 colors where the terminal has no 24-bit color.
- **Pages.** A step starts a clean page, and so does each question that a flag or the answers file does not answer: its title, the explanation (what the question is, the choices and what each costs, the recommended one, the default) and the question at the foot, set apart by a rule. What must outlive a page is a check, a warning or a kept line (see "After the screen closes"), or a row of the summary. A page that is taller than the window is trimmed from its end, in this order: blank lines, then the explanation (behind the line `… enlarge the window to read the rest`), then whole warnings. The title, the question and a critical warning are never trimmed, so enlarge the window to read all of a page. When even those do not fit together, or a page of lines with no title to keep (the checks of `doctor`) is taller than the window, the last rows show behind a first row that says `… enlarge the window to read the rest`, and the checks of `doctor` are all in the scrollback after the screen closes. A **critical warning** is one of the few that nothing may hide among the others, such as the one on the recovery kit: on a full screen it is a red box, and in plain mode it is a warning line.
- **Questions.** A choice among a few answers is a list. Up and Down move the highlight (past an end it goes round), Enter picks it, and the default is highlighted first. A multiple choice, such as the repositories to protect, has a box in each row: Space picks or drops the row, Enter confirms, and a count that the question does not allow is refused with a line under the list. A yes or no question is a list of Yes and No. Enter takes the highlighted row: No for a question that must never be answered by habit (such as setting up GitHub), and Yes for three questions that exist to help (starting a stopped service before an upgrade, making a recovery key where a backup needs one, and the copy of the program on the PATH). A list can have no default, as the list of check runs of a repository whose runs give no better guess than another: nothing is highlighted, and Enter is refused, with a note, until an arrow has picked a row. A text answer is typed, and Enter takes the default that the question states; when the default is a long reference (the release image), the page shows it as a row and the hint line says that Enter takes it. The hint line at the foot names the keys that apply to the open question. Where the terminal cannot read single keys, the list is numbered and you type the number (`Choose [1]:`), and a multiple choice takes numbers or names, comma-separated. A flag or an answers-file key answers a question with no list, and plain mode types it, `label (a or b) [default]:`, where Enter takes the default.
- **Which installation.** When a command works on an installation that exists and this computer has several, a page titled `Which installation?` shows the full text of each one above the choice, and no row is picked beforehand, so Enter alone never picks the default one (section 5, "Which installation a command works on"). Plain mode lists them and asks for the settings file of one. A run with no terminal, or with `--yes` or `--answers`, stops and names `--settings` and `--token-file`. `doctor --json` never asks.
- **A script on a pseudo-terminal.** A script that drives a command through a pseudo-terminal (`ssh -t`, `expect`) gets the full screen and its final Enter. Give `--plain` to get the lines and no wait. Send each answer only after its question is on the screen: on a terminal the installer drops every key that came before a question was drawn (what was typed ahead, and the second Enter of a double press), so that no key answers a question the person has not seen, a typed question and a page that waits for Enter included. That holds with `--plain` too. A terminal that cannot be flushed (a read-only console handle, for one) has the flush turned off and the questions still work: the installer's own buffer of keys is still discarded. Input that is not a terminal (a pipe, a file) keeps its keys and answers the questions in order.
- **Plain lines.** The command prints lines with no escape sequence, as it did before the screens existed, with no explanation pages and no closing summary: an install ends by naming `suiteward doctor` as the next command, and a question that needs a person is the typed one. It does so when standard input or standard output is not a terminal (a pipe, a script, a coding agent, CI), when the terminal is smaller than 60 columns by 20 rows, when `NO_COLOR` is set (to any value, an empty one too) or `TERM` is `dumb`, when a Windows console cannot take escape sequences, and when you give `--plain`. `plain: "yes"` in the answers file does the same for `install` and `install host`; the other commands take only the flag. `doctor --json` never draws.
- **The steps of each command.**
  - `install`, co-located: Environment, Checks, GitHub, Start, Owner (setup), Done.
  - `install`, isolated: Checks, Images, GitHub, Units, Start, Owner (setup), Done.
  - `install --upgrade`: Plan, Backup, Images, Replace, Check.
  - `uninstall`: Confirm, Remove.
  - `install host`: Podman, Account, Metadata, Executor, Next.
  - `enroll`: Instance, Owner.
  - `backup init`: Keys, Kit, Settings.
  - `backup`: Status, Dump, Artifacts, Encrypt.
  - `restore`: Verify, Preview, Safety backup, Stop, Load, Start, Compare.
  - `doctor`: one page of checks.
- **A failure.** When a command fails on the full screen, the window does not vanish. The page the command stopped on stays, the title bar says `failed` and the step it failed in is marked (a command that fails before its first step has none to mark), the title bar word, the step and the error are red, the error is written under the page, wrapped to the window and marked with `!`, and the hint offers Enter. Press Enter to close the screen: the error is then printed on your terminal as the line `suiteward: <error>`, with the exit code the command always had (1). Plain output (`--plain`, a pipe, no terminal), an interrupt (Ctrl-C, exit code 130) and a usage error (exit code 2) show no such page and wait for nothing. `doctor`'s failed checks are results and not an error: it keeps its one page with the counts. The text of the error is the text that stderr gets, with the credentials of a URL hidden.
- **Setup is outside the frame.** Setup prints your TOTP secret, so the installer never draws it and never holds it. On Windows and macOS it opens setup in a window of its own and waits on a screen of its own, with a page before and a page after that say what happens. Elsewhere (Linux, SSH, the isolated tier) it leaves the full screen, prints the warning to turn off session recording and runs setup on your own terminal, then waits for Enter so that the secret stays in front of you until you have copied it, and the screen comes back. Section 6 has both. The screen draws none of setup's output and does not repeat it when it closes.
- **Ctrl-C.**
  - At a question (a list, a multiple choice or a typed answer), or while a command works, Ctrl-C ends the command at once with exit code 130 and the line `interrupted`, on a Windows console too. `doctor` does the same while it checks (`doctor --json` keeps the code of its checks), and so does an install or an upgrade while its closing checks run: the summary shows what there is, and the command ends as interrupted.
  - A prompt that hides what you type and is read by the terminal's own no-echo reader, such as a pasted App key or the recovery key of a restore, cannot be interrupted while it reads: press Enter first. The paste of the manifest code (section 5.3, step 3) is hidden too, and Ctrl-C does stop it, as does GitHub's answer where the terminal can be waited on.
  - Ctrl-C at the Enter that ends setup, the summary or the last page, during the short wait for the service that comes just before a summary (the summary may then lack its `Instance ID` and `Version` rows), or before the closing checks have started, only skips the wait or the checks, because the work is done (the `Doctor` row then reads `skipped (Ctrl-C)`; one that interrupts the checks reads `interrupted` and the command exits 130): the exit code is the command's own, and `doctor` keeps the exit code of its checks. The offers that come after the work, the copy of the program on the PATH and the removal of that copy at a purge, count a Ctrl-C as No, and the command still ends with exit code 0; a Ctrl-C at the copy offer also skips the closing checks that follow it (`Doctor: skipped (Ctrl-C)`).
  - Ctrl-C at the page of an error (above) only closes it, and the exit code stays the command's own.
- **After the screen closes.** The command leaves the full-screen window and prints on your normal terminal what you must not lose, so it stays in the scrollback: every check and warning of the run, of every step, in the order they were written, with the `✓` and `!` marks the screen drew (a `FAIL` or `WARN` of `doctor` keeps its word beside the `!`), and the lines the command kept. After an install or an upgrade, the summary follows, with these rows: `Installation type` (`on this computer` or `on a separate server`), on the co-located tier a row `Security limit` that holds the reduced-assurance sentence of section 2, `Container program`, `Instance ID` and `Version` (the version of the service), the GitHub App and its repositories, the owner, where to read `/status`, the `Settings file` and, on the co-located tier, the `Access token file` and a row `Test runner` (how the executor is kept running, as the mechanism of the system and the path of its copy of the program, or `not set up: <why>` when its setup failed or another instance's executor is registered); an upgrade's swapped image as `Image: <digest> (was <digest>)`; on Windows the copy of the program; the result of the closing `suiteward doctor` (its counts, and one warning with its fix for each result that needs a look). An upgrade also keeps the way back for its tier. On a window too small for the whole summary, the screen keeps the rows `Installation type`, `Security limit`, `Instance ID`, `Status` and `Doctor` and trims the rest behind a line that says so, the warnings first (from the end), then the other rows. The `Security limit` row stays because the sentence is a security disclosure; the lines kept for your terminal are never trimmed, so everything is there after the screen closes. After `backup init`, `backup` and `restore`, the summary follows and the kept lines name what you must keep: where the recovery kit is and to keep it off the machine, which key a backup is encrypted to, where the backup is and the `suiteward restore` command for it, and, after a restore, where the backup of the state before it is and how to bring the canonical level with the default branch ([the backup runbook](backup.md#3-restore)). After `uninstall`, `install host`, `enroll`, `doctor` and an upgrade with nothing to do, it is the last page as it was held (the command to run next, what was removed, the results of the checks and their counts). After a failure it is the page the command stopped on, and then the error.

### The answers file

A flat YAML file in which every key is a flag name, except `github-app-key` and `manifest-code`, which exist only here because they are secrets, and every value is a plain scalar. The installer reads the answer from the flag, else from the file, else it asks at the terminal. When it cannot ask (standard input is not a terminal), it takes the default, or stops and names the missing flag. On Linux and macOS, the file must be readable by you only (`chmod 600`): the installer refuses a file that others can read. Windows has no such check, so keep the file in a folder only you can read. A secret never goes in a flag, where it would show in the process list: the installer refuses `--manifest-code`, so give a manifest code as `manifest-code` in the answers file, and the App's key as `--github-app-key-file`, or as `github-app-key` (the PEM) in the answers file. Example, without any secret:

```yaml
tier: co-located
runtime: podman
http-port: 27081
mcp-port: 27091
github: "yes"
github-account: personal
github-repositories: owner/name
github-owner: octo
test-check: "owner/name=CI / test"
ruleset-imported: "yes"
```

`test-check.owner/name` sets the check of one repository. Never put the TOTP secret or a TOTP code in this file. The App's private key (only as `github-app-key`) and a manifest code (only as `manifest-code`) may be in it, only at mode 600: delete the file afterwards.

### What the installer does, for review

The installer replaces about 11 manual commands on the co-located tier and about 62 on the isolated tier. This list maps its steps to the manual procedure that older releases documented, and says why. [The v0.2.0 guide](https://github.com/IgnisDevNE/SuiteWard/blob/v0.2.0/docs/install.md) has that procedure.

| Step | Why |
| --- | --- |
| Refuses a rootful Podman connection, and never runs as root. | A rootless store keeps the containers away from the host's root. Isolated splits the administrator steps from the service account's. |
| Identifies the engine behind the runtime and prints it. | The name `docker` can be Podman's shim, and the default Docker endpoint can belong to Podman's machine. |
| Pulls images by digest only, and refuses a tag. | A tag can be rewritten and a digest cannot. The binary carries the signed digest of its release. |
| Checks both ports before it changes anything. A new install takes 27081 and 27091 and a stack that exists keeps its own. | A refusal must leave a running stack alone. The defaults are off the crowded 8080-8099 range and below the ephemeral ports of Linux (32768-60999) and Windows (49152 and up), where an outgoing connection can hold a port. |
| Creates the network, the two volumes and the database owner secrets, with a generated password. | The password is never typed, shown or passed as an argument. |
| Starts the database, creates the role `suiteward_app`, runs `suiteward migrate`, and only then starts the service. | The service runs as a role that owns nothing and cannot change the schema or the immutability triggers. Only the one-shot migrate container holds the owner's URL. |
| Runs every container read-only, with all capabilities dropped and `no-new-privileges`, the service and migrate as user 65532 and the database as 999, with the published ports on 127.0.0.1 only. | Defence in depth: the listeners are never reachable from the network. |
| Creates the App through the manifest flow, with exactly five permissions, no webhook, `public: false`. | No Contents write and no Administration write: SuiteWard never commits and never changes protection. |
| Converts the manifest code on the machine that keeps the key, with a random `state`, and writes the key straight into the secret store. | The key never touches disk or the terminal. The code passes through your browser, as a downloaded key would. |
| Writes the ruleset JSON, waits for your Import, reads the protection back and deletes the file of each repository that reads as enforced. | The App has no permission to change rules. A rule change stays a human click for each repository, and the file is only the way to that click, so it goes once the import worked and stays while the import is still needed. |
| Runs setup with the real terminal and never captures its output; on Windows and macOS it runs setup in a window of its own that clears itself, and elsewhere it leaves the full screen first, so that the screen never draws or repeats the secret. It refuses to run setup without a terminal, and skips it when an owner is enrolled or `/status` cannot be read. | Setup prints the TOTP secret. A coding agent must not read it, and a second setup would replace the secret of the enrolled owner. |
| Gives the service `SUITEWARD_REPORT_BASE_URL=http://127.0.0.1:<HTTP port>`, on both tiers, with the port you chose. | It is the host's loopback address where the unit or container publishes the service's HTTP port (the one you chose). The installer never publishes that port beyond 127.0.0.1. A stack of an earlier release lacks the variable and is adopted as it is: `install --upgrade` adds it, and so does a Podman re-run of `install`, which replaces both containers. A Docker re-run keeps a running service of an unchanged image as it is, so that service stays without the variable, and its comments have no link, until `install --upgrade`. |
| `--upgrade` backs up the database, the artifact volume and the status first, as one encrypted file that only the holder of the recovery kit opens. | Migrations only go forward, so the backup is the only way back, and it holds the TOTP secret, so it is never written in plaintext. A run with no key and no terminal refuses before it changes anything. |
| `suiteward backup init` makes a post-quantum key pair, writes the private key only into a kit file that only you can read and that it never overwrites, and stores only the public key in the settings. | The instance needs the public key to encrypt, and never the private one: whoever reads the settings cannot read a backup. The kit is the owner's to keep off the machine, and it is removed if you do not confirm that you copied it. |
| `suiteward backup` dumps the database in memory, spools the artifact volume in a private directory, and writes one encrypted file, while the service keeps running. | The dump holds the TOTP secret, so it is never a file in plaintext. The dump comes first, so the volume holds every artifact that the dump names. |
| `suiteward restore` verifies the whole backup, previews it, backs up the state it replaces, stops the service, loads the dump in one transaction, replaces the volume, migrates, starts and compares `/status`. | A restore replaces data, so it checks everything before it touches anything, always keeps a way back, and never leaves a half-loaded database: the transaction commits only after the last line of the dump. |
| Writes its settings to a file of its own. | `doctor` and the next run read it back, and nothing else is silently overwritten. |
| On Windows, offers to copy itself to `%LOCALAPPDATA%\SuiteWard\bin` and to add that folder to the PATH of the user, and refreshes that copy on `--upgrade`. | Every command it prints must work in the terminal of the user. The offer is a question with a default, the copy is the user's own, and nothing is changed without a yes. |
| Enables `podman-restart.service` for the rootless user (Podman). | A rootless `--restart always` needs it after the machine restarts. |
| Isolated: checks Podman 5.5 or later with the CVE fix, makes the account, its subordinate ids and linger, and offers the metadata rule. | Rootless Podman needs the ranges, the services must outlive a login, and a metadata service hands out instance credentials. |
| Isolated: writes six unit files and checks them with the generator's dry run. | Podman skips a unit it cannot parse, and you would only see "unit not found" later. |
| Makes the executor's token once (32 random bytes), keeps one copy for the executor and gives the service a secret, and never prints it. | The executor holds one credential, its own token, which is not the MCP token and not a credential of the service. |
| Runs the executor as a separate process from a copy of the program: co-located, a copy beside the token files; isolated, a root-owned copy with a pin. | The service keeps the App key and the database and never gets a container-runtime socket. A copy is not taken along when the program that was run is moved, and the pin lets `doctor` see drift. |
| Co-located: starts the executor with the mechanism of the operating system, a scheduled task of the logged-on user on Windows, a launch agent on macOS and a systemd user unit on Linux. | Each starts the program when the user logs on and keeps it running, with no administrator rights and no stored password, as the user whose container runtime the executor drives. On Windows the task runs the script through `conhost.exe --headless`, so that no window opens, and the script starts the executor again about 5 seconds after it ends, because Task Scheduler does not restart an action that exited. |
| Co-located: stops the executor as a whole tree on Windows (the task, the script and the program, found by this instance's paths, never by name) before it replaces or removes it, and stops with an error if a process is left. | `schtasks /End` ends only the console host, and the script would start the program again. A name would also end another instance's executor. |
| Co-located: says the reduced assurance of the tier once: on the page that introduces it, in the summary of an install and of an upgrade (the row `Security limit`, which a small window keeps), and at the end of a plain install or of a plain upgrade that upgrades. | It is a security disclosure, and repeating it in every row of `doctor` would bury it. |
| Pulls the Go image of the sandboxes by digest: co-located with the install, isolated in the host step, into the executor's own storage. | Every sandbox starts with `--pull=never`, so an engine or an account without the image would end every job as unavailable. |
| Isolated: gives the executor an account of its own with its own subordinate ids and linger, and a drop-in that delegates the cgroup controllers `cpu cpuset io memory pids`. | Two rootless Podmans must not share a user namespace, the service account must not reach the executor, and EL9 gives a user manager only `memory` and `pids`, so `--cpus` would fail. |
| Isolated: refuses `169.254.169.254` and `fd00:ec2::254` to the executor's uid on every port, without asking. | Rootless containers connect as a process of that account, so a rule for the account covers its sandboxes. The executor runs what a pull request brings. |
| Isolated: requires the release's `SHA256SUMS` (`--sha256sums`, or the answer to a question on a terminal) to install the executor's binary, whose line is its pin, and refuses to run without it. Co-located: takes it as an option, and without it pins the hash of the copy and says so once. | The pin must come from the release, and not from the program that was run. The co-located tier keeps the option, and `doctor` warns while the pin is only the hash of the copy. |
| Isolated: gives the executor's unit `MemoryMax=3G`, `GOMEMLIMIT=2500MiB`, `KillMode=mixed` and a stop timeout of 45 seconds. | The executor's peak is about 1.5 GiB live; the Go runtime collects before the cgroup kills the process; a signal to the `podman run` child would fail the job; and a job in flight gets 30 seconds after SIGTERM. |

### What `suiteward doctor` checks

`doctor` only reads. Its rows do not repeat the reduced assurance of the co-located tier: the installer says it once (section 2). It prints `ok <name>`, `WARN <name>: <what needs a look> — <the fix>` or `FAIL <name>: <what is wrong> — <the fix>`, and exits non-zero when anything failed: a warning does not. The install and the upgrade run the same checks as the last step of their summary on a full screen, and show the counts and the fix of each result that needs a look; they never fail because a check failed. With `--json`, a warning has `"warning": true`. It runs `suiteward check --json` inside the service container and merges its results. The service does not know the flags of the instance, so a row of the service names a command such as `suiteward enroll` by its bare name in a list of its own, and `doctor` writes each of those commands with the `--settings` and `--token-file` that name the instance it checks (none for the default instance; a service of an earlier release sends no such list, and its rows are shown as it wrote them). On an instance installed without GitHub, the database checks run, and `github.app`, `github.installation`, `github.permissions`, `github.repositories` and `owner.enrolled` are warnings; run the install with `--github yes` to set GitHub up.

| Name | A FAIL means |
| --- | --- |
| `settings` | There is no settings file, or it is invalid. Run `suiteward install`, or pass `--settings`. |
| `machine` | The Podman machine does not exist, is starting or is not running. Run `podman machine start`. |
| `runtime` | The engine does not answer, the connection is rootful (select the rootless one), or `docker` is not Docker. Set `connection` in the settings file. |
| `containers` (co-located) | `suiteward-db` or `suiteward` is not running, or the database is not healthy. Read the container's log, fix the cause and start it. |
| `restart` | The containers or units would not come back after a restart: a restart policy is not `always`, or `podman-restart.service` is not enabled for the rootless user (co-located), or a unit lacks `WantedBy=default.target` (isolated). Enable the service as the fix names. |
| `units`, `linger` (isolated) | A unit is not in its expected state, or the account does not linger. Read the journal, or run `sudo loginctl enable-linger suiteward`. |
| `pins` | The release images of the units or containers are not one digest, or the database image is not the pinned one. Run `suiteward install --upgrade`, or undo the edit it names. |
| `ports`, `healthz`, `status` | `/readyz`, `/healthz` or `/status` does not answer on the recorded port, or `/status` reports a failed outbox message or a discarded job. Read the service log. |
| `network`, `memory` (isolated) | The Podman network backend is not `netavark`, or the database is not limited to 384 MiB. The fix text says what to do: install netavark and set it in `containers.conf`, or check `PodmanArgs=--memory=384m` in `suiteward-db.container`, restart the unit and check that `podman inspect` prints 402653184. |
| `metadata` (isolated) | `169.254.169.254` answers from the service network. As an administrator, run `sudo /usr/local/bin/suiteward install host --sha256sums <the release's SHA256SUMS file> --metadata-rule yes`, which adds a firewall rule that blocks the address for the service account, then run doctor again. |
| `executor.account`, `executor.delegation`, `executor.network`, `executor.unit` (isolated) | `suiteward-exec` does not exist, has the service account's uid, or has subordinate id ranges that overlap the service account's, or does not linger; its user manager lacks the `cpu`, `memory` or `pids` controllers (or `delegate.conf` is not the release's); the rule file `exec-block.nft` is not the release's or `suiteward-exec-block.service` is not active (doctor runs as the service account and cannot read the loaded table, so it checks the file and its unit); or `suiteward-executor.service` differs from the unit of the release, which names the port the service publishes. As the administrator, run the host step again (10.2): the fix of a unit that names another port is `--http-port <port>`. |
| `executor.binary` | There is no copy of the program or no pin beside it, the copy changed since it was installed, or it is another build than the program that runs doctor. Isolated: also when the pin does not name a release asset (`suiteward_<tag>_linux_<arch>`), because on this tier the executor's binary is pinned to the release's line of `SHA256SUMS`, which the host step requires. Co-located: a warning (not a failure) while the pin is only the hash of the installed copy, so that nothing checked it against a release (`The test runner has not been checked against an official release. This is normal for a development build.`). Doctor never reads the `SHA256SUMS`: it compares the binary with its pin and checks the name that the pin carries. The fix of a failure: run the host step again with this program and `--sha256sums <the release's SHA256SUMS file>` (isolated, as the administrator), or `suiteward install --upgrade` with this program, or `suiteward install` again (co-located; when another instance's executor is registered, that instance's removal, as for `executor.lifecycle`). The fix of the warning: `suiteward install --upgrade --sha256sums <the release's SHA256SUMS file>` with the program of that release. |
| `executor.token` (co-located) | The executor's token copy is not there, or the service container has no executor token (it was made by an earlier release). Run `suiteward install --upgrade` with this program, or `suiteward install` again. Or doctor does not know where this instance's token copy is: the settings file is not the default one and `--token-file` was left out, so the default token file is the main instance's. It fails this one row, and checks no other executor row (`executor.lifecycle`, `executor.binary`, `executor.running`, `executor.image`, `executor.loopback`), because they would read the main instance's executor. Pass `--token-file` with the token file of this instance (the one its install was given), or, for the only instance on the computer, `--token-file` with the default token file. |
| `executor.lifecycle` (co-located) | The operating system does not know the executor: it should be a scheduled task, a launch agent or a user unit (section 5.4), or the operating system could not be asked. Run `suiteward install` again, which registers and starts it. Or, on Windows, the scheduled task is not the one this build makes (the `task.xml` that the install left differs: a task of an earlier build, which opens a window and does not start the executor again, or one that was changed), or `task.xml` cannot be read: run `suiteward install` or `suiteward install --upgrade`, which end the old tree and register the current task. Or the executor of this user belongs to another instance (a computer has one executor): remove that instance (`suiteward uninstall`, with its `--settings` and `--token-file`, none for the main instance), then run `suiteward install` again for this one, because until then an install leaves the registered executor as it is. |
| `executor.running` | `/status` has no `execution` object (the service is older than this release); the service has no executor token (`SUITEWARD_EXECUTOR_TOKEN` is unset, so every job is unavailable); the executor's process is not running (when another instance's executor is the registered one, none runs for this instance); or it runs and the service last saw an executor more than 2 minutes ago (it cannot reach the service at `http://127.0.0.1:<HTTP port>`, or it sends another token). The fix names the command that starts it or gives the token, and where its log is; for another instance's executor it is that instance's removal. On the isolated host, a service without the token needs the host step and then `suiteward install --tier isolated` as the service account, which gives the service the token and restarts it. |
| `executor.image` | Co-located: the engine has no Go image of the sandboxes under its digest, so every job is unavailable; the install pulls it. Isolated: doctor cannot read the storage of `suiteward-exec`, so it passes with that said, and the host step is what pulls and verifies the image at every run (run it again after an upgrade). |
| `executor.loopback` (co-located, a Podman machine) | This PC cannot reach the port that the machine publishes for the service, so the executor, a program of this PC, cannot reach it either: the runs read `no-executor`, and the owner can unblock each head. Restart the machine (`podman machine stop`, then `podman machine start`) and run doctor again. |
| `github.app`, `github.installation`, `github.permissions`, `github.repositories` | GitHub refuses the App key, the installation is not the App's, the installation's permissions are not exactly the five, or a repository is not covered or not readable. Check the App ID and the key against the App's settings page. |
| `protection.<owner/name>` | The repository's protection is not `enforced`. Its fix names the finding (section 7). |
| `owner.enrolled` | Setup has not run. Run it (section 6). |
| `database.schema`, `database.role` | The schema is not at this release's version, or the service's role is a superuser, can create roles or bypasses row-level security. |
| `instance.check` | `suiteward check` could not run in the service container. Start the service. |

## 13. Configuration reference

Every setting is an environment variable named `SUITEWARD_<NAME>`. A secret can instead be given as `SUITEWARD_<NAME>_FILE`, the path of a file whose content is the value. Give one form, not both. A variable that is set but empty counts as unset.

Where you set them:

- **Isolated host:** the installer renders the units, with the ports and the job timeout of `--http-port`, `--mcp-port` and `--job-timeout` when they are given. It carries the tier, the two ports and the job timeout over from the installed units, and any other edit of a unit stops the next install with a diff. The three GitHub values are in `~/.config/suiteward/github.env`. After a hand edit, run `systemctl --user daemon-reload` and `systemctl --user restart suiteward.service` as `suiteward`. After a change in `suiteward-migrate.container`, or to an `Image=` line, restart `suiteward-migrate.service` instead. The service unit mounts the executor's token from the secret `suiteward-executor-token` when it exists, and the executor, which is not one of these units, has its own unit that only the host step writes (10.2); the three `SUITEWARD_EXECUTOR_*` durations have no installer setting, so on this host they keep their defaults.
- **Co-located PC:** `suiteward install` has flags for the ports (`--http-port`, `--mcp-port`), the image, and `--job-timeout` (`SUITEWARD_JOB_TIMEOUT`, for the service container only). The GitHub values come from its GitHub flow. The other settings keep their defaults on this PC, and the installer makes the executor's token and gives it to the service container. Pass `--job-timeout` on every run that should have it: a run without it keeps the saved value. The three `SUITEWARD_EXECUTOR_*` durations below have no flag: they keep their defaults.

| Setting | Default | Meaning |
| --- | --- | --- |
| `SUITEWARD_DATABASE_URL` (secret, required) | none | The PostgreSQL URL of the application role `suiteward_app`, never the owner. Use the `_FILE` form. The isolated units mount it from the Podman secret `suiteward-database-url`. |
| `SUITEWARD_MIGRATION_DATABASE_URL` (secret) | none | The PostgreSQL URL of the database owner. Only `suiteward migrate` connects with it, and it requires it; `serve`, `setup` and `probe` refuse to start when it is set, so never put it in the service's unit. Use the `_FILE` form. Only the migration unit mounts it, from the Podman secret `suiteward-database-owner-url`: the service never gets it. |
| `SUITEWARD_ARTIFACT_DIR` (required) | none. The image sets `/data/artifacts` | Absolute path of the artifact store. |
| `SUITEWARD_HTTP_ADDR` | `127.0.0.1:8080`. The image sets `0.0.0.0:8080` | Address of the HTTP listener. The units publish it on the host's loopback only. |
| `SUITEWARD_SHUTDOWN_TIMEOUT` | `30s` (1 s to 10 min) | Time allowed for a graceful stop. The container's stop timeout must exceed this by at least 5 s. The units set 45 s, which covers the default. A value of 40 s or more needs a larger stop timeout. |
| `SUITEWARD_LOG_LEVEL` | `info` | One of `debug`, `info`, `warn`, `error`. |
| `SUITEWARD_JOB_WORKERS` | `4` (1 to 64) | Number of background workers. |
| `SUITEWARD_JOB_TIMEOUT` | `1m` (1 s to 1 h) | Time limit of one attempt of a background job. A `propose` or a check reads about a thousand protected files per minute of this value (eight at a time, and what was read is kept for the next attempt); raise it only for a very large test suite. On the isolated host, set it in `suiteward.container`; on the co-located PC, pass `--job-timeout <value>` (for example `3m`) to `suiteward install` (section 5). |
| `SUITEWARD_JOB_MAX_ATTEMPTS` | `5` (1 to 25) | Attempts before a background job is marked discarded. |
| `SUITEWARD_OUTBOX_MAX_ATTEMPTS` | `8` (1 to 25) | Attempts to deliver a message to GitHub before it is marked failed. |
| `SUITEWARD_OUTBOX_POLL_INTERVAL` | `5s` (1 s to 1 h) | How often the relay looks for messages to send. |
| `SUITEWARD_OUTBOX_LEASE` | `1m` (at least 5 s) | Lease on a message while it is being sent. |
| `SUITEWARD_GITHUB_APP_ID` | none | Your App ID, a positive integer. The four GitHub settings are all set or all unset. |
| `SUITEWARD_GITHUB_APP_KEY` (secret) | none | The App's private key in PEM form. Use the `_FILE` form. |
| `SUITEWARD_GITHUB_INSTALLATION_ID` | none | The installation ID, a positive integer. |
| `SUITEWARD_GITHUB_REPOSITORIES` | none | `owner/name` entries, comma-separated, 1 to 20, no duplicates. |
| `SUITEWARD_GITHUB_API_URL` | `https://api.github.com` | The GitHub API address. Keep the default for github.com. It must be `https`, except that `http` is accepted for a loopback host (for a local test server). |
| `SUITEWARD_INSTALLATION_TIER` | `co-located` | `isolated` or `co-located`. Set the tier you installed. SuiteWard never claims more than you set. The isolated units set `isolated`. |
| `SUITEWARD_REPORT_BASE_URL` | none | The loopback origin of the instance, `http://127.0.0.1:<port>` or `http://localhost:<port>`, with the port that the HTTP listener is published on at the machine that runs the instance (`--http-port`, 27081 by default), not the port inside the container that `SUITEWARD_HTTP_ADDR` names (no path, query or user info; a trailing slash is dropped). The links of the revision comment (the change report, and the pull request page when the receipt applies) and of the comments of a head start with it. Anything else stops the service at startup, and the value is not echoed. Without it, these comments have no link. The installer sets it on both tiers from `--http-port`. |
| `SUITEWARD_MCP_ADDR` | `127.0.0.1:8090`. The image sets `0.0.0.0:8090` | Address of the MCP listener. It starts only when `SUITEWARD_MCP_TOKEN` is set. |
| `SUITEWARD_MCP_TOKEN` (secret) | none | The MCP bearer token, at least 32 bytes. Use the `_FILE` form. |
| `SUITEWARD_MCP_ALLOWED_ORIGINS` | empty | Browser origins allowed to call MCP, comma-separated. Clients that are not browsers send no origin. |
| `SUITEWARD_EXECUTOR_TOKEN` (secret) | none | The bearer token of the executor API, at least 32 bytes, separate from the MCP token. Use the `_FILE` form. Unset: the executor routes answer 404, and every execution job is created already `unavailable` (`executor-not-configured`). The installer makes it and gives the same value to the service and the executor. |
| `SUITEWARD_EXECUTOR_JOB_TIMEOUT` | `30m` (12m30s to 6 h) | How long one whole attempt may run once an executor leased it; it ends the attempt as `timeout`, which is counted and retried. A smaller value than 12m30s stops the service at startup. The floor is what the first run of a hung test needs to end as `go test`'s own kill (the test reads `fail`) and not as the executor's drop of the attempt: the 10 minutes of `-timeout`, the minute after which `go test` kills a binary that ran past it, the 30 seconds before the deadline at which the executor drops an attempt, and 60 seconds for everything around the test binary (the download, the prefetch, the tar, the container start and a cold compile before it, the parse and the post after it). It does not cover a test that hangs on every rerun ("Limits of canonical execution"). Every container builds with a cold cache, so size it for the whole attempt (about 32 s per container for this repository's untagged tests on 4 CPUs). It is not `SUITEWARD_JOB_TIMEOUT`, which bounds a background job. |
| `SUITEWARD_EXECUTOR_LEASE_WAIT` | `2m` (2 m to 1 h) | How long the service may go without seeing an executor (a lease request, a heartbeat or a result post) before its pending jobs become `unavailable` (`no-executor`) and are not retried. It is the time since an executor was last seen, never the age of a job, and it starts at the start of the service. A head reads not responding after the same silence of about 30 seconds, which is not a setting (section 9). |
| `SUITEWARD_EXECUTOR_GITHUB_WAIT` | `30m` (1 m to 6 h) | How long a job may keep failing to read GitHub (the tree, the merge base, an archive; counted from its first failure) before it becomes `unavailable` (`github-unavailable`). |

The executor reads three settings of its own, and no other: `SUITEWARD_EXECUTOR_URL` (the origin of the service's HTTP listener, `https`, or `http` for a loopback host; required), `SUITEWARD_EXECUTOR_TOKEN` or `SUITEWARD_EXECUTOR_TOKEN_FILE` (the same value as the service's; required) and `SUITEWARD_EXECUTOR_RUNTIME` (`podman`, the default, or `docker`). It refuses to start, naming the variable, when its environment holds `SUITEWARD_DATABASE_URL`, `SUITEWARD_MIGRATION_DATABASE_URL`, `SUITEWARD_GITHUB_APP_KEY`, `SUITEWARD_MCP_TOKEN` or the `_FILE` form of one of them. The installer writes all of this into the unit, the task or the launch agent, so you do not set them by hand. The Go image is not a setting: it is pinned by digest in the program, and the service names it in each lease.

## 14. Source code

SuiteWard is licensed under `AGPL-3.0-only`. The license text is in the repository's `LICENSE` file. The image carries that text as `/licenses/LICENSE`, and the license of every module it links as `/licenses/THIRD_PARTY_NOTICES` (`deploy/notices.sh` writes it at the image build). The executor is the same binary, so its modules are in that notice too: `golang.org/x/mod`, which validates module paths and versions for the dependency prefetch, joined it with the executor.

`/status` reports the URL of the exact source revision the binary was built from, as `source`. The project chose this as its pointer to the source ([D-RELEASE](plan/decisions.md#d-release-platforms-versions-license-and-notices)). For a release, that is `https://github.com/IgnisDevNE/SuiteWard/tree/vX.Y.Z`. If `source` is absent, the build set none.

`/status` is reachable only over the loopback address of the host, so it does not by itself satisfy section 13 of the AGPL for remote users. If you modify SuiteWard, you must offer the corresponding source of your modified version where your users interact with it, and point `source` at that source. Build the image yourself with the `SOURCE` build argument, alongside `VERSION`:

```
podman build -f deploy/Containerfile --build-arg VERSION=sha-<commit> --build-arg SOURCE=<url of your modified source> -t localhost/suiteward:local .
```

`/licenses` in the built image holds the license and the third-party notices, whatever `SOURCE` you build with.

## 15. Troubleshooting

Start with `suiteward doctor`: it names what is wrong and the fix, and it reads nothing it should not (section 12). Then read `/status` and the logs.

- **Isolated host (as `suiteward`):** `curl -s http://127.0.0.1:<HTTP port>/status` (27081 by default, 8081 on a host installed before M1.14), then `journalctl --user -u suiteward.service -n 100 --no-pager`, for the migration `journalctl --user -u suiteward-migrate.service -n 50 --no-pager`, and for the database `journalctl --user -u suiteward-db.service -n 50 --no-pager`. The migration container is removed when it exits, so `podman logs` cannot show it. The executor belongs to the other account: as the administrator, `sudo journalctl _SYSTEMD_USER_UNIT=suiteward-executor.service _UID=$(id -u suiteward-exec) -n 100 --no-pager`.
- **Co-located PC:** the installer prints where to read `/status` at its end: `http://127.0.0.1:<HTTP port>/status` (27081 by default, or the port of your stack) when it answers from this PC. When it does not (the published port of a Podman machine may not answer from Windows itself), it prints the command that reads it inside the machine, `podman machine ssh --username user <machine> "curl -s http://127.0.0.1:<HTTP port>/status"`; on macOS that is the same command with your machine's user (step 5.1). Then `podman logs --tail 50 suiteward` (with the rootless connection selected, step 5.1), or the engine's own `logs` command on Docker. The migration runs in the foreground of `suiteward install`, which shows its output. The executor's log is `executor.log` in its directory on Windows and macOS (section 5.4) and the user journal on Linux, `journalctl --user -u suiteward-executor.service`.

On AlmaLinux, `journalctl --user` can report that no journal files were opened: user journals are readable only to members of `systemd-journal`. Read the service's own log instead, with `podman logs --since 30m suiteward` (and `suiteward-migrate` or `suiteward-db`).

If the log shows `github_checks` ending in `context deadline exceeded` again and again, then `budget_exhausted`: a first assessment of a large test suite takes longer than `SUITEWARD_JOB_TIMEOUT`, and every cancelled attempt reads the files again and spends the API budget. Raise `SUITEWARD_JOB_TIMEOUT` (section 13: one minute covers about a thousand protected files, read eight at a time). Read `budget` in `/status` (or the MCP `status` tool): `budget.remaining` is what is left and `budget.reset` is when requests resume. The budget recovers when GitHub's hourly window resets, and the queued check is then published by itself.

These are the `/status` fields you read:

- `tier` is the effective tier. `tierNote` appears when the setting and the enrollment disagree. Run `suiteward enroll` (section 6; `--tier isolated` on the isolated tier).
- `owner` shows the enrolled login. It is absent until setup succeeds.
- `budget` is the GitHub API budget: `budget.remaining` is the number of requests left in the current hourly window, and `budget.reset` is when the window resets. It is absent until GitHub has answered once, and when GitHub is not configured.
- `unconfiguredRepositories` lists the enrolled repositories that the configuration does not name. It is absent when there are none.
- `github` has one entry per repository:
  - `lastSuccess` is the last successful synchronization.
  - `lastError` is the last synchronization error, as short text without secrets. If `waitUntil` is set, GitHub asked SuiteWard to wait because of a rate limit, and SuiteWard resumes by itself. Otherwise, check that the App is installed on that repository, and that the App ID, the installation ID and the key are the ones from step 10.4.
  - `protection` shows the results of section 7.
  - `checks` is the last error while SuiteWard published that repository's check. It is absent when there is none.
  - `bootstrap` shows why the first contract is waiting or stopped. `read-failed` means GitHub could not be read, and SuiteWard retries. `repository-changed` means the configured name now points at a different repository from the one enrolled, so check the name. `origin-not-passed` means the default branch's contract could not be read as a passing source. `assessment-conflict` means two assessments of one source disagree. `blocked-<reason>` means a block for the stated reason. `failed` means the bootstrap failed for good. Read the logs for the last three. The field is absent when nothing is wrong.
  - `merges` shows merge decisions. `waiting` means GitHub has not yet reported the merge commit, and SuiteWard retries. `read-failed`, `assessment-conflict` and `failed` need the logs.
  - `integrity` is `passed`, `failed` or `unavailable` for the current version. It appears after the first integrity check, which runs when the service starts, right after each promotion and then every hour, so a canonical shows its `integrity` within moments of its promotion. `failed` means SuiteWard fails the check on every pull request of that repository and does not promote until the problem is resolved; it does not block merges by itself — your branch protection does that, if you require the check. `unavailable` changes no check.
- `outbox.failed` counts messages that SuiteWard could not deliver to GitHub after its retries. It should be 0. Read the logs for the repository. A refused write is often a missing App permission, so compare with step 10.4. If the failed message was a check, SuiteWard sends it again by itself about 15 minutes after the cause is fixed. Until then a pull request can lack its required `SuiteWard / Contract` check. Push a new commit to that pull request to get a new check at once.
- `jobs.discarded` counts background jobs that failed for good. Read the logs.
- `execution` describes the executor's side: `enabled` is true when the service has an executor token, `jobs` counts the execution jobs in each state (`pending`, `leased`, `complete`, `unavailable`, `cancelled`), and `lastSeenAt` is when an executor last asked for a job, sent a heartbeat or posted a result. The service sets that time to its own start when it starts, so a recent `lastSeenAt` right after a restart does not prove an executor exists: `suiteward doctor` pairs it with the executor's process.
- `version`, `schemaVersion` and `source` identify the release and the database schema that run. `instance` is the first 8 characters of the instance id, the same as in the name of the authenticator entry that setup creates (`SuiteWard:<login> (<tier> <instance>)`), so you can match an entry to an instance.

Common problems:

- **The installer says that the connection is rootful, or asks for `--connection`.** The stack must run rootless. Select the machine's rootless connection with `--connection <name>` (step 5.1) and run it again. The installer never changes your Podman default.
- **The installer says that `docker` is not Docker, or that the container program behind it is Podman.** On a PC with both, `docker` can be Podman's shim (`C:\Program Files\RedHat\Podman\docker.cmd`), and the default endpoint (`npipe:////./pipe/docker_engine`) can be served by the Podman machine. Use Podman, or give Docker Desktop's own context with `--connection desktop-linux`. The installer runs Docker Desktop's CLI by its full path, `C:\Program Files\Docker\Docker\resources\bin\docker.exe`.
- **Docker Desktop fails to start with `open \\.\pipe\docker_engine: Access denied`.** Whichever engine starts first owns the `docker_engine` pipe, and the Podman machine had it. Stop the Podman machine, start Docker Desktop, then start the machine again: it then uses its own pipe. The installer and `doctor` address each engine by its own endpoint, so they do not depend on the pipe.
- **A Docker pull fails with `error getting credentials`.** Docker Desktop's credential helper lives in `C:\Program Files\Docker\Docker\resources\bin`. The installer puts that folder on the PATH of the commands it runs. For a pull you run by hand, add it to your PATH.
- **After Windows or macOS restarts, nothing answers.** The Podman machine does not start at logon in this release. Run `podman machine start`: the containers then come back by themselves, and `suiteward doctor` reports the machine until you do.
- **The one-line install prints a 404 error from curl, or stops with a message that names `SUITEWARD_VERSION`.**
  - A 404 before any message of the script means the release has no `install.sh` (no release built before phase M1.13 has one). `curl -f` wrote nothing, so the shell received nothing and ran nothing. The pipe's exit status is the shell's, not curl's, so read the message.
  - A message that names `SUITEWARD_VERSION` comes from the script itself. The release does not exist or has no `SHA256SUMS`, or its `SHA256SUMS` does not list `suiteward_<tag>_<os>_<arch>` exactly once, or that binary cannot be downloaded, or GitHub refused the anonymous lookup of the latest release.
  - In both cases, give the tag of a release whose page lists `install.sh` and the binary of your system (section 4.1). Nothing was installed.
- **The one-line install says the signature was not verified, or that cosign could not verify it.** Without cosign the script installs on the hash of `SHA256SUMS` alone and prints how to verify the signature elsewhere; install cosign 3.x to have it checked, or set `SUITEWARD_REQUIRE_COSIGN=1` to refuse to go on without it. When cosign is there and fails, the script stops and installs nothing: the file is not the one the release workflow signed, or cosign is older than 3.x. Do not run a binary that was not verified.
- **macOS refuses to open `suiteward` and says that Apple could not check it.** Gatekeeper blocked a file that carries the quarantine flag, as a browser download usually does (section 4.2). Verify the file, then run `xattr -d com.apple.quarantine <file>`.
- **A port is in use.** The installer names the flag: choose another with `--http-port` or `--mcp-port`. Docker Desktop's VM shares a network namespace with the Podman machine, so two stacks on one PC need different ports.
- **A command says that `http_port` or `mcp_port` is not set in the settings file.** The installer always writes both ports, and it refuses a file without them: a default would move a stack that exists to another port at the next run. Add the ports the stack publishes (`podman ps` shows them) to the file, or install again with `--http-port` and `--mcp-port`.
- **The install ended with exit code 0, but its summary shows failures.** The closing checks of a full screen report what needs a look and never fail the install. Read each line: it names the fix, such as the ruleset to import. `suiteward doctor` runs the checks again.
- **A command that the installer printed says that `suiteward` is not found (Windows).** The program is not on your PATH, and the installer names it by the path it was run from when it is not. Run it by that path, or accept the copy to your PATH that an install or an upgrade offers on a full screen (section 5.7).
- **The installer stops with a diff, or says that a container of the stack's name exists that it did not make.** It never overwrites a stack it cannot adopt. Compare the diff with what you changed by hand, remove the stranger, or give a second instance its own `--settings`, `--token-file` and ports.
- **The service does not start on the isolated host.** Podman refuses to start a container while a secret it names (`suiteward-database-url`, `suiteward-database-owner-url` for the migration, the GitHub key or the MCP token) or `~/.config/suiteward/github.env` is missing, and the journal shows which. The service restarts every five seconds until it starts, and it needs the migration to have exited with code 0 (`systemctl --user status suiteward-migrate.service`). A unit that Podman cannot parse is not generated at all: run `/usr/lib/systemd/system-generators/podman-system-generator --user --dryrun` (find it with `rpm -ql podman | grep generator`), or run the installer again, which does that check.
- **The service restarts in a loop and its log says `schema version X, this build requires Y`.** The service refuses a schema that is older than its image, and it never migrates. Someone changed an image and restarted the service alone, or the migration has not run. On the isolated host, as `suiteward`, run `systemctl --user restart suiteward-migrate.service`, which migrates and restarts the service. On a co-located PC, run `suiteward install`, which migrates before it starts the service. If the message says the database was migrated by a newer release, the image is older than the schema: use the newer release, or restore a backup ([the backup runbook](backup.md)). Never start an older image on the database.
- **`suiteward-migrate.service` fails (isolated), or `suiteward install` stops at migrate.** Read the migration's journal (isolated) or the output above the failure. The unit is not retried by itself: the service stays down until you fix the cause and run the install again (or `systemctl --user start suiteward.service`). The usual causes are these:
  - The database role `suiteward_app` does not exist: run the installer again, which creates it. A fresh database volume has no role.
  - The message says the service must connect as a least-privilege role: `suiteward-database-url` names a role that owns the schema or a table in it, is a member of the owner, a superuser or has `BYPASSRLS`, for example the owner's URL. Run the installer again after you remove that secret, so that it makes the application role's one.
  - The message says the database is not reachable after 30 attempts, or that it refused the owner connection: the database is not running or not healthy, or `suiteward-database-owner-url` holds a password that the database does not have.
  - The message starts with `migrate the database`: a migration failed. Report the message and do not edit the database. The schema is left as the failed migration left it, so restore your backup before you try another image ([the backup runbook](backup.md)).
- **The service stays down after a power loss.** If PostgreSQL's crash recovery takes longer than the migration's wait, the migration fails closed and the service stays down. Wait until the database accepts connections (`podman ps` shows `suiteward-db` healthy), then start the service again: `systemctl --user start suiteward.service` on the isolated host, `suiteward install` on a co-located PC.
- **`/readyz` answers 503.** The database does not answer, or the schema is not ready. Check that `suiteward-db` is healthy with `podman ps` (on the isolated host, as `suiteward`), and read its logs.
- **The log says `github commands stopped: the bot account could not be resolved`, with a status of 401.** GitHub refuses the App key that is installed, for example because it was revoked or is not the key you meant. All GitHub calls (reads, checks and comments) stop within about an hour, when the tokens that the service already holds expire. This line is an early signal after a restart, not the first symptom. Follow [Rotating the App key](#rotating-the-app-key), and compare the fingerprints.
- **An install failed after it created the GitHub App.** The installer records that App in `<settings path>.pending-app`: beside `settings.yaml` (`%APPDATA%\suiteward` on Windows, `~/.config/suiteward` on Linux, including the isolated account's). The record holds the App's id, slug and owner, never the key, which is in the secret store as `suiteward-github-app-key`. Run the installer again with `--github yes`: it takes up that App, with no second App, and waits for the installation. If the App is gone from GitHub (404 on `GET /app`), the error names the record, the secret and the command that removes it: delete the App on GitHub, the record and the secret, then run again. If only its key secret is gone, the error offers the two routes of section 5.3 (an App named without its key): give `--github-app-key-file <file>` with a key of that App, which takes the App up, or `--github new-app`, which creates a new App, replaces the record and prints the page that deletes the old one. Running with `--github-app-id`, `--github-installation-id` and the key file works too. A run with `--github no` keeps the record: when the settings name no App it prints a note on how to take the App up or throw it away, and when they name another App it refuses (see section 5.3, "A new App that stops partway"). A successful install removes the record, and so does `uninstall --purge`.
- **The browser cannot reach the manifest listener, or the manifest wait timed out.** After 2 minutes without an answer, on a terminal, the installer asks you to paste the address of the error page, or its `code=` value (the question is hidden; where the terminal can be waited on, GitHub's answer ends it by itself and an Enter with nothing pasted keeps waiting, and elsewhere an Enter ends it and takes the answer if it came meanwhile; section 5.3, step 3). The wait ends after 15 minutes: run the installer again, because GitHub's code lives one hour and converts once. On the isolated tier, start the Session Manager port forward that the installer printed first, and pin the port with `--manifest-port` (step 10.4).
- **GitHub says `Invalid integration ids` when you import the ruleset.** The App must be installed on the repository first. Add the repository to the installation, then import the file again.
- **Setup exits with code 2.** The `--test-check` list does not match the configured repositories. Give exactly one per repository, with no duplicates.
- **Setup exits with code 1.** A lookup failed. The owner login may not be a user account, the App may not be installed on every configured repository, or GitHub could not be reached. Nothing was written.
- **`propose` was refused.** The acknowledgment names the reason: `canonical-present` (the repository already has a contract; `propose` only works before the first one), `fork` (pull requests from forks are not supported), `not-open` (the pull request is no longer open), `base-not-target` (the pull request's base branch is not the repository's default branch, so merging it could never decide the first contract), `declaration-missing` (no `.suiteward.yml` was found on the default branch or the pull request head; see the suggested file and link, section 8), or `invalid-source` (`.suiteward.yml` is invalid, a symbolic link that the scope reaches points at a directory, outside the repository or nowhere (section 8), or GitHub truncated the tree, which happens with very large monorepos and cannot be protected in this release).
- **A command gets no reply.** Check that the first line starts with `/suiteward`, outside a code block, that it comes from your account, that you did not edit it, and that the pull request is still open. Another account's command gets no reply by design.
- **A repository gets no reply and no checks,** `/status` lists it in `unconfiguredRepositories`, and the log says `github commands skip an enrolled repository that is not configured in GITHUB_REPOSITORIES`. A repository you removed from the configuration, or deleted on GitHub, is still enrolled, and SuiteWard skips it. See [Stop protecting a repository](#stop-protecting-a-repository), or add it back to the configuration.
- **An approval is rejected.** The reply gives the reason: an invalid, replayed or expired code, or an unknown revision. Use a fresh code, and check the reference against the newest revision comment.
- **The check shows `approval-missing` after a push.** The push changed a protected file, which creates a new revision. Approve the revision named in the newest comment.
- **The new image does not start after an update.** Do not start an older image, because after a migration it refuses to run. Read the logs of the migration and of the service and report them to the project. To return to the earlier state, restore your backup, as described in [the backup runbook](backup.md#going-back-after-an-upgrade).
- **`suiteward install --upgrade` or `suiteward backup` refuses because no recovery key is set.** A backup is encrypted and never written in plaintext, and nothing could ask you to make a key. Run `suiteward backup init` on a terminal and keep the kit off the machine. For an unattended upgrade, give `--backup-recipient age1pq1...` (the public key) or `backup_recipient` in the answers file. `--yes` never makes a key. `suiteward backup` takes its key from the settings only, so its message names only `suiteward backup init`; the message of an upgrade names `--backup-recipient` too.
- **`suiteward backup init` says that a recovery key is set, or that the kit exists.** A key that is set is replaced only with `--replace` (the backups made with the old key still need the old kit). A kit file is never overwritten: name another with `--kit`, or move the old one away.
- **`suiteward backup` or `backup init` says that the service does not answer `/status`.** The status belongs in the backup, and the instance id names the kit. Start the service (the message names the command) and run the command again, or take the [backup by hand](backup.md#isolated-host-bash-as-suiteward). `suiteward restore` does not need the service: it needs the database container to run and be healthy, and it backs up an instance that does not answer with its status recorded as unavailable. A plaintext directory is the exception: its release can be compared only when the service answers.
- **`suiteward restore` refuses because the backup is of another release.** The message names the release of the backup and the `suiteward install --image ...` command for it. Install that release first ([the backup runbook](backup.md#3-restore)), then run the restore again.
- **`suiteward restore` says that this recovery kit does not open the backup** (`this recovery kit does not open the backup: use the kit of the instance that made it`). The kit is not the one of the key that the backup was encrypted to. The fingerprint (`SHA256:...`) is in the kit and in the output of `suiteward backup`. A message that the backup is invalid means that it is damaged, cut short, or not a SuiteWard backup: take another copy.
- **A restore stopped after it stopped the service.** The message says where it stopped, how to get the service back, how to run the restore again and where the backup of the state before it is ([the backup runbook](backup.md#3-restore)).
- **A directory `.suiteward-spool-...` or `.suiteward-restore-...` is in the backup folder.** A backup or a restore was killed and left a private copy of the data in plaintext. The next `suiteward backup`, `restore` or upgrade removes it and says so; you can remove it yourself at once.
- **A link in a comment does not open, or answers 404.** The links of the revision comment and of the comments of a head open on the machine that runs the instance (section 9): on the isolated host, forward the HTTP port first. The report of a revision answers 404 when the repository is not enrolled, the revision is unknown, it is the baseline of the first contract, or it was recorded before M1.13. The pull request page answers 404 when the repository is not enrolled or SuiteWard has not seen the pull request. A comment of a stack that has no `SUITEWARD_REPORT_BASE_URL` has no link at all (section 12, "What the installer does").
- **A run reads `no-executor`, a check says `canonical-not-responding` or `canonical-unavailable`, or doctor fails `executor.running`.** No executor asked the service for a job for about 30 seconds (the head reads not responding) or for 2 minutes (the run reads `no-executor`). Run `suiteward doctor`: the fix of `executor.running` names the command that starts the executor and where its log is (section 5.4 for the PC, 10.2 for the host). The executor's log says why it stopped: a wrong token or an address that does not answer shows as lease requests that fail and back off up to 20 seconds, for ever. A fresh job replaces a `no-executor` run once an executor is seen again, unless the owner unblocked it (an unblocked job stays, and the next push runs the tests). Until then the owner can lift the head with `/suiteward unblock` (section 9), from the moment it reads not responding. On a PC that has a second instance, `executor.lifecycle` and `executor.running` can instead say that the test runner on this computer belongs to another instance: a computer has one, and the fix is to remove that instance first (section 5.4, "Seven things to know"). A second instance's `doctor` without `--token-file` fails `executor.token` and checks no other executor row: give it the token file of that instance.
- **The executor runs and the service never sees it (`executor.running`, last seen long ago).** It cannot reach the service at `http://127.0.0.1:<HTTP port>`, or it sends another token than the service's. On the isolated host, check that the unit names the port the service publishes (`executor.unit`; the fix is the host step with `--http-port`), then run the host step again and `suiteward install --tier isolated` as `suiteward`, which make the executor's token and the service's secret one (at the installed release, `install --upgrade` settles only a token that the host step replaced). On the co-located tier, `suiteward install` again, or `install --upgrade` with this program, does it. On a PC with a Podman machine, read `executor.loopback`.
- **Every run reads `sandbox-unavailable`.** The runtime could not build the sandbox or honor one of its limits (no network, a read-only root, 3 GiB of memory, 4 CPUs, 512 processes), or it is a Docker CLI against Podman's socket (section 5.4). On the isolated host it can also be a user manager without the `cpu` controller (`executor.delegation`) or an executor account without the Go image (the host step pulls it). Read the executor's log.
- **A run reads `resource-limit`.** The sandbox was killed by its memory limit, exited with 137 that the executor did not cause, or printed more than 64 MiB. A Podman machine or Docker Desktop's VM with less memory than the tests need causes it too (section 3). Read the cause before you unblock it: a candidate can cause it.
- **A revision comment says that it has no counts** (`SuiteWard could not read the files of this revision to count the changed lines, so it has no counts.`). SuiteWard could not count the changed lines when it posted the comment: the revision was recorded before M1.13, or a file of it could not be read from the store. The service log has the cause (`the change report is unavailable, so the numbers are left out`). The comment lists the protected files instead, and has no link. SuiteWard never edits a comment, so it stays.
