# Remote host (isolated target): owner runbook

Host `<instance-id>`, us-east-2, AlmaLinux 9 (EL9) arm64, Podman 5.5 or later (EL9 ships 5.8.2 with the CVE-2026-57231 backport; check it as [install.md step 10.1](../docs/install.md#10-running-on-a-separate-host-operators) does), rootless for the unprivileged `suiteward` user. Check that `amazon-ssm-agent` is active (`systemctl is-active amazon-ssm-agent.service`) before you rely on Session Manager. SELinux stays enforcing: the units use named volumes, which Podman labels by itself, and no step here bind-mounts a path. No inbound ports and no SSH daemon: you administer it through SSM Session Manager from your own workstation. This runs the product image and its PostgreSQL as three rootless containers from the Quadlet units in `deploy/quadlet/`: `suiteward-db`, the one-shot `suiteward-migrate` (the database owner migrates the schema and grants the application role its access) and `suiteward` (the service, which requires the migration and connects as the least-privilege role `suiteward_app`). It needs five Podman secrets, all mounted as files: a generated database owner password and the owner URL (section 3, you never type them), the application role's URL (section 5, generated by the role step), the GitHub App's private key and a generated MCP token (section 4a, M1.4). The three non-secret GitHub settings live in a host file you write (section 4a). The images are pinned by digest in the units; there is no automatic update (section 5).

Never paste into chat, a file, a PR, or a log: any password or database URL, a GitHub or AWS credential (the App key, the MCP token), an SSM session token, the TOTP `otpauth://` URI, the base32 secret and any TOTP code. The only place the App key and the MCP token go is your own Session Manager terminal on the host, as the steps below say. An agent never holds host access; you run these steps in your own session and paste back only the outputs listed in section 6.

The co-located steps in this runbook run in a PowerShell session where you selected the machine's rootless connection ([install.md step 5.2](../docs/install.md#5-install-co-located)), and every `podman machine ssh` takes `--username user`: the default ssh user is `root`, the rootful store, which does not hold the co-located stack. `deploy/local.ps1` refuses a rootful connection.

## 0. Before the host steps (GitHub, once)

1. The first release run creates the GHCR package `suiteward` as private. Make it public (GitHub, owner profile, Packages, `suiteward`, Package settings, Change visibility), so the host needs no registry credential; the image contains no secret. If the run fails with `permission_denied: write_package`, open the package settings, "Manage Actions access", grant the `SuiteWard` repository write access, and re-run the job.
2. The host runs a release image, pinned by its signed index digest in both SuiteWard units. No workflow moves a tag the host follows: the Deploy workflow and the `deploy` tag are retired, and the `remote-poc` environment is no longer used. Take the index digest from the release notes (the `Index digest:` line of the release run's summary) and verify it as [install.md step 10.9](../docs/install.md#10-running-on-a-separate-host-operators) says.

## 1. Open a session

```
aws ssm start-session --target <instance-id> --region us-east-2
```

You land as `ssm-user`. On a new host, do the preparation of [install.md step 10.1](../docs/install.md#10-running-on-a-separate-host-operators) once first as the administrator: `dnf install podman openssl`, the changelog check of CVE-2026-57231, the `suiteward` account with no login shell, and its subordinate id ranges. Then become the service user with its systemd user manager (the account has a `nologin` shell, so `sudo -iu` fails):

```
sudo loginctl enable-linger suiteward
r=/run/user/$(id -u suiteward)
sudo -u suiteward -H env XDG_RUNTIME_DIR=$r \
  DBUS_SESSION_BUS_ADDRESS=unix:path=$r/bus bash
systemctl --user is-system-running
```

The lines are short on purpose: long lines pasted into a Session Manager terminal can break. `is-system-running` must print `running` (or `degraded`); if the bus socket is missing, wait a few seconds and retry. Start every new session this way. Every block below runs as `suiteward` unless it says otherwise.

## 3. Create the database owner secrets

One chained command generates the owner password and creates both Podman secrets from it, so you never see or type it and the two cannot disagree: `suiteward-db-password` (read by PostgreSQL, whose bootstrap role `suiteward` is the owner of the schema) and `suiteward-database-owner-url` (the owner's URL, read only by the migration unit). A line ending in `&&` or `|` continues on the next one, and the chain stops at the first failure. The application role's own secret, `suiteward-database-url`, is created in section 5, once the database runs.

```
pw=$(openssl rand -hex 24) &&
h='suiteward-db:5432/suiteward?sslmode=disable' &&
printf '%s' "$pw" |
  podman secret create suiteward-db-password - &&
printf 'postgres://suiteward:%s@%s' "$pw" "$h" |
  podman secret create suiteward-database-owner-url -
unset pw h
podman secret ls
```

Both names must be listed. Then check the shape of both values without showing them; each `grep -c` prints only a count, and both must print `1` (48 hex characters, and the URL around them):

```
s='{{.SecretData}}'
p='[0-9a-f]{48}'
podman secret inspect --showsecret --format "$s" \
  suiteward-db-password | grep -Ecx "$p"
h='@suiteward-db:5432/suiteward[?]sslmode=disable'
podman secret inspect --showsecret --format "$s" \
  suiteward-database-owner-url |
  grep -Ecx "postgres://suiteward:$p$h"
unset s p h
```

A `0` means a value is malformed: remove both secrets and repeat this section (nothing has started yet, so no volume holds the password). Run the creation once. The database is initialised with the password on its first start and keeps it in the `suiteward-db-data` volume, so replacing a secret later locks the owner out; to start over, stop all three units first (`systemctl --user stop suiteward.service suiteward-migrate.service suiteward-db.service`), then remove the volume (`podman volume rm suiteward-db-data`) and the secrets (`podman secret rm suiteward-db-password suiteward-database-owner-url suiteward-database-url`), then repeat this step and the role step of section 5. The step is only re-runnable after removing a first secret it created before failing, because `podman secret create` refuses an existing name. `sslmode=disable` is deliberate: the database listens only on the private `suiteward` network and its image carries no certificate.

## 4. Block the metadata service for the `suiteward` user

Do this before the services start. D-DEPLOY says IMDSv2 with hop limit 1 keeps containers from the instance role; S1 showed a rootless container can still obtain a token, because rootless networking makes the connection from a process of the `suiteward` user on the host. Reject `169.254.169.254` for that user.

First the S1 check, as `suiteward` (open a shell as in section 1), before the rule exists. It must print `200`, which shows the check can see the problem:

```
podman run --rm docker.io/curlimages/curl@sha256:58adaa4e8dca9c988bae2aba4ab3434a0bb2da16bbe3f92dec39ec7785166777 -s -m 3 -X PUT -H 'X-aws-ec2-metadata-token-ttl-seconds: 60' -o /dev/null -w '%{http_code}\n' http://169.254.169.254/latest/api/token
```

Then, as `ssm-user` (type `exit` to leave the `suiteward` shell), make sure `nft` exists:

```
command -v nft || sudo dnf install -y nftables
```

Write the rule. Run the first command, wait until the cursor stops, paste the nft block that follows it, then press Ctrl-D on an empty line:

```
sudo mkdir -p /etc/suiteward
sudo tee /etc/suiteward/imds-block.nft >/dev/null
```

```
add table inet suiteward_imds
delete table inet suiteward_imds
table inet suiteward_imds {
  chain output {
    type filter hook output priority 0; policy accept;
    meta skuid suiteward ip daddr 169.254.169.254 reject
  }
}
```

Then a unit that loads it at every boot, independent of `/etc/sysconfig/nftables.conf` and of `firewalld`, which keeps its own table. It uses the path `command -v nft` reports, not a hardcoded one; `ExecStop` starts with `-` so a missing table never fails a stop:

```
NFT=$(sudo sh -c 'command -v nft')
sudo tee /etc/systemd/system/suiteward-imds-block.service >/dev/null <<EOF
[Unit]
Description=Reject the instance metadata service for the suiteward user
Before=systemd-user-sessions.service
After=nftables.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=$NFT -f /etc/suiteward/imds-block.nft
ExecStop=-$NFT delete table inet suiteward_imds

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl enable --now suiteward-imds-block.service
sudo nft list table inet suiteward_imds
```

Run the curl check from above again as `suiteward`. It must now print `000` (anything but `200`; if it still prints `200`, stop: the rule does not cover the container traffic). Then confirm the SSM agent still works, which proves the rule does not touch it: as `ssm-user`, `sudo systemctl is-active amazon-ssm-agent.service` prints `active`, and a second `aws ssm start-session` from your workstation still opens.

Limits of the rule: it covers IPv4 only, which is enough because the IPv6 metadata endpoint is off by default on EC2. The table lives in the kernel until reboot and is reloaded by the enabled unit. `nftables.service` is disabled by default on AlmaLinux 9. If you enable it and `/etc/sysconfig/nftables.conf` starts with `flush ruleset`, restarting `nftables.service` drops the table; load it again with `sudo systemctl restart suiteward-imds-block.service`. Optionally reboot the instance once and repeat `sudo nft list table inet suiteward_imds` to confirm the rule is loaded at boot. Never run commands that print metadata credentials.

## 4a. GitHub and MCP settings (M1.4)

Before the updated `suiteward.container` is installed (section 5; on a host that already runs M1.2, before you replace that file). The unit now mounts two more Podman secrets and reads one env file, and all three are mandatory: a missing secret or a missing file makes `podman` refuse to start the container, which `Restart=always` repeats every five seconds and the journal shows. It does not run silently without GitHub. The GitHub settings are all set or all unset (runtime contract): an env file with only some of them makes `serve` exit at startup, and `smoke.sh` then fails at `readyz` after its timeout.

**The three non-secret settings.** As `ssm-user` (type `exit` to leave the `suiteward` shell). Run the first command, wait until the cursor stops, paste the three lines with the placeholders replaced (the App id and installation id from the App's settings page, the repositories as `owner/name`, comma-separated, 1 to 20, no spaces or quotes), then press Ctrl-D on an empty line:

```
sudo mkdir -p /etc/suiteward
sudo tee /etc/suiteward/github.env >/dev/null
```

```
SUITEWARD_GITHUB_APP_ID=<app id>
SUITEWARD_GITHUB_INSTALLATION_ID=<installation id>
SUITEWARD_GITHUB_REPOSITORIES=<owner/name>,<owner/name>
```

The file holds no secret (the quadlet reads it as `EnvironmentFile=/etc/suiteward/github.env`, readable by the `suiteward` user). Never commit these values.

**The App key.** As `suiteward`. Copy the App's private key (PEM) to the host through your own session. The first line turns the terminal echo off, so the key does not appear on screen (or in a Session Manager log that records output): run it, wait until the cursor stops, paste the whole PEM from the file on your workstation, press Enter, then Ctrl-D (you see nothing while you do). The next command reads that file into the secret and the last one destroys it; the key is never echoed:

```
trap 'stty echo' INT; stty -echo; (umask 077; cat > ~/app-key.pem); stty echo; trap - INT
podman secret create suiteward-github-app-key ~/app-key.pem
shred -u ~/app-key.pem
```

If the terminal goes silent, type `stty echo` and press Enter; after an aborted paste, run `shred -u ~/app-key.pem` and repeat.

Check the shape without showing the value; it must print `1`:

```
podman secret inspect --showsecret \
  --format '{{.SecretData}}' suiteward-github-app-key |
  grep -Ec '^-----BEGIN (RSA )?PRIVATE KEY-----$'
```

**The MCP token.** Generated on the host, 32 random bytes hex-encoded (64 characters, above the 32-byte minimum), straight into the secret. `printf` drops the newline that `openssl` appends; with a newline the secret would be 65 bytes and the client would need it too:

```
printf '%s' "$(openssl rand -hex 32)" |
  podman secret create suiteward-mcp-token -
podman secret inspect --showsecret \
  --format '{{.SecretData}}' suiteward-mcp-token |
  grep -Ecx '[0-9a-f]{64}'
```

It must print `1`. Run each creation once (`podman secret create` refuses an existing name; to replace a secret, `podman secret rm` it, create it again and `systemctl --user restart suiteward.service`).

**Where the client gets the token.** The token never goes in the repository and never in chat. Podman supports `--showsecret` (section 3 already uses it), so you read it once on the host, in your own Session Manager terminal, and put it in your own secret store (your password manager); nothing else keeps a copy:

```
podman secret inspect --showsecret \
  --format '{{.SecretData}}' suiteward-mcp-token
```

That prints the token to the terminal. If Session Manager session logging (S3 or CloudWatch) is on for this instance, treat the token as exposed to that log, and replace it as above once the verification is done. On the client side `claude mcp add --transport http` sends it as `Authorization: Bearer <token>` (section 7); Claude Code stores that header in its own configuration on your workstation, not in a repository.

## 5. Install the quadlets and start

Copy the six files in `deploy/quadlet/` from the repository (on your workstation) into place, one `cat` per file: run the command, wait until the cursor stops, paste the file's content, then press Ctrl-D on an empty line. Pull the images first: the two SuiteWard units pin the image by digest, never by a tag.

```
podman pull docker.io/library/postgres:18.6-trixie@sha256:74935e72241653ca55e0414067e6d8763aceb8a810eb51b452253ec3dcfc4336
podman pull ghcr.io/ignisdevne/suiteward@sha256:<index>
```

`<index>` is the image index digest of the release, from its release notes. Verify its signature first ([install.md step 10.9](../docs/install.md#10-running-on-a-separate-host-operators): `pwsh ./scripts/verify-release.ps1 -Reference ghcr.io/ignisdevne/suiteward@sha256:<index>` on a machine with cosign 3.x). Then the files:

```
mkdir -p ~/.config/containers/systemd
cat > ~/.config/containers/systemd/suiteward.network
cat > ~/.config/containers/systemd/suiteward-db-data.volume
cat > ~/.config/containers/systemd/suiteward-data.volume
cat > ~/.config/containers/systemd/suiteward-db.container
cat > ~/.config/containers/systemd/suiteward-migrate.container
cat > ~/.config/containers/systemd/suiteward.container
```

Put the verified digest into BOTH SuiteWard units. They must name the same image: the migration must run the release the service runs. Name the two files, never a `*.container` glob, which would also rewrite the database pin. The chain stops unless `d` has the form of a digest, so it never writes an incomplete line:

```
d=sha256:<index>
[[ "$d" =~ ^sha256:[0-9a-f]{64}$ ]] &&
sed -i "s|^Image=ghcr.io/ignisdevne/suiteward@.*|Image=ghcr.io/ignisdevne/suiteward@$d|" \
  ~/.config/containers/systemd/suiteward-migrate.container \
  ~/.config/containers/systemd/suiteward.container
grep -c '^Image=ghcr.io/ignisdevne/suiteward@sha256:[0-9a-f]\{64\}$' \
  ~/.config/containers/systemd/suiteward-migrate.container \
  ~/.config/containers/systemd/suiteward.container
```

The `grep` must print `1` for each of the two files; a `0` means the pin is missing, so run the chain again.

Podman skips a unit it cannot parse (you would only see "unit not found"). Dry-run the generator; it prints every generated unit or the error. It must list the three services `suiteward-db`, `suiteward-migrate` and `suiteward`, the network and both volumes:

```
podman --version
/usr/lib/systemd/system-generators/podman-system-generator --user --dryrun
```

The units use only keys that Podman 5 documents; the memory limits and stop timeouts go through `PodmanArgs`, and there is no `Notify=healthy`. The dry run is the check. If a key is rejected, remove that line, start anyway, and report which one. Start the database alone first: the application role must exist before the migration unit runs. Wait until it is healthy:

```
systemctl --user daemon-reload
systemctl --user start suiteward-db.service
until [ "$(podman inspect --format '{{.State.Health.Status}}' suiteward-db)" = healthy ]; do sleep 2; done
```

**The application role.** Run the role chain and the shape check of [install.md step 10.11](../docs/install.md#10-running-on-a-separate-host-operators) here, as they are written there (they create the role `suiteward_app` with a generated password sent on standard input, and the secret `suiteward-database-url`; they print only the ID of the new secret, never a value). Do not paste the password anywhere. Then start the service. It requires the migration, which requires the database, so this starts `suiteward-migrate.service` first (it applies the schema as the owner and grants the role its access) and the service only after migrate exited 0:

```
systemctl --user start suiteward.service
systemctl --user status suiteward-db.service suiteward-migrate.service suiteward.service --no-pager
podman ps
```

`suiteward-migrate` shows `active (exited)`: it ran once and stays active, so the service can restart without migrating again. `podman ps` does not list it (its container is removed when it exits); its log is `journalctl --user -u suiteward-migrate.service -n 50 --no-pager`. If the `start` reports a failed dependency, migrate failed: read that journal, fix the cause (a missing role or secret, usually), and start the service again once migrate is `active (exited)`.

Two checks that the host honours what the units ask for (the memory limit needs memory cgroup delegation to the user manager):

```
podman info --format '{{.Host.NetworkBackend}}'
podman inspect suiteward-db --format '{{.HostConfig.Memory}}'
```

The first must print `netavark`; the second must print `402653184` (384 MiB). If either differs, report it with the dry-run output; do not improvise a fix. Then re-run the S1 curl check from section 4 with `--network suiteward` added right after `--rm`, which is the network the service itself uses; it must print `000` too.

The service now also needs outbound HTTPS to `https://api.github.com`. The IMDS rule of section 4 rejects only `169.254.169.254` for the `suiteward` user and leaves every other destination alone, so GitHub stays reachable; check it from the same network the service uses (an unauthenticated `GET /zen`, which prints `200`; `403` would mean the shared unauthenticated rate limit is used up, and `000` that the host cannot reach GitHub, so stop and report it):

```
podman run --rm --network suiteward docker.io/curlimages/curl@sha256:58adaa4e8dca9c988bae2aba4ab3434a0bb2da16bbe3f92dec39ec7785166777 -s -m 10 -o /dev/null -w '%{http_code}\n' https://api.github.com/zen
```

**Update the host (a new image).** The service never changes the schema and refuses one that is not its image's, so an update goes through the migration unit. Take the index digest of the release, verify it as in install.md step 10.9, pull by it, set BOTH `Image=` lines, reload and restart `suiteward-migrate.service`, which migrates and then restarts the service through `Requires=`. Never restart `suiteward.service` alone after an image change: it would start the new image on the old schema, refuse it (`schema version X, this build requires Y`) and loop. Back up first (migrations only go forward; the way back is the backup, [install.md step 11.6](../docs/install.md#11-updating)):

```
d=sha256:<index>
[[ "$d" =~ ^sha256:[0-9a-f]{64}$ ]] &&
podman pull ghcr.io/ignisdevne/suiteward@$d &&
sed -i "s|^Image=ghcr.io/ignisdevne/suiteward@.*|Image=ghcr.io/ignisdevne/suiteward@$d|" \
  ~/.config/containers/systemd/suiteward-migrate.container \
  ~/.config/containers/systemd/suiteward.container &&
systemctl --user daemon-reload &&
systemctl --user restart suiteward-migrate.service
```

Check the pins as above (the `grep -c` prints `1` for each of the two files) and the units with `systemctl --user status suiteward-migrate.service suiteward.service --no-pager`.

Updating the host is this block, then the smoke test of section 6. A v0.1.x host that enabled the timer must run `systemctl --user disable --now podman-auto-update.timer` first, and keep it disabled (also before a rollback to v0.1.x). On a host still on v0.1.x, [install.md step 11.5](../docs/install.md#11-updating) comes first: the owner URL moves to its own secret, the role and the migrate unit are created.

**Automatic updates are not supported.** The host updates only by digest, with the block above. Podman's auto-update cannot update the migration unit (its container exists only while it runs), so an update of the service alone would start it on the old schema and loop. Do not add `AutoUpdate=` or enable `podman-auto-update.timer`.

Generated units start at boot through linger; `enable` is not used on them. The migration has no `Restart=`: it waits for the database itself (30 attempts), and nothing retries it after that. A failed migrate leaves the service down, visible in `systemctl --user status` and the journal. Fix the cause, then `systemctl --user start suiteward.service`. `suiteward-db` must show `(healthy)`. Logs:

```
journalctl --user -u suiteward.service -n 100 --no-pager
journalctl --user -u suiteward-migrate.service -n 50 --no-pager
journalctl --user -u suiteward-db.service -n 50 --no-pager
```

## 6. Smoke test and what to paste back

The service listens on loopback port 8081 (HTTP) and 8091 (MCP). Copy `deploy/smoke.sh` from the repository into place (same `cat` and paste, then Ctrl-D), as `suiteward`:

```
cat > ~/smoke.sh
sh ~/smoke.sh
```

It waits for `/readyz`, checks `/healthz` and `/status` (zero failed and discarded), then the `tier` step (M1.5: `/status` must report a `tier`; run it as `SMOKE_TIER=isolated sh ~/smoke.sh` on this host so anything but `isolated` fails, locally `SMOKE_TIER=co-located`), then two M1.4 steps. `github` waits (up to `SMOKE_GITHUB_TIMEOUT`, 120 s by default) until every repository in the `github` array of `/status` shows `lastSuccess`; it fails at once on a `lastError` and when `/status` has no `github` array (this host must run with GitHub configured; `SMOKE_GITHUB=0` skips only the step, for a stack started without the GitHub settings). `mcp` sends two requests to `http://127.0.0.1:8091/mcp` (`SMOKE_MCP_BASE`) and never reads the token: a POST without a token must answer 401, a POST with `Origin: http://evil.example` 403. Then it runs a probe through the worker (the outbox relay is a periodic job, so a probe takes from about a second to several seconds to be delivered), enqueues a probe whose job is delayed by 20 s, restarts the service and checks that the delayed job still ran afterwards, and prints a summary block with a timestamp and elapsed milliseconds per step. That step proves a delayed job survives a restart; it does not show whether the probe's outbox message was relayed before or after the restart, so it is no proof of outbox durability. `/status` reports the image version, which is the release tag for a release image; to assert it, run `SMOKE_VERSION=v0.2.0 sh ~/smoke.sh` (use your tag). `podman inspect suiteward --format '{{index .Config.Labels "org.opencontainers.image.revision"}}'` prints the commit of the running release image (only release images carry that label). A local build reports `dev`, or `sha-<commit>` when it was built with that `VERSION` build argument. It exits non-zero and names the failing step otherwise. Update by digest as section 5 says.

Paste back: the whole summary block (it holds the `tier`, `github` and `mcp` lines; if any step fails, add `journalctl --user -u suiteward.service -n 50 --no-pager`: log lines carry no secret, and a restart loop shows its cause there); the output of `systemctl --user status suiteward-db.service suiteward.service --no-pager`; `podman --version` and the generator dry run (they contain no secret); the one-line IMDS status codes (200 before the rule, 000 after, on both networks); `podman inspect suiteward --format '{{.Config.StopTimeout}}'` (must print 45, the contract needs it above the 30 s shutdown timeout); `sudo ss -tlnp` (every listener on `127.0.0.1` or `::1` except the system and SSM ones you recognise; both published ports, 8081 and 8091, show as `rootlessport`); about 30 `journalctl` lines of the service around the restart; and how long the first pull and start took.

## 7. Reach `/status`

From your workstation, in a second terminal:

```
aws ssm start-session --target <instance-id> --region us-east-2 --document-name AWS-StartPortForwardingSession --parameters portNumber=8081,localPortNumber=8081
curl http://127.0.0.1:8081/status
```

M1.4 adds the MCP listener, forwarded the same way (a second terminal, or a second session). The token is your own to give the client; it never goes in a file of the repository:

```
aws ssm start-session --target <instance-id> --region us-east-2 --document-name AWS-StartPortForwardingSession --parameters portNumber=8091,localPortNumber=8091
```
