# M1-C01: Persistent canonical state and artifact storage

- Phase: M1.01; base `432c4f2f73d03ef74c7d4c82c8c852593cb1ba95`.
- Status: frozen reviewed contract; A (`m101_schema`), B (`m101_postgres`) and C (`m101_artifact`) independently accepted this packet before behavior implementation.
- Authority: existing M0 domain/application APIs and ADRs 0004, 0007, 0010, 0011, 0018, 0023 and 0024 remain governing. This contract resolves storage implementation details, not deferred approval-context, owner identity, scope or GitHub policy.

## Consumed boundaries

`postgres.Store` implements the existing `governance.Store` without changing its load/commit signatures. Its constructor takes a concrete pgx pool and a required, small artifact verifier; these adapter details do not enter domain/application types. `ArtifactVerifier.Verify(context.Context, artifact.Digest) error` is consumed by canonical/history/replay reads and promotion commits. The filesystem implementation satisfies that boundary.

`InitializeTrusted` is an insert-only adapter entry point for one unbaselined Suite: absent canonical version, governing Policy, integration target, Schedule and scoped Proposal/Consent/assessment inputs. It never replaces existing authority or imports a fabricated canonical history. Initial consent must have no processed results or aliases; real application consent processing creates its durable receipts/audits/acknowledgments. Canonical history enters through `Bootstrap`, `Promote` or `Correct`. Construction/restoration of facts is not remote authentication or owner authorization.

Immutable M0 values cannot be reconstructed by ordinary JSON over private fields. B owns narrowly consumed, versioned domain checkpoint export/restore support for proposal revision history, consent state/results/aliases, scheduling entries/pending/order/aliases and historical promotion effects/command results. Other values use their existing validating constructors. Digests parse only exact `sha256:` plus 64 lowercase hexadecimal digits. Checkpoints copy mutable collections and reject invalid versions, malformed or inconsistent identities/state; they must not reapply historical consent under today's proposal/policy. No unsafe/reflection mutation, provider/database import into domain, candidate-controlled restoration, or unvalidated authority constructor is permitted. B consumes `StateCheckpoint` through `EncodeStateCheckpoint(StateCheckpoint) ([]byte, error)` and `RestoreStateCheckpoint([]byte) (StateCheckpoint, error)`. Its fields cover only actual domain values consumed by authority/version/receipt reconstruction. The private JSON encoding is versioned, rejects unsupported or malformed envelopes, and remains a reconstruction format rather than a provider contract.

## Database and migration contract

Use PostgreSQL 18.6 from the existing immutable development image, pgx v5.11.0 and Goose v3.28.0. sqlc remains pinned to 1.31.1. Goose Provider uses embedded sequential SQL, per-provider configuration and PostgreSQL session locking; no global migration registry, automatic out-of-order changes or nontransactional migrations. See [ADR 0026](../decisions/0026-versioned-postgresql-migrations.md).

Migration 1 creates the relational storage, identity checks and foreign keys. Migration 2 adds immutable-history and exact revision-advance guards. A populated migration-1 installation upgrades transactionally to 2 without losing existing state; the adapter is ready only after the full supported migration sequence. Fresh install, repeated/concurrent application, populated upgrade and rollback on failed migration are real PostgreSQL scenarios. Production migration direction is forward only; destructive down migration is rejected. Restore is separate later-phase work.

The reviewed relation set is:

| Relation | Identity and responsibility |
| --- | --- |
| suites | Project/Suite composite key, nullable canonical pointer, whole-authority uint64 revision stored as checked numeric, versioned object payload containing coherent governance state. |
| suite_versions | Project/Suite/version identity, exact manifest digest and immutable version/contract/provenance payload. |
| operation_receipts | Instance-global operation ID, explicit Project/Suite and kind, immutable original processing outcome; aliases retain the original outcome under a distinct reserved operation ID. |
| consent_sources | Instance-global source-command identity and scoped foreign key to the original consent operation. A source alias never duplicates the original audit/acknowledgment. |
| promotions | One operation and version, unique exact Project/Suite/proposal/revision; expected/corrected versions have same-Suite foreign keys. |
| audit_events | Immutable operation-associated promotion or consent audit, kind consistent with the referenced receipt. |
| publication_intents | Immutable promotion-associated publication intent, not a delivered external result. |
| consent_acknowledgments | Immutable fresh-consent acknowledgment tied to its original operation receipt. |

Global operation/source identity preserves the M0 reference model: reuse in another aggregate conflicts rather than silently processing a second action. Future transport IDs must carry their required namespace; no GitHub-specific field is introduced here. SQLC access code stays private under `internal/adapters/postgres/internal/dbgen`.

The canonical pointer has deferred same-Suite foreign keys to the stored version and its promotion. Promotions require their matching receipt, audit and publication intent at commit, using appropriate deferred reciprocal constraints. Consent audits/acknowledgments are distinct from promotions; aliases do not require new effects. Foreign keys must not associate another operation kind or Suite. Immutable relations reject UPDATE, DELETE and TRUNCATE; direct trusted-host administration remains outside the adversary boundary of ADR 0007. Mutable Suite authority advances its revision by exactly one for every write, including aliases/waiting-only changes. Exhaustion fails without effects.

A owns minimal consumed queries: coherent get/lock, insert-only initialization, CAS with `:execrows` and nullable-pointer equality, insert/find version and operation, insert/find source alias, promotion lookup by exact reference, and insert audit/publication/acknowledgment. Numeric revision is exposed to adapter code as exact decimal text, never float or signed truncation. Failed unique identities are translated to stable domain/application conflict categories; generated pgx/sqlc types never escape the adapter.

## Atomic behavior

Load reads one coherent transaction snapshot and releases its read transaction. Original operation/source receipts are resolved before current authority eligibility, preserving M0 historical replay semantics. Relevant returned canonical/historical content must be present and hash-valid; a historical replay verifies the content bound to that original outcome rather than substituting today's contract. No unavailable/corrupt referenced object yields successful canonical verification.

Commit takes the whole-Suite fence, starts a transaction, locks/reloads stored authority and validates the supplied fence against current policy, proposal, consent, scheduling and canonical state. Promotion re-runs the appropriate existing M0 domain decision and compares the full proposed effect/receipt/scheduling to stored authority; consent re-runs existing command evaluation and validates original outcomes/aliases. Caller-provided approval or effect alone cannot grant authority. CAS must report exactly one changed row.

A promotion commits its immutable version/contract/provenance, pointer, receipt, promotion, audit, scheduling and publication intent together. Fresh consent commits consent state, command/source identity, receipt, audit, acknowledgment and authority revision together. An exact source alias commits only its reservation/consent alias state and whole-authority revision. Failed SQL statements or commit-time constraints roll back every staged effect. Repeated exact operations return original durable outcomes; mismatched identities conflict.

## Content storage contract

The filesystem adapter exposes `NewStore(root string) (*Store, error)`, `Put(context.Context, artifact.Digest, io.Reader) error`, `Read(context.Context, artifact.Digest) ([]byte, error)` and `Verify(context.Context, artifact.Digest) error`. Its root is trusted instance configuration, never a candidate path. Reject blank, non-directory and symlink roots; create a missing root privately. Open rooted operations for each call. Ancestor/root replacement by a malicious host administrator is not a claimed defense.

Objects use flat `sha256-<64 lowercase hex>` names derived only from a validated digest. Stage to a unique file in the same root, stream and hash every supplied reader (even for duplicate puts), sync and close before atomic no-clobber hardlink publication. Never use an overwrite-capable rename fallback. Unsupported publication semantics fail operationally. Reject symlink/nonregular destinations. Duplicate publication succeeds only if existing exact bytes revalidate; corrupt existing content is never silently repaired.

Absent digest returns the domain invalid-digest category; mismatched supplied bytes have a distinguishable digest-mismatch error; missing objects preserve `fs.ErrNotExist`; nonregular, symlink and hash-corrupt objects have a corruption category. Other I/O errors preserve their wrapped cause. Reads/verification hash content. Normal failures clean only their owned staging file. A postpublication cleanup failure preserves the wrapped cause; valid published bytes may remain and a retry revalidates them. Partial stages are never addressable by digest; abandoned orphan stages remain ignored until a separately defined maintenance operation. Cancellation is checked cooperatively; arbitrary blocked readers are not promised interruption.

Raw objects correspond to manifest entry content digests. The manifest digest is recomputed from validated manifest metadata using existing versioned encoding; it is not falsely treated as a raw file-object reference. Scope/covered-input bindings are not additional raw-object references unless present in the manifest inventory. Promotion verifies all referenced proposed content before authority commit, and canonical/history reads verify their referenced content. File bytes are published before metadata references them; a failed database transaction may leave an unreferenced immutable object. No cross-volume/database atomicity or power-loss directory durability is claimed. Concurrent host deletion/corruption after verification is an operational failure, not a prevented transaction across PostgreSQL and the filesystem.

## Ownership and review

A owns migrations, migration runner, SQL queries, schema tests, sqlc configuration/generated output and coordinated module dependency files. B owns PostgreSQL governance/promotion/transaction code and its real adapter tests, plus consumed domain restoration/digest parsing code with its own RED/GREEN evidence. C owns filesystem artifact code/tests. I owns actual adapter composition scenarios, project-local persistence/generation verification, CI service/coverage integration and final phase evidence. C0 owns this contract, migration ADR/decision register and backlog/generated ownership changes.

Each checkout owns tools, credentials, database volume and port. Integration-tagged PostgreSQL tests fail if their explicitly required connection is absent; portable M0/unit checks remain service-free. Linux CI uses the already accepted PostgreSQL service-container design. Windows-to-PostgreSQL integration is exercised locally against each worktree's Podman container. The coverage job must include real integration tests and generation freshness rather than declaring adapter success from skipped tests.

Workers observe meaningful compiled behavioral RED before implementing each behavior, preserve checkpoints and obtain independent review. Final evidence lists exact owned files and commands. This contract does not select any future managed hosting/execution arrangement, user-facing scope rule, approval context, owner proof, GitHub queue recovery or cryptographic format.
