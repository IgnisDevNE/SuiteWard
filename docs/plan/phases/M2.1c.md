# M2.1c: fixes from the M2.1b acceptance test

**Goal:** fix what the owner's acceptance test of [M2.1b](M2.1b.md#the-owners-acceptance-test) found, before any new profile, and ship it as `v0.5.0-alpha.4`. First the two signals that can mislead the owner before an approval (SW-22, SW-23); then the results comment and page, the installer and the test runner, the install guide, the removal of `/suiteward mode`, the note of `doctor` for a Podman older than 5.0, and the measurement of this repository's runs. One phase, so one round of live tests ([D-ROADMAP](../decisions.md#d-roadmap-the-order-after-m21), owner, 2026-11-03). The phase card is SW-39 in the itsaplan project `SW`, and its subtasks are the cards below (20 at the start, 21 since decision 18).

## Owner decisions (2026-11-03)

1. **SW-22: no "met" next to failing approved tests.** When the approved tests have a failed, missing or flaky test, or a test is weakened, the results comment does not say which kind of change the receipt meets: it says that the approved tests failed and sends the reader to the report. Only under `receipt: required`, when the next step is an approve, it asks for the approval with the existing approve-with-mode command. No new command.
2. **SW-20: a short "What went wrong" section** right after "Tests by state" on the pull request page, one line per problem with a link to its table. The long tables stay where they are; with nothing wrong, the page keeps today's order.
3. **SW-23: a new marker kind, "removed test case",** for Go only in this phase.
4. **SW-26: only the warning changes.** A release binary is never called a development build; no trust claim changes.
5. **The release comes after the merge,** as in M2.1b: the live tests with a development build before the pull request; the merge; `v0.5.0-alpha.4` cut from `main`; then the full isolated flow, SW-26 and the owner's acceptance test on the release.
6. **Memtrace is indexed only if it is stale,** with no label change.
7. **A new test repository:** `IgnisDevNE/SuiteWard-m21b` is deleted, and the co-located live tests use a new `IgnisDevNE/SuiteWard-m21c` with new test Apps.

Accepted with the plan (the orchestrator's proposals, 2026-11-03):

8. **SW-37:** below Podman 5.0, doctor's runtime row is a `pass` with a note in its detail, not a `warn`: on Ubuntu 24.04 (Podman 4.9.3) a warning would stay forever with nothing to act on. The isolated floor of 5.5 stays.
9. **SW-16:** `/suiteward mode` is answered as an unknown command, with no new reason code in the ledger, and with the sentence below. `PreviewMode` leaves the store; earlier `mode-set` rows still read (the enum and the migration's CHECK stay).
10. **SW-24:** refuse in plain words, with no global `chdir` (it would change relative paths such as `--backup-dir`); `deploy/HOST.md` stops using `cd "$(mktemp -d)"`; the host step's "Next" names `install --upgrade` when the service's quadlet exists.
11. **SW-25:** the executor exits when its console host is gone (Windows only), and the `run.cmd` loop ends when its pause fails (`ping … || exit /b`). The guide says how to stop the runner.
12. **SW-29:** the backoff is in Go, in the executor's loop, for every platform (`Pacing`, `Backoff`, `MaxBackoff` exist); doctor says in plain words that the container program is not running.
13. **SW-27:** the link is tried as today and, if it fails, again with `sudo -n` inside the machine; doctor's printed fix uses the same path.
14. **SW-15:** the co-located block only (Windows, Linux, macOS), written after SW-25 and SW-29 so it describes the final behavior.
15. **SW-14:** first a quick check on a throwaway AlmaLinux 9 distro that a global `podman --log-level=error` silences conmon. If it does, one argv change; if not, the card goes back to the Backlog (the stdin redesign belongs to M2.4).
16. **SW-38:** the orchestrator collects from GitHub the times and counts of each head since #64, and prepares a read-only query for the owner to run on the host; the owner decides the levels before the phase's pull request is final. A `required` level rides that pull request's approval. `receipt: required` without SW-22 would refuse approves on a misleading "met"; both land together.

Decided from the measurement (owner, 2026-11-03):

17. **This repository moves to `canonical: required`; the receipt stays `advisory`.** The measurement of 11 heads of #64 to #69: the results came a median of 8m17s after a push (7m57s to 12m16s), no approved test gave different results or no result, and two heads had approved tests that failed while the advisory Contract check stayed green. `canonical: required` adds about 8 minutes to each head and holds such a head; `receipt: required` would ask for a mode on every approve. The cost: every merge waits for the governing host's run, and while its test runner is down each head needs `/suiteward unblock` (D-GOVERNING-HOST-CLOUD is still open). The level governs from the promotion of this phase's pull request; that pull request itself still runs under `advisory`.
18. **SW-47 joins the phase.** The review of SW-1 found that the Contract check, the Receipt check and the execution acknowledgment still offer `/suiteward unblock <code>` in their older words, without saying what `<code>` is. They take the words of the comments' offer (text 4).

## The texts

Fixed with the plan; small grammar fixes are the reviewer's.

1. **SW-22, results comment.** When the approved tests have a failed, missing or flaky test, or at least one test is weakened, the kinds block is replaced by: "The approved tests failed (3 failed, 1 weakened), so this comment does not say which kind of change (`fix`, `feature`, `refactor`) this change is. The details are in the report." The parentheses show only the counts above zero; when the only problem is a weakened test, it opens with "This change weakens an approved test (1 weakened), …". Only under `receipt: required` and with the next step `NextApprove`, it adds "If you want to approve this revision anyway, name the kind of change that the report shows as met, and comment:", which introduces the `modeApproveCommand` block that `nextText` already prints under `ApproveMode` (the command is not shown twice). Never with `NextBlocked`, and never when nothing awaits approval. If the Receipt check states the kinds, it follows the same rule ([ADR 0029](../../decisions/0029-results-communication.md) wording rule).
2. **SW-21, the link.** Right after the approved counts: "See the full report here:" and the link to the pull request page (its text stays "pull request page"), then the `linkNote`. With no canonical run, right after the lead; with no web address, `noLinkText` takes the same place.
3. **SW-21, the tables.** "Tests this change adds or edits: N." is followed by a table `| What the test shows | Tests |` with today's seven rows, all shown. The kinds block reads "Does the receipt meet each kind of change? It looks only at the tests this change adds or edits." and a table `| Kind of change | Met? | Why not |` (Yes or No, and today's sentence). The Receipt check summary and the refusal acknowledgment (`countsText`) use the same tables.
4. **SW-1, not responding.** The shared `unblockOffer` becomes "To go on without these tests, the owner can comment `/suiteward unblock <code>`, where `<code>` is a current code from the authenticator app. That lets this commit pass its checks without them, and they do not run for this commit. A new push runs them." With `Unblock`, it follows "The checks of this commit wait for these tests."; without it (advisory, or an approval still missing): "Nothing waits for these tests. An unblock is not needed here: it would only keep these tests from running when the test runner answers again." No payload change.
5. **SW-28, did not run.** The next step by reason: `no-executor` with no unblock, "SuiteWard runs them when the test runner answers again."; `executor-not-configured`, "SuiteWard runs them once the test runner is set up."; another reason, "A new push runs them."; with an unblock, "Nothing runs them for this commit now. A new push runs the tests." One comment only: no not-responding comment when the runner was already silent past the lease wait when the job was created; `executionStep` reads the clock once and carries it on `executionOutcome`.
6. **SW-2, the V1 comment,** when the canonical level is not `off`: "From now on, SuiteWard runs the approved tests on every open pull request and on every push. A results comment follows when a run ends."; under `canonical: required` also "The checks of a commit wait for its run." Unchanged without a profile or with `canonical: off`. Its only producer is the existing-baseline bootstrap (`bootstrapJob.bootstrap`), and the text does not assume that the carrier pull request is still open.
7. **SW-16, the old command:** "`/suiteward mode` is no longer a command. Name the kind of change in the approve instead: `/suiteward approve P<n>-R<m> <fix|feature|refactor> <code>`."
8. **SW-20, "What went wrong":** one line per problem, each linking its table, for example "3 approved tests failed.", "1 approved test gave no result.", "1 approved test is weakened by this change.", "2 tests this change adds or edits fail.", "The receipt meets no kind of change." The kinds section of the page adds "It looks only at the tests this change adds or edits."
9. **SW-23:** the label is "Removed test case". It counts a removed line of a `_test.go` file shaped like a table row: a keyed entry (`"…": …,`) or a struct literal row (`{…},`). False positives are accepted: a marker is a line to look at, not a verdict.

The installer texts (SW-15, SW-26, SW-27, SW-29, SW-30, SW-37) follow decisions 8 to 14; each brief fixes the exact words, and the owner reads them in the live tests.

## Live tests

With a development build before the pull request, one at a time, on `SuiteWard-m21c`:

1. Co-located on Windows with Docker (SW-25, SW-30 item 3, SW-28 with the runner stopped).
2. Co-located with Podman on a machine of its own, `podman-machine-default` stopped by the owner (SW-27 on a 6.1 machine, SW-29 with the machine stopped). Stopping the default machine takes itsaplan offline, so this step is one block with no commit and no card move; its findings go to the ledger until the owner restarts the default machine.
3. Co-located on Linux, a WSL Ubuntu 24.04 distro with a UID 1001 user and Podman 4.9.3 (SW-37, exit 137).
4. Isolated, on a throwaway AlmaLinux 9 distro: the sandbox tests and the host step (SW-24's "Next" and its refusal from a folder the account cannot read, SW-14). SW-24's upgrade accepts only a release image, so it is seen in the isolated flow after the merge.
5. Last, the Windows test runner started by a real logon.

The owner posts every `/suiteward` command and reads the `Security limit` row (D-SECURITY-LIMIT-LABEL). After the merge, on `v0.5.0-alpha.4`: the full isolated flow, SW-26 (the one-line install on WSL and the Windows `.exe`) and the owner's acceptance test. This repository shows the new comments only once its governing host runs alpha.4.
