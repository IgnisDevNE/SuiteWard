# M1.4: GitHub synchronization

**Goal:** discover and reconcile pull requests over outbound GitHub access only, within a bounded API budget, with a local MCP endpoint that lets an agent request a sync and read status.

**Decisions:** D-SYNC (defaults accepted; numbers confirmed by S1), D-GITHUB-ACCESS (accepted 2026-10-11 from the S1 findings). D-IDENTITY stays open: the GitHub settings of this phase are an interim operator configuration (see the [GitHub contract](../../contracts/github.md#configuration-interim-m14)). D-COMMENT-EDIT (accepted 2026-10-11: one comment is one action) is implemented in M1.6.

**Exit:** a configured repository's PRs, heads and comments are synchronized on schedule and on MCP request, and its source tree at any commit can be read as an `inventory.Tree`; omitting MCP calls still converges; API use stays within budget; restart catches up. (Narrowed 2026-10-11: the original exit said "protected files are synchronized". The protected inventory of a PR head is built in M1.6-B, which produces the integrity evidence from it; M1.4 records the heads and provides `Reader.Tree`.)

- **A1** — the App JWT (RS256, standard library) and installation tokens with an explicit permission map and repository list, reused until five minutes before expiry, behind an injected clock; the token never reaches an error, a log or `fmt` output.
- **A2** — conditional GETs with an ETag cache scoped to the token identity, immutable reads without the cache, the per-process budget at half the rate limit compared in server time, bounded and copied bodies, and typed errors.
- **A3** — open PRs, PR comments, and an `inventory.Tree` over the git trees API (links and submodules typed; a truncated tree is an error; blobs read only when asked).
- **A4** — the GitHub settings, all or none (composition moved to B2, where it has a consumer).
- **B1** — observations are evidence, not governance facts: no `Tx`, no Suite revision; comment versions are append-only so edits stay visible; deletions and closed PRs are marked, never removed.
- **B2** — one tick per minute over all repositories with bounded concurrency, a coalesced per-repository job for MCP requests, `wait_until` honored across restarts, per-repository state in `/status`.
- **C1/C2** — `sync` and `status` only, local token, `Origin` validated, no approval or administration capability; MCP Streamable HTTP through the official Go SDK (revision `2026-07-28` plus legacy clients), verified with the real Claude Code client.
- **D** — both verification targets run the GitHub synchronization and the MCP listener with secrets mounted, never in the image.
- **Live test** — asserts first the permissions S1 did not measure with a narrowed token on a private repository (`GET /pulls/{n}`, commit reads) and that the granted map equals the requested one.

The phase changes what runs, so it is verified on both targets. Owner steps: add `phase/M1.4` to the deployment branch rule of the `remote-poc` environment; place the App key on the host and on the development machine for the live test; on the host, create the Podman secrets for the App key and the MCP token once task D lands.

Notes from the reviews (non-blocking): the configuration accepts an out-of-range port in `GITHUB_API_URL` and keeps the URL verbatim (B2 joins paths without a double slash); the repository count error counts items before trimming.

B2 review (2026-10-11, non-blocking): a recorded failure is not logged, so `/status` shows only its kind (C2 adds a warn log with repo, kind and status, never the error text); `github_sync_repo` for an unconfigured repository is retried as a job failure (C2 validates the repository before inserting); `ErrInvalidArgument` and unmatched read errors classify as `transport`; `ErrCreationTimeChanged`/`ErrInvalidObservation` are visible only in logs.
