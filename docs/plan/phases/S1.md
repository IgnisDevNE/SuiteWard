# S1: GitHub walking skeleton

**Goal:** prove, against real GitHub and before building the GitHub-facing phases, that SuiteWard's core loop works: an App observes a PR, publishes a required check, accepts an owner approval, and records a promotion after merge. Learn the facts that settle D-GITHUB-ACCESS, D-CHECKS, D-INTEGRATION and the numbers of D-SYNC.

**Kind:** time-boxed spike (two working days of agent effort). The code is throwaway, lives under `spikes/s1/`, and is exempt from the TDD rule. It is never imported by `internal/`.

**Exit:** a findings document `docs/spikes/s1-github.md` reviewed by the user, and decision-register updates proposed (not applied) for the four gates.

## Setup (user)

- A separate test GitHub App and a throwaway test repository under the user's control; never the SuiteWard production App or repository.
- Branch protection on the test repository requiring the spike's check, configured by hand.

## Tasks

- **S1-A Poll and check.** A small Go program authenticates as the test App, polls one repository with conditional requests, lists open PRs, computes a digest of a hard-coded glob of test files at the PR head, and publishes a check run (pending/success/failure). Record: permissions needed, rate-limit headers and ETag behavior, latency from push to check.
- **S1-B Approve and promote.** The program reads PR comments, accepts `/suiteward approve <ref>` from the configured owner login, turns the check green, detects the merge (merge, squash and rebase methods), and records the integrated SHA and the protected digest in a local JSON file. Record: how each merge method exposes the integrated source, same-SHA cases, comment edit/delete behavior, timing.
- **S1-C Findings.** Write `docs/spikes/s1-github.md`: the permission matrix, the check identity and state mapping, merge-method results, measured polling numbers, surprises, and the proposed decisions.

## Out of scope

TOTP, persistence, River, MCP, multiple repositories, installation flow.
