# M1.6a: Bootstrap and owner commands

**Goal:** bootstrap a repository's first canonical from its principal branch (ADR 0010) and turn the owner's `/suiteward approve|revoke <ref> <code>` comments into exact, TOTP-confirmed consent outcomes, each acknowledged in the PR (ADRs 0002, 0011, 0027).

**Decisions:**
- D-COMMANDS (accepted 2026-10-13): identifiers, syntax, order, ledger, bootstrap, and owner change refused;
- the ADR 0011 amendment of 2026-10-13: other accounts are ignored;
- D-TRUST and D-COMMENT-EDIT;
- D-GITHUB-ACCESS, amended from P0 for the comment write.

**Exit:** on `IgnisDevNE/SuiteWardQ`, after `setup`:
- the bootstrap summary appears in an open PR;
- the owner's `/suiteward approve P1-R1 <code>` bootstraps canonical `V1` and is acknowledged;
- a replayed or wrong code is rejected with an acknowledgment and changes nothing;
- `/suiteward revoke` on a later revision is acknowledged;
- a comment from another account gets nothing;
- restart reprocesses nothing.

This is verified on one target at a time (below).

## Verification on one target at a time

Both targets watching the same repositories would both post comments, and each has its own TOTP secret: one would reject the owner's code. D-COMMANDS forbids it as a standing rule, so only the target under test runs with the GitHub settings. The host is the default watcher of `SuiteWardQ`; the co-located stack runs with GitHub only during its own verification. The exact steps are in [HOST.md, section 6b](../../../deploy/HOST.md#6b-pr-commands-and-bootstrap-m16a) and [local development](../../local-development.md#verifying-m16a-on-the-co-located-stack).

Comments carry the instance id in their marker, and each instance ignores comments created before its own enrollment. Verify each target on a fresh PR, so that each has a bootstrap proposal of its own, and close that PR before the other target watches again: an instance answers the other's earlier commands on any open PR with an invalid-code acknowledgment.

The co-located stack was purged after M1.5, so its verification needs `local.ps1` and `setup` again, with a fresh authenticator entry.

4. **Run the scenario on the host**, on a fresh PR, with no other watcher:
   1. the bootstrap summary appears up to about 2 to 3 minutes after the PR is opened (60 s sync, 60 s bootstrap, relay), with the inventory and `/suiteward approve P1-R1 <code>`;
   2. approve `P1-R1` with the authenticator code: an approval acknowledgment in about 2 to 3 minutes, then "Bootstrap complete" (`V1`) up to a minute later;
   3. repeat the same comment and code within 30 seconds (a minute at best): a replayed-code acknowledgment; a later retry gets invalid-code;
   4. revoke with a new code: an acknowledgment that the canonical version is unchanged;
   5. optionally comment from another account: no reply;
   6. comment and quickly edit a command with a made-up code: refused as edited before it was read;
   7. `/status`: `outbox.delivered` grew, `failed` is 0.
5. **Close that PR.**
6. **Co-located stack.** Stop the host's service, start the stack with `local.ps1` and the GitHub settings, run `suiteward setup` with a fresh authenticator entry, run step 4 on a new PR, close it, stop the stack's GitHub watching, then restore the host and check its `/status` again. Do not reboot the host meanwhile: a stop does not survive a reboot.

Never put a token, code, secret or setup output in a ticket, log or message.

## Verification (2026-10-14)

Both targets ran the owner scenario on `IgnisDevNE/SuiteWardQ`, one target at a time, with the image of `1e73ffa`. In each case the smoke test passed with that exact version and schema 13.

- **Remote host (isolated), PR #13 and PR #15.**
  - The first run, on `c95c1ff`, proposed an empty `P1-R1`: the repository had no `.suiteward.yml`, so nothing was protected. The domain refused to promote it (ADR 0010). A5b fixed the proposal side, and the empty `P1-R1` was recovered by hand: revoked on the reopened PR #13, which was then closed.
  - On `f3d57cb`, every bootstrap of the approved `P2-R1` failed: the promotion time had nanoseconds, which PostgreSQL refuses. A5c fixed it.
  - On `1e73ffa`, PR #15 showed every expected acknowledgment:
    - the summary for `P2-R1`, with 13 protected files and the scope;
    - the approval;
    - a reused code ("already used");
    - an invalid code ("not accepted");
    - an edited-before-read command;
    - a revocation before promotion;
    - "Bootstrap complete" with `V1`, which says no tests ran;
    - a revocation after promotion, with the canonical unchanged.
- **Co-located stack, PR #16**, with its own enrollment and authenticator entry:
  - the summary, with the reduced-assurance paragraph;
  - the approval;
  - a reused code;
  - `V1`;
  - an edited-before-read command;
  - a revocation after promotion.

  The comment markers carry each instance's own id. The stack then went back to running without GitHub, and the host resumed watching at 20:25: `1e73ffa`, both repositories synchronizing, SuiteWardQ `enforced`, `outbox.failed` 0.

  PR #16 was closed about a minute after the host restarted, not before. During that minute the host answered the co-located commands with three invalid-code acknowledgments and one edited-before-read acknowledgment. Nothing changed and no step was used: one instance rejects the other's codes, as HOST.md 6b.5 warns. The only cost is noise on the closed PR.
- **Ruleset.** SuiteWardQ's ruleset had to be disabled briefly so the owner could push `.suiteward.yml`. When it was restored, the App check was first entered as `SuiteWard Spike / Contract`, and the protection check reported `missing-contract-check` until it was corrected to `SuiteWard / Contract`.

## Outcome

Completed 2026-10-14 on `phase/M1.6a` (PR #22).

**Delivered**
- **`commandtext`:** parses owner commands and renders every acknowledgment and the bootstrap summary. Bodies are bounded, and repository text is rendered inert.
- **Governance writes:**
  - `CreateSuite`;
  - `RecordAssessment`, which accepts only evidence from the service emitter;
  - outbox messages written inside the use cases, atomically with their facts.
- **Command ledger (migration `00013`):**
  - every disposition, including `unknown-proposal`;
  - the instance id;
  - consumed TOTP steps bound to their command.
- **GitHub writes:**
  - `rest.Post`, with no cache, counted in the budget, and status-only errors;
  - the comment writer, holding `pull_requests: write` only;
  - the branch head;
  - the bot identity.
- **Jobs:**
  - `github_bootstrap`, which never proposes an empty baseline;
  - `github_commands`, with the sync watermark, edited-first, TOTP ±1, replay protection and bounded retries;
  - the `github_comment` publisher, which reads back the marker before posting and binds each receipt to its comment.
- **Deployment:** HOST.md 6b describes the one-target-at-a-time scenario.

**Evidence**
- The P0 write measurement.
- `check` and `persistence` on a freshly reset database at every merge.
- The race-enabled integration run.
- PR CI, including coverage.
- Both targets, as recorded under Verification.

**Deviations**
- Migration `00013` was edited in place before its first deployment. It is frozen from now on.
- `unknown-proposal` was added after the contract freeze, because ADR 0011 requires the acknowledgment.
- A6a's composition test was written after the code. A5b later added a mutation-checked composition test.

**Limitations**, carried to M1.6b (see its backlog):
- ADR 0010's path that bootstraps from the first PR carrying tests is not built.
- "Eligible for promotion" overstates when a bootstrap is blocked.
- A failing `github_bootstrap` is visible only in the journal. `/status` excludes its job counts.
- A repository removed from the configuration without re-running setup stalls commands silently.
- TOTP ±1 leaves about 30 to 60 s to post a code. Owner codes were rejected as stale several times.
- The flaky `TestProbeWithoutAServerTimesOut` is tracked separately.
