# M1.7b: Bootstrap from the first test PR

**Goal.** A repository whose default branch has no protected files adopts SuiteWard from the first PR that carries tests ([ADR 0010](../../decisions/0010-repository-bootstrap.md), "New repository or repository without an initial test contract"). That PR gets:
- a bootstrap proposal from its exact head;
- a "Bootstrap ready for integration" check after the owner's approval;
- V1, promoted from the exact merge commit after the merge.

The phase also adds one comment per new change-proposal revision, with the protected changes and the copyable command.

**Depends on:** M1.7. Planned 2026-10-15 with the advisor.

**Decisions:**
- The ADR 0010 amendment of 2026-10-15: origin kinds, precedence, which PR.
- The D-CHECKS amendments of 2026-10-15: `bootstrap-ready`, the bootstrap proposal from a PR, the revision comment.
- The D-SYNC amendment of 2026-10-15: latency moves to [M1.7c](M1.7c.md).

**Contracts:**
- [persistence](../../contracts/persistence.md#bootstrap-from-a-pr-and-the-revision-comment-m17b-normative): origin kind, `BaselineProposalFor`, `AssessBootstrapHead`, `PromoteMerge` without a canonical, the revision hook;
- [runtime](../../contracts/runtime.md#bootstrap-from-a-pr-and-the-revision-comment-m17b): who writes what, checks and merges without a canonical, the comment keys.

**Exit:**
- **Promotion.** With no canonical and no protected files on the default branch, the first PR carrying tests gets a bootstrap proposal from its head, a readiness check after approval, and V1 from its exact merge commit.
- **No PR head without a merge.** A PR head never becomes canonical without the merge; the domain enforces this.
- **Precedence.** Protected files on the default branch make the existing-baseline path win.
- **Revision comment.** Each new change-proposal revision gets one comment.

## Verification plan

**Per task:** `check`, `persistence` on a freshly reset database for A1 and A3, RED observed, and `sw-reviewer`.

**Phase:** `check`, `persistence`, the race integration run, a whole-phase review, and the advisor.

**The two targets use separate repositories,** so they can run at the same time with no stop and restore. The host watches `SuiteWardQ`, `SuiteWardQ-private` and `SuiteWardQ2`. The co-located stack watches only `SuiteWardQ3`.

**Owner preparation:**
- Create `IgnisDevNE/SuiteWardQ2` (for the host) and `IgnisDevNE/SuiteWardQ3` (for the co-located stack). Both are public and contain only a README.
- Install the test App and the bot App on both.
- Add a strict ruleset requiring `SuiteWard / Contract` (App 5257122) and `CI / test`.
- On the host:
  - add `SuiteWardQ2` to `GITHUB_REPOSITORIES`;
  - run `setup` again with a new authenticator entry and the test checks of every configured repository. This re-keys TOTP for every host repository: the old host entry stops working for `SuiteWardQ` as well.

**Host, on SuiteWardQ2:**
1. `/status` shows `awaiting-initial-contract`, and a README-only PR shows `bootstrap-pending`.
2. A PR adds `tests/` and `.github/workflows/ci.yml`. It gets a bootstrap comment from its head and `in_progress` with `P1-R1`.
3. A protected push gives R2 and a new comment.
4. After approval, the check is `success`, "Bootstrap ready for integration".
5. After the merge, V1 is promoted from the merge commit, with a comment.
6. A later change PR gets the `revision` comment and promotes V2.

**Co-located, on SuiteWardQ3,** after the stack is purged and set up again: steps 1, 2, 4 and 5.

**Regression, on SuiteWardQ (host):** a change PR shows the `revision` comment.

**Known limitations planned:**
- While a PR bootstrap is under way, `/status` still shows the bootstrap job's `awaiting-initial-contract` for that repository. The check carries the real state.

**Covered only by tests:**
- the branch path superseding a pending `pull` proposal;
- a blocked first-test merge;
- a non-carrier merge with no canonical;
- two PRs carrying tests at once.
