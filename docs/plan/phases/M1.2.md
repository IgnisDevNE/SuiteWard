# M1.2: Runtime

**Goal:** a runnable `suiteward serve` that loads configuration, migrates, composes the PostgreSQL unit of work and the artifact store, runs River workers whose jobs are enqueued in the same transaction as the governance write, delivers publications through an outbox, and shuts down gracefully.

**Decisions:** D-RUNTIME (accepted).

**Exit:** the binary starts against a fresh database, processes an enqueued job end to end, survives a restart without losing work, and stops within the configured timeout; real PostgreSQL tests in CI; the same image passes a smoke run on both [verification targets](../README.md#verification-targets).

## Tasks

- **M1.2-C0 Contract** (orchestrator): add `Enqueue` and `Outbox` to the `Tx` port and the outbox table in [persistence](../../contracts/persistence.md#jobs-and-outbox-m12-normative), and freeze the settings, commands, endpoints, lifecycle and container conventions in [runtime](../../contracts/runtime.md). Frozen before the others start. Changes made while planning: the outbox row is the single owner of delivery state (the relay is a periodic River job, with no River job per message); River's schema is vendored into goose migrations; the first job is a diagnostic `probe` run through `suiteward probe`.
- **M1.2-A Configuration** — owns `internal/config/**`. Environment variables plus file-mounted secrets; validation errors name the setting and never print secret values; the environment is injected, never read from the process. Tests for required, defaulted and invalid settings.
- **M1.2-B Transactional jobs and outbox** — owns the code of the port (`internal/application/governance/uow.go`, `governancetest/**` including conformance cases), `internal/adapters/postgres` additions (queries, `tx.go`, sqlc output), the new migrations (River vendored, then the outbox), `internal/adapters/river/**` and `go.mod`/`go.sum`. River job insertion inside `UnitOfWork.Do`; outbox rows written with the governance fact; the relay with bounded retries and a visible terminal state; the `probe` job and publisher. Tests: rollback removes both the fact and the job/outbox row; a crash re-delivers; terminal state after the retry limit. Early checks: River with Go 1.27.2, with the harness's schema-per-test `search_path`, and the stuck-job rescue interval.
- **M1.2-C Composition and lifecycle** — owns `cmd/suiteward/**`, `internal/app/**` and the Chi dependency. `serve` and `probe` commands, migration on start, `/healthz`, `/readyz`, `/status`, signal handling, graceful shutdown with timeout; `main` is one call into `internal/app`. Tests with a real database: start, health, stop within timeout, restart resumes pending jobs.
- **M1.2-D Packaging and deployment** — owns `deploy/**`, the image build file, and a deployment workflow. One OCI image built in CI and published to the registry chosen in D-DEPLOY; a local Podman definition (co-located) and a Podman quadlet unit for the remote host (isolated); an approval-gated GitHub Actions deployment to the remote host; a smoke script (health, migrate, one job end to end, restart) run against both targets. Builds on the S1 deployment findings and the settled D-DEPLOY. Details fixed while planning: image `ghcr.io/ignisdevne/suiteward`; PostgreSQL as a rootless container beside the service on both targets; a host firewall step for the IMDS; the host runbook `deploy/HOST.md` with copy-paste steps the owner runs through Session Manager (including removing the S1 spike); the smoke script is POSIX `sh` using `podman` and `curl`, run on this PC inside the Podman machine and on the host in the owner's session; the S1 publish workflow is removed.
- **M1.2-I Integration** (orchestrator): phase checks, CI service wiring if needed, dual-target smoke results in the PR.

## Outcome

Delivered 2026-10-10 in PR 14. Task D was done in two parts (files against the frozen contract first, then the real image and the local smoke once the binary existed), and the runtime contract was amended after review (the 5 s forced-stop grace, what `/readyz` reflects, the `/status` job counts). D-JOB-RETENTION is open.

Exit criteria:

1. Starts against a fresh database, processes an enqueued job end to end, survives a restart and stops within the timeout: proven by integration tests against real PostgreSQL in CI and by both smoke runs below.
2. Real PostgreSQL tests in CI: the `coverage` job runs `-tags=integration` against a PostgreSQL service; patch coverage 98.23% at the last Go revision.
3. The same image on both verification targets: the Containerfile and Go code are the same on both, but the local run used a local build of that source (linux/amd64) and the remote run the image built by CI (multi-arch, arm64 pulled, index digest `sha256:f28d6c545d6b6b388407cde504eea0c4a39f675a20f6ff24faa1980245a3d878`).

Smoke results (`deploy/smoke.sh`, the same script on both):

| Step | Local (Podman 6.0.2, rootful, WSL, amd64) | Remote (Podman 4.9.3, rootless, Ubuntu 24.04, aarch64) |
| --- | --- | --- |
| `/readyz`, `/healthz`, `/status` | 8, 7, 13 ms | 26, 13, 25 ms |
| `/status` version | `sha-7ce7b43...` | `sha-2882462...` |
| probe (job `completed`, outbox `delivered`) | 802 ms | 4803 ms |
| service restart | 378 ms | 375 ms |
| ready after restart (including the restart) | 1394 ms | 425 ms |
| delayed probe job (due in 20 s) survived the restart | yes, 19.4 s wait | yes, 20.1 s wait |
| total | 21.9 s | about 25 s |

The probe took longer remotely and the restart took less. Likely reasons are the outbox relay (a periodic job with a 5 s default interval, so delivery depends on where the tick falls) and the different hosts; neither difference was investigated. The delayed-probe step proves that a delayed job survives a restart; it does not prove outbox durability (in the remote run the message of that probe was published after the restart, which is one observation, not a guarantee).

Checks on the remote host: the quadlets generated and started on Podman 4.9.3 rootless (the generator dry run reported no rejected key); `StopTimeout` 45; the database memory limit was applied (`402653184`); `netavark`; the first `systemctl --user restart` produced the clean shutdown sequence (`shutting down`, `http server stopped`, `River client stopped`, `job runtime stopped` with `forced:false`, `database pool closed`) within about 5 ms; the IMDS rejection rule loaded at boot through a systemd unit (`enabled`, `active`) turned the metadata token request from `200` (before the rule) to `000` (after it) on the default network and gave `000` on the `suiteward` network, while Session Manager kept working (a second session opened); every listener is on loopback; the only secret was a generated database password the owner never saw. The pulled image digest equals the digest published by CI. The host had no S1 service, secret, volume or quadlet left, so the removal section was skipped.

What went wrong during the remote run, and what it changes:

- The Session Manager terminal received pasted long lines split or with a stray control character. The first symptoms were a broken `sudo ... env ... bash` line and a `^H`.
- The `suiteward-database-url` secret was created malformed (a stray control character is the suspected cause, not confirmed). The service then exited 1 at startup with `SUITEWARD_DATABASE_URL: must be a postgres:// or postgresql:// URL` and `Restart=always` retried every 5 s (45 attempts) until the secret was recreated with a script that rebuilt it from the database password secret and checked its length and shape without printing it. The database and its password were unaffected. The settings validation did its job: the error names the variable and prints no secret.

Follow-ups, not in this PR (a change under `deploy/**` triggers a new `Deploy` run and would move the host off the digest that was tested): rewrite the long lines of `deploy/HOST.md` sections 1 and 3 as short lines, add a check of the URL secret's length and shape after creating it, and keep the one-line IMDS test as a small script. Known limits: the 45 s `StopTimeout` was checked as a value, not as behaviour under a long job; the IMDS block unit is ordered `After=nftables.service` only, so a seconds-wide window at boot before the rule loads is possible; River's producer logs an `INFO` line every 5 s for the outbox queue.
