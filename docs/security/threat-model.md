# SuiteWard threat model

- **Updated:** 2026-10-26 (the executor and its sandbox, boundary B7, and the owner's `unblock` and the preview `mode` in B3, for phase M2.1, which is designed and not implemented yet); 2026-10-24 (the Windows PATH copy of the installer, phase M1.14; the one-line install script and the fifth installer binary, the encrypted backups with their recovery kit and restore, and the change report page on loopback, phase M1.13)
- **Status:** Active. Describes the assets, actors, trust boundaries, threats and controls of the system as hardened in phase SH, for release `v0.2.0`. The rows for the one-line install, the encrypted backups, the restore and the change report page describe phase M1.13, released as `v0.4.0-alpha.1`. The row for the Windows PATH copy of the installer describes phase M1.14, released as `v0.4.0-alpha.2`. Boundary B7 and the rows of B3 for `unblock` and `mode` describe phase M2.1 ([ADR 0028](../decisions/0028-canonical-execution-and-the-receipt.md)), which is not implemented yet: their controls cite the contracts and their tests are planned.
- **Scope:** SuiteWard as installed under [ADR 0027](../decisions/0027-agent-human-trust-separation.md): the service, its GitHub App, its PostgreSQL database and its image and release pipeline.

This document backs the claims of [ADR 0007](../decisions/0007-canonical-contract-authority.md), [ADR 0012](../decisions/0012-mvp-authorization-policy.md) and [ADR 0015](../decisions/0015-required-contract-check.md). A control is cited by `file:line`, and a test by its name.

## 2. Security goal

No change to a protected file reaches the default branch's canonical contract without the owner's TOTP approval of that exact revision ([ADR 0007](../decisions/0007-canonical-contract-authority.md), [ADR 0012](../decisions/0012-mvp-authorization-policy.md), [ADR 0027](../decisions/0027-agent-human-trust-separation.md)). The published `SuiteWard / Contract` check cannot be forged by another GitHub App or by a pull request's own content ([ADR 0015](../decisions/0015-required-contract-check.md)).

Invariants behind the goal: canonical immutability, candidate non-authority, exact-revision approval, atomic promotion, and evidence is not authority ([AGENTS.md](../../AGENTS.md#invariants)).

## 3. Assets

| Asset | Why it matters | Held in |
| --- | --- | --- |
| Canonical contract and its history | The authority every approval and check is judged against | PostgreSQL; artifact volume |
| Approval authority | Turns a comment into an approval: the TOTP secret, the owner binding by numeric account id, and the consumed steps | PostgreSQL |
| GitHub App private key and installation tokens | Publish comments and check runs; read repositories | Podman secret mounted as a file; process memory |
| The `SuiteWard / Contract` check | What branch protection waits for | GitHub check runs of the App |
| Command ledger and outbox | Record every command once and publish each acknowledgment once | PostgreSQL |
| The database | Holds every asset above except the key | PostgreSQL container, private network |
| The encrypted backups and the recovery kit | A backup holds the whole database, TOTP secret included, and the kit holds the one key that opens every backup of the instance | The backup folder and wherever the operator copied them; the kit file, which the operator keeps off the machine |
| The protected files of proposals (the change report) | Proposed test files, some of them never merged, which can be part of the source of a private repository | The artifact store; the report page of the HTTP listener |
| The image and release pipeline | What runs on the host | GitHub Actions, the registry |
| The executor token and the execution results (M2.1) | The token lets a process lease jobs, download the source of every enrolled repository's commits and post results. Results are evidence that can lift a `required` gate | A secret file of the executor's account; the database |

## 4. Actors

| Actor | Capability | Position |
| --- | --- | --- |
| AI agent with repository write access | Pushes branches, opens pull requests, edits tests and `.suiteward.yml`, writes comments, reads GitHub text | Primary adversary (ADR 0027 context) |
| Outside GitHub user | Opens fork pull requests, writes comments and issue text | Adversary |
| Compromised dependency, action or base image | Runs code in CI or in the image | Adversary |
| Co-located process on the developer machine | Runs as the same OS user as SuiteWard (co-located tier) | Reduced assurance, labeled in [install.md](../install.md) section 2 and ADR 0027; the isolated tier gives the full assurance |
| Candidate code under test (M2.1) | Runs the repository's tests and dependencies in the sandbox, with the pull request's own source | Adversary: the sandbox is its only barrier |
| Trusted host administrator | Controls the host, the database and the credentials | Trusted: out of scope (section 7) |
| Owner | Holds the authenticator and the GitHub account bound at setup | Trusted principal |

## 5. Trust boundaries

Two installation tiers share the same image ([ADR 0027](../decisions/0027-agent-human-trust-separation.md); [verification targets](../plan/README.md#verification-targets)):

| Tier | Shape | Assurance |
| --- | --- | --- |
| Isolated | Another OS user, VM or host; outbound-only; status and MCP reached through a forwarded loopback port | Full |
| Co-located | Same machine and user as the agent; SuiteWard reports the tier | Labeled, as published |

| Id | Boundary | Crossing |
| --- | --- | --- |
| B1 | GitHub to SuiteWard | Polling reads of pull requests, comments, trees and check runs; no webhooks |
| B2 | SuiteWard to GitHub | App installation tokens, one per purpose; writes limited to comments and check runs |
| B3 | Owner to SuiteWard | `/suiteward approve <ref> <code>` in a pull request comment |
| B4 | Host listeners | `/status` on loopback; `/mcp` on loopback with a bearer token |
| B5 | SuiteWard to PostgreSQL | Private container network, secret-mounted URL, history tables protected by triggers |
| B6 | CI and release to registry to host | Workflows, owner-approved environments, image promoted by digest |
| B7 | SuiteWard to the executor and its sandbox (M2.1) | The executor API with a bearer token, commit archives streamed through the service, and candidate code in a disposable container |

When the downloader is BusyBox wget, which can accept any TLS certificate, it says so too. `SUITEWARD_RELEASE_BASE`, the variable that points the script at another origin for its own test, never turns the HTTPS rule off: the script refuses a base that is not `https://` or `file://` before it downloads, and refuses a `file://` base with wget, so the first URL is always `https://` or `file://`. With a base set, curl is limited to `--proto '=https,file' --proto-redir '=https'`. Not prevented: wget is given no protocol flag, so its redirects are not restricted (it may follow a redirect from an `https://` URL to `http://`), and BusyBox wget may not check certificates at all; the script is not verified before it runs, so the first trust is GitHub's HTTPS and the tag the user named; without cosign, `SHA256SUMS` comes from the same place as the binary and only TLS authenticates it, and over BusyBox wget not even that; a base of someone else's `https://` server, or a `file://` directory, that is set in the environment of the run replaces GitHub as the origin of both files, so the install guide tells the user, and [agent-install.md](../agent-install.md) tells an agent, never to set it; a compromised release workflow or owner account. Without `SUITEWARD_VERSION` the script takes GitHub's latest release, which is never a pre-release ([install.md](../install.md), section 4.1) | `scripts/install_test.sh` ("a cosign failure stops the install", "the pinned identity", "a wrong hash", "a binary that SHA256SUMS lists twice", "a binary that SHA256SUMS does not list", the `SUITEWARD_REQUIRE_COSIGN` cases, "busybox wget without cosign", "the production URLs and curl flags" with and without cosign, and the release base cases: "the release base '…' is refused" for `http://`, another scheme and a bare path, "a file:// release base is accepted", "an https:// release base is accepted", "wget with a file:// release base is refused") | CICD-SEC-3; CICD-SEC-9 |
| T, E | The piped script runs only partly, or does more than put one file in place | The whole script is one function that its last line calls, so a download that stops anywhere defines functions and runs nothing. It installs one file, runs nothing it downloaded and calls no `sudo`: a directory it cannot write is an error that names it. `SUITEWARD_VERSION` must have the shape of a release tag, after a character-set check, so it cannot reach another address or file name. The file is staged in the target directory, hashed there and moved in with one `mv`, and every temporary file goes on exit and on INT, TERM and HUP. Not prevented: a user who pipes a script they did not read | `scripts/install_test.sh` ("the script cut after N lines", "sudo", "pre-release tags", "a staged copy that differs from the verified download", "the target is a directory", the signal cases) | CICD-SEC-3 |

[ADR 0028](../decisions/0028-canonical-execution-and-the-receipt.md) records the design, and the [runtime contract](../contracts/runtime.md#execution-m21-normative) and the [GitHub contract](../contracts/github.md#m21-execution-reads-normative) give the wire. This boundary is not implemented yet, so a control cites its contract, and a test is named by the task that will write it. The row moves to the `file:line` form when the task lands.

## 7. Out of scope

- The trusted host administrator: SuiteWard trusts the instance's authorized administrators and does not claim to defeat a malicious one with direct database, storage and credential control ([ADR 0007](../decisions/0007-canonical-contract-authority.md), line 47; [ADR 0012](../decisions/0012-mvp-authorization-policy.md), line 49).
- Denial of service by GitHub itself: an outage or a rate limit delays synchronization and checks; SuiteWard waits and resumes ([install.md](../install.md), status fields `waitUntil` and `lastError`).
- The assurance of the co-located tier beyond what [install.md](../install.md) section 2 states.
- The TOTP secret is stored in the database without column encryption, accepted for the MVP (owner, 2026-10-20); encryption with a host key is an M3 candidate ([ADR 0027](../decisions/0027-agent-human-trust-separation.md)).
- Execution evidence on the co-located tier against a determined agent: it can read the executor token and report what it likes, and run as the user that owns the sandbox. The pins catch drift, not that agent (ADR 0028, section 13). Remote attestation is an M3 or managed-service candidate.
- Code that behaves differently under test: markers and the layers of ADR 0028 detect and flag, and do not prove.
- A maintainer command to authorize or refuse the merge of a fork pull request: fork pull requests fail closed until a deeper analysis ([decision register](../plan/decisions.md#post-mvp)).
