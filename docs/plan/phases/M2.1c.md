# M2.1c: fixes from the M2.1b acceptance test

**Goal:** fix what the owner's acceptance test of [M2.1b](M2.1b.md#the-owners-acceptance-test) found, before any new profile, and ship it as `v0.5.0-alpha.4`. First the two signals that can mislead the owner before an approval (SW-22, SW-23); then the results comment and page, the installer and the test runner, the install guide, the removal of `/suiteward mode`, the note of `doctor` for a Podman older than 5.0, and the measurement of this repository's runs. One phase, so one round of live tests ([D-ROADMAP](../decisions.md#d-roadmap-the-order-after-m21), owner, 2026-11-03). The phase card is SW-39 in the itsaplan project `SW`, and its subtasks are the cards below (20 at the start, 21 since decision 18, 22 since decision 21).

## Owner decisions (2026-11-03)

1. **SW-22: no "met" next to failing approved tests.** When the approved tests have a failed, missing or flaky test, or a test is weakened, the results comment does not say which kind of change the receipt meets: it says that the approved tests failed and sends the reader to the report. Only under `receipt: required`, when the next step is an approve, it asks for the approval with the existing approve-with-mode command. No new command.
2. **SW-20: a short "What went wrong" section** right after "Tests by state" on the pull request page, one line per problem with a link to its table. The long tables stay where they are; with nothing wrong, the page keeps today's order.
3. **SW-23: a new marker kind, "removed test case",** for Go only in this phase.
4. **SW-26: only the warning changes.** A release binary is never called a development build; no trust claim changes.
5. **The release comes after the merge,** as in M2.1b: the live tests with a development build before the pull request; the merge; `v0.5.0-alpha.4` cut from `main`; then the full isolated flow, SW-26 and the owner's acceptance test on the release.
6. **Memtrace is indexed only if it is stale,** with no label change.
7. **A new test repository:** `IgnisDevNE/SuiteWard-m21b` is deleted, and the co-located live tests use a new `IgnisDevNE/SuiteWard-m21c` with new test Apps.

Accepted with the plan (the orchestrator's proposals, 2026-11-03):

## The texts

Fixed with the plan; small grammar fixes are the reviewer's.

1. **SW-22, results comment.** When the approved tests have a failed, missing or flaky test, or at least one test is weakened, the kinds block is replaced by: "The approved tests failed (3 failed, 1 weakened), so this comment does not say which kind of change (`fix`, `feature`, `refactor`) this change is. The details are in the report." The parentheses show only the counts above zero; when the only problem is a weakened test, it opens with "This change weakens an approved test (1 weakened), …". Only under `receipt: required` and with the next step `NextApprove`, it adds "If you want to approve this revision anyway, name the kind of change that the report shows as met, and comment:", which introduces the `modeApproveCommand` block that `nextText` already prints under `ApproveMode` (the command is not shown twice). Never with `NextBlocked`, and never when nothing awaits approval. If the Receipt check states the kinds, it follows the same rule ([ADR 0029](../../decisions/0029-results-communication.md) wording rule).
2. **SW-21, the link.** Right after the approved counts: "See the full report here:" and the link to the pull request page (its text stays "pull request page"), then the `linkNote`. With no canonical run, right after the lead; with no web address, `noLinkText` takes the same place.
3. **SW-21, the tables.** "Tests this change adds or edits: N." is followed by a table `| What the test shows | Tests |` with today's seven rows, all shown. The kinds block reads "Does the receipt meet each kind of change? It looks only at the tests this change adds or edits." and a table `| Kind of change | Met? | Why not |` (Yes or No, and today's sentence). The Receipt check summary and the refusal acknowledgment (`countsText`) use the same tables.
4. **SW-1, not responding.** The shared `unblockOffer` becomes "To go on without these tests, the owner can comment `/suiteward unblock <code>`, where `<code>` is a current code from the authenticator app. That lets this commit pass its checks without them, and they do not run for this commit. A new push runs them." With `Unblock`, it follows "The checks of this commit wait for these tests."; without it (advisory, or an approval still missing): "Nothing waits for these tests. An unblock is not needed here: it would only keep these tests from running when the test runner answers again." No payload change.
5. **SW-28, did not run.** The next step by reason: `no-executor` with no unblock, "SuiteWard runs them when the test runner answers again."; `executor-not-configured`, "SuiteWard runs them once the test runner is set up."; another reason, "A new push runs them."; with an unblock, "Nothing runs them for this commit now. A new push runs the tests." One comment only: no not-responding comment when the runner was already silent past the lease wait when the job was created; `executionStep` reads the clock once and carries it on `executionOutcome`. *Added after the live round (task A12):* the first two sentences also come first whatever the next step is (the unblock offer, an approve, a fix or a block), and not only when there is none, and the Contract check of such a head says "Next: SuiteWard runs the approved tests when the test runner answers again." (or "once the test runner is set up."), before the unblock command.
6. **SW-2, the V1 comment,** when the canonical level is not `off`: "From now on, SuiteWard runs the approved tests on every open pull request and on every push. A results comment follows when a run ends."; under `canonical: required` also "The checks of a commit wait for its run." Unchanged without a profile or with `canonical: off`. Its only producer is the existing-baseline bootstrap (`bootstrapJob.bootstrap`), and the text does not assume that the carrier pull request is still open.
7. **SW-16, the old command:** "`/suiteward mode` is no longer a command. Name the kind of change in the approve instead: `/suiteward approve P<n>-R<m> <fix|feature|refactor> <code>`."
8. **SW-20, "What went wrong":** one line per problem, each linking its table, for example "3 approved tests failed.", "1 approved test gave no result.", "1 approved test is weakened by this change.", "2 tests this change adds or edits fail.", "The receipt meets no kind of change." The kinds section of the page adds "It looks only at the tests this change adds or edits."
9. **SW-23:** the label is "Removed test case". It counts a removed line of a `_test.go` file shaped like a table row: a keyed entry (`"…": …,`) or a struct literal row (`{…},`). False positives are accepted: a marker is a line to look at, not a verdict.

The installer texts (SW-15, SW-26, SW-27, SW-29, SW-30, SW-37) follow decisions 8 to 14; each brief fixes the exact words, and the owner reads them in the live tests.
