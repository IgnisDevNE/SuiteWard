# M1.8: MVP acceptance

**Goal:** an installable MVP that the owner uses on SuiteWard itself.

**Decisions:** D-RELEASE (supported platforms and license notices) before publishing a release.

**Exit:** on both [verification targets](../README.md#verification-targets) (local container, co-located; remote host, isolated), a fresh install following the guide protects a real repository end to end (bootstrap, protected PR blocked, TOTP approval, merge, promotion, correction); backup and re-bootstrap are rehearsed; SuiteWard's own tests are governed by SuiteWard; assurance wording matches ADR 0014 and ADR 0027.

## Tasks (refined before start)

- **M1.8-A Install guide and packaging** — container image and local binary, configuration reference, tier guidance, and both installation paths (local container; remote host with approval-gated deployment).
- **M1.8-B Backup and re-bootstrap runbook** — `pg_dump` plus artifact-volume tarball; restore rehearsal; re-bootstrap from the protected main branch.
- **M1.8-C End-to-end acceptance and dogfooding** — scripted acceptance against a test repository; enable on SuiteWard.

## Decisions to take at planning (prepared 2026-10-17)

Each one is the owner's. They are listed with the options and a recommendation.

1. **D-RELEASE: platforms, versions and license notices** (needed before a release).
   - **Recommended platforms:** the container image only (`linux/amd64`, `linux/arm64`). A native local binary waits until after the MVP. Both verification targets already run the image.
   - **Versions:** `vX.Y.Z` tags on GHCR, plus a moving `latest-stable` tag. `deploy` stays our internal promotion tag.
   - **License notices:** third-party notices generated from `go.mod` at build time and shipped inside the image.
2. **The update channel for the end user.**
   - **Recommended:** the user pins a version tag and updates when they choose, with `podman pull` and a restart.
   - The opt-in alternative: Podman auto-update on `latest-stable`.
   - Either way, no approval of ours sits in their path. Our `remote-poc` promote gate stays for our own verification.
3. **GitHub App creation for the end user.** Today the user would create the App by hand: the permissions, the private key and the installation. This is the heaviest install step.
   - **Option A:** GitHub's App manifest flow. A one-click page creates the App with the exact permission map, and `setup` consumes the result.
   - **Option B:** a guided manual checklist in the install guide.
   - **Recommendation:** B for the MVP, with A in the backlog, unless the acceptance shows B is too error-prone.
4. **TOTP tolerance** (D-COMMANDS, "before M1.8").
   - Today: ±1 step of 30 s around the comment's `created_at`.
   - The data: one refusal for timing in the M1.7b live run, none in M1.7c. The `would_match` log lines give the offsets.
   - **Recommended:** keep ±1, read the host journal's `would_match` lines first, and widen to ±2 only if they show near misses.
5. **Deploy from `main`.** Dogfooding on SuiteWard needs the host to run a merged build.
   - Add `main` to the `deploy.yml` trigger and to the `remote-poc` deployment branches.
   - **Recommended:** yes, with the promote approval kept.
6. **The dogfooding target.** **Recommended:** the remote host (isolated), with SuiteWard's own `CI / test` as the test check, after the acceptance run on a test repository.
7. **The backup scope for the MVP.** Plain `pg_dump` plus the artifact-volume tarball, kept by the owner. Encrypted backups and guided restore stay after the MVP (ADRs 0019–0021). **Recommended:** accept plain backups for the MVP, with the runbook warning that a backup holds the TOTP secret.

## Backlog carried into M1.8 (known limits and loose ends)

- **Not exercised live:** the default-branch bootstrap path (V1 at approval from a branch proposal) and the one-click editor link for a branch name containing `/`. The acceptance run should cover both.
- **Command limits:**
  - About 150 protected files per `JOB_TIMEOUT` for a `propose`.
  - Moving the reads out of the commands queue, or raising `JOB_TIMEOUT`, is open.
- **Carrier rejections:** a mistyped `skip` or `propose` on the carrier turns it `failure`, because the ledger does not record the verb. The carrier gets one cancelled comment per revision.
- **Merges before V1:** they read trees for every merge. A tree unreadable for 30 minutes stalls that repository's merge queue.
- **Sync and wake-ups:**
  - `sync_repo` (MCP) requests are not counted in the pacing.
  - A wake-up check and insert are not atomic, so there is one extra job per concurrent waker.
  - The wake-up Warn line drops the error, by the contract's rule.
- **Orbit:**
  - The Node preload fix is merged upstream (PR #69) but is in no released build: 2.163.65 predates it.
  - After every Orbit reinstall, repeat the extraction in [orbit.md](../orbit.md), known issue 5.
- **Memtrace:** the MCP server of the orchestrator session was disconnected through M1.7b and M1.7c. Reconnect it, or keep the documented fallback.
