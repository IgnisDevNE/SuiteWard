# M1.6a: Bootstrap and owner commands

**Goal:** bootstrap a repository's first canonical from its principal branch (ADR 0010) and turn the owner's `/suiteward approve|revoke <ref> <code>` comments into exact, TOTP-confirmed consent outcomes, each acknowledged in the PR (ADRs 0002, 0011, 0027).

**Decisions:**
- D-COMMANDS (accepted 2026-10-13): identifiers, syntax, order, ledger, bootstrap, and owner change refused;
- the ADR 0011 amendment of 2026-10-13: other accounts are ignored;
- D-TRUST and D-COMMENT-EDIT;
- D-GITHUB-ACCESS, amended from P0 for the comment write.

**Exit:** on `IgnisDevNE/SuiteWardQ`, after `setup`:
- the bootstrap summary appears in an open PR;
- the owner's `/suiteward approve P1-R1 <code>` bootstraps canonical `V1` and is acknowledged;
- a replayed or wrong code is rejected with an acknowledgment and changes nothing;
- `/suiteward revoke` on a later revision is acknowledged;
- a comment from another account gets nothing;
- restart reprocesses nothing.

This is verified on one target at a time (below).

## Verification on one target at a time

Both targets watching the same repositories would both post comments, and each has its own TOTP secret: one would reject the owner's code. D-COMMANDS forbids it as a standing rule, so only the target under test runs with the GitHub settings. The host is the default watcher of `SuiteWardQ`; the co-located stack runs with GitHub only during its own verification. The exact steps are in [HOST.md, section 6b](../../../deploy/HOST.md#6b-pr-commands-and-bootstrap-m16a) and [local development](../../local-development.md#verifying-m16a-on-the-co-located-stack).

Comments carry the instance id in their marker, and each instance ignores comments created before its own enrollment. Verify each target on a fresh PR, so that each has a bootstrap proposal of its own, and close that PR before the other target watches again: an instance answers the other's earlier commands on any open PR with an invalid-code acknowledgment.

The co-located stack was purged after M1.5, so its verification needs `local.ps1` and `setup` again, with a fresh authenticator entry.

4. **Run the scenario on the host**, on a fresh PR, with no other watcher:
   1. the bootstrap summary appears within about a minute, with the inventory and `/suiteward approve P1-R1 <code>`;
   2. approve `P1-R1` with the authenticator code: an approval acknowledgment, then "Bootstrap complete" (`V1`), after about 2 to 3 minutes;
   3. repeat the same comment and code: a replayed-code acknowledgment;
   4. revoke with a new code: an acknowledgment that the canonical version is unchanged;
   5. optionally comment from another account: no reply;
   6. comment and quickly edit a command with a made-up code: refused as edited before it was read;
   7. `/status`: `outbox.delivered` grew, `failed` is 0.
5. **Close that PR.**
6. **Co-located stack.** Stop the host's service, start the stack with `local.ps1` and the GitHub settings, run `suiteward setup` with a fresh authenticator entry, run step 4 on a new PR, close it, stop the stack's GitHub watching, then restore the host and check its `/status` again.
