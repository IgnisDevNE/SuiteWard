# M2.1: canonical execution, the receipt, and the Go profile

**Goal:** SuiteWard runs tests itself, in disposable sandboxes driven by a separate executor. It runs the approved tests on each head (canonical execution, ADR 0008's M2), and it runs the tests a pull request adds or changes on the head and again on the base source, so the owner sees whether they detect the change before approving (the receipt). Go is the first ecosystem; M2.2 adds Python and M2.3 TypeScript. Everything is built from scratch.

## Owner decisions (2026-10-26)

1. **One engine, two plans.** The canonical plan runs the governing tests on the head: the canonical version until a consent covers the head, then the consented revision. The receipt runs the revision's tests on the head and on a base-side tree. Both are evidence about a head and never enter the consent binding (D-APPROVAL-CONTEXT holds).
2. **The canonical declaration decides** what is a test and what reverts to the base; the head can add, never silence.
3. **The mode comes from the owner, never from candidate text.** The gating mode travels in the approve, `/suiteward approve P<n>-R<m> <fix|feature|refactor> <code>`; `/suiteward mode <fix|feature|refactor>`, with no code, only sets the preview shown in the receipt.
4. **A governed policy in `.suiteward.yml`:** `execution.canonical: off|advisory|required` and `execution.receipt: off|advisory|before-approval|required`, advisory and advisory by default. The receipt gates the approval; canonical execution gates the `SuiteWard / Contract` check. The canonical policy governs the pull request that changes it.
5. **Failure rules.** A receipt that is pending, failed, unavailable or not meeting the mode refuses an approve under `receipt: required` (and a pending one under `before-approval`), against the head current when the command is processed. The code is verified and consumed first, so a refused comment cannot be reused with another mode; the check does not change, and a retry waits for the next code. After an approval, a push that breaks the approved tests keeps the approval, and `canonical: required` fails the Contract check until a push fixes it.
6. **A separate executor.** The service keeps the App key and the database and never gets a container-runtime socket. Sandboxes are disposable, hold no secret and have no network at all: the executor fetches the dependencies the `go.sum` names from the Go module proxy, validated and bounded, and hands them to the sandbox with the source (owner, 2026-10-26, after the sandbox spike; it replaces "network only for the dependency install"). Co-located: the executor runs on the agent's machine, with reduced assurance. Isolated: it runs on the host under its own account.
7. **Where the receipt shows:** a non-required `SuiteWard / Receipt` check per head (`failure` only on FAILS or MISSING, otherwise `success`), a fixed line with a link in the revision comment, which is still posted once and never edited, and the full receipt on an HTML page served on loopback.
8. **Sealing.** On the isolated tier the agent never reaches the host; the executor's binary and image are pinned to the signed release and checked by `doctor`, sandbox images are pinned by digest, and every result records what ran. On the co-located tier this catches drift, not a determined agent, and is stated as reduced assurance. Remote attestation is an M3 or managed-service candidate.
9. **Opt-in.** Nothing runs until the canonical declaration names a profile (`execution: {profile: go}`), so turning execution on is a governed change approved with TOTP; the advisory defaults apply once a profile is named. A Receipt check whose receipt could not be produced is `neutral`, never `success`.
10. **The escape, `/suiteward unblock <code>`.** When a head's run is unavailable (the executor is down, for one), the owner unblocks that head with a TOTP code: it lifts only an unavailable run, never failing tests or a pending run, is recorded, and both checks of the head say so. A new push needs its own unblock.
11. **Levels without a profile are an invalid declaration,** so nobody believes a policy is on while nothing runs.
12. **Order:** Go, Python, TypeScript. The isolated host is enlarged for the verification (the owner's action). This repository's test helpers join the protected `include` in this phase.
13. **One rule for what a text says about running tests (2026-10-27).** M1 ran no tests; SuiteWard does from now on. No text or current document says that SuiteWard does not run tests, with no variant by profile, and only a text computed from a run says what ran ([runtime contract](../../contracts/runtime.md#what-a-text-says-about-running-tests)). Every current document is updated (D1); ADRs and past phase pages keep their words, and an ADR that states the M1 claim as a rule gains a note.
14. **The executor's pin on the isolated tier (2026-10-27).** `install host` requires `--sha256sums`, so the executor binary is pinned to the signed release; `doctor` fails an isolated executor whose pin names no release asset or whose binary differs from the pin (it never reads the sums file itself). The co-located tier keeps a `doctor` warning.
15. **Where the live runs happen (2026-10-27).** Before the pull request: the co-located tier on Docker with a development build, and on a throwaway AlmaLinux 9 WSL distro the sandbox tests under rootless Podman and the host step. The full isolated flow runs after the merge on the published alpha: the isolated install accepts only the release image, and the release's `SHA256SUMS` is what the pin checks.
16. **A nested module cannot silence an approved test (2026-10-27, from the whole-phase review).** In the canonical plan only a `go.mod` that the governing manifest lists excludes the tests under it as `nested-module`. Under any other nested `go.mod`, one the head added for example, the test runs and go's setup failure reads `FAIL`. As implemented: a head `go.mod` at a path the governing scope covers is dropped from the composed tree with the other head files the manifest lacks, so the tests run as usual; only one outside the scope stays and reads `FAIL`. A repository with a real nested module protects that `go.mod`.
17. **The same rule in the receipt (2026-10-27).** In the receipt only a nested `go.mod` present in the merge base or listed in the revision's manifest excludes the tests under it. Under any other, the test runs and go's setup failure counts as `FAILS`. As implemented: "listed in the revision's manifest" is a head `go.mod` at a path the expected canonical's approved patterns cover (or that it lists); a pattern only the head adds counts for nothing.
18. **The executor is never a window on the user's computer (2026-10-27, from the live run).** On Windows the co-located executor runs with no console window, stops for real when asked, and starts again after it exits.
19. **The installer's texts in plain language, in this phase (2026-10-27).** Every installer text (screens, questions, doctor rows and fixes, summaries, errors) is rewritten so that a person with little technical background understands it: what happened, whether it is a problem, and what to do. The other texts (comments, check summaries, pages) follow in a later phase.
20. **The ruleset file does not stay behind (2026-10-27).** The installer deletes the ruleset JSON it wrote for the import once the repository's protection is read.
21. **A suggested command names the same instance (2026-10-28, from the live run).** Every command the installer and `doctor` suggest carries the `--settings` and `--token-file` the person gave, so a copied command never acts on another instance. Fixed in this phase (F11b).
22. **What changes before the release, and what waits (2026-10-28, from the live run).** In this phase (F11a): the Contract check's approve command names the mode as the revision comment does; while it awaits approval under `canonical: required`, the check states the counts of a complete canonical run; the revision comment's receipt link is a hyperlink; `EXECUTOR_LEASE_WAIT` defaults to 2 minutes. In a results-communication phase before M2.2: a results comment for every pull request (also those with no protected change, and when a run is unavailable), one page per pull request with tables, the meaning of each state and the reason for each mode's summary, a signal for an approved test that a change edits and that fails in its approved version, a "test runner not responding, SuiteWard keeps trying" state with the unblock offered early, an installer that asks on screen what it can instead of taking flags (which installation, when there are several), and the remaining wording of comments, check summaries and pages.

The design is recorded in ADR 0028 (task A0).

## Outcome

**Seen live before the pull request.**
- **Co-located tier, Windows 11, Docker Desktop, a development build** (two runs, 2026-10-27 and 2026-10-28, on a throwaway repository and instance):
  - a fix whose added test DETECTS, approved with `fix`;
  - a test that detects nothing (INERT): `mode refactor` recorded as a preview, `approve … fix` refused by the receipt gate with its code used, then `approve … refactor` accepted;
  - broken code without a test change: the Contract check fails (`canonical-failing`);
  - a test weakened to accept broken code: the canonical run of the approved version fails on the head, and the check states those counts while it awaits approval;
  - `os.Exit(0)` in `init`: every test MISSING, the check fails;
  - a nested `go.mod` that the head adds: the tests fail, none excluded (decision 16);
  - the executor stopped: the run reads unavailable and `/suiteward unblock` lets the head pass;
  - the Receipt check, the revision comment's line with its hyperlink, and the receipt page;
  - the executor with no window, its restart about a minute after a crash, the installer's own stop of the running executor during `install --upgrade` with the move to schema 22, and the purge leaving no task, process or token;
  - the commands that the installer and `doctor` suggest carry the instance's `--settings` and `--token-file`.
- **A throwaway AlmaLinux 9 WSL distro:** the sandbox tests under rootless Podman as a non-root user, and the host step (`install host` refuses without `--sha256sums`).

**Seen live after the merge, on the published `v0.5.0-alpha.1`** (2026-10-28, a throwaway AlmaLinux 9.8 WSL distro and repository):
- the release's `SHA256SUMS`, Linux binary and image index verified with the pinned `cosign`; the host step with `--sha256sums` pinning the test runner to the release's line;
- the service and its database as rootless Podman quadlets, and `doctor` passing every row of the isolated test runner (`executor.binary` with no warning);
- the bootstrap (`/suiteward propose`, then the approve that made V1); a fix whose added test DETECTS, approved with `fix` (V2), whose approval held across a branch update with no protected change while the canonical run ran again on the new head; broken code failing the Contract check; the test runner stopped, the run unavailable 2 minutes 29 seconds after the runner was last seen (the 2-minute lease wait and the next pass), then `/suiteward unblock`;
- each sandbox in a cgroup scope of its own under the test runner's account, with its memory (no swap), process and CPU limits;
- the purge as the service account, and the test runner then stopped with the command the guide gives the administrator.

A trap of the test environment, not of the product: WSL stops a distro when its last session ends, so a live run keeps a session open.

**Not seen live yet.** The co-located test runner with Podman, the recommended program; the co-located test runner on macOS and Linux; a real PowerShell Constrained Language Mode refusal; the task started by a real logon; and the isolated tier on a real server (the AWS host, with cloud metadata answering). The roadmap ([D-ROADMAP](../decisions.md#d-roadmap-the-order-after-m21)) places Podman and Linux in the live tests of each phase (the owner's decision) with the real logon (the orchestrator's placement), and macOS, the AWS host and a real Constrained Language Mode refusal in the verification phase after M3.

## Not in this phase

Python and TypeScript (M2.2, M2.3), integration tests that need a service such as PostgreSQL in the sandbox, sealed tests kept outside the repository, mutation testing, remote attestation, and execution by a managed service. Private Go modules work only when vendored; fetching private modules hosted on GitHub through the App's read access, under a governed list of prefixes, is a later phase (owner, 2026-10-26). A candidate that forces `resource-limit` to soften an advisory receipt or pass `before-approval` is recorded for a later SecOps phase (owner, 2026-10-26).
