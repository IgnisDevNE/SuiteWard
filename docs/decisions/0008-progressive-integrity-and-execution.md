# ADR 0008: Deliver integrity before canonical execution

- **Date:** 2026-09-26
- **Status:** Accepted; M0 and M1 implemented and released (v0.1.0 onward), M2 and M3 planned. Amended 2026-10-20: release provenance, SBOM and keyless signing are adopted ahead of M3 (see the amendment below). Amended 2026-10-26: M2 is delivered as phases M2.1 to M2.3, through a separate executor ([ADR 0028](0028-canonical-execution-and-the-receipt.md)).
- **Scope:** Milestone order, assurance levels, and first execution backend.
- **Origin:** Roadmap recovered from the original system design.

## Context

The product can provide value by protecting the canonical test contract before operating an independent execution environment. Making every execution and supply-chain capability a prerequisite would delay that initial value.

Governance and independent execution offer different guarantees and must be described separately.

## Decision

Deliver the product in this order:

| Milestone | Delivery | Exit evidence |
| --- | --- | --- |
| M0: Domain Proof | Model and exercise immutable versions, proposals, exact approvals, policies, promotion, and concurrency. | Executable positive and negative cases for the governing invariants; GitHub and Docker are not prerequisites for the domain proof. |
| M1: GitHub Integrity Vault | Bootstrap, protected inventory, proposals, human approval, integrity checks, promotion, audit, and usable self-hosted operation. Include the App, MCP trigger, and independent polling from ADR 0001. | A connected project can govern and evolve its contract; retries and conflicts preserve state; results explicitly describe integrity assurance. |
| M2: Canonical Execution | ExecutionPlan, executable RunnerProfile, DockerExecutionBackend, isolated candidate execution, trusted observation, and bound execution evidence. | Real failures fail, corrections pass, and candidate-controlled commands or reports cannot replace the trusted verification process. |
| M3: Supply-chain hardening | Add key management, further signing and transparency controls, and related controls where a demonstrated need justifies them. Release image provenance, SBOM and keyless signing are adopted and in place from the first release built after the amendment below. | Each adopted control has a concrete threat, verification, and operational cost assessment. |

M1 is a usable integrity MVP. It does not require a Docker execution backend. Docker Compose for service packaging is distinct from DockerExecutionBackend for running candidate code.

The first execution backend in M2 is DockerExecutionBackend. SuiteWard coordinates an existing container runtime; it does not build its own runtime or claim that containers alone provide every necessary isolation property.

Keep required assurance explicit:

- **Integrity:** canonical content, governance, approved changes, and promotion provenance.
- **Execution:** integrity plus execution under the required trusted plan, isolation, and evidence collection.

An installation requiring execution must not silently accept integrity-only evidence when its execution backend is unavailable. A policy change follows the existing governance process.

M1 may inspect checks from the customer's existing CI when policy requires them. Record their source and revision without presenting them as SuiteWard-independent execution. Promotion requires post-integration validation of the exact integrated revision: integrity and governance in M1, plus canonical execution when required in M2. [ADR 0014](0014-merge-triggered-canonical-promotion.md) defines the default M1 flow: rely on the project's merge process for test acceptance, preserve exact approval, validate integrated contract integrity, and conditionally promote without executing tests. Optional external CI gates and strict integration coordination remain open.

Authenticate evidence emitters from the start. Model attestations so stronger exportable signatures can be added later; do not require optional KMS, OIDC, or transparency integrations for the initial increment. This deferral does not defer basic access control, backup, or audit.

## Amendment 2026-10-20: release provenance, SBOM and keyless signing

The owner brought forward three controls for the release image; the threat is a swapped or tampered image between the release workflow and the operator, and the cost is one pinned tool and one OIDC permission on one job.

- **Provenance and SBOM.** `release.yml` and `deploy.yml` build with `--provenance=mode=max` and an SBOM from BuildKit's Syft scanner (`--attest type=sbom`, the scanner image pinned by digest). BuildKit stores both as attestation manifests in the pushed OCI index, so they travel with the image and `deploy.yml`'s `:deploy` tag moves the whole index. The provenance is generated by BuildKit on the GitHub runner: it records the workflow run, the source revision and the build arguments, and it is not a separately isolated SLSA builder.
- **Keyless signing.** The `publish` job of `release.yml` (the owner-approved `release` environment) signs the pushed index digest with cosign through GitHub's OIDC token (`id-token: write` on that job only). The certificate identity is that workflow at a `refs/tags/v*` ref; the issuer is `https://token.actions.githubusercontent.com`. Signing the index covers the attestation manifests it references, so none is signed separately. `:deploy` builds are not signed: the owner's approval of the `remote-poc` environment and the digest-pinned units are their control.
- **Order.** The build pushes only the version tag. After the signature is created and verified, a final release moves `latest-stable` to the signed digest; a pre-release never does. The version tag is therefore public before signing completes: a failed signing leaves an unsigned version tag and a red job, while `latest-stable` moves only after a verified signature.
- **Transparency.** Keyless signing records the signature in the public Rekor log, which publishes the repository, workflow and tag of each release. The owner confirmed this on 2026-10-20.
- **Verification.** The workflow verifies the signature right after signing. An operator runs `scripts/verify-release.ps1 -Reference ghcr.io/ignisdevne/suiteward@sha256:<digest>` (a wrapper over `cosign verify` with the fixed identity and issuer; a tag reference is refused) before pinning the digest, and may read the attestations with `docker buildx imagetools inspect <image>@<digest> --format '{{ json .Provenance }}'` and `--format '{{ json .SBOM }}'`.
- **Tool pin.** cosign 3.1.4 (linux-amd64) is pinned by URL and SHA-256 in `dev/tools.json` and checked in the workflow before it runs; no third-party action is used.

This verifies that the image was built and signed by this repository's release workflow at a tag. It does not prove the source is free of defects, and it does not replace the owner's approval of the release.

## Amendment 2026-10-21: the Deploy workflow is retired

`deploy.yml`, its `:deploy` tag and the `remote-poc` environment were removed (D-DEPLOY). The statements above about `deploy.yml` describe it as it was. `release.yml` is now the only workflow that pushes an image, so every published image carries the provenance, the SBOM and the signature. CI builds the image for both platforms without pushing it.

## Amendment 2026-10-26: M2 is delivered as M2.1 to M2.3, through a separate executor

[ADR 0028](0028-canonical-execution-and-the-receipt.md) records the design of M2. It does not reopen the order of the table above, and it changes four things.

- **Delivery.** M2 arrives one ecosystem at a time: M2.1 is Go, M2.2 is Python and M2.3 is TypeScript. M2.1 also delivers the receipt, a report of what the tests that a pull request adds or changes do on the head and on the code before the change. The receipt was not part of the original M2.
- **The backend is a separate executor.** The table's `DockerExecutionBackend` is not built into the service. A separate process, `suiteward execute`, drives a container runtime CLI (Podman or Docker) and holds only its own token. The service keeps the App key and the database and never receives a runtime socket. Docker Compose for service packaging stays distinct from running candidate code, as above.
- **The first profile is Go, and execution is opt-in.** The open decision "first supported test ecosystem and executable RunnerProfile" is settled for Go. Nothing runs until the canonical declaration names a profile, and the levels of enforcement are part of that governed declaration.
- **The exit evidence, as built.** "Real failures fail, corrections pass" is the canonical plan and its gate on the Contract check. "Candidate-controlled commands or reports cannot replace the trusted verification process" is the fixed command of the pinned profile, the expected tests taken from static analysis, the commit source checked against its tree entries, and the layers of ADR 0028 that detect and flag. They are not proof: code that behaves differently under test cannot be ruled out.

An installation that requires execution does not accept integrity-only evidence when its executor is unavailable. With `canonical: required` the Contract check stays `in_progress` and never becomes `success` from integrity alone. A policy change follows the existing governance process.

Of the open decisions below, private dependencies, network and secrets are answered for Go: a sandbox holds no secret, has network only for the dependency install, and private modules are not supported. Provider or customer infrastructure stays open ([D-MANAGED-EXECUTION](../plan/decisions.md#open)).

## Alternatives and consequences

- **Execution-first MVP:** earlier execution assurance, with a larger initial operating and isolation burden.
- **One undifferentiated green check:** simpler wording, but obscures which guarantee was actually established.
- **Mandatory advanced signing in M1:** more upfront deployment requirements before the initial governance workflow is proven.

The chosen sequence exposes useful governance early while making the limits of each release visible.

## Open decisions

- First supported test ecosystem and executable RunnerProfile; deferred to M2 rather than required for the integrity MVP.
- HTTP/E2E with Playwright is a candidate from the design discussion, not an accepted selection.
- Untrusted execution isolation, private dependencies, network access, and secrets.
- Exact external CI gates allowed by M1 policy.
- Which hardening controls become necessary in M3.
- Whether a future managed service executes on provider infrastructure, customer infrastructure, or both.

See [ADR 0006](0006-provider-agnostic-modular-monolith.md) for boundaries and [ADR 0007](0007-canonical-contract-authority.md) for invariant requirements.
