# M1.12: The installer

**Goal:** make installing SuiteWard one guided command on each tier, and hand the first distributable version to testers. Today an install takes about 11 commands co-located and about 62 isolated (nine pastes, the image digest typed three times, and an App made by hand), and several mistakes stay silent. The phase ships as `v0.3.0-alpha.1`. Everything after the alpha is post-MVP.

**Decision:** owner, 2026-10-21, recorded as [D-INSTALLER](../decisions.md#d-installer-the-installer-and-the-first-distributable-version).

**Rules:**
- **Test first** for every behavior change ([TDD rule](../../tdd.md)).
- **The repository is public.** No secrets, and no names of throwaway Apps, repositories or instances.
- **This repository is governed by SuiteWard.** Protected files (tests, workflows, runner scripts) change in as few pushes as possible, and the owner approves them in batches.

## Owner decisions (2026-10-21)

Recorded in [D-INSTALLER](../decisions.md#d-installer-the-installer-and-the-first-distributable-version):

1. **Order:** `doctor`, then the isolated installer with ruleset and setup assistance, then the App manifest flow, then the release-pinned binary.
2. **One App per instance,** created through the manifest flow. One owner per instance, up to 20 repositories.
3. **Runtimes:** isolated is Podman only. Co-located strongly recommends Podman; Docker is allowed co-located only, as an explicitly discouraged option (rootful daemon, and no secrets outside Swarm, so the secrets land on disk).
4. **Distribution:** the `suiteward` binary as release assets for linux/amd64, linux/arm64, windows/amd64 and darwin/arm64, with the signed index digest embedded. macOS is covered by build and tests only.
5. **The GitHub env file** moves to the service account, and the prompts are plain line prompts.
6. **`deploy/local.ps1` is removed** in the alpha.
7. **Hand-over:** `v0.3.0-alpha.1` goes to individual testers; everything after it is post-MVP.

## Constraints the installer keeps

These come from [ADR 0027](../../decisions/0027-agent-human-trust-separation.md), the install guide and the security hardening.

- **Isolated:** the App key and the database never leave the host.
- **Secrets** are never in argv and never printed. Podman secrets are written through stdin without a trailing newline, and the PEM goes from the manifest response straight into the secret store without touching disk. On Docker the secrets land on disk in a private per-user directory; that is part of why Docker is discouraged.
- **Images** are digest-pinned only, never a tag. The release binary carries its own signed index digest.
- **Setup** runs inside the instance with the real TTY passed through, and the installer never captures or logs its output, which holds the TOTP enrollment URI and secret. The installer tells the user to turn off session recording first.
- **App permissions** are exactly the five of the install guide: no Contents write, no Administration write, webhook off, `public: false`. The ruleset stays a human Import click per repository.
- **Privilege:** co-located is rootless Podman, and a rootful connection is refused. Isolated splits the administrator steps from the service-account steps, and the installer never runs as root.
- **Manifest code:** it is converted on the machine that keeps the key, with a random `state` and a listener on 127.0.0.1 only. The code passes through the user's browser, as the PEM download did; this is written down.

## Design summary

- **Entry points.** `install` and `doctor` are dispatched in `internal/app` before the configuration is loaded, because the host has no `SUITEWARD_*` environment. A new in-container subcommand `check` runs after the configuration is loaded: it is the GitHub and database half of `doctor`, run through `exec`.
- **Package `internal/installer`** uses the standard library plus `golang.org/x/term`. Every prompt has a flag and an answers-file key. A `runtime` seam runs the `podman` or `docker` CLI through an injected exec function, so tests use a fake and no container API client is needed.
- **Units.** The quadlet files move from `deploy/quadlet` into the installer with `//go:embed`. Only the image digest placeholder and the per-install values are rendered (tier, ports, the GitHub env file); the PostgreSQL digest stays literal so the pin check keeps one agreeing copy. The installer owns the unit files, and local settings live in an installer-owned settings file, so `--upgrade` never loses an edit.
- **GitHub access** reuses `appauth` and the REST client, with two small additions: listing the App's installations, and an installation token for listing repositories. Protection is read with the existing reader and evaluator.
- **Port of `local.ps1`:** the rootless connection choice, secret generation, the database, migrate and serve flag sets, the health wait and the role creation keep their behavior.

## Tasks

- **I0 Records (orchestrator):** this page, D-INSTALLER, the plan pages, and `v0.2.0` released with its signed index digest in the notes. A3 and the AlmaLinux host move to the final digest.
- **I1 Spike S2 (owner clicks; only notes are merged):** live checks before the design is locked, written to `docs/spikes/s2-installer.md`.
  - App manifest, from a personal account and from an organization: the loopback redirect and the paste-the-code fallback, the webhook with `active: false` and with no `hook_attributes`, `public: false`, the five permission keys, and conversion within the hour.
  - The install click and polling the App's installations with the new key.
  - The ruleset Import JSON, with the integration set to the App, and whether a check that never ran can be required.
  - Docker Desktop on the developer PC, each a named check: no `--replace` and no `--secret` outside Swarm; secrets as read-only bind mounts from a Windows path and who can read them; the flag sets unchanged; `exec -it` passing the TTY; the published port; and non-default ports, since Docker Desktop's VM shares a network namespace with the Podman machine.
  - The briefs below are adjusted from the notes, then the advisor checkpoint.
- **I2 `suiteward doctor` and the in-container `check`:** the host checks (runtime and connection, containers or units active, the two release pins equal, linger on isolated, metadata refused on cloud, ports, and the read-only half of `smoke.sh`) and the in-container checks (the App JWT, the installation visible, exact permissions, every repository readable, the protection result per repository with the test check found, the owner enrolled, the schema version, and no superuser, create-role or bypass-RLS privilege on `suiteward_app`). Every failure is named with a one-line fix, and the exit code is non-zero when anything fails. Tested with a fake runtime and an httptest GitHub; the `check` cases run against the PostgreSQL harness.
- **I3 Installer core:** the answers file, flags and prompts, preflight, the `runtime` seam for Podman and Docker, secret creation, unit embedding and rendering, and an idempotent re-run that creates only what is missing. It adds `--http-port` and `--mcp-port` (default 8081 and 8091) stored in the settings file, which `doctor` and the smoke base URL read. An adoption guard diffs an existing stack against the release actually installed, carries over the known fields and stops with the diff for anything else, so nothing is overwritten silently. The quadlet assertions of `scripts/test-deploy.ps1` become Go tests over the embedded units.
- **I4 Co-located install and the removal of `local.ps1`:** Podman selects the rootless machine connection as `local.ps1` does and refuses a rootful one. Docker sits behind an explicit choice, with a warning that names the reduced assurance and recommends Podman, and keeps its secrets as files in a private per-user directory mounted read-only. A stack made by `local.ps1` is adopted under the same names. `deploy/local.ps1` and its tests are removed and `check-foundation` stops calling them; `smoke.sh` stays. Windows is validated live; macOS and Linux are covered by tests with the fake runtime, and the alpha docs say so.
- **I5 Isolated install:** `sudo suiteward install host` checks or installs Podman, creates the `suiteward` user with its subuid and subgid ranges, enables linger and, when asked, adds the rule that refuses the cloud metadata endpoint. `suiteward install` as the service account then creates the secrets and units, writes the GitHub env file under the service account, starts the database, creates the role, migrates and starts the service. It adopts a host installed by hand from the install guide, and moves an existing `/etc` env file.
- **I6 GitHub flow:**
  - the manifest through a loopback listener with `state` checked, with a paste-the-code fallback, then the PEM into the secret store (for isolated, the port-forward command is printed);
  - the install click, then polling for the installation and choosing repositories (at most 20, one owner);
  - a ruleset JSON per repository (`SuiteWard / Contract` pinned to the App, a test check, strict, default branch), the link to Import, and a re-read through the protection reader;
  - the test check is offered from the check runs on the default branch's head and never from a ruleset that does not exist yet; with no check runs the user types the name, and `doctor` reports `missing-test-check` until it exists.

  The order is: install the App, choose the test checks, write and import the rulesets, run setup, then `doctor`.
- **I7 `install --upgrade`:** back up into a private directory (`pg_dump` and the volume export, mode 600 files in a 700 directory), pull the new digests, rewrite the units, restart the database when its pin changed, migrate, start, then `doctor`. A rollback note points to the backup.
- **I8 Release binaries:** a `binaries` job in `release.yml` after `publish` builds the four targets with the version, source and index digest embedded, writes `SHA256SUMS`, signs each file with `cosign sign-blob` under the same workflow identity and uploads them to the Release, with `contents: write` on that job only and no third-party actions. The tag pattern and the pre-release detection accept `-alpha.N`, in `release.yml` and `scripts/verify-release.ps1`, because otherwise an alpha would be treated as final and would move `latest-stable`; `test-release.ps1` gets the cases. `verify-release.ps1` gets a blob mode. On the isolated host the binary is verified once on the PC and the host compares the same files with `sha256sum -c` against a `SHA256SUMS` hash the PC printed. A development build without an embedded digest requires `--image`.
- **I9 Docs:** `docs/install.md` is rewritten around the installer: the tier choice, verifying the binary once, `install`, `doctor` and `--upgrade`, the Docker section (discouraged, with the reasons), what the installer does for review, and troubleshooting. `quickstart.md`, `agent-install.md`, `backup.md`, `HOST.md`, `local-development.md` (it still references `local.ps1`) and the README install lines follow, plus the threat-model rows for the manifest code and the installer binary as a trust root.

## Verification

- **Per task:** `./scripts/dev.ps1 check`, plus `./scripts/dev.ps1 persistence` for I2's `check` and anything that touches the database role.
- **Installer tests:** a fake runtime that also checks argv for secrets, golden renders of the units, and an httptest GitHub for the manifest, installations, repositories and protection.
- **CI:** `go build` for the four targets as a new matrix step, so Windows and macOS keep compiling.
- **Live:** the validation runs below, each ending with `suiteward doctor` green.

## Release and validation for `v0.3.0-alpha.1`

1. **A fresh co-located install with Docker Desktop** on the developer PC: a new App through the manifest and a throwaway repository, on the installer's non-default ports because the Podman stack keeps its own.
2. **A3 converted** from the `local.ps1` stack through `install --upgrade` (Podman), then smoke, then `doctor`.
3. **A fresh isolated install** on a throwaway AlmaLinux 9 instance, owner-run, with a Session Manager port forward for the manifest, then `doctor`.
4. **The AlmaLinux host upgraded** from v0.2.0 through `install --upgrade`, then `doctor`.
5. **The binaries verified** with `verify-release.ps1` in blob mode. macOS: build and unit tests only.
6. **The owner tags `v0.3.0-alpha.1`** (a pre-release) and hands it to testers. The owner deletes the throwaway Apps, repositories and instances afterwards.

## Size

About ten tasks, a live spike and four live validation runs. The owner is needed for the spike (manifest clicks, ruleset import, Docker Desktop), for each validation run (App create and install clicks, TOTP, the throwaway instance), for two approval batches, the merge and the tags.
