# M1.13: macOS, one-line install, installer screens, change report, encrypted backups

**Goal:** the owner's sprint after the alpha (2026-10-22). It makes the installer available on macOS and through one command, gives it full-screen steps in the brand colors, reports what changed in protected files as an HTML page, and adds encrypted backups with a guided restore. Wave 0 was `v0.3.0-alpha.2` ([M1.12](M1.12.md#v030-alpha2)), merged on its own as [#53](https://github.com/IgnisDevNE/SuiteWard/pull/53).

## Owner decisions (2026-10-22 and 2026-10-23)

1. **Report:** the revision comment becomes a numeric summary and links to the full HTML report that the instance serves on loopback. The link opens only where the instance is reachable: the same PC, or the isolated host through a port forward. Nothing new goes to GitHub, because the App keeps no Contents write.
2. **Backups:** an age key pair of the hybrid post-quantum kind, ML-KEM-768 with X25519 (2026-10-23): a backup lives for years and holds the TOTP secret. The instance keeps only the public key; the private key goes into a recovery kit that the owner keeps off the machine. Remote storage (ADR 0021) stays deferred: it needs Contents write.
3. **macOS:** the owner validates on their own Mac. The binary is not notarized.
4. **Installer screens:** the mockup shown in chat (2026-10-22) is the template: a frame with a title bar, the step list, choices, progress bars, and a summary screen. A plain mode keeps today's output.
5. **CI:** a job that dry-runs the quadlet generator of AlmaLinux 9's Podman against the rendered units (2026-10-23).

## Outcome

The owner's validation of the release follows, and the findings of its fresh install are the start of [M1.14](M1.14.md).

**Delivered.**
- **macOS and the one-line install:** darwin binaries, a macOS CI job, `scripts/install.sh` as a signed release asset ([install guide](../../install.md#4-get-and-verify-the-installer)).
- **The installer screens:** every installer command runs on one full-screen or plain console ([install guide](../../install.md#the-installers-screens)).
- **The change report:** the numeric revision comment with the report link, the numbers in the check summary, and the page on loopback ([runtime contract](../../contracts/runtime.md#change-report-m113-normative), [install guide](../../install.md#9-day-to-day)).
- **Encrypted backups:** `suiteward backup init`, `suiteward backup`, `suiteward restore` and the encrypted backup of `install --upgrade` ([backup runbook](../../backup.md)). The ADR amendments list where they differ from [ADR 0019](../../decisions/0019-encrypted-backups-and-instance-recovery-key.md) and [ADR 0020](../../decisions/0020-guided-local-cli-recovery.md).
- **The CI job** that dry-runs the quadlet generator of AlmaLinux 9.

**Live validation (2026-10-23, overnight).** Dev builds of the phase branch that carry the alpha.1 image digest, with GitHub off, so no TOTP was involved. The backup and restore runs used B2 at `4da8cb22`, before its merge.
- **Isolated regressions** (phase head `850a2189`, AlmaLinux 9 under WSL): the isolated script of the alpha.2 reruns passed unchanged: a busy default port refused, an install on ports 18082 and 18092, a re-run to 18083, the upgrade refusal, a same-release upgrade, `doctor` and a purge. Only plain mode could be seen from a headless shell.
- **Backup and restore on Docker Desktop (co-located):** install, `backup init --kit ... --yes` (a post-quantum kit, and `backup_recipient: age1pq1...` in the settings), `backup --to`. Then a probe row in the database and a marker in the volume were added, and `restore` with `--kit ... --yes --instance <id>` made the safety backup first, brought the database back to the backup (the later table was gone), brought the volume back (the later marker was gone, and the artifacts kept their owner 65532:65532), and `/status` showed the same instance and schema. `doctor` was ok, and a purge ended the run.
- **An interrupted load, shown directly:** a stream of `BEGIN`, `DROP SCHEMA public CASCADE`, `CREATE SCHEMA public` and a new table, with no `COMMIT`, piped to `psql -X -q -v ON_ERROR_STOP=1 -f -`: `psql` exited 0, the old tables were intact, and the new table did not exist, because the server rolled the transaction back.
- **Backup and restore on AlmaLinux 9 (isolated, rootless Podman 5.8.2):** the same cycle passed: the kit and the backup at mode 0600, the restore with its safety backup, the database and the volume back, no spool or restore directory left, `doctor` and a purge.
- **The encrypted upgrade:** v0.2.0 installed. `install --upgrade --yes` without a key and without a terminal refused before any change, saying that a backup is never written in plaintext. After `backup init`, the upgrade to the alpha image wrote `suiteward-backup-<ts>.tar.age` and the directory `suiteward-backup-<ts>.units`, and named `suiteward restore` in its rollback advice.

**Known limits.**
- **The restore replaces data in place** and starts the service at once, with no recovery mode. It differs from ADR 0020, and the owner decides ([D-RESTORE-INPLACE](../decisions.md#open)).
- **age does not authenticate who wrote a backup.** Whoever has the public recipient can write an archive that decrypts with the kit. Only a backup that the operator made and kept is safe to restore. Task B3 (merged) refuses malformed manifest fields and member hashes and cleans what the restore prints from `status.json`, and what those fields claim stays a claim.
- **The report page has no authentication** beyond loopback and the Host check: anyone who can reach the HTTP port reads the protected files of every proposal ([threat model](../../security/threat-model.md)).
- **The numbers are counted when a comment is delivered.** A failure posts the comment with the lists of paths and says that the numbers are unknown, and SuiteWard never edits a comment. A revision recorded before this phase has no numbers and no report page.
- **A Docker re-run of `suiteward install` over an alpha.2 stack** keeps a running service without `SUITEWARD_REPORT_BASE_URL` until `install --upgrade` (the `planKeep` shortcut in `internal/installer/colocated.go`).
- **The `shortcut:` comments** the phase added, each with the limit and when to upgrade:
  - `internal/installer/backup_archive.go`: the dump is held in memory, so it must fit in the installer's memory; and two runs at once in one backup folder remove each other's private directory, because there is no lock;
  - `internal/installer/docker.go`: the same for the volume tarball on Docker;
  - `internal/installer/restore.go`: the line that ends a dump is looked for in its last 4 KiB;
  - `internal/installer/ui/os.go`, `ui/render.go` and `ui/screen.go`: the reason that a console cannot draw is not reported, there is no scrollback on the full screen, and the size is read once, with a layout that counts runes and not terminal columns.
- **Protection of this repository.** `scripts/install.sh` and the self-tests `scripts/install_test.sh` and `deploy/smoke_test.sh` match no pattern of `.suiteward.yml` ([D-SELF-SCOPE](../decisions.md#open)).

**Validation of the release (owner, 2026-10-23).** The owner ran `v0.4.0-alpha.1` on Windows and on Ubuntu under WSL. The one-line install passed: the hash-only path warns and prints the `SHA256SUMS sha256` line (the same as on Windows), `SUITEWARD_REQUIRE_COSIGN=1` without cosign refuses, and a run with no `SUITEWARD_VERSION` refuses with the right command. The change report passed on a pull request (the numbers, the markers, the link, the page and the check summary). The restore passed (verify, preview, the typed confirmation, the safety backup, load, start and compare). A fresh install as a new user, on Windows with a Podman machine, found the 25 points that [M1.14](M1.14.md) addresses.

**Release notes (draft)** for the release that carries this phase, `v0.4.0-alpha.1`.
- *New:* `darwin/amd64` and `darwin/arm64` binaries (not notarized); `install.sh`, the one-line install, as a signed release asset; a full-screen installer in the SuiteWard colors (`--plain` keeps the lines); revision comments that state the numbers of the change and link a report that the instance serves on loopback; encrypted backups with `suiteward backup init`, `suiteward backup` and `suiteward restore`.
- *Changed:* an unattended `suiteward install --upgrade --yes` needs a recovery key: run `suiteward backup init` first, or give `--backup-recipient`. The backup of an upgrade is one `.tar.age` file, not a directory, and `--backup-dir` names the folder for it. Ctrl-C and SIGTERM end the installer commands with exit code 130. The check summary states the numbers of the change.
- *Know before you upgrade:* revisions recorded before the upgrade show no numbers and have no report page. A Docker stack needs `install --upgrade` for the report link. The restore needs the release that made the backup.
