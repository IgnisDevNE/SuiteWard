# S1: GitHub walking skeleton

**Goal:** prove, against real GitHub and before building the GitHub-facing phases, that SuiteWard's core loop works: an App observes a PR, publishes a required check, accepts an owner approval, and records a promotion after merge. Learn the facts that settle D-GITHUB-ACCESS, D-CHECKS, D-INTEGRATION and the numbers of D-SYNC.

**Kind:** time-boxed spike (two working days of agent effort). The code is throwaway, lives under `spikes/s1/` as a separate Go module with its own `go.mod` (so the main module's CI, vet and coverage never include it), and is exempt from the TDD rule. It is never imported by `internal/`.

**Exit:** the skeleton runs the full loop on both [verification targets](../README.md#verification-targets) — the local container and the remote host — and a findings document `docs/spikes/s1-github.md` reviewed by the user proposes (does not apply) decision-register updates for D-GITHUB-ACCESS, D-CHECKS, D-INTEGRATION, D-SYNC and D-DEPLOY.

## Setup (user)

- A separate test GitHub App and a throwaway test repository under the user's control; never the SuiteWard production App or repository.
- Branch protection on the test repository requiring the spike's check, configured by hand.
- The remote host from D-DEPLOY is provisioned (AWS `i-0f556162ae6b59b22`, us-east-2, arm64, rootless Podman user `suiteward`, admin through SSM only) and its Cloudflare tunnel answers 404 at `suiteward-poc.magalz.space`. Before S1-D the owner adds a Cloudflare Access application for that hostname and places the test App key on the host through Session Manager; the agent has no AWS access.
- A GitHub environment (for example `remote-poc`) that requires the owner's approval and gates promotion of the GHCR image tag the host pulls; no host credential is stored in GitHub, because deployment is pull-based.

## Tasks

- **S1-A Poll and check.** A small Go program authenticates as the test App, polls one repository with conditional requests, lists open PRs, computes a digest of a hard-coded glob of test files at the PR head, and publishes a check run (pending/success/failure). Record: permissions needed, rate-limit headers and ETag behavior, latency from push to check.
- **S1-B Approve and promote.** The program reads PR comments, accepts `/suiteward approve <ref>` from the configured owner login, turns the check green, detects the merge (merge, squash and rebase methods), and records the integrated SHA and the protected digest in a local JSON file. Record: how each merge method exposes the integrated source, same-SHA cases, comment edit/delete behavior, timing.
- **S1-D Both targets.** Package the skeleton as one OCI image (configuration through environment variables, secrets as mounted files). Build it multi-arch (amd64 + arm64) and publish to GHCR through the bot. Run it locally under Podman (co-located) and on the remote host as a rootless Podman quadlet of the `suiteward` user with `AutoUpdate=registry`, pulling the tag promoted by the approval-gated workflow (isolated); add the tunnel ingress rule only behind Cloudflare Access; the agent never holds host credentials. Run the S1-A/S1-B loop on each target and record differences: startup, outbound-only behavior, clock and polling latency, restart, logs, how status is reached through Tailscale or an SSH tunnel.
- **S1-C Findings.** Write `docs/spikes/s1-github.md`: the permission matrix, the check identity and state mapping, merge-method results, measured polling numbers, surprises, and the proposed decisions.

## Orchestration notes (2026-10-09)

- The tasks run as waves, recorded as they change: wave 1 is S1-A (`spikes/s1/**`) and S1-D1 (image, publish workflow, quadlet, actionlint extension; owns `.github/` and `scripts/`); wave 2 is S1-B on top of S1-A; S1-D2 (running both targets) needs credentials and the owner's host steps; S1-C closes the phase. The frozen interface is [`spikes/s1/CONTRACT.md`](../../../spikes/s1/CONTRACT.md).
- Test App `SuiteWardQ Spike` (`suitewardq-spike`) is installed only on `IgnisDevNE/SuiteWardQ`. It was granted a superset of permissions (`checks`, `contents`, `issues`, `pull_requests` write, `metadata` read) so that it also drives the scenarios; the matrix records the minimum per call by narrowing each installation token at runtime, and marks the write permissions used only by the harness. The key lives outside the repository.
- GHCR publication uses the workflow's `GITHUB_TOKEN`; the bot only pushes the workflow file. The `remote-poc` environment requires the owner's approval and does not let administrators bypass it.
