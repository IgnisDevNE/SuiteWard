# M1.6a: Bootstrap and owner commands

**Goal:** bootstrap a repository's first canonical from its principal branch (ADR 0010) and turn the owner's `/suiteward approve|revoke <ref> <code>` comments into exact, TOTP-confirmed consent outcomes, each acknowledged in the PR (ADRs 0002, 0011, 0027).

**Decisions:**
- D-COMMANDS (accepted 2026-10-14): identifiers, syntax, order, ledger, bootstrap, and owner change refused;
- the ADR 0011 amendment of 2026-10-14: other accounts are ignored;
- D-TRUST and D-COMMENT-EDIT;
- D-GITHUB-ACCESS, to be amended from P0 for the comment write.

**Exit:** on `IgnisDevNE/SuiteWardQ`, after `setup`:
- the bootstrap summary appears in an open PR;
- the owner's `/suiteward approve P1-R1 <code>` bootstraps canonical `V1` and is acknowledged;
- a replayed or wrong code is rejected with an acknowledgment and changes nothing;
- `/suiteward revoke` on a later revision is acknowledged;
- a comment from another account gets nothing;
- restart reprocesses nothing.

This is verified on one target at a time (below).

## Verification on one target at a time

Both targets watching the same repositories would both post comments, and each has its own TOTP secret: one would reject the owner's code. So during M1.6a verification, only the target under test runs with the GitHub settings. Stop the other service, or start it without GitHub, for the duration.

Comments carry the instance id in their marker, and each instance ignores comments created before its own enrollment. So the second target neither skips its own summaries nor rejects the first target's approvals. Still, verify each target on a fresh PR, so that each target has a bootstrap proposal of its own to approve.

The co-located stack was purged after M1.5, so its verification needs `local.ps1` and `setup` again, with a fresh authenticator entry.

## Owner steps

- **Before P0:** grant the test App **Pull requests: Read and write** and accept it on the installation. Right after, check the host's `/status`: a `lastError` on synchronization would mean that the read-only token no longer mints. P0 asserts this too.
- **During verification:** run the scenario on `SuiteWardQ`:
  1. open a PR that changes a protected file;
  2. approve `P1-R1` with a code;
  3. try a reused code;
  4. revoke;
  5. comment from another account, if one is available.
